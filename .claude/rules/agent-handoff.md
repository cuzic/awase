# 並列エージェント開発の約束(ADR-242・ADR-243)

適用: team-lead が実装・レビューのエージェントを並列に起動して PR を作るとき。人のセッションには適用しない。

1. PR 本文は自分のタスク名の付いたファイルから書く(共有の /tmp/*.md、b.md・body.md のような名前は使わない)。更新後に gh pr view <N> --json body で自分の本文か確かめる。
2. PR 作成後と「CI を待っている」と報告する前に gh pr view <N> --json mergeable,mergeStateStatus を見る。CONFLICTING・DIRTY なら CI は起動しないので、最新の origin/develop に rebase して git push --no-verify --force-with-lease origin <ブランチ> で push し直す。
3. PR の状態・CI・マージ・コミットの有無は、報告の直前に実行したコマンドの出力で書く。
   - 他人が次の作業の前提にする事実の主張(ある・無い・何件)には、確かめたコマンドを 1 行添える。git grep は打ったコミット、gh は PR の head SHA か日時を添える。
   - コマンド 1 本で確かめられない主張(CI の run・実機が要るもの)は「未確認」と書き、確かめる手段(run ID・ジョブ名)を添える。
   - PR に後からコミットを足したら、タイトルと本文の数値がまだ合っているかを見直す(#530・#531)。
4. レビュー指摘への返信は、指摘 ID ごとに「反映した(コミット)/反映しない(理由)」を列挙する。
5. 取り消し・一時停止: 出す側は 1 行目に「作業を止める。PR は作らない」(または「PR #N を閉じる」)、2 行目にブランチ名と PR 番号。受ける側は、PR がもうあれば理由をコメントして閉じる(ブランチは消さない)。push と gh pr create は別々のツール呼び出しにする。
6. push(team-lead が起動したエージェントのみ): git push --no-verify origin <ブランチ>。2 回目以降の push の前に、再発ファミリーのファイルを変えたなら PR 本文に fix-requires-evidence の (a)/(b) を書いたか確かめる。
7. 指示書に仕様を書くとき(team-lead): 最新の origin/develop の該当行をそのまま引用し、ファイル名・節・コミットを添える。要約し直さない。
