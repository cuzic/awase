# ADR-280 C0: `eisu_threshold` を 14 より上げる案の測定(2026-10-24)

コード変更なしの Python 評価。結果は集計値のみで、利用者の本文・コーパス・打鍵列は含めない。

## 測ったもの

`ime_on_eisu` の入りの実効の閾値は `max(eisu_threshold, en_threshold)`(既定 `max(14, 8) = 14`)。これを 14・16・18・20・24(参考で 8〜12)に変え、#819 以後の `KanaModel::delta`(仮名に読めないキーは増分 0、直前の仮名の文脈を切る)と同じ判定で、`ja_threshold = 4`・`max_keys = 7`、親指なしの連続区間を判定にかけた。

- (a) 日本語を `NotJapanese` と誤判定する率(エピソード開始を文中のあちこちに取る従来の方法)
- (b) 英文・コード・他言語で `NotJapanese` に達する率と、達するまでの打鍵数(= 英数側の保持の長さ)
- (c) 7 打以内に決まらない(`Undecided`)率

## 再現できたか

#819 の表(`en_threshold` 8/10/12/14)の日本語→英数の誤判定は 7.0 / 3.5 / 1.6 / 1.0% で、本測定の 7.02 / 3.48 / 1.57 / 0.95% と一致(14 は 0.95% を 1.0% に丸めた値)。英文の NotJapanese 率は #819 の 96.8 / 94.6 / 91.3 / 85.3% に対し 96.7 / 93.7 / 90.7 / 84.9%(差 0.1〜0.9 ポイント)。原因は、元の eval8 が閾値ごとに英文区間の無作為標本を引き直しているのに対し、本スクリプトは全閾値で同じ標本を使うこと(日本語側は乱数列が同じで一致)。実装との一致は、`KanaModel::delta` の `delta = 0`・`prev` の切り方(`src/lang_detect.rs:218-241`、`on_char_down`)をスクリプトの判定ループと読み比べて確かめた(Rust は実行していない)。

## 結論と推奨

導出(tuning-constants の流儀): 日本語の誤入りは閾値を 2 上げるごとに約半分(14→16 で 0.95→0.43%、18 で 0.22%)になる一方、英数側の保持は平均 +0.4 打鍵(14→16)、+0.6(18)、英文の NotJapanese 率は 84.9→77.6→70.7% と 7〜8 ポイントずつ下がる(= Undecided に倒れて保持が 7 打張り付く英文が増える)。20 以上は誤入り 0.15% を得る代わりに英文の 4 割が決まらず、割に合わない。

推奨: **実機で試すなら `eisu_threshold = 16`**。誤入りを半減(0.95→0.43%)させ、英数側の遅れは平均 +0.4 打鍵・p90 は 7 のまま。それでも誤入りが journal で見えたら 18(0.22%、平均 +0.6 打鍵)まで。16 未満は 14 との差が小さく、20 以上は英数側の遅れが大きい。

限界: (1) 評価は文単位の生成データで、実際の無操作後の再開(C1 の対象)の文脈は測れない。(2) #819 の事故(llr -43)は #819 で解消済みで、C0 が効くのは残る約 1% の仮名の珍しい並び。(3) 実機の journal での再校正は D1 の段階 1 の対象。

## 再現手順

評価データは `research-private/v3-eval/` の `data_*.jsonl`・`data2_*.jsonl`・`data3_*.jsonl`(合計 2710 行。日本語は読み付き、英文、コード、欧州・マレー系)で、リポジトリには入れない。

```sh
uv run --no-project python -I tools/lang-detect-eval/eval_eisu_threshold.py --repo . --data-dir <データのディレクトリ> --thresholds 8,10,12,14,16,18,20,24
```
