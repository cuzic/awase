# ADR-265 段階 2: 実機測定の手順書(草案、レビュー待ち)

[ADR-265](../adr/265-mozc-readable-integration.md) の段階 2(mozc-readable の共有メモリを belief に採る)の前提になる測定の手順です。**草案で、実機ではまだ何も実行していません**。「要確認」と書いた前提は、実行前に確かめます。

## 1. 目的

belief に採ってよいか(Low → Medium)を、**測定の前に決めた基準**で判断する。結果に合わせて基準を変えない。

**基準(2026-10-18 ユーザー決定、測定前に固定)**: 開閉(open)について、受け入れた読み(`verdict=accepted`)の総数 **N ≥ 200** のうち、**操作から決まる正解と食い違う件数が 0**。1 件でも食い違えば Low のまま(journal に記録するだけ)にして、原因を調べる。入力モード(mode)は、open が基準を満たした後に別に判断する。

理由: 開閉の取り違えは非対称な被害になる(ADR-191・INV-45)ので、誤採用は 1 件でも許さない。一致率(99% など)にすると、件数が少ないとき 1 件の誤りで割合が大きく動き、誤採用を許容してしまう。

## 2. 何を測るか(CI の既存の検査との違い)

- **共有メモリそのものの正しさ**(書き出し側が、押したキーに対して正しい値を出すか)は、mozc-readable の CI(`verify.ps1` の state・apps・appcontainer)がすでに、キー操作から決まる期待値と比べて確かめている。N は 1 run あたり数件と少ない。
- **この測定で新しく測るのは、awase を介したときの誤採用**:
  1. awase が**正しいスレッド**の共有メモリを読んでいるか。実装は既存のフォーカス解決の窓のスレッドで、`hwndFocus` が無ければ `hwndActive` へフォールバックする(別セッションの確認。ADR-265 D3 の脚注)。フォールバックで別のスレッドのブロックを読むと、別の窓の状態を採ってしまう。
  2. awase が起動していて、IME キーに介入する(通す/止める/自分で IME を操作する)環境での、共有メモリの値と正解の食い違い。
  3. 古いブロック(スレッド ID の再利用、IME を切り替えた後の残り)を `process_id` 照合と `active` が実際に弾くか。

## 3. 正解の定義

**正解は、awase にも共有メモリにも依存しない情報**で決める。第一候補は、入力した文字の結果(IME がオンのひらがななら「あ」、オフなら「a」)を、対象のアプリのテキストから読む方法。**要確認**: 実機の対象アプリ(メモ帳・Chrome)から、自動でテキストを読めるか(UI Automation で取れる見込みだが未確認)。

読めない場合の代替は、**操作列から決まる期待値**(mozc-readable の CI と同じ)。ただし、awase が起動していると、awase が IME キーを書き換える・止める可能性があり(**要確認**: F2・F1・F0 など、awase の既定の設定での扱い)、操作列だけでは正解が決まらない場合がある。その場合は、その窓・その操作を N から外して理由を記録する(基準を満たすための取捨選択はしない。外した件数も報告する)。

## 4. 操作と窓

- 操作: mozc-readable の CI と同じ列を繰り返す。`F2`(ひらがな、ON)→ `F1`(全角カタカナ)→ `F0`(半角英数)→ `F2` → `19`(OFF)。期待される (open, mode) は (1,1) → (1,2) → (1,3) → (1,1) → (0,*)。
- 窓: メモ帳(通常の Win32)、Chrome(TSF ネイティブ)、AppContainer 内のプロセス(UWP の代用。`readable/ci/ac_launch.py`)。実在の UWP アプリ(Windows Terminal など)は別枠で数件。
- 1 窓種あたり 20 周(5 遷移 × 20 = 100 件)を目安に、3 窓種で N ≥ 200 に届くようにする。届かなければ周回を増やす。
- 各遷移の前後で入力先を切り替える周回も混ぜる(フォーカス移動直後の読み = スレッド選択の誤りが出やすい場面)。

## 5. 実機での実行(dragonflyg4、clipwire)

**要確認の前提**(1 つでも崩れたら、先に直す):
1. Mozc Readable の MSI を実機に渡す手段。MSI は mozc-readable の GitHub Actions の成果物(Release はまだ無い。ADR-265 段階 0 の後)。Linux 側で取得して実機へ運ぶ方法が要る(clipwire の exec で取得できるか未確認)。
2. インストールに**管理者権限(UAC)が要る**。clipwire は非管理者で動くので、昇格の手順(RunAs)が要る(利用者の操作が要る)。
3. 実機に Python があるか(キー注入・読み取りの CI スクリプトを使うため)。無ければ PowerShell で書き直す。
4. awase を、ADR-265 段階 1 の入った `develop`(PR #644、`101dfd2f` 以降)でビルドして動かす(`[diagnostics] mozc_shm_shadow = true`)。
5. journal の取り出し: ホットキー(Alt+変換 → Alt+無変換 を 2 回連続)で `%TEMP%\awase_journal_<tick_ms>.json`。**要確認**: そのホットキーが実機の現在の設定で効くか。効かなければ不具合報告経由(`bug-report-fetch`)。
6. **実機の操作との干渉**: キー注入とフォーカス移動を行うので、測定中は実機を使えない。測定の時間帯を利用者が決める。
7. 後始末: Mozc Readable のアンインストールと、入力方式(言語リスト)を元に戻す。実行前に、元の入力方式の一覧を記録する。

## 6. 集計

journal の `MozcShm` 記録(`verdict`、`route`、`tsf_open`・`tsf_mode`・`effective_*`、`version`、`reason`、`profile`、`belief_open`、`belief_mode`)を、正解の記録と**順序で**突き合わせる(記録はフォーカス変更時と結果が変わったときだけなので、受け入れた状態の並びが、期待される並びと一致するかを見る。**要確認**: journal の時刻と、操作側の時刻を突き合わせられるか。突き合わせられない場合は、順序だけで比べる)。

報告する数字:
- N(受け入れた読みの総数)、窓種ごとの内訳。
- 食い違い件数(基準: 0)。1 件でもあれば、その窓種・操作・`route`・`reason`・フォーカスの直前の状態。
- 参考: `verdict=rejected`/`failed` の件数と `reason` の内訳(読めなかった割合。採用の可否の条件ではない)。
- 参考(利益の指標): belief が正解と食い違い、共有メモリが正しかった件数(採ると救える件数。採用の可否の条件ではない)。
