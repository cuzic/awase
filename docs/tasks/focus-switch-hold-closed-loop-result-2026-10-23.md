## 範囲と前提

- **本物で回したもの**: `FocusSwitchHold`(純粋関数そのもの)と、擬似 IME の遷移表(ADR-277 の `TransitionTable`。GJI は ATOK の格子、MS-IME は本体の格子)。
- **cfg(windows) の配線は対象外**。殻(`runtime/focus_switch_hold.rs`・`deliver_key_event`・`INPUT_DEFER.replay_later` と drain・`spawn_ime_refresh` の世代・debounce)はコードを読んで小さく写した `Sim` で表した。写した性質: フックの打鍵は defer キューに未処理があればキューへ積む(`app/mod.rs::handle_hook_key_event`)、drain はタイムスタンプ順、refresh は debounce 50ms の後に spawn され spawn 時点の窓と世代を読む、解放は refresh の完了・期限のタイマー・上限・期限超えの打鍵。写しと本物の配線の一致は検査していない。
- **読み直しの時間分布は CI 実測値を入力として与えている**: #817 本文の `[focus-sync]` → `[notify-refresh]`(n=1,564、P50/P90/P95/P99/max = 67/77/81/109/228ms)。全列挙は分位点と 55・60・150・200・245・250・255・300・400ms・取りこぼしを並べ、ランダムウォークは分位点の区分一様で引く(250ms 超 0.2%・取りこぼし 0.1% は仮定)。表の「R≤228」が実測の範囲。
- **IME とエンジンの効きの仮定**: エンジンの活性 = 文脈の窓(最後に完了した refresh が読んだ窓)の belief が開。素通しの IME キーはフォーカスの窓の真値を擬似 IME の表で動かし、予測(belief)は文脈の窓に付く。読める窓は refresh の完了で belief を真値に合わせ、読めない窓は合わせない。固着(fix)の数はこの仮定に依る。
- 防御を外せる写し(`Mirror`、既定)は、E1 とランダムウォークの全件で本物と同じ軌跡を出した(違えばテストが落ちる)。ablation はこの写しから防御を 1 つずつ外して回した。

## 既知の制限(未修正)

再現の事象の並びは golden の「最短の再現」にある。時刻はフォーカス変更からの ms。

- **V3: 上限 8 Down での解放は、refresh を待たずに古い文脈で再生し、以後は待機に戻らない。** E1 の R≤228 の stale_start・fix は全てこれ(6ms 間隔 12 打・外部注入 20 打)。人の打鍵(40ms 間隔 6 打)では 0。機械の速さの入力(他プロセスの注入・音声入力)が切替直後に重なるときだけ。
- **V4: 保持中のフォーカス変更で、前の窓で打った打鍵が次の窓に届く。** 保持は世代を新しくして次の refresh を待つ設計なので、再生先が前面の窓になるのは避けられない(保持なしなら前の窓に古い文脈で届く)。
- **V5: フォーカスからちょうど 250ms の打鍵は、同じ時刻の refresh の完了より先に処理されると古い文脈になる**(待機の期限が `>=`)。読み直し 250ms の区分だけで、実測の範囲外。
- **読み直しが 250ms を超える・取りこぼす**: 期限で古い文脈のまま再生するか、待機の期限の後に素通しになる(E1 の R>250 で stale_start 48,026・fix 24,180)。#817 本文のとおりの設計上の限界。
- **古い読み直しの問題(#817 と無関係)**: 古い世代の refresh が新しい世代の後に完了すると文脈が古い窓に戻る(ランダムウォークで 552/2,951 本、`stale_regress`)。保持の世代照合は解放だけを守り、refresh の適用自体は世代を見ない(写しはそう表した。実際の `apply_focus_probe_result` の扱いは未確認)。

## ablation(防御を 1 つずつ外す)

検出率 **11/12**(基準の「保持なし」を含む)。

| 外した防御 | 検出 | 増えた違反(組の数) |
|---|---|---|
| 保持そのもの(基準) | 検出 | stale_start 18,849・fix 11,693 |
| 上限 8 Down | 検出(cap の列だけ) | cap 5,190(機能の不変条件は逆に減る: stale_start −3,081・fix −1,699) |
| 世代の照合 | 検出 | stale_release 5,898・stale_start 4,990・fix 2,503 |
| 保持を始める打鍵の絞り込み(種類・修飾・注入) | 検出 | delay 20,455・route 5,663 |
| 同(Down だけ) | 検出 | delay 34,700・route 7,910 |
| 保持対象の絞り込み(保持の外の Down の Up を通す) | 検出 | delay 4,455・route 596 |
| 期限のタイマー | 検出 | loss 4,891・stuck 4,891・bound 5,357 |
| 待機の期限 | 検出 | delay 5,689・route 845 |
| 保持中のフォーカス変更で世代を新しくする | 検出 | stale_release 2,696・stale_start 1,338 |
| IME のモードキーから保持を始める(V2 の修正) | 検出 | stale_start 10,993・fix 11,091 |
| 保持中の打鍵が使った修飾キーの Up を足す(V1 の修正) | 検出 | modifier 3,002 |
| 期限超えの打鍵での解放 | **検出できない** | なし |

- **期限超えの打鍵での解放**は期限のタイマーと冗長で、この事象の集合では外しても何も変わらない。タイマーの取りこぼしをモデルに入れていないので、保険としての要否は言えない。
- **上限 8 Down** は上限そのものの列でしか検出されず、外すと V3 が無くなって機能の不変条件は良くなる。期限 250ms がある限り、保持の量の上限以上の役目はしていない。

## 修正案(未実装)

- V3: 上限での解放の後、refresh がまだなら待機(同じ世代)に戻す。または外部注入の Down を上限の数に入れない。
- V4: 設計上の帰結として残す。
- V5: 待機の期限の比較で、同時刻の refresh の完了を先に見る。
- 古い読み直し: refresh の適用に世代の照合を入れる(#817 とは別の件)。

## 確かめていないこと

- cfg(windows) の配線が写し(`Sim`)どおりか。
- 固着の仮定(予測が文脈の窓に付く・読めない窓の belief がフォーカス復帰で戻る)の実機での成否。
- `FOCUS_RESYNC`・戻り待ちの保持(ADR-245 R2)・ime-off-rescue の再生との組み合わせ。
- 読み直しが CI の実測より遅い実機。
