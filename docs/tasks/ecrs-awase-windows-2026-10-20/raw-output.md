## 先に書く: 候補にしなかったもの(理由のあるコード)

- `tsf/probe.rs:110-117` の doc が明言: 本番の `TsfReadinessProbe` は `min_ms=0`・`total_max_ms=0` しか渡されない(`vk_send.rs:291`、`tsf/warmup/cold_warmup.rs:114-118`)が「今 0 が渡っているから分岐を削除しないこと」(cold-start 待機は何度も出し入れされた領域、tuning-constants.md)。**E 候補にしない**。
- `vk_send.rs` の `send_char_as_tsf`/`send_char_as_vk` の `CharResolution::Vk` フォールバック(「現状は理論上到達しない」)は、BUG-47 で「到達しない」主張が一度誤りだった履歴がコメントにある。**削除候補にしない**。
- `defer_if_probe_in_flight` / `_recovery_exempt` / `defer_vks_if_probe_or_recovery_in_flight` / `probe_or_recovery_block_reason` / `drain_pending_deferred_before_send_if_queue_only` は `architecture_guard.rs:8217-8300`(`deferred_gate_wiring_violations`)が関数名と呼び出し形を文字列で固定している。統合・改名は不可(候補にするなら guard の同時更新が前提)。
- `raw_recovery_owns_deferred` の `#[expect(clippy::unused_self)]`(mod.rs:1165)は、呼び出し箇所数を固定する guard(`raw_recovery_owns_deferred_call_sites_are_accounted_for`)があるため形を変えない、と本文に書いてある。

## 上位 5 件の詳述

### A1: 起動と設定リロードのキー設定手順の重複(C)

- **何を**: `bootstrap.rs:1157-1226` と `mod.rs:849-930` にあるキー設定の組み立てを、1 つの関数 `compile_key_config(&ValidatedConfig, thumb_vks: (VkCode, VkCode), diag) -> KeyConfig { special_keys, sync_toggle/on/off, ... }` にする。`panic_trigger_combos` の設定と `warn_on_engine_hotkey_collision` と `migrate_legacy_solo_tap_actions` も中に入れる。呼び出し元は「親指 VK をどこから得るか」と「結果をどう Engine に渡すか」だけを持つ。
- **なぜ安全か**: 2 つの手順は同じ関数を同じ順に呼んでおり、差は 3 点(上表)だけで、いずれも引数と呼び出し順で表せる。この領域は再発ファミリー表に無い。
- **先に要るテスト**: 現状は組み立て自体のテストが無い。`init_ime_sync_keys` の 2 本のテスト(BUG-140)を残す。関数が `diag` の代わりに `Vec<String>` を返す形にすれば Linux で単体テストにできる(A10 と同時にやる)。`run_all` の focus scope→IME cache の順序 guard(architecture_guard 4369)は触れない。

### A2: 親指キー由来の Engine 設定の二重化(C+R)

- **何を**: 「親指 VK 2 つ + `GeneralConfig` から、space/無変換/変換/enter の VK と各 `TextKeyConfig`/`ModeKeyConfig`、`thumb_shift_faces_enabled` を求める」純関数を core に置く。起動(`bootstrap.rs:1228-1286`)と `apply_config_update`(`runtime/mod.rs:2236-2285`)が同じ関数の結果を Engine に適用する。`awase-linux` / `awase-macos` の `main.rs` も同じ形に揃えられる。
- **なぜ安全か**: 4 本の `[left,right].find(|&vk| vk == VK_X)` と 5 つの setter の引数組み立てが一字違いで 2 箇所にある。片方だけ直すと起動とリロードで挙動が割れる(今は割れていないことを読んで確認した)。VK_* の定数は platform から引数で渡すので ADR-019 にも反しない。
- **先に要るテスト**: 純関数に対する Linux の単体テスト(Space を左右どちらに置いた/Enter を置いた/Shift を置いた〈faces 無効〉)。reload 側の `ReloadKeys` 経路にはテストが無いので、`closed_loop_scenarios` に「リロードで親指キーを Enter に変えた」シナリオを足すのが望ましい(未確認: 既存シナリオに有るか)。
- **注意**: 起動だけが設定する `set_backspace_vk`(観測専用)・`apply_general_config`・`engine_off_solo_repeat` は共通化の対象外。runtime/mod.rs は ecrs-runtime の担当範囲なので、この候補は連携して扱う。

### A3: `send_romaji_batched_gated` / `send_romaji_as_tsf_gated` の前処理の重複(C)

- **何を**: 共通の前処理を `fn prepare_romaji_send(&self, romaji, gate, label) -> Option<(VkSequence, WarmthContext)>` にする(`chars` が空なら `None`、KeyInput の shadow push、`[key-output]` ログ、drain-before-send、`assess_warmth`、`defer_respecting_gate` が true なら `None`)。cold/warm の分岐は各関数に残す。
- **なぜ安全か**: 2 つの前処理は、ログの語と tsf 側の定数 `used_eager_path=false` を除いて同一(上表のとおり読み比べた)。前処理を 1 つにすると、`drain → assess_warmth → defer` の順序を 1 箇所に閉じ込められる。順序が崩れる事故(vk_send.rs:57-64 の round3 指摘)を構造で防げる。
- **先に要るテスト**: 前処理の順序を固定するテストが無い。`FakeProbeIo` のような差し替えが `Output` の前処理には無い(`Output` を直接作る既存テストは `drain_*` の 3 本、vk_send.rs:822-897)。先に「blocking 中の `prepare` は `None` を返し、drain しない」「`Exempt` では drain しない」のテストを足す。さらに `assess_warmth` 本体と `send_romaji_as_tsf_warm` 本体を走査する `warm_send_wiring_violations` は今のまま通ること。
- **注意**: 再発ファミリー(warmup / defer キュー)。fix-requires-evidence の (a) 回帰テストが要る。

### A4: `observer/ime_observer.rs` の判断部分を core へ(R)

- **何を**: `ImeSnapshot`(ime.rs:467、純データ)と `classify_ime_snapshot`・`classify_poll_outcome`・`log_input_mode_decision`・`log_eisu_diagnostics`・`classify_fetched_snapshot` を `awase-windows-core/src/state/` へ。殻の `observer/ime_observer.rs` には `poll_and_classify_ime`(Win32 の読み取り+ `classify_fetched_snapshot` 呼び出し)だけを残す。同時に、`poll_and_classify_ime` が `trust_input_mode` を再計算している 8 行を `classify_fetched_snapshot` への委譲に畳む(C)。
- **なぜ安全か**: 外部から呼ばれるのは `classify_fetched_snapshot` と `poll_and_classify_ime` の 2 つだけで、シグネチャは変わらない。判断部分は `state/` の純関数(`decide_input_mode`・`filter_eisu_adoption`・`read_miss_is_imm_evidence`)を並べるだけ。IME belief のレイヤー規約(Observe → pure classify → reduce)で言う Pure の層がそのまま core に入る。

- **注意**: 再発ファミリー(IME belief)。移動だけなので挙動は変わらないが、`.claude/rules/ime-belief-architecture.md` を読んでから着手する。

### A5: `Output` の `warmup_coord` 委譲 20 本の整理(S)
