# ADR-265 belief 接続の設計: 実機実験の結果(2026-10-18)

手順書: [adr265-belief-experiments.md](adr265-belief-experiments.md)(基準は測る前に固定)。道具: `tools/adr265_stage2/`(`drive_belief_exp.py`、`ui_host_exp.py`、`analyze_belief_exp.py`)。
実機: dragonflyg4。Mozc Readable 3.35.6354.100(`607a6a6`)。測定窓は自前の Win32 窓 `ui_host_exp.py`(通常の EDIT と、`ES_PASSWORD` の EDIT)。測定中は利用者の awase を止め、ja の入力方式を Mozc Readable だけにした(終了後に戻した)。
記録は `h_e2/h_e3a/h_e3b/h_e4.jsonl`(文書の本文は保存しない)。**1 台・1 窓の種類(IMM ベースの素の Win32 窓)の結果**で、Chrome・Edge・TSF ネイティブの窓の E3・E4 は測っていない。

### E3 の読み方の注意
- ドライバーの `send_vk` は、キーダウン→30ms→キーアップ→30ms と待つ(約 60 ms)。**変化は多くの場合、その待ちの最中に起きており、私の読み取りの開始時点では既に済んでいた**(「送信完了から」の遅れが 0〜1 ms に張り付いている)。したがって、キー押下からの 92〜95 ms は、約 60 ms の下限を含む**上限の目安**で、実際の遅れの分布ではない。170ms に対して余裕がある、という判断には使える。
- 窓は素の Win32 窓(IMM ベース)。TSF ネイティブの窓(Notepad の XAML 等)の分布は、段階 2 の実機測定(約 61 ms)と CI の flip(約 0.12 秒)だけ。負荷は Python の busy ループ 8 つで、実際の高負荷の再現ではない。

### E4 の読み方の注意(結論なしの理由)
- 測ったのは Win32 の `ES_PASSWORD`(パスワードの入力欄の窓スタイル)で、**web の `<input type=password>` や TSF の入力スコープ(`IS_PASSWORD`)ではない**。目的の「入力スコープで `tsf_open` と `effective_open` が割れるか」には答えていない。
- 「a」を打った結果の判定(文字数の増減・最後の文字の種類)は、通常の欄でも文字数が増えない記録が多く、**信頼できなかった**(測定器の不備。どの欄の入力が IME で変換されたかは分からない)。
- IME の ON を押した記録で、`effective_open` が 0 のままのものがあった(F2 が効く前、またはクリックでフォーカスが変わった可能性。未調査)。

## 誤りと訂正

1. **Notepad の文書の全文を記録してしまった**: 最初の E2 で、「a」を打った結果を見るために Notepad の入力欄の全文を読み、JSONL に保存して、確認の出力にも出した。新しい Notepad が前回のタブを復元していて、そこに LINE のチャネルシークレット・トークン・webhook の URL があった。
   Linux 側のコピーと実機のファイルは削除した(その文字列を含むファイルが残っていないことを確認)。**会話の記録には残っている**ので、利用者へ再発行を勧めた。ドライバーは、本文を保存せず、文字数の増減と最後の文字の種類だけを返す形に直し、測定の窓は自前の窓に替えた。
   この記録(削除した run)の E2 の数字は、私がそのとき見たコンソールの集計(0/50、`getopen` 25/25 ずつ、「あ」)だけで、ファイルは残っていない。
2. **最初の E2 は IME を ON にできず中断**した(新しい窓の最初のキーが約 8 秒遅れる件。待ちを 9 秒から 40 秒に延ばして解決)。
3. **ビルドの背景起動が 2 回失敗**した(引用符の崩れ、`C:\` 直下へのログ)。結果には影響しない。
4. **利用者の通常の入力が使えなくなった**: ja の入力方式を Mozc Readable だけにしたため。利用者の指摘で戻した。実験の間(約 10 分)、利用者の日本語入力と親指シフトを止めた(承認は得ていたが、影響の大きさを事前に十分伝えていなかった)。

## 結論(この実験で言えること、言えないこと)

- **共有メモリは、TIP の実際の状態に合う**(E2 の Notepad: IMM の読み戻しは書き込みに追随したが、実際の入力は変わらず、共有メモリも変わらなかった)。IMM の `ImmGetOpenStatus` の読みと食い違うことがある、という点で、「共有メモリを事実として優先する」方針(利用者決定)を支持する。ただし 1 窓。
- **IMM の書き込みが TIP に届くかは、窓の種類で違う**: 素の Win32 窓では、書き込み中に TIP が同期的に更新する(0.5 ms 未満。ただし開の 16% が不達)。TSF ネイティブの窓では、書き込み自体が Mozc に効かなかった。レビューの H1 が指摘した「ImmCross の書き込みは共有メモリに同期的に現れる」という前提は、窓の種類に依存する。
- **キー→共有メモリの遅れは、この条件で 95 ms 以下**。M1(170 ms の窓との差が小さい)は、この条件では実害が小さい。ただし TSF ネイティブの窓・実高負荷は未測定。
- **E1 の再測定(別セッション rust-nicola-56、12:30〜12:32 UTC、6 合図で打ち切り)**: 合図の前に、共有メモリが 開 → 閉 に変わった(`seq` 6→8、`eff_open=0`・`tsf_open=0`)。利用者が合図の前に何をしたか(メニューか、キーか)は**記録しておらず不明**。
  合図の 6 回のあいだは、共有メモリ・`IMC_GETOPENSTATUS`(0)・変換モード(9)が一定で、互いに一致した(閉の 1 点だけの独立確認)。probe の時点のフォーカスは `Windows.UI.Input.InputSite.WindowClass`(**インジケーターの XAML のフライアウト**)にあり、ホスト窓ではなかった。「a」を打った結果の判定は 6 回とも未実施。
  読み取れること: (1) インジケーターの右クリックメニューは、Win32 の `#32768` ではなく XAML のフライアウトで、これが私の UIA 自動化が失敗した理由と整合する。(2) 共有メモリが変わる場合があるので、1 回目の「0/20」から「ツールバー操作は出ない」とは言えない。(3) メニュー選択ごとの対応は、どちらの測定でも取れていない(操作の内容と時刻を記録していない)。
- **E1 の 3 回目(別セッション rust-nicola-56、全スレッド走査版、12:52〜12:54 UTC、合図 6 回)**: システム全体で `Local\mozc-readable-ime-<tid>` を持つ 23 スレッド(explorer 6、Edge・Chrome・Slack・Teams・LINE・Windows Terminal・Zoom ほか)を 50ms で全部ポーリングした。
  **共有メモリが変わったのは自前窓のスレッド(tid 43064)だけ**(他の 22 スレッドは 1 つも変化なし)。変化は 7 回(12:53:03〜54:28)で、毎回 開⇄閉 が反転し、`seq` は +2 ずつ(8→20)。probe 6 回すべてで `IMC_GETOPENSTATUS` が共有メモリの `eff_open` と一致(6/6)。「a」を打った結果の判定は、閉の 1 回で ASCII を確認しただけ(他は判定不能)。
  合図ごとの対応は判定できない(利用者が何を選んだかの記録がなく、最初の合図の前に操作した形跡がある)。
  **読み取れること**: (1) 「読んだスレッドが違う」仮説は、この測定では支持されない(他のスレッドは動かない)。(2) この環境・この窓では、メニュー操作で共有メモリは変わる。**1 回目の「0/20」は再現しなかった**。
- **E1 の 1 回目(私)の読み方**: 20 窓で共有メモリが変わらず、利用者は「インジケーターの表示は変わった」と申告した。ただし、(a) 合図が窓の表示の約 3 秒後に始まり準備が足りなかった、(b) 選んだ項目と時刻を記録していない、(c) フォーカスがフライアウトに移っていた可能性を確かめていない。**「出ない」の仮説は、再現していない。未解決**。
- **(未解決・不一致)ツールバーの操作と共有メモリの関係**: 1 回目(私、0/20)と、2・3 回目(別セッション、変化あり)が食い違い、**違いの原因は不明**(候補: 1 回目は利用者の申告だけで操作の記録が無い、操作が「選択」でなく取り消しだった、窓のフォーカスの状態、など。どれも未確認)。以下は 1 回目の仮説で、**再現していない**:(E1 の 1 回目。1 台・自前の Win32 窓・Mozc Readable `607a6a6`)。**もし本当なら、「共有メモリは常に TIP の事実」という前提の穴**である。
  実際に IME のモードが変わったのに共有メモリは古い値のままなので、共有メモリを High で採ると、**ツールバーで閉じた直後から、belief が「開」のまま固定される**可能性がある(逆向きの P1。E1 が再現するなら)。
  原因は未調査(rust-nicola-56 が静的に読んだ範囲では、`UpdatePrivateContext` が応答に `status` が無いと公開せず早期に戻る点が候補。未確認)。**私が読んだだけの推測**: メニューの選択は `TipLangBarCallback::OnMenuSelect`(`tip_text_service.cc` 903〜912 行)→ `TipEditSession::SwitchInputModeAsync` の非同期の経路で、公開(`PublishOnExit`)は `tip_input_mode_manager.cc` の関数にある(キー操作はそこを通って共有メモリに出る)。メニュー経由がそこを通らない、または編集セッションが失敗している可能性。確認していない。
  確認の手がかり: 同じ窓で、(a) メニューの選択のあとに `ImmGetOpenStatus`・変換モード・実際に打った文字の種類を記録し、IME の実際の状態が変わったことを共有メモリとは独立に確かめる(今回は利用者の申告だけ)、(b) 共有メモリの `update_tick_ms`・`seq` が動かないことを再確認、(c) mozc-readable 側(仕様の持ち主)で、メニュー選択の経路が公開を呼ぶかを調べる。
- **言えないこと**: アプリ起点の変更が共有メモリに現れるか(E2 の IMM の書き込みは窓の種類で結果が違った)、パスワード欄(web / 入力スコープ)で値が割れるか(E4 は測定器の不備で結論なし)、`drift correction` が共有メモリと争うか(belief 接続が未実装)。
- 最新の awase(`779fc52f`)のログに、`{AFC94560-…}`(Mozc Readable の識別子)を GJI 系として認識する行がある(`[tip-detect] GJI family CLSIDs`)。10/12 のビルドで「親指シフトにならない・入力直後にバックスペース」が起きた原因の確認は、していない(古いビルドのログは読んでいない)。

## 残り

E1 の自動化は試して失敗した(インジケーターは UIA で見つかったが、右クリックでメニュー窓が開かなかった。DPI 対応にしても同じ。原因不明)。E1 は人の操作で行い、上の結果を得た。人の操作では、合図が窓の表示の約 3 秒後に始まり、準備の時間が足りなかった(最初の数回は取りこぼした可能性。ただし 20 窓すべて 0 件なので、結論は変わらないと見ている)。E4 は、web の `<input type=password>`(Edge)か、TSF の入力スコープを持つ窓で、判定の方法を直してからやり直す。E2 の開の不達 4 回の原因(最初の周への集中)も調べる。

## 追補: applied を Confirmed にしてよいかの検証の結果(2026-10-18、rust-nicola-56 が実機で実施)

手順書: [adr265-applied-confirmed-verification.md](adr265-applied-confirmed-verification.md)(基準は測る前に固定)。実機 dragonflyg4、13:26〜13:54 UTC、利用者の了承済み。
**私は、生データ(`applied_final.jsonl`・`applied_edge_final.jsonl`)を数え直して、次の数字を確かめた**。測定のドライバーのコードは読んでいない。

| 窓 | 検証 | 試行 | 規則 R(strict)が通った件 | R が通った読みの食い違い | R なしの生の読みの食い違い |
| --- | --- | --- | --- | --- | --- |
| 素の Win32 窓 | A(漢字キーのトグル、読みは 30〜311 ms 後のランダムな時点) | 40 | 39 | **0** | **0** |
| 素の Win32 窓 | B(IMM の書き込み、開→閉 25 往復) | 50 | 9 | **0** | **0**(書き込みが実際に効いた 50/50、「実際の状態が変わったのに共有メモリが追随しない」0) |
| Edge(TSF ネイティブ、使い捨てプロファイル) | A(同上、読みは 14〜294 ms 後) | 40 | 3 | **0** | **0** |

- 判定器の対照: 素の Win32 窓 20/20、Edge 20/20(Edge の最初の 0/20 は、判定器が Enter の後に読んでいた誤り。閉では Enter が欄を空にして種類が none に戻る。Enter の前に読む形に直した)。
- **古い読みは 1 件も観測されなかった**(最短 14 ms でも、読みは既に新しい状態)。したがって、規則 R が古い読みを除いたことを示す事例は、無い。R の必要性は、確かめられていない(R が「十分」かも、古い読みが起きていないので確かめられていない)。
- **R の c3(`update_tick_ms` が直前の書き込み・打鍵より後)は、strict だと便益がほとんど出ない**(Edge 3/40、B 9/50)。`GetTickCount64` の分解能が約 15.6 ms で、TIP の反映が 1 目盛り以内に済むため、`update_tick_ms − 基準` が 0 になる(Edge は 37/40 が 0、B は 40/41 が 0)。`>=` にすれば Edge 40/40・食い違い 0 だが、**`>=` の危険(直前の別の変化が同じ目盛りに書かれた古い読み)を起こす条件は作っていない**ので、安全性は未検証。
  **ただし、この便益の数字は、全試行が「自分の操作の直後」であることによる偏りがある**(c3 が最も通りにくい場面)。実際の利用で `applied` の訂正が要るのは、外から変えられて(ツールバー・アプリ)、awase の最後の操作から時間が経った後で、そのとき c3 は自明に通る、というのが私の推測(未測定)。
- **予定外の発見**: (1) この環境(Mozc Readable、現在のキーマップ)では F2 が IME を開かず、漢字キー(0x19)のトグルが効いた(0xF3 で閉、0xF4 で開も確認)。(2) 新しい窓の**最初のキーは効かず**、先に「a」と Enter を 1 回打つと IME キーが効いた(「TIP がテキスト入力を 1 回受けるまで IME キーを受け付けない」ように見える。因果は未確認。BUG-200 に関係しうる)。

**判断(手順書の規則どおり)**: A・B とも R(strict)で食い違い 0 で、素の Win32 窓と Edge(TSF ネイティブ)で合格。Confirmed の入口は、この 2 種類の窓だけを確認済みとして実装に進める。範囲外(ツールバーのメニュー、パスワード欄、Chrome・Windows Terminal、負荷時、複数窓、連続した打鍵)は、実装では `Unknown` に下げる側にする。
**残る未解決**: E1 の不一致(外からの変更が共有メモリに出ない場合があるか)。これが本当にあるなら、`applied` が古いまま Confirmed として残る危険は、規則 R では防げない。
