## 結論

測定前に固定した基準(開閉について、受け入れた読み N ≥ 200 のうち、正解との食い違い 0 件)は **満たした**。

- 実機(dragonflyg4)の第 1 回: Notepad と Chrome で、受け入れた読み 300 件、食い違い 0、フォーカスと違うスレッドを読んだ記録 0。
- 実機の追加測定(IME の切り替え、25 往復): 古い共有メモリの誤採用 0、awase は毎回、TIP の無効を検知。
- GitHub Actions(別セッション、run `39111907389`): フォーカス移動・同一プロセスの別スレッド・AppContainer・IME 切り替え後の各場面で、受け入れた読み 約 960 件、食い違い 0
  (私は run と要約の数字を確認した。測定の設計とドライバーのコードは読んでいない)。

**今も測れていないもの**: スレッド ID の再利用、状態を切り替えた直後にフォーカスを移す場面、物理キーでの操作と belief との比較(採用の利益)、負荷時の `read_us`、
実機でのフォーカス移動と AppContainer(GitHub Actions では測れた)。belief への接続(Medium)に進むかは、これらの扱いと合わせて利用者の判断待ち。

## 誤りと訂正(測定の途中で起きたこと)

1. **ドライバーの誤り 1**: 最初の版は、前面窓(ウィンドウ)のスレッドで共有メモリを探した。モダン Notepad では、入力のスレッドが別なので見つからず、
   exit 3 になった。フォーカスを持つ窓(`GetGUIThreadInfo`)のスレッドを使う版に直した。
2. **ドライバーの誤り 2**: 窓の中央をクリックしていた。この実機の大きな Chrome では、ページの入力欄のフォーカスを外し、IME が反応しなくなった
   (awase を止めても同じ)。クリックをやめると、awase なしで 12/12 が期待どおりになった。
3. **awase の `accepted` と `not-found` の約 1 秒ごとの交互**(2 回目の run、Notepad の準備中): 同じプロセスの 2 つのスレッド(1384 と 15588)を
   行き来していた。私は一時「awase の読むスレッドが入れ替わっている疑い」と書いたが、このときドライバーが 1 秒ごとに窓の中央をクリックしていた。
   クリックをやめた本番では起きなかった。**原因が私のクリックだったと、確定はしていない**(クリックありの再現はしていない)。
4. **最初の 2 回の run は失敗**: 新しい Notepad / Chrome が、Mozc Readable ではなく Google 日本語入力で始まった。入力方式が(「アプリごとに入力方式を
   変える」設定が既定のオフのため)全体で共有され、「既定の入力方式」の設定だけでは新しい窓に効かなかった。ja の入力方式を測定中だけ Mozc Readable
   だけにして解決した。
5. **集計スクリプトの誤り**: 最初の集計は「食い違い 100 件」と出した。原因は、モード名の対応表の不備(awase は `full-katakana`、表は `full_katakana`)。
   修正は名前の正規化だけで、判定の基準は変えていない。修正の前後で、100 件はすべてその理由で解消し、未知のモード名は 0 件。初版は
   `tools/adr265_stage2/analyze.py` には残していない(コミット履歴はこの PR)。

## 追加測定(2026-10-18、危ない場面)

### 実機(dragonflyg4)での追加測定: 場面 B は完走、場面 A は測れなかった

道具: `tools/adr265_stage2/`(`drive_scenarios.py`・`analyze_scenarios.py`・`scenarios.ps1`)。条件は第 1 回と同じ(`develop` の `f828af0c` の awase、Mozc Readable 3.35.6354.100、
ja の入力方式は測定中だけ Mozc Readable のみ、注入キー)。誤採用の定義と基準(0 件)は、測定の前に [手順書の 6-2 章](adr265-stage2-measurement.md) で固定した。

- **場面 B(IME の切り替え。Notepad で IME をオンにしてから、Win+Space で TIP の無い入力方式へ切り替えて戻す、25 往復)**: 完走。
  - 切り替えてから共有メモリが `active=0` になるまで 209〜235 ミリ秒、戻してから有効に戻るまで 217〜235 ミリ秒(ドライバーの読み)。
  - **誤採用(TIP が無効の間に、残っていた「開」を採った記録): 0 件。** awase は 25 回とも TIP の無効を検知した(最初の `rejected`(`inactive`)の記録まで 209〜694 ミリ秒、
    約 1 回の tick の範囲)。「戻す」直前の awase の最後の記録は、25 回とも `rejected`(`inactive`)。「気づかない」(最後の記録が採用された「開」のまま)は 0 件。
  - 集計の見落としを 1 つ直した: TIP が無効の間に記録が 1 件もないと、「誤採用 0 件」が何も起きていないだけで成立してしまう。そこで、最後の記録が採用された「開」のままではないか
    (NOT-NOTICED)も判定に加えた。仕込んだケースで検出を確認済み。
- **場面 A(フォーカス移動)**: **実機では測れなかった(データなし)。** 2 つ目の窓を、外から確実に IME 操作できなかった。
  - Chrome: 最初の ON のキーが、複数回の再試行(最大 8 回、約 64 秒)でも効かなかった(別セッションが CI でも報告している、Chrome だけに残る現象。BUG-002 と整合するが、同じ原因とは未確認)。
  - 素の Win32 のテスト窓(`ui_host.py`): 共有メモリは awase が正しく読めていたのに(`accepted`、`open=false`)、F2 が 66 秒間効かなかった。原因は未究明。
  - モダン Notepad では、窓の中央をクリックすると、フォーカスがテキスト欄(RichEdit のスレッド)とウィンドウの入力サイトの間で入れ替わった。
    窓を一度離れて戻した直後も、フォーカスが入力サイトに留まり、IME に届かないキーがあった。「誤りと訂正」の 3 の「約 1 秒ごとの交互」は、このクリックが原因とみられる
    (クリックの有無での再現は未実施)。
  - 別セッションの指摘: 実機のドライバーでも、2 つ目の窓の操作では、`SetForegroundWindow` が前面でないプロセスから黙って失敗していた(前面が取れていなかった)可能性がある(未確認。
    私のドライバーは前面になったかを確かめて Alt で再試行するが、IME の反応までは確かめていない)。別セッションの CI の `tools/mozc_shm_ci/shmci.py` の `force_foreground`(前面の確認と Alt のフォールバック)を、実機で試す手がある。
