# ADR-265 段階 2: 実機測定の結果(2026-10-18)

手順書: [adr265-stage2-measurement.md](adr265-stage2-measurement.md)。道具: [tools/adr265_stage2/](../../tools/adr265_stage2/README.md)。

## 結論

測定前に固定した基準(開閉について、受け入れた読み N ≥ 200 のうち、正解との食い違い 0 件)は **満たした**(N = 300、食い違い 0、
実際のフォーカスと違うスレッドを読んだ記録 0)。**ただし、測った条件は素直で、基準が守ろうとしている危ない場面は測っていない**
(下の「測っていないこと」)。belief への接続(Medium)に進むかは、追加測定の要否と合わせて利用者の判断待ち。

## 誤りと訂正(測定の途中で起きたこと)

1. **ドライバーの誤り 1**: 最初の版は、前面窓(ウィンドウ)のスレッドで共有メモリを探した。モダン Notepad では、入力のスレッドが別なので見つからず、
   exit 3 になった。フォーカスを持つ窓(`GetGUIThreadInfo`)のスレッドを使う版に直した。
2. **ドライバーの誤り 2**: 窓の中央をクリックしていた。この実機の大きな Chrome では、ページの入力欄のフォーカスを外し、IME が反応しなくなった
   (awase を止めても同じ)。クリックをやめると、awase なしで 12/12 が期待どおりになった。
3. **awase の `accepted` と `not-found` の約 1 秒ごとの交互**(2 回目の run、Notepad の準備中): 同じプロセスの 2 つのスレッド(1384 と 15588)を
   行き来していた。私は一時「awase の読むスレッドが入れ替わっている疑い」と書いたが、このときドライバーが 1 秒ごとに窓の中央をクリックしていた。
   クリックをやめた本番では起きなかった。**原因が私のクリックだったと、確定はしていない**(クリックありの再現はしていない)。
4. **最初の 2 回の run は失敗**: 新しい Notepad / Chrome が、Mozc Readable ではなく Google 日本語入力で始まった。入力方式が(「アプリごとに入力方式を
   変える」設定が既定のオフのため)全体で共有され、「既定の入力方式」の設定だけでは新しい窓に効かなかった。ja の入力方式を測定中だけ Mozc Readable
   だけにして解決した。
5. **集計スクリプトの誤り**: 最初の集計は「食い違い 100 件」と出した。原因は、モード名の対応表の不備(awase は `full-katakana`、表は `full_katakana`)。
   修正は名前の正規化だけで、判定の基準は変えていない。修正の前後で、100 件はすべてその理由で解消し、未知のモード名は 0 件。初版は
   `tools/adr265_stage2/analyze.py` には残していない(コミット履歴はこの PR)。

## 測っていないこと(基準が守ろうとしている場面を含む)

- **フォーカスを窓の間で移した直後の読み**(スレッド選択の誤りが出やすい場面)。
- **IME を別のものへ切り替えたあとの、古い共有メモリ**(`active=0`)を、awase が弾くか。
- **同じプロセスの別スレッドへのフォーカス移動**中の読み(フォーカス窓の情報が古いと、別のスレッドの状態を採る恐れ)。
- **AppContainer(UWP)の窓**、スレッド ID の再利用。
- **物理キー**での操作と、belief との比較(採用の利益)。
- 条件の多様性: 同じ 6 キーの周回を 25 回ずつ、1 台の実機、約 8.5 分、1 回だけ。`read_us` は通常時の値で、負荷時は未測定。
