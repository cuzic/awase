# BUG-208: Mozc で、かなが直接(unicode)送られ、入力中の文字・変換候補ができない

**状態(2026-10-19):** 修正を PR にした(`PendingGjiConfirm` と eager unicode を、GJI の I/O を観測できないときは使わない)。実機の確認は未実施。

**症状(利用者の報告、dragonflyg4、Windows Terminal + Mozc Readable):** ひらがなにはなるが変換候補にならない。窓の切替や無操作の後に出る。「このず」と打つと、かなが直接入る。最初の 1 文字だけが英字になることもある(原因は未確認)。IME の OFF→ON で一時的に直る。

**証拠:** 
- 共有メモリの記録(version 3、UTC 2026-10-19 06:47:00.7〜07:8)で、awase が 18 打鍵を送る間、約 7 秒 `phase=0`・`preedit_utf16_len=0` のまま(正常な打鍵は 0.06 秒以内に `phase>=1`、32 件中 32 件)。
- `RUST_LOG=debug` のログ(07:52 以降)で、awase の送信 506 回のうち 467 回が `[h1-run] unicode TSF`(かな直接)、494 回が `PendingGjiConfirm: GJI 未応答 → unicode で強制送信`。利用者が「このず」で再発と言った 07:59:26・37・53 がこの経路。
- 最初の引き金(07:25:46、cold=4): `[gji-coro] GjiProbe 完了 (gji_idle=<現在の時刻と同じ値>ms settled=false)` → `[tsf-transmit] → unicode (eager=true)` → `[post-unicode] PendingGjiConfirm 開始`。

**原因:** (1) `tsf/warmup/probe_fsm.rs::decide_transmit_plan` が cold start の最初の打鍵を unicode の eager 送信にする。(2) その後 `state/warm_send_plan.rs::is_post_unicode_pending` は「`gji_last_io_ms` が最後の unicode 送信時刻より新しくなるまで」次のキーも unicode で送る。`gji_last_io_ms` は GJI の I/O 監視が更新するが、Mozc 系では GJI の監視を外す(ADR-269 D1)ので 0 のまま動かず、応答待ちが終わらない。unicode 送信のたびに時刻が更新されるので自己維持する。フォーカス変更と cold の印付けでだけ解ける(IME の OFF→ON で一時的に直る理由)。ADR-269 D1 は literal 判定だけを GJI の証拠から外し、この 2 経路を取りこぼしていた。

**修正:** `is_post_unicode_pending` に `gji_active`(`gji_is_active_ime()`)を足し、偽なら常に偽。`decide_transmit_plan` は `gji_active` が偽なら eager にしない。

**回帰テスト:** `warm_send_plan.rs::post_unicode_pending_is_never_true_without_gji_evidence`(Linux)、`probe_fsm.rs::decide_plan_without_gji_evidence_never_uses_unicode_eager_path` と対照テスト(Windows の CI)、`architecture_guard` の呼び出しの形の固定を更新。

**未確認:** 実機での確認。最初の 1 文字が英字になる症状との関係。cold の最初の打鍵が VK sequential になって、Mozc でリテラルが起きるか(ADR-269 の未確認)。
