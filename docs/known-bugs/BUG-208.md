# BUG-208: Mozc で、かなが直接(unicode)送られ、入力中の文字・変換候補ができない

**状態(2026-10-19):** 修正を PR #691 にした(`PendingGjiConfirm` と eager unicode を、GJI の証拠が無いと確定しているとき〈Mozc 系〉は使わない)。独立レビュー(Opus)の指摘を反映済み。実機の確認は未実施。

**症状(利用者の報告、dragonflyg4、Windows Terminal + Mozc Readable):** ひらがなにはなるが変換候補にならない。窓の切替や無操作の後に出る。「このず」と打つと、かなが直接入る。最初の 1 文字だけが英字になることもある(原因は未確認)。IME の OFF→ON で一時的に直る。

**証拠:** 
- 共有メモリの記録(version 3、UTC 2026-10-19 06:47:00.7〜07:8)で、awase が 18 打鍵を送る間、約 7 秒 `phase=0`・`preedit_utf16_len=0` のまま(正常な打鍵は 0.06 秒以内に `phase>=1`、32 件中 32 件)。
- `RUST_LOG=debug` のログ(07:52 以降)で、awase の送信 506 回のうち 467 回が `[h1-run] unicode TSF`(かな直接)、494 回が `PendingGjiConfirm: GJI 未応答 → unicode で強制送信`。利用者が「このず」で再発と言った 07:59:26・37・53 がこの経路。
- 最初の引き金(07:25:46、cold=4): `[gji-coro] GjiProbe 完了 (gji_idle=<現在の時刻と同じ値>ms settled=false)` → `[tsf-transmit] → unicode (eager=true)` → `[post-unicode] PendingGjiConfirm 開始`。

**原因:** (1) Mozc では毎回 Long cold になる(`gji_last_io_ms` が 0 なので `gji_idle_ms` が常に `LONG_IDLE_MS` を超える。`ColdKind::classify`)。(2) cold の GjiWarmupCoro は、監視が不健全だと `nc_fired=true` に倒し(`gji_warmup_coro.rs:101-115`)、`decide_transmit_plan` が `forces_prepend_f2` により eager(unicode)を選ぶ。(3) eager で送ると cold 経路(`output/probe_io.rs::transmit_tsf`)が `last_unicode_transmit_ms` を立て、以後の warm 経路(`state/warm_send_plan.rs::is_post_unicode_pending`)は「`gji_last_io_ms` が `last_unicode_transmit_ms` より新しくなるまで」次のキーも unicode で送る。Mozc 系では GJI の I/O 監視を外す(ADR-269 D1)ので `gji_last_io_ms` が 0 のまま動かず、この条件が成り立ち続けて解けない(unicode 送信のたびに時刻が更新されるのではなく、解除条件が来ない)。ほぼ全ての打鍵が unicode になった(506 回中 467 回)。`last_unicode_transmit_ms` はフォーカス変更と cold の印付けで 0 に戻る(`tsf/probe.rs`)が、Mozc ではその直後の cold で再び Long cold → eager になるはずで、「IME の OFF→ON で一時的に直る」理由の説明は**推定**(`deferred_pending` などで eager を外れた回だけ直った可能性もある。未確認)。ADR-269 D1 は literal 判定だけを GJI の証拠から外し、この 2 経路を取りこぼしていた。

**修正:** `tsf/observer.rs` に `gji_evidence_absent`(アクティブな TIP が Mozc 系で、`gji_monitor` の確定した `converter_target` が `NoEvidence`)を足し、`is_post_unicode_pending`(`PostUnicodeFacts.gji_evidence_absent`)と `decide_transmit_plan`(`TsfEnvSnapshot.gji_evidence_absent`)がこれを見て、真なら応答待ち・eager を使わない。**`gji_is_active_ime()` の否定にはしない**(レビュー M1): 本物の GJI で変換プロセスが未起動・再接続待ち(最大 3 秒)の間は `gji_is_active_ime()` が偽でも、`gji_evidence_absent` は偽のままで、従来どおり(cold の最初の打鍵は unicode でリテラル化を避ける)。

**回帰テスト:** `warm_send_plan.rs::post_unicode_pending_is_never_true_when_gji_evidence_is_absent`(Linux)、`probe_fsm.rs::decide_plan_with_gji_evidence_absent_never_uses_unicode_eager_path` と対照 2 件(GJI 監視が健全、GJI 監視が一時的に未接続で eager のまま。Windows の CI)、`architecture_guard`(呼び出しの形、`output/mod.rs` の env の配線、`gji_monitor` が確定した target から立てること)。

**未確認:** 実機での確認。最初の 1 文字が英字になる症状との関係(別の機構の可能性。キーの通過は Engine OFF 中または Ctrl 押下中に起きていた)。cold の最初の打鍵が VK sequential になって、Mozc でリテラルが起きるか(ADR-269 の未確認)。Mozc で窓の切り替えのたびに Long cold になり、`cold_warmup.rs::run_start` が conv を書く・coro が後続の打鍵を数 tick 退避する影響(害は未確認、別課題)。
