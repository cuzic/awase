# BUG-143: classify_mode_key_ime_actionがsession_keymap==CUSTOM以外ではcustom_keymap_tableを一切参照せず、実在するHenkan=IMEOn設定を無視していた（ADR-174）

**アプリ:** Windows Terminal（`WindowsTerminal.exe`、`AppImeProfile::TsfNative`）。
**IME:** Google 日本語入力（GJI）。

**症状:** 半角モード（`ime_on=false`、直接入力）中に変換キーを単独タップすると、
GJI自身がIMEをON（ひらがな）にする。しかしawaseのbeliefは追従せず、
`Engine::compute_state`が`Inactive(ImeOff)`のまま残り、NICOLAエンジンが
有効化されない（ユーザー報告、2026-09-15）。

**再現手順（dragonflyg4実機、2026-09-15確認）:**
1. Windows Terminal + GJIで直接入力状態にする。
2. 変換キーを1回、単独でタップする。
3. GJI自身がIMEをひらがなに変える（実機確認済み）が、`[shadow-toggle]`
   ログが一切出力されず、Engineは活性化しない。

**根本原因（実機の`config1.db`を取得・解析して確定）:**
`classify_mode_key_ime_action`（`crates/awase-windows/src/
gji_charset_autodetect.rs`）は`session_keymap == SESSION_KEYMAP_CUSTOM(0)`
のときしか`custom_keymap_table`を参照せず、それ以外の値では
`MSIME`/`MOBILE`プリセットの静的知識（Henkan/Muhenkanは`None`）へ
無条件に落ちていた。

実機の`config1.db`は`session_keymap = Some(2)`（MSIME）のまま、
`custom_keymap_table`に175行の実際のカスタムテーブル（
`DirectInput\tHenkan\tIMEOn`を含む、F15-F19のSetMode割り当て等と共存）
を保持していた。旧実装はこのテーブルの存在を`session_keymap`の値だけで
判断して完全に無視し、GJIが実際にHenkanをIMEOnとして扱っているにも
関わらず`None`（割り当てなし）と誤判定していた。

**修正:** `custom_keymap_table`が存在し該当キーの行があれば、
`session_keymap`の値に関わらず優先する。テーブルに該当行が無い場合のみ
従来のプリセット静的知識へフォールスルーする。真に`CUSTOM(0)`選択時の
挙動（テーブルに無ければ`None`、他プリセットの知識を借用しない）は
変更していない。

回帰テスト:
`classify_msime_session_keymap_with_populated_custom_table_prefers_table`、
`classify_msime_session_keymap_with_table_lacking_henkan_falls_back_to_preset`
（いずれもLinux CIで実行可能、`gji_charset_autodetect.rs`のmod tests）。

**実機確認済み（dragonflyg4、2026-09-15）**: 修正版ビルドで直接入力中に
変換キーを単独タップ→ログで`[shadow-toggle] intent 昇格: vk=0x1C ...
action=TurnOn ... false→true`に続けて`Engine activated (ime=true,
romaji=true, japanese=true, user=true, reason=Active)`を確認、続く
文字入力もNICOLA配列で正しく動作した。

**教訓:** `session_keymap`フィールドは「ユーザーがGJI設定UIでどの
キーマップスタイルを選んでいるか」を必ずしも正確に表さない——本家tsvの
静的知識だけを頼りに`custom_keymap_table`の実在を無視すると、実機で
プリセットからの逸脱（部分的なカスタマイズ）を見落とす。
