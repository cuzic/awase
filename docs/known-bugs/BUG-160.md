# BUG-160: `is_mode_key_thumb_shift_passthrough` が `explicit_ime_action` しか見ておらず `ModeKeyConfig::Passthrough` に効かない

**発見経緯:** 2026-09-22、ADR-191（PR #240）マージ後の実機最終確認で、Shift+無変換のIME効果検証を試みたところ、この実機の無変換キーが
NICOLA親指シフトの左親指キーとして分類され、IMEモードキーの分類経路（`kp_stage_mode_key_follow`）を通らないことが判明。ユーザー指摘
「シフト＋変換・無変換が親指になるのは実装の不具合だと思う。パススルー設定ならパススルーされるべき」を受けて調査。

**原因:** `is_mode_key_thumb_shift_passthrough`（ADR-186 残る問題2、レビュー round2 C-N1）は、Shift+親指の無変換/変換を
`PendingThumb` へ入れず即座に `PassThrough` する条件を、`thumb_solo_special_handling(vk).explicit_ime_action.is_some()`
（`*_solo_tap_ime_action` の明示config、優先順位2）だけで判定していた。`*_solo_tap_ime_action` を設定せず
`ModeKeyConfig`（優先順位3、`mode_key_muhenkan`/`mode_key_henkan`）だけを `Passthrough` にしたユーザーには、この早期判定が
効かず、Shift+無変換が通常の `PendingThumb` に入る。保留の間（`simultaneous_threshold_ms`、既定100ms）にもう1キー来ると、
Shiftを押しているのにNICOLAの同時打鍵（チョード）判定に巻き込まれうる。`ModeKeyConfig::Suppress`（既定）のキーには実害がない
（最終的に何も送らない設定のため、チョードに巻き込まれても無音のまま）が、`Passthrough` を選んだユーザーの意図（このキーは
IMEへ生のまま届けたい）に反する。

**修正:** `is_mode_key_thumb_shift_passthrough` の条件に `special.mode_key_config.is_some_and(ModeKeyConfig::is_passthrough)`
を追加。`*_solo_tap_ime_action` を持たないキーでも、`ModeKeyConfig`（idle側）が `Passthrough` なら同じ理由で即座に素通しにする。
Suppress のキーは従来どおり `PendingThumb` へ入る（変更なし）。新しい状態は持たない（純粋な条件式の拡張のみ）。
単体テスト2本（`shift_muhenkan_with_mode_key_config_passthrough_is_not_captured_as_thumb`、
`shift_muhenkan_with_mode_key_config_suppress_is_still_captured_as_thumb`、`src/engine/tests.rs`）。修正前はpassthroughテストが
落ち、修正後は通ることを確認済み。

**副作用:** レビュー round3 A-NEW-5/C-N9 と同型——このガードが真になる親指キーでは、Shift+その親指の複合面（ADR-097）は
成立しない。`*_solo_tap_ime_action` 版で既に受け入れている副作用と同じ扱い。

**検証（Linux、コア crate は OS非依存）:** `cargo test --lib`（1012件、新規2件含む）、windows ターゲットの
`cargo check --target x86_64-pc-windows-msvc -p awase -p awase-windows --tests --lib`、`cargo fmt --check`、
`cargo clippy -p awase` はいずれもクリーン。実機・CIでの半角/全角(0xF3/0xF4)・漢字(0x19)等の非親指IMEモードキーでの
Shift併用検証は別途必要（このガードはそもそも親指キー限定 `ev.key_class.is_thumb()` のため対象外）。
