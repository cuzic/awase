# BUG-150: ATOK+パススルーで無変換/変換のIME開閉にEngineが追随しない

**発見経緯:** ADR-186のCI実機E2E(`--walk`、`check_consistency.py`)で、`atok-passthrough`各3/3が再現。

**症状:** ATOKプリセットのGJI(既定=opt-in無し)で、かなON中に無変換/変換を押すと実IMEはOFFになるが、Engineは残ったままONで、
直接入力にNICOLA変換が効く。

**原因(3層):** (1)通過後に読み直す契機が無い(`may_change_ime`は無変換/変換を含まず、親指キーのKeyDownはFSMがConsume)。
(2)直前の明示意図(`IntentStore`と`ImeModel::last_intent`)が`effective_open()`を固定し、観測が入っても`ctx.ime_on`が動かない。
(3)20ms後の再読み取りがtyping-idleガードで`SkipTyping`になる。詳細はADR-187。

**修正:** follow方式(ADR-187)。生キー通過点(FSMの`SendKeys`と、Engine OFF時の`PassThrough`)で通過マーク+20ms再読み取り
(typing-idleバイパス)を予約し、観測が成功した直後に対象hwndの`IntentStore`と`last_intent`を捨てる(`ImeEvent::ModeKeyPassedThrough`)。
回帰: CIの`atok-passthrough(-henkan)`と`-cold`(各3/3追随)、`ime_model`/`platform_state`の単体テスト、`architecture_guard`の出現数固定。

**適用範囲:** IMMで開閉を読めるアプリ。TsfNative/Imm32Unavailable(メモ帳・Windows Terminal・Chrome/Edge)は未検証([BUG-149](BUG-149.md)参照)。

**追記(2026-09-23、未検証):** 上記「修正」節のfollow方式(ADR-187個別実装)は、その後より広範な
[ADR-191](../adr/191-ime-is-source-of-truth-observe-not-write.md)(IMEを状態の正とし観測・予測に追随する設計転換、
PR #240でdevelop統合済み)の通過マーク機構(`ModeKeyPassMark`/`ModeKeyPassLatch`等)に置き換わっている可能性が高い。
`fix_commits`が空のままなのは、ADR-187個別実装からADR-191統合後の機構への移行を裏取りできていないため。
着手する場合はまずATOKパススルー構成のCI/実機再検証で現行developでの再現有無を確認すること。
