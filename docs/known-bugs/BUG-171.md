# BUG-171: 途中の語で StaleConfirm→ESC が直前の未確定文字を巻き込む（未修正）

**状態(2026-10-04、v2.0.0 時点):** 未修正(コード上は残存・CI では途中の語の ESC を再現できず、2026-10-04) — `crates/awase-windows/src/tsf/warmup/literal_detect_fsm.rs:89` の `per_vk_recovery_params(is_stale, failed_idx)` は 2 引数のままで、「途中の語」を区別する引数は無く、`escape_composition = failed_idx > 0` も変わっていない。BUG-170 の修正(`52cd221f`、ADR-203)は OffCold 固着の防止と、OnComposing 中の Reopen を no-op にする部分(`gji_fsm.rs` のテスト `reopen_while_composing_is_a_no_op`)のみで、本バグの方針(語頭で未確定文字の有無を記録して ESC を抑止)は未実装。README・移行ガイド・`docs/tasks/v2-e2-v1-backport-inventory-2026-09-29.md` も「v2 でも未修正」と記載し、`d97e612e` で v2.0.0 の CHANGELOG/移行ガイドから「修正済み」を外している。

(以下は当時の記述)

**発見経緯:** [BUG-170](BUG-170.md) の調査（report `01M3NBQA8KH2JN6S1PYHP8DJRF`、Opus レビュー）。BUG-168 追記・BUG-075 系と同根。

**症状:** 「これ」を未確定のまま「で」を打つと、「で」の per-VK が StaleConfirm になり `escape=true` の `VK_ESCAPE` で「これ」ごと消える（journal 上 per-VK 約26セッション中4回）。

**原因:** `per_vk_recovery_params(true, idx=1) → (0, true)`（`tsf/warmup/literal_detect_fsm.rs`）は「IME セッション最初の1文字専用」の前提で、ESC の破壊範囲は pending composition 内に閉じるとしている。
しかし「pending composition = この語」ではない。途中の語では候補窓が既に可視で、per-VK の可視ショートカットが Stale に倒れやすい。
ADR-203 で GjiFsm の OffCold 固着を直しても、OnComposing 中の CompositionReset+gji_idle≥7000ms（OnCold(Medium)）や `WarmupAborted→AbortedCold`、
1語目の probe が `StartComposition` より前に Stale で終わって `OnCold(kind, NotStarted)` に戻る経路で再発する。

**方針（未着手）:** 語の最初の VK を送る時点で「未確定文字が既に存在したか」（候補窓可視・`ime_composition_active_now()`・GjiFsm が OnComposing か）を記録し、存在したら `escape_composition=false`
（または途中の語の Stale は confirm 扱い）。`per_vk_recovery_params` に引数を足して全組合せを単体テストする。`docs/windows-api-constraints.md §1-2` に「pending composition = この語ではない」を追記する。

**状態（2026-09-29）:** 未着手・未修正。[BUG-170](BUG-170.md) の残作業と独立に着手できる（BUG-170 の実機検証で消失が0件でも本バグは残りうる）。

**追記(2026-10-04、CI 調査 — `tsx-bug171-*`、run 37187818532。同日、解釈を訂正):** 語の途中(10 文字目の直後)で 500ms / 8000ms 止めてから再開する 30ms 間隔の打鍵を、GJI で tsf(TsfNative 相当)・実 Chrome の textarea に注入した(各 6 run×12 試行、awase なしの対照あり)。
- **文字の消失は 28 run すべてで 0**(判定は全 PASS)。実 Chrome は StaleConfirm 自体が 0 件。
- tsf で 24 run 中 7 run が `per-VK[1/1] stale confirm 検出 … escape=true` を出したが、**7 件すべて `cold=1`・直前の GJI 状態が `OnCold(Long)` = セッション最初の文字**(本文が「ESC の破壊範囲は pending composition 内に閉じる」とする安全側)。初報で「途中の語で通る」と書いたのは誤りで、`idx` は 1 つのかなのローマ字内の VK 位置(`ka` の `a`)であって語の位置ではなかった。不変条件 I5 を直前の StartComposition の遷移元(OnCold か否か)で「最初の文字」と「途中の語」に分け直し、実データで再判定: 途中の語 0 件。
- **まだ再現できていない**: 前の未確定文字がある状態(OnWarm/OnComposing)での StaleConfirm→ESC。本文の「候補窓が既に可視で per-VK の可視ショートカットが Stale に倒れる」条件は、今回の打鍵(単一の語内、30ms)では作れていない。次は、確定せずに語をまたぐ打鍵(`--interrupt` や IME 確定キーを挟まない長い連続入力)と、候補窓可視の保持。

**追記(2026-10-04、長打鍵版 — `tsx-bug171long-*`、run 37191690769):** 確定せずに 80 文字を打ち続け(候補窓が可視のまま)、20 文字目の直後に 300ms 止める。tsf・実 Chrome × 30ms・5ms 間隔、各 8 run×4 試行(計 256 試行)。**文字の消失 0、途中の語での StaleConfirm→ESC 0**(tsf の StaleConfirm 13 件はすべてセッション最初の文字)。pause 版(144 試行)と合わせ、現行の CI の打鍵条件では「前の未確定文字がある状態の StaleConfirm→ESC」を作れていない。per-VK confirm は cold セッションでだけ走るため、途中の語で通るには CompositionReset+GJI idle≥7s などで cold に戻す必要がある(BUG 本文の journal の 4/26 は実利用の条件)。CI で追うなら journal 由来の打鍵列の再生(`ADR-159` 系)が向く。
**追記(2026-10-05、遅延注入の検討):** 閉ループ(`tests/closed_loop_scenarios.rs`)には足せなかった。StaleConfirm→ESC は `cfg(windows)` の `tsf/warmup/probe_fsm.rs` にあり、ハーネスは TSF warmup を写していない(遅延を入れても消費者がない)。代わりに ungated な `tsf/gji_fsm.rs` で入口を固定した: `bug171_composition_reset_while_composing_with_stale_idle_falls_to_cold`(`OnComposing` + `gji_idle_ms >= MEDIUM_IDLE_PROBE_MS` の `CompositionReset` で `OnCold(Medium, NotStarted)` に落ち、次の KeyInput で StartProbe。idle は実時間でなく引数で注入)。ESC 側は `per_vk_recovery_params(true, idx>=1) == (0, true)` の既存テストが固定済み。修正時はこの特性テストの期待を反転する。probe_fsm まで Linux で通すには ADR-228 級の ungate が先(メモリの案A)。

**追記(2026-10-05、相手を遅くする摂動 — `tsx-susp-bug171-*`、run 37275672249):** 打鍵開始の 300ms 後に `GoogleIMEJaConverter.exe` を `NtSuspendProcess` で 800/2500ms 止めた(tsf・実 Chrome、各 3 run×12 試行)。
停止は **36 試行すべてで実際に効いた**(PID 取得・status=0・実停止時間 dur_ms_actual=2500)が、**下流に差は出なかった**: 文字の消失・リテラル化は 0、窓内の `delay` は最大 1ms、StaleConfirm 件数は停止なしの対照と同じ(tsf 2 件・Chrome 0 件、全て従来どおり)。
読み方: 変換サーバを止めても per-VK confirm の経路(候補窓の可視判定)は遅れない。次は候補窓を描く `GoogleIMEJaRenderer` を止める案(未実施)。

**追記(2026-10-05、候補窓の描画側を止めた CI 調査 — `tsx-susp-rend-*`/`tsx-susp-survey-*`、run 37313441380):** 変換サーバ(Converter)を止めても差が出なかった(#489)ので、候補窓を描く側を疑った。
- 打鍵中の survey で `GoogleIMEJaRenderer.exe` が実在し、可視の `GoogleJapaneseInputCandidateWindow` を所有することを確認した。
- 80 文字相当の打鍵(30ms)の 300ms 後に `GoogleIMEJaRenderer` を 800ms / 2500ms 停止(tsf・実 Chrome の 4 構成 × 3 run × 12 試行 = 各 36 試行)。停止は全試行で効いた(`suspend_status=0`、36/36)。
- **当たらなかった**: 入力先の文字の消失・リテラル化・入れ替わりは 0(各 0/36、Wilson 95% で 0〜10%)。`i5_mid_word_stale_escape` は全構成 0。StaleConfirm は tsf で 3 件ずつ出たが、停止なしの survey 構成も同じ 3 件で、全て最初の文字(`first_char`)。実 Chrome は 0 件。
- 読み方: Renderer を止めても per-VK の判定経路(StaleConfirm の発火条件)は変わらない。途中の語の StaleConfirm→ESC は、まだ再現できていない。修正は入れていない(BUG-171 は未修正のまま)。
