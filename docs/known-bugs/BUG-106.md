# BUG-106: Teams(WebView2/MS-IME) で送信 romaji VK が JIS かな配列として解釈される

**症状（issue #137、Microsoft Teams / `TeamsWebView` / WebView2 上の MS-IME）:**
awase が正しく送信した romaji VK 列が、IME 側で「ローマ字入力」ではなく
「かな入力」として解釈され、無関係な文字になる。代表例は A キー相当が
「な」、S キー相当を含む列が「とに」のように表示されるケース。

**判定シグネチャ:** 再発時はログを開く前に、送信 VK 列を JIS かな配列表で
デコードして表示結果と突き合わせる。完全一致するなら、awase の送信ミスではなく
IME 側の入力方式反転を第一容疑にする。

| 送信VK | JISかな解釈 | 観測例 |
| --- | --- | --- |
| U | な | 「な」 |
| S | と | 「とに」の先頭 |
| I | に | 「とに」の末尾 |

**BUG-08 との関係:** ROMAN 喪失により romaji VK が JIS かな化する点では同型。
ただし BUG-08 は foreign-injected `VK_KANA` まで原因を特定済みだったのに対し、
本件は Teams/WebView2/MS-IME のどこで入力方式が反転したか未特定。

**自動復旧不可:** BUG-61/BUG-62 追補4で、`ImmSetConversionStatus` による
ROMAN ビット書き込み、`VK_DBE_ROMAN` の `SendInput` 注入、言語バー COM 操作の
いずれも実機で無反応と確認済み。Microsoft Q&A の同種回答でも、Win32 には
「ローマ字入力 / かな入力」の入力方式そのものを外部プロセスから切り替える
公式 API が無い、という整理になっている。したがって awase は復旧を書き込まず、
ユーザーへの案内だけを行う。

**今回追加した実機検証:** `crates/awase-windows/examples/spike_kana_lock_probe.rs`
で、Teams focus 中に言語バーから MS-IME を「かな入力」へ切り替えると
`GetKeyState(VK_KANA)&1` が `off -> on` に追従し、「ローマ字入力」へ戻すと
`on -> off` に追従することを確認した。

```text
KANA bit=on (prev=off) fg_class=TeamsWebView
KANA bit=off (prev=on) fg_class=TeamsWebView
```

**Teams で conv 読み取り経路が存在しない根拠:** `TeamsWebView` は
`crates/awase-windows/src/focus/class_names.rs:24` で
`IMM32_UNAVAILABLE_CLASSES` に含まれる。`is_tsf_native_window` は同ファイル
`:51-59`、`is_effectively_tsf_native` は `:75-77` だが、`from_class_name` は
`IMM32_UNAVAILABLE_CLASSES` を優先するため Teams は `Imm32Unavailable` 扱いになる。
さらに `runtime/key_pipeline.rs:643-646` のとおり `kp_stage_idle_conv_check` は
TsfNative 専用かつ ROMAN ビットを信頼しない設計で、Teams の反転検知には使えない。

**`swallow_alt_kana_input_method_switch` との関係:** swallow の有無は復旧可否と
無関係。既定 ON は Alt+かな による「かなに落ちる」方向の予防であり、OFF にしても
復旧手段にはならず、むしろ入力方式反転のリスクを増やすだけ。

**対応:** `src/engine/kana_input_warn.rs` に OS 非依存のヒステリシス
（On 3連続で警告、Off 2連続で解除）を追加し、`observer/kana_lock.rs` が
`GetKeyState(VK_KANA)&1` を読み、VK/TSF の romaji 送信直前に1打鍵1サンプルで
観測する。警告時は既存トレイ右クリックメニューに「かな入力になっています
（対処方法）」を出し、ツールチップを「awase - かな入力になっています」へ変更する。
belief/engine/IMM への書き込み、`ImeEvent` dispatch、自動復旧は行わない。

**修正履歴:** `40a2d091`（2026-09-02、`feat/issue-137-teams-kana-lock-detection`）。

**追補1（スコープ拡大、2026-09-06〜07 実機報告2件）:** 不具合報告
`01M1WH2F0YMCVMKV1A1SEKH0HP`（1.18.0）・`01M1WK863PTTNMV8GDKPWWN1QC`
（同一ユーザーの約38分後の再報告、1.19.0）で、判定シグネチャ（U→な/S→と/I→に）
が完全一致する症状が **Chrome** でも発生し、awase 再起動・PC 再起動でも
復旧しないことを確認した。当初の記述「Teams/WebView2/MS-IME のどこで入力方式が
反転したか未特定」は Teams 固有ではなく、MS-IME の入力方式反転自体がアプリ非依存で
起きうることを示す。1.18.0→1.19.0 の両バージョンで再現しており、対応が
「復旧不可・OS制約」である以上バージョンアップでは直らない性質のもの。

副次的な観測として、両報告のログに `observer/ime_observer.rs::
input_mode_from_romaji_flag` が出す `IME input method changed: romaji → kana`
という info ログが、`awase_tray_window`（awase 自身のトレイウィンドウ）や
`Windows.UI.Input.InputSite.WindowClass`（UWP シェル）へフォーカスが移った
瞬間・`classify_focus` がタイムアウトした直後に頻発している（1報告あたり
7〜12回）。この経路は BUG-106 の対応で追加した `observer/kana_lock.rs`
（VK 送信直前に1打鍵1サンプル）とは**別の観測点**で、通常の IME poll/probe
（`ImeSnapshot.is_romaji`）が実際の編集対象ではないウィンドウの値を拾って
`current_input_mode` と食い違ったときに発火する。実際の文字化けと対応する
観測なのか、フォーカス遷移時のノイズ的な誤検出（実害なし）なのかは未分離。
`kana_input_warn` のヒステリシス（On 3連続で警告）がこのノイズで誤発火しうるか
どうかは次回の調査対象。

**追補2（同一ユーザーの継続再発、2026-09-09/09-10 実機報告2件）:** 不具合報告
`01M21X336TN7TFG6QJTTWWTW8W`（2026-09-09、Edge/Firefox）・`01M258NJN75XJ2DTX394M1V3J0`
（2026-09-10、Edge/Chrome、`01M258N6KT97RBACNM2AEFHETE`は12秒差の重複投稿）は
`config.toml`が完全一致しており同一ユーザー。両報告の`awase.log.txt`に
`observer/ime_observer.rs`の`IME input method changed: romaji → kana`が実際に
記録されており（前者は5連続、後者は1回）、その直後の`[key-output]`romajiは
awase側では正しいローマ字列（例: "gu"→ぐ相当）のまま送信され続けている。
送信romaji自体は健全で、IME側の入力方式反転のみが原因という追補1の結論を
再確認した。1〜2日間ブラウザを閉じても直らず、Word/Excel等の別issue #189の
SSOT問題とは別に、この反転単体が最短2日間持続することを示す新しいデータ。
GitHub issue #137へコメントで回答済み（対処法: 対象アプリのIME言語バーから
手動で「ローマ字入力」に戻す）。

**追補3（追補1の未分離課題を解消、追補2の記述を訂正、2026-09-13）:** 追補1で
「未分離」としていた `IME input method changed` ログについて、issue #137関連の
不具合報告4件（`01M1WH2F0YMCVMKV1A1SEKH0HP`・`01M1WK863PTTNMV8GDKPWWN1QC`・
`01M21X336TN7TFG6QJTTWWTW8W`・`01M258NJN75XJ2DTX394M1V3J0`、実質2ユーザー分）の
`awase.log.txt`を再取得し、該当ログ計25回全てのタイムスタンプを直前の
`FocusChange`/`classify_focus timed out`ログと突き合わせた。結果、**25回中25回
（100%）が `awase_tray_window` または `awase-settings.exe` へのフォーカス遷移
（`classify_focus` の300msタイムアウト直後）と一致し、ユーザーが実際に入力して
いた対象アプリ（Chrome/Edge/Firefox/Teams）へのフォーカス中に発火した例は
一件もなかった**。フォーカス遷移のタイミング（症状に気づいてから報告するまでの
数分間に断続的に出現）から、ユーザーがトラブルシューティングのつもりでトレイ
アイコンをクリックした（再起動・ON/OFF切替を試みた）際に生じたノイズと考えられる。

これにより追補2の「ログに実際の`IME input method changed: romaji → kana`を
確認し...本Issueの原因と完全に同期した」という記述は**誤り**と判明した——
`01M258NJN75XJ2DTX394M1V3J0`の「1回」も実際には`kana → romaji`（回復方向）で
あり、かつフォーカス先は`awase-settings.exe`だった。**現在のログには、実際の
編集対象アプリ上でMS-IMEの入力方式が反転する瞬間を捉えた観測が一件も存在しない**
——反転自体はユーザー報告・手動復旧手順の一致から実在が強く疑われるが、その
発生機序は今のところ完全に未観測。次の一手は、`classify_focus`のタイムアウトや
`awase_tray_window`等の非編集対象クラスに一致する場合は`is_romaji`のpoll結果を
`current_input_mode`更新に採用しない（Noneのまま前回値を維持する）よう
`classify_ime_snapshot`を絞り込み、ノイズ除去後に本当の編集対象アプリ上での
反転だけをログに残すこと。

副次的な観測: 4件全てで`Hook watchdog: no activity`（issue #165、OS全体では
直近に入力があるのにawaseのフックにイベントが届いていない）が慢性的に発生
しており、直近2件では全チェックの約半数が実際のフック詰まり判定だった。
4件ともOSビルドが`10.0.26200.9168`/`.9445`という通常の安定版より新しい番号帯に
揃っている。いずれも因果関係は未確認（相関のみ）。

**追補4（ノイズはbelief汚染だった、修正実施、2026-09-13）:** 追補3の25件は
ログに出るだけの無害なノイズではなく、実際に`input_mode` beliefを汚染していた。
`observer/ime_observer.rs::input_mode_from_romaji_flag`が`awase_tray_window`
から読んだ`is_romaji=false`を`InputModeObserved{confidence: Medium}`として
そのままdispatchし、open軸（`AcceptedObservation`によるガード済み）とは非対称に、
input_mode軸には観測元を検証するガードが一切無かった。結果、belief が
`ObservedKana`になり`decide_needs_romaji_pre_write`が`false`を返すため、
**awase自身がIME ON時のROMAN補完(`IMC_SETCONVERSIONMODE`)を送るのを止めて
しまう**経路が実在した（`state/ime_actuation_decision.rs`）。「1〜2日直らない」
という追補2の報告と噛み合う実害経路であり、仮説ではなくコード上確認済み。

修正: `ImeSnapshot`に`focused_class: Option<String>`を追加（`read_ime_state_full`
が既に計算していた値を保持するだけ、新規Win32呼び出しはゼロ）。
`focus::class_names::is_own_ui_window(class_name, process_name)`を新設し
（`awase_tray_window`はクラス名、`awase-settings.exe`はプロセス名で判定——
後者はwinit既定の一般的なクラス名`"Window Class"`のため無関係な他社アプリとの
誤判定を避ける）、`classify_ime_snapshot`に`trust_input_mode: bool`引数を追加。
`false`のとき`new_input_mode`と`new_prev_conversion_mode`の両方をNoneにする
（片方だけ採用しないと次のpollで偽のconv遷移を作ってノイズが1サイクルずれる
だけになる）。open軸（`ime_on`）は今回のスコープ外（既存の`AcceptedObservation`
ガードで別途守られている）。

opus-adversarial-consultで2ラウンド設計レビュー（非同期IMM probe案・
`focus_kind`ゲート案はいずれも対象アプリで空振りする/probe詰まり中に前回値が
残るため不採用と判明、詳細は`docs/design/opus-review-p1-passive-ime-probe.md`）。
回帰テストは`observer/ime_observer.rs`（`classify_ignores_input_mode_and_conv_when_not_trusted`
等）と`focus/class_names.rs`（`is_own_ui_window_*`3件、うち「無関係なwinitアプリを
排除しないこと」が過剰排除の回帰を防ぐ本質）。`cargo test --lib`・
`cargo nextest run -p awase-windows --test architecture_guard --test layer_boundary_guard`
（771件）ともに通過。

なお`input_mode_from_romaji_flag`の`tracing::info!`に`focused_class`を追加した
ため、次の不具合報告で「反転ログが残っているか、残っているならどの窓か」を
grep一発で判定できる。本追補が排除したのはトレイ/設定画面由来のノイズのみで、
**実際の編集対象アプリ上でMS-IMEの入力方式が反転する瞬間を捉えた観測は
依然として存在しない**——発生機序の特定は引き続き未解決。

**追補5（issue #165との相関を受動観測する仕組みを追加、2026-09-13）:**
根本原因（実際にMS-IMEの入力方式が反転する瞬間）は追補4の修正後も未観測の
ままのため、`runtime/message_handlers.rs`の`TIMER_HOOK_WATCHDOG`（3秒周期）が
「フックにイベントが届いていない疑い」（issue #165、`os_idle_ms < 5000`）を
検知した時点で、`observer/kana_lock.rs::read_kana_lock()`
（`GetKeyState(VK_KANA)&1`、BUG-106本文の実機spikeで言語バー操作への追従を
確認済みの唯一のチャネル）と`foreground_class_name()`を受動的にサンプルし、
前回値から変化したときだけ`tracing::warn!`で1行記録するようにした
（`Runtime::watchdog_kana_edge: Option<KanaLockReading>`、新規フィールド1本の
み・IMM/TSF/`run_with_timeout`/`spawn_local`は一切使わない・
`kana_lock_hysteresis`とは完全に独立——後者に混ぜると1打鍵1サンプル前提の
較正が壊れ無打鍵でもトレイ警告が誤発火する）。

**ログの読み方で注意すべき点(誤読しやすい)**: サンプリングは`hook_starved`
（フック詰まりを検知した）ときにしか走らないため、ログ行`Hook watchdog kana
lock edge: X → Y`の`X`(=`previous`)は**「前回フック詰まりを検知した時点」**の
値であり、「直前の3秒間でXからYに変わった」ことを意味しない——フックが健全な
間に反転してからしばらく後に詰まりが起きた場合、反転はその間のどこかで
起きたとしか言えない。また`own_ui=true`の行は追補3・4のノイズと同系統
（awase自身のUIにフォーカスがある状態での観測）として扱い、
`grep -v own_ui=true`で機械的に分離できる。

opus-adversarial-consultで設計→実装差分の2段階レビュー実施（実装は
Codex CLIに委譲）。回帰テストは`runtime/`が`#[cfg(windows)]`配下でLinux上の
自動テストを付けられないため、本追補が
[fix-requires-evidence](../../.claude/rules/fix-requires-evidence.md)の(b)を
満たす記録。検証は`cargo check`/`cargo clippy`（Windowsターゲット）・
`cargo fmt --check`。次に実際のユーザー報告でこのログが出た場合、
`own_ui=false`かつ`stale_ms`/`os_idle_ms`が小さい行が反転の前後に見つかれば、
issue #165とissue #137の相関を初めて実機データで確認できる。
