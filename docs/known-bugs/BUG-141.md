# BUG-141: 長時間cold状態のGJIにCtrl+無変換を送っても3回連続で無効、候補ウィンドウが再表示され続ける（msedge.exe/Imm32Unavailable/GjiDirect）

**症状（report `01M2D8HS5SBWSZ221P240Z4ZXE`、2026-09-13、GJI、msedge.exe/`Chrome_WidgetWin_1`/`profile=Imm32Unavailable`）:**
「Ctrl + 無変換 で IME OFF になってほしいのにならなかった」。

**初回調査の誤り**: journalの`ActuationDecision{mechanism:GjiDirect, outcome:Applied}`
と`GjiFsmTransition{OnCold(Long)→OffCold}`だけを見て「OFFは成功している、
再現していない」と誤って報告した。ユーザー指摘を受けて`GjiFsmTransition
{StartComposition(candidate SHOW)}`（`observer.rs`の`EVENT_OBJECT_SHOW`＝
GJI候補ウィンドウの実際の表示イベント、キー入力の解釈ではなく実OS UI）を
見落としていた。

**実際の経過（elapsed_ms、すべて同一msedge.exeフォーカス中。全イベントを
時系列で再突き合わせして訂正——後述するとおり「3回目の押下で直った」という
記述も不正確だった）:**
1. `6128805`: Ctrl+無変換 1回目 → `Applied`、`OffCold`へ遷移（内部beliefはOFF）
2. `6130242`〜: `C`,`H`,`A`入力 → `6130462`で**候補ウィンドウ表示**（失敗）
3. Backspace×2 → Ctrl+無変換 2回目（`6131393`、`AlreadyMatched`）
4. `C`,`H`,`A`再入力 → `6131714`で**再び候補ウィンドウ表示**（失敗、2回目）
5. Backspace×2 → 物理半角/全角キー相当イベント（`vk=0xF3/0xF4`、
   `self_injected=false`＝本物の物理キー、`6132761`）→ `UserImeSetIntent
   {source:PhysicalImeKey}`
6. `C`,`H`,`A`再入力（Ctrl+無変換は押していない） → `6133308`で**またも
   候補ウィンドウ表示**（失敗、3回目。直前の物理半角/全角キーも無効だった）
7. Ctrl+無変換 3回目（`6135183`、`AlreadyMatched`）
8. `C`,`H`,`A`4回目の入力（`6135583`〜）で**初めて候補ウィンドウ無し**、
   Enter確定 → ここでようやく実際にOFFへ収束

**「race condition」という初期の説明は誤り（ユーザー指摘で訂正）**:
真のレースなら1回のリトライで直るはずだが、実際は**同一のCtrl+無変換
コマンド（`SendVk(26)`）を3回送っても最初の2回は無効**で、間に挟まった
無関係な物理半角/全角キーイベントも無効だった。3回目の押下の後でようやく
候補ウィンドウが出なくなったが、最初のCtrl+無変換(`6128805`)から数えると
約6.9秒・3回のOFF送信・2回のBackspace訂正を経ている。「1回タイミングが
ズレて即座にリカバリする」という一発リトライ型の競合ではなく、**GJIが
cold状態から脱するまで数秒間、こちらが送るOFFコマンドを繰り返し無視/
上書きし続ける**という、時間・累積活動量に依存する現象に見える。何が
最終的に効いたのか（3回目のCtrl+無変換そのものか、単に経過時間か、
累積したキー入力量か）はこのjournal単体では切り分けられない。

**メカニズム（確定）**: `ActuationDecision`の`outcome:Applied`/`AlreadyMatched`は
「awase→GJIへVK_IME_OFF(0x1A)のSendInputが成功した」ことしか示さず、GJI側が
実際に候補ウィンドウ（TSF composition）を閉じたかを検証しない。
`gji_fsm.rs:885-887`の`StartComposition while engine off`分岐は「awase自身の
belief破壊を防ぐ」設計だが、GJI実体への訂正コマンド（OFF再送・候補キャンセル）
を発行しない受動的な無視であり、実際に3回連続でGJIがcomposition再開したことを
止める機構になっていない。候補ウィンドウ（`GoogleJapaneseInputCandidateWindow`
クラス）はGJIレンダラープロセスが持つデスクトップ単一のシングルトンUIのため、
`SetWinEventHook`がhwnd/pid無指定（システム全体監視、`win_event_obs.rs:84-93`）
であっても、実際にIMEフォーカスを持つ現在のmsedge.exeの状態を正しく反映している
（フォーカス遷移が本区間に無いことも確認済み）。

**根本原因（作業仮説、実機未検証。訂正: 初版はEdge固有説だったが、
ユーザーから「通常はmsedgeでも問題なくIME OFFできる」と指摘され撤回）**:
journalをさらに遡ると、Ctrl+無変換1回目を押す**約108秒前**（elapsed `6020935ms`、
windowsterminal.exe→msedge.exeへのFocusChange時点）で、GJI側は既に
`FocusChange(gji_idle_ms=27656)`＝**GJI関連の入力が27.7秒間無かった**ことを
記録しており、`ColdKind::classify`により`OnCold(Long)`へ分類されている
（Chrome/Edge系の`InjectionMode::Vk`は`CHROME_LONG_IDLE_MS=5000ms`が閾値、
`tuning.rs:68`）。その後108秒間、journal上のKeyInputは矢印キー(↑/↓)連打と
Ctrl+V(ペースト)のみ（elapsed `6119189`〜`6123659`）で、いずれもGJI宛の
ローマ字/親指シフト入力ではないため`gji_idle`はリセットされず、Ctrl+無変換を
押した瞬間もGJIは**長時間（実質2分以上）本当にcoldのまま**だった。

`GjiDirectStrategy`（`ime_controller.rs:75-110`）のOFF方向（`VK_IME_OFF`送信）
には、ON方向の`send_eager_tsf_warmup`（cold時にF2/`VK_IME_ON`warmupペアを
同梱、ADR-100）に相当する**cold対応が一切無い**——コメント上も「冪等キーで
GJIがネイティブに処理する」としか書かれておらず、GJIのTSFセッションが
cold（休眠）状態のときに送っても確実に反映される保証はない。
`docs/windows-api-constraints.md`§2（TSFベースIMEのCold Start）が記録する
「cold状態のGJIへの操作は、GJI自身のセッション再初期化（~1000ms前後）が
完了するまで一時的に予期しない動作をする」という既知パターン群（§2-2/2-4、
いずれもON方向のリテラル化）の**OFF方向・鏡像**である可能性が高い:
cold状態でVK_IME_OFFを送っても内部的に受理されない、あるいはGJI自身が
直後の物理キー入力をトリガーに独自の再初期化シーケンスへ入り、その過程で
「最後に確認できたON状態」へ暗黙に復帰する、という機序が考えられる。

**ユーザーの「通常は問題ない」という指摘と整合する点**: GJIがwarm
（直近の入力からgji_idle < 5000ms）な状態でCtrl+無変換を押す通常の使用では
再現しないはずで、今回は「msedge.exeに戻ってから100秒以上GJI関連入力が
無いまま初めてIME操作をした」という比較的まれな条件が重なって発生したと
考えられる。Edge固有ではなく、**GJIが長時間cold状態にあるときのOFF操作**が
条件と考えるのが現時点で最も裏付けの強い仮説。

**対応状況**: 未対応（根本原因未確定、実機再現待ち）。次のアクション:
(1) 実機で「GJIをidle 5秒以上放置→Ctrl+無変換」を再現条件として意図的に
試し、候補ウィンドウ再表示が再現するか確認（chrome.exeでも同条件で
再現するなら「Edge固有」説は完全に排除できる）、(2) `GjiFsmTransition
{StartComposition}`発生時に直近の`SendVk(26)`からの経過ms・その時点の
`gji_idle_ms`を診断ログへ残し、タイミング相関を定量化、(3) 再現条件が
固まったら`GjiDirectStrategy`のOFF方向にもcold対応（warmup同梱 or
`StartComposition`ignore分岐でのOFF再送）を追加する設計を検討。次に同一
症状が再現した際は、`GjiFsmTransition{StartComposition}`の有無と、その
直前の`OnCold`/`gji_idle_ms`を最初に確認すること
（`ActuationDecision`の`outcome`だけでは判断できない）。
