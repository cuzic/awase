# BUG-141: Ctrl+無変換で「Applied」記録されたIME OFF後も、GJI候補ウィンドウが実際に再表示され英字入力が変換され続ける（msedge.exe/Imm32Unavailable/GjiDirect）

**症状（report `01M2D8HS5SBWSZ221P240Z4ZXE`、2026-09-13、GJI、msedge.exe/`Chrome_WidgetWin_1`/`profile=Imm32Unavailable`）:**
「Ctrl + 無変換 で IME OFF になってほしいのにならなかった」。

**初回調査の誤り**: journalの`ActuationDecision{mechanism:GjiDirect, outcome:Applied}`
と`GjiFsmTransition{OnCold(Long)→OffCold}`だけを見て「OFFは成功している、
再現していない」と誤って報告した。ユーザー指摘を受けて`GjiFsmTransition
{StartComposition(candidate SHOW)}`（`observer.rs`の`EVENT_OBJECT_SHOW`＝
GJI候補ウィンドウの実際の表示イベント、キー入力の解釈ではなく実OS UI）を
見落としていた。

**実際の経過（elapsed_ms、すべて同一msedge.exeフォーカス中）:**
1. `6128805`: Ctrl+無変換 1回目 → `Applied`、`OffCold`へ遷移（内部beliefはOFF）
2. `6130242`〜: ユーザーが`C`,`H`,`A`を入力（`PassThrough`で素通し扱い）
3. `6130462`: **GJI候補ウィンドウが実際に表示**（`StartComposition`、
   `gji_fsm.rs:885-887`の`"while engine off — ignored"`分岐で内部状態は
   保持されるが、GJI側の候補ウィンドウそのものは閉じない）
4. Backspace×2で訂正 → Ctrl+無変換 2回目（`6131393`、`AlreadyMatched`）
5. `C`,`H`,`A`再入力 → `6131714`で**再び候補ウィンドウ表示**（同一パターン再現）
6. Backspace×2 → 物理半角/全角キー相当イベント（`vk=0xF3/0xF4`）→
   Ctrl+無変換 3回目（`6135090`、`AlreadyMatched`）
7. `C`,`H`,`A`4回目の入力（`6135583`〜）で候補ウィンドウは表示されず、
   Enter確定 → ここでようやく実際にOFFへ収束

**メカニズム（確定）**: `ActuationDecision`の`outcome:Applied`/`AlreadyMatched`は
「awase→GJIへVK_IME_OFF(0x1A)のSendInputが成功した」ことしか示さず、GJI側が
実際に候補ウィンドウ（TSF composition）を閉じたかを検証しない。
`gji_fsm.rs:885-887`の`StartComposition while engine off`分岐は「awase自身の
belief破壊を防ぐ」設計だが、GJI実体への訂正コマンド（OFF再送・候補キャンセル）
を発行しない受動的な無視であり、実際に2回連続でGJIがcomposition再開したことを
止める機構になっていない。候補ウィンドウ（`GoogleJapaneseInputCandidateWindow`
クラス）はGJIレンダラープロセスが持つデスクトップ単一のシングルトンUIのため、
`SetWinEventHook`がhwnd/pid無指定（システム全体監視、`win_event_obs.rs:84-93`）
であっても、実際にIMEフォーカスを持つ現在のmsedge.exeの状態を正しく反映している
（フォーカス遷移が本区間に無いことも確認済み）。

**根本原因（作業仮説、実機未検証）**: `ADR-034`はGJIのVK_IME_ON/OFFが
「Chrome・WezTerm・Windows Terminal」で動作確認済み（2026-06-28）としているが、
確認対象は`chrome.exe`であり、本reportの`msedge.exe`（Edge）を明示的に検証した
記録はコードベース中に見つからない。`docs/windows-api-constraints.md`§1-1は
そもそも「Chrome/Edgeでは`ImmSetOpenStatus`/`VK_IME_ON/OFF`が無効
（`Chrome_WidgetWin_1`はIMM-broken）」という汎用Win32 IME APIの制約を記録しており、
ADR-034はこれを「GJIはTSFのキーイベントとして`VK_IME_ON/OFF`を独自に処理するため
この制約を回避できる」という上書き決定にしている。この上書きがEdge固有の
TSF/IME統合（Chrome本体には無いEdge独自機能）でも完全に成立するかは未検証
であり、`§1-4`/`§1-5`が別機構（ImmCross）で記録している「async確認とshadow
モデルの陳腐化によるOFF直後のON復帰」と同型の未特定レースがGjiDirect側にも
存在する可能性がある。

**対応状況**: 未対応（根本原因未確定、実機再現待ち）。次のアクション:
(1) msedge.exe限定で本パターンが再現するか実機で確認（chrome.exeでは
再現しないなら「Edge固有」説が濃厚）、(2) `GjiFsmTransition{StartComposition}`
発生時に直近の`SendVk(26)`からの経過msを診断ログへ残し、タイミング相関を
定量化、(3) 再現条件が固まったら`StartComposition`ignore分岐へOFF再送等の
訂正アクションを追加する設計を検討。次に同一症状が再現した際は、
`GjiFsmTransition{StartComposition}`の有無を最初に確認すること
（`ActuationDecision`の`outcome`だけでは判断できない）。
