# BUG-141: gji_direct_already_matchesがcandidate_was_seen desync証拠を無視し2・3回目のCtrl+無変換を無送信で握り潰す（Mozc/ChromiumのOnSetFocus機序は補助的要因）

**症状（report `01M2D8HS5SBWSZ221P240Z4ZXE`、2026-09-13、GJI、msedge.exe/`Chrome_WidgetWin_1`/`profile=Imm32Unavailable`）:**
「Ctrl + 無変換 で IME OFF になってほしいのにならなかった」。

**初回調査の誤り**: journalの`ActuationDecision{mechanism:GjiDirect, outcome:Applied}`
と`GjiFsmTransition{OnCold(Long)→OffCold}`だけを見て「OFFは成功している、
再現していない」と誤って報告した。ユーザー指摘を受けて`GjiFsmTransition
{StartComposition(candidate SHOW)}`（`observer.rs`の`EVENT_OBJECT_SHOW`＝
GJI候補ウィンドウの実際の表示イベント、キー入力の解釈ではなく実OS UI）を
見落としていた。

**実際の経過（elapsed_ms、すべて同一msedge.exeフォーカス中。全イベントを
時系列で再突き合わせして訂正——後述するとおり「3回目の押下で直った」という
記述も不正確だった）:**
1. `6128805`: Ctrl+無変換 1回目 → `Applied`、`OffCold`へ遷移（内部beliefはOFF）
2. `6130242`〜: `C`,`H`,`A`入力 → `6130462`で**候補ウィンドウ表示**（失敗）
3. Backspace×2 → Ctrl+無変換 2回目（`6131393`、`AlreadyMatched`）
4. `C`,`H`,`A`再入力 → `6131714`で**再び候補ウィンドウ表示**（失敗、2回目）
5. Backspace×2 → 物理半角/全角キー相当イベント（`vk=0xF3/0xF4`、
   `self_injected=false`＝本物の物理キー、`6132761`）→ `UserImeSetIntent
   {source:PhysicalImeKey}`
6. `C`,`H`,`A`再入力（Ctrl+無変換は押していない） → `6133308`で**またも
   候補ウィンドウ表示**（失敗、3回目。直前の物理半角/全角キーも無効だった）
7. Ctrl+無変換 3回目（`6135183`、`AlreadyMatched`）
8. `C`,`H`,`A`4回目の入力（`6135583`〜）で**初めて候補ウィンドウ無し**、
   Enter確定 → ここでようやく実際にOFFへ収束

**「race condition」という初期の説明は誤り（ユーザー指摘で訂正）**:
真のレースなら1回のリトライで直るはずだが、候補ウィンドウは3回連続で
再表示されている。

**さらに重要な訂正（opus-adversarial-consult round2指摘、`ADR-171`参照）**:
上記「3回のOFF送信」という記述自体が誤りだった。journalを`ImeOpenApplied`/
`ActuationDecision`まで精読すると、**実際にGJIへ`VK_IME_OFF`が送信された
のは1回目（`6128805`、`outcome:Applied`）だけ**であり、2回目（`6131393`）・
3回目（`6135183`）はいずれも`outcome:AlreadyMatched`——`gji_direct_
already_matches`（`state/ime_actuation_decision.rs:142-144`）が
`shadow_on==Some(false)==open`と判定し、`send_ime_mode_key`自体を呼んで
いない。つまり実際に起きていたのは「GJIが3回とも無視した」ではなく、
**「awase自身が2回目以降の再送をshadowモデル任せで握り潰していた」**。
awaseはこの間、候補ウィンドウの実際の再表示という desync の直接証拠
（`tsf/observer.rs::candidate_was_seen`ラッチ）を既に保持していたが、
`gji_direct_already_matches`の判定にはこの証拠が渡っていなかった
（`impl From<&ImeControlView<'_>> for DecisionInputs`が`candidate_was_seen`
をコピーしていない）。この配線漏れの修正が[ADR-171](../adr/171-gji-candidate-reopen-after-off-observation.md)
「案Z」。

また、app.log/journalを実測で確認した結果、この区間（elapsed `6128715`〜
`6136419`）では`ir_apply_drift_correction`の周期チェーンが一度も回って
いなかったことも確認した（`runtime/mod.rs::reschedule_ime_refresh`が
「`explicit_intent().is_some()`の間は次回tickを張らない」という設計、
BUG-51と同型の別の既知の穴、`ADR-171`「関連する別の穴」節参照）。

**メカニズム（確定）**: `ActuationDecision`の`outcome:Applied`/`AlreadyMatched`は
「awase→GJIへVK_IME_OFF(0x1A)のSendInputが成功した」ことしか示さず、GJI側が
実際に候補ウィンドウ（TSF composition）を閉じたかを検証しない。
`gji_fsm.rs:885-887`の`StartComposition while engine off`分岐は「awase自身の
belief破壊を防ぐ」設計だが、GJI実体への訂正コマンド（OFF再送・候補キャンセル）
を発行しない受動的な無視であり、実際に3回連続でGJIがcomposition再開したことを
止める機構になっていない。候補ウィンドウ（`GoogleJapaneseInputCandidateWindow`
クラス）はGJIレンダラープロセスが持つデスクトップ単一のシングルトンUIのため、
`SetWinEventHook`がhwnd/pid無指定（システム全体監視、`win_event_obs.rs:84-93`）
であっても、実際にIMEフォーカスを持つ現在のmsedge.exeの状態を正しく反映している
（フォーカス遷移が本区間に無いことも確認済み）。

**根本原因（作業仮説、実機未検証。訂正: 初版はEdge固有説だったが、
ユーザーから「通常はmsedgeでも問題なくIME OFFできる」と指摘され撤回）**:
journalをさらに遡ると、Ctrl+無変換1回目を押す**約108秒前**（elapsed `6020935ms`、
windowsterminal.exe→msedge.exeへのFocusChange時点）で、GJI側は既に
`FocusChange(gji_idle_ms=27656)`＝**GJI関連の入力が27.7秒間無かった**ことを
記録しており、`ColdKind::classify`により`OnCold(Long)`へ分類されている
（Chrome/Edge系の`InjectionMode::Vk`は`CHROME_LONG_IDLE_MS=5000ms`が閾値、
`tuning.rs:68`）。その後108秒間、journal上のKeyInputは矢印キー(↑/↓)連打と
Ctrl+V(ペースト)のみ（elapsed `6119189`〜`6123659`）で、いずれもGJI宛の
ローマ字/親指シフト入力ではないため`gji_idle`はリセットされず、Ctrl+無変換を
押した瞬間もGJIは**長時間（実質2分以上）本当にcoldのまま**だった。

`GjiDirectStrategy`（`ime_controller.rs:75-110`）のOFF方向（`VK_IME_OFF`送信）
には、ON方向の`send_eager_tsf_warmup`（cold時にF2/`VK_IME_ON`warmupペアを
同梱、ADR-100）に相当する**cold対応が一切無い**——コメント上も「冪等キーで
GJIがネイティブに処理する」としか書かれておらず、GJIのTSFセッションが
cold（休眠）状態のときに送っても確実に反映される保証はない。
`docs/windows-api-constraints.md`§2（TSFベースIMEのCold Start）が記録する
「cold状態のGJIへの操作は、GJI自身のセッション再初期化（~1000ms前後）が
完了するまで一時的に予期しない動作をする」という既知パターン群（§2-2/2-4、
いずれもON方向のリテラル化）の**OFF方向・鏡像**である可能性が高い:
cold状態でVK_IME_OFFを送っても内部的に受理されない、あるいはGJI自身が
直後の物理キー入力をトリガーに独自の再初期化シーケンスへ入り、その過程で
「最後に確認できたON状態」へ暗黙に復帰する、という機序が考えられる。

**ユーザーからの追加情報（2026-09-13）**: 「TsfNative の Windows Terminal
等ではこの現象は起きない」との指摘。cold状態単独では説明できない
——cold状態はTsfNative（WezTerm/Windows Terminal）でも普通に起こりうる
（`docs/windows-api-constraints.md`§2の既存cold-startバグ群もむしろ
WezTerm/Windows Terminal側の事例が中心）。**cold状態単独が十分条件ではなく、
ホストアプリの種別との組み合わせが条件**と考えるべき。

**根本原因（Mozc/Chromiumの公開ソースで直接確認、2026-09-13）**: 続けて
ユーザーから「MozcもChromiumもオープンソースだ」との指摘を受け、実際に
両者のソースを確認した。`GjiDirectStrategy`が送る`SendVk(26)`(`VK_IME_OFF`)
自体はTsfNative/Imm32Unavailableで完全に同一経路（`ime_controller.rs`の
`is_applicable`はGJI検出のみで判定）——awase側が送る内容に差は無い。

Mozcの[`win32/tip/tip_input_mode_manager.cc`](https://github.com/google/mozc/blob/master/src/win32/tip/tip_input_mode_manager.cc)
（`TipInputModeManager`）は、IME open/close状態を`tsf_state_`/`mozc_state_`の
2系統で保持する。VK_IME_OFF等の明示コマンドは`OnReceiveCommand(bool
mozc_open_close_mode, ...)`経由で両方の状態を更新するが、**`OnSetFocus(bool
system_open_close_mode, DWORD system_conversion_mode, ...)`はフォーカスが
再通知されるたびに`tsf_state_.open_close`を呼び出し元が渡す
`system_open_close_mode`で無条件に上書きする**——明示的なOFFコマンドの直後
であっても、フォーカスの再通知が来れば「system側の値」で問答無用に
差し替えられる。この呼び出し元（`system_open_close_mode`の実際の値）は
Mozc側からは見えず、TSFホスト（Chromium/コンソールホスト）が
`ITfThreadMgrEventSink::OnSetFocus`をどのタイミング・どの値で発火させるか
に依存する。

Chromiumの[`ui/base/ime/win/tsf_bridge.cc`](https://chromium.googlesource.com/chromium/src/+/9ff13081c1766eac6edc574d3af12e72519e8091/ui/base/ime/win/tsf_bridge.cc)
は、テキスト入力欄の種別（text/password/email等）ごとに**別々の
`ITfDocumentMgr`を使い分け**、`SetFocusedClient`（フォーカス対象クライアント
変更）や`OnTextInputTypeChanged`（入力欄の種別変更）のたびに
`thread_manager_->AssociateFocus()`でフォーカス関連付けを**再実行**する。
コード内コメントにも「一部のIMEはdocument focusの変化がないと状態を
更新しない」ことを踏まえた設計だと明記されている——つまりChromium自身が
「IME側の状態を確実に更新させるため、意図的に頻繁にフォーカス再通知を
送る」実装になっている。これがMozcの無条件上書きロジックと組み合わさると、
ページ内の要素間フォーカス移動やタブの前面化等のたびに`OnSetFocus`が
再発火し、直前に明示送信した`VK_IME_OFF`をMozc自身が握り潰してしまう
経路が成立する。Windows Terminalのような単一の永続ウィンドウ（テキスト
入力欄の種別切り替えが発生しない、フォーカス対象自体が変わらない）では
この種のフォーカス再通知そのものが起きにくいと考えられ、ユーザーの
「TsfNativeでは起きない」という観察と整合する。

**確度**: Mozc/Chromiumの該当ロジックの存在は公開ソース読解で確認済み
（WebFetchでの取得・要約、原文の直接引用ではない点は留意、要再照合）。
ただし「本reportの実際のタイミングでOnSetFocusが実際に発火したか」は
Windows実機のETW/デバッグログでしか確認できず未検証。

**重要な限界**: `tsf_bridge.cc`が再発火させるフォーカス関連付け
（`SetFocusedClient`/`OnTextInputTypeChanged`、ページ内のDOM要素間の
フォーカス移動やomnibox↔ページ間の移動等）は**msedge.exeプロセス内部の
イベントであり、OS/ウィンドウレベルの変化を伴わない**。実際、本reportの
journalでは`FocusTransition`（awaseの`WinEventHook`ベースのhwnd/pid
フォーカス追跡）は6020935msから6139610msまで一度も発生していない
——しかしこれは「Chrome内部でTSFフォーカスの再関連付けが起きなかった」
ことの証拠にはならない。**awaseの現在の計装では、この機序が実際に発生した
かどうかを直接観測できない**（プロセス内部のTSFフォーカス再関連付けを
捕捉するフックが存在しない）。次に同一症状を調査する際、既存の
`FocusTransition`が「無かった」ことをもってこの仮説を否定しないこと。

**対応状況**: 未対応（[ADR-171](../adr/171-gji-candidate-reopen-after-off-observation.md)
「案Z」として起草済み、opus-adversarial-consult round1〜round3反映済み、
round4待ち。実装未着手）。Mozc/Chromium側の`OnSetFocus`機序（上記）は
awaseの管理外のため根治不能だが、**awase自身がユーザーの再送を握り潰して
いた**という、この報告で確定した直接原因はADR-171「案Z」（`gji_direct_
already_matches`に`candidate_was_seen`/`candidate_visible`を渡すだけの
最小修正）で解消できる。実機A/B（BUG-113の症状、特に候補ウィンドウ可視中の
同一キー連打で再発しないことの確認）を実装後に実施予定。
