# BUG-209: Mozc の cold の最初の打鍵が、入力中の文字にならずリテラルになる

**状態(2026-10-19):** 修正を PR にした(ADR-270: cold の最初のローマ字の送信後、共有メモリで入力中の文字ができたかを確かめ、リテラルなら消して送り直す)。実機は未確認。

**症状(利用者の報告、dragonflyg4、Windows Terminal + Mozc Readable):** 窓の切り替えやひらがなキーの直後の最初の 1 打鍵だけが、アルファベット(「けいり」→「ke いり」、「をもと」→「wo もと」)。2 打鍵目から正常。BUG-208 の修正(awase PR #691)の後に出た。

**証拠(`RUST_LOG=debug` の awase.log、UTC 2026-10-19 09:23:04):** `[tsf-send] warm=false prepend_f2_warmup=true`(`reason=NativeF2Consumed`)→ `[gji-coro] GjiProbe 完了 (16ms gji_idle=69478156ms settled=false)` → `[tsf-transmit] romaji="wo" → vk-run (eager=false)`、`vks=[57,4F]`。続く `mo` `to` は入力中の文字が普通にできた。cold の処理は 13 分で 13 回(cold=2〜14)。

**原因:** Mozc は GJI の I/O が動かない(ADR-269 D1)ので、cold の GjiWarmupCoro は準備を確認せず(16ms で完了、`settled=false`)、ローマ字を VK で送る。cold の直後(ひらがなキー・窓の切り替えの後)は、最初のキーが目覚め前の Mozc に届くとアプリにリテラルで出る。BUG-208 の修正前は、最初の打鍵が unicode(かな直接)で、リテラルにならなかった。

**修正(ADR-270):** cold の最初のローマ字の送信の直前に共有メモリ(version 3、80 バイト)を読んで確認の対象にするかを決め(`should_check_compose`)、`MozcComposeCheckFsm` が 10ms ごとに `phase` を読む。0.3 秒たっても入力中の文字ができず、`server_ready == 1` ならリテラルとして、既存の `RawTsfLiteralRecovery`(送ったローマ字の文字数の Backspace と再送)を使う。`server_ready == 0` のとき、リテラルと判断する直前に対象のスレッドが IME の読み取りに応答しないとき(IME の同期呼び出しで止まっていて、キーがまだ処理されていない)、宛先の窓が変わったときは、消さない。FSM は `install_followup_tsf` で張り、終わる段の記録と宛先を壊さない(独立レビュー C1・C2)。

**回帰テスト:** `state/mozc_shm.rs` の単体テスト(Linux: 80 バイトの解釈、対象にする条件、判定、消す文字数)、`mozc_compose_check_fsm.rs` の単体テスト(Windows の CI)。

**未確認:** 実機で効くか、再送が成功するか。部分的なリテラル(`ke` の `k` だけ)は検出できない。Windows Terminal 以外(Chrome・WezTerm)。
