# BUG-202: コンテキストメニューの項目へのホバーが「窓の切替」として扱われる

**状態(2026-10-18):** **PR #636 で修正済み・develop にマージ済み**(マージコミット `c816800e`、2026-10-18)。修正前は CI(windows-latest、awase debug・`RUST_LOG=debug`)で再現済み。実機での実害(打鍵への影響)と、修正後の実機確認は未実施。

**症状(ログ):** 任意の Win32 コンテキストメニュー(クラス `#32768`)の項目にカーソルが乗る(ハイライトされる)と、メニュー窓への `EVENT_OBJECT_FOCUS` が出て、awase が次を記録する。
`[focus-sync] hwnd=… class="#32768" app_kind=Win32 hint=Default → mode=Unicode` と
`[tsf-gate] focus change → PendingWarmup (held cleared)`(**保持キーの解除**)。メニュー窓への UIA 分類(`NonText`)も走る。

**再現(CI):** ブランチ `ci/indicator-menu-verify`、run 39081235242(`tools/ci/indicator_menu/run.ps1 -Mode full`)。タスクバーの入力インジケーターを右クリックして開いたメニューで、
項目にカーソルを乗せた 4 通り(MS-IME 本体・GJI × 通常の窓・観測の無い窓の近似)すべてで、ホバーの瞬間に上のログが出た。ホバー時刻と `focus-sync` の時刻が一致(右クリックから +1.9〜2.1 秒)。
**対照**(同 run、`-Mode control`): メニューを開いて何もしない(読み取りも、マウス移動も無し)と、6〜8 秒開いたままでも `#32768` への反応は出ない。メニューを開く・UI Automation で読むだけでも出ない。
入力インジケーターのメニューに限らず、**どのアプリの右クリックメニューでも項目をハイライトすれば同じ経路を通る**はず(別アプリのメニューでは未確認)。

**影響(想定。未確認):** メニューを操作するたびに、保持中の打鍵(`held`)が捨てられ、TSF の warmup 状態が `PendingWarmup` に戻り、フォーカス窓の分類(`HwndCache`・UIA)が走る。
メニューを閉じたあとの最初の打鍵が、cold-start 扱いになる恐れがある。メニューの操作中は通常打鍵していないので害は小さい見込みだが、親指シフトの保留中にメニューが開くと保持キーが消える。

**原因(読解):** focus 追跡が `EVENT_OBJECT_FOCUS` の対象窓を、メニューの窓かどうかを区別せず、新しいフォーカス窓として扱う。メニューは元の窓にフォーカスを残したまま、別の窓(`#32768`)へ `FOCUS` を出す。

**方針案:** [ADR-264](../adr/264-indicator-menu-mode-evidence.md) 決定 7。`MENUSTART`〜`MENUEND`(同じスレッド)の間は、`#32768` のクラスの窓へのフォーカスを、`focus-sync`・`HwndCache` の保存/復元・`tsf-gate` の遷移の対象にしない。
`focus_tracking.rs` 系は再発ファミリー([fix-requires-evidence](../../.claude/rules/fix-requires-evidence.md))なので、直す際は golden か journal のテストを足す。実機でメニュー操作が打鍵に影響するかを先に確かめる。

**修正履歴:** PR #636(`fix/bug202-ignore-menu-focus`、2026-10-18)。`win_event_proc` の入口で、クラス `#32768` の窓へのフォーカスを、**重複排除(`LAST_FOCUS_HWND.swap`)より前**で弾く(後だと、メニューを閉じて元の窓へ戻る `FOCUS` が新しい窓として再び拾われる)。回帰テスト: core の単体テスト 2 件・`architecture_guard` の順序ガード 1 件。
