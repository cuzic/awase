# BUG-207: Mozc Readable で `raw-tsf-literal` の誤判定により、入力直後の文字が消される

**状態(2026-10-19):** 修正を PR #686 にした(Mozc 系がアクティブなら GJI の監視を外す)。BUG-207 の条件(Mozc がアクティブ、静止した GJI の変換サーバーが同名で動く)の CI 再現で、修正前 tsf INVALID ×4 → 修正後 PASS ×4(下記)。実機での確認は未実施。

**症状(利用者の報告):** Mozc Readable(日本語の入力方式を Mozc だけにした状態)で入力すると、入力した直後に awase にバックスペースで消されて入力できない。

**証拠(dragonflyg4、`awase.log`、develop 64b65541 相当、UTC 2026-10-18 23:04:03〜14。入力先のアプリ名はログに無く未確認):**
- ひらがなキー(`vk=0xF2`)→`S`(`vk=0x53`)→ `KeyInput(tsf): romaji="a" ime=GJI`。0.5 秒後に `[comp-probe] setopen-per-vk-literal cold=1 ... profile=TsfNative himc_null=true`、`WARN output::probe_io: [raw-tsf-literal] cold=1 raw TSF literal suspected → backspace + re-send "a" scheduled`。
- 以降 `cold=2 consecutive raw-tsf-literal (count=2) → giving up, backs=1 cleanup only` が約 0.5 秒ごとに cold=8 まで。`FocusProbe ... gji_io=18860ms`(GJI の I/O が 18.9 秒前のまま)。
- 同時に `GoogleIMEJaConverter`(GJI)と `mozc_server.exe`(Mozc Readable)が動いていた。`[gji-monitor] attached to GJI process`。

**原因:** literal 判定(`output/probe_io.rs`、`tsf/probe.rs::LiteralDetector`)は、GJI の変換サーバーの累積書き込み量(`gji_write_bytes`、閾値 350B)が増えなければ「リテラル」とする。判定は `gji_is_active_ime()`(= GJI の監視が健全 かつ GJI 系がアクティブ)のときだけ走る。実機は GJI の変換サーバーも動いていたため監視が GJI に付き、Mozc がアクティブなのに静止した GJI を見て誤判定した。Mozc だけの環境では監視が付かず、判定は走らない(develop の CI で確認: 下記)。

**一度目の修正の誤り(PR #686 の途中、run 39175765485):** 監視を `mozc_server` に向けた。Mozc の書き込みは 1 VK あたり約 0.2〜0.3KB で閾値 350B に届かず、かつ監視が付くと Mozc だけの環境でも判定が有効になるため、CI の tsf 入力先(`Chrome_RenderWidgetHostHWND` を名乗る RichEdit)で 4/4 が INVALID(準備確認で `ready` の text が空、Escape/BS で組成が消えた)。修正前(develop)は同じ構成が PASS(tsf 4/4、`trials=12`)で、監視は付かず `raw-tsf-literal` は 0 件(run 39177357191)。取り下げた一度目の修正は `95db75cb`。つまり一度目の修正は Mozc 単独環境に誤判定を持ち込んでいた。Opus レビュー(ADR-269 round 1)と develop の比較で判明。

**修正(PR #686):** `converter_target`(コア、純関数)で、GJI 系かつ `TipIdentity::Gji` でない TIP(Mozc 系)は `ConverterTarget::NoEvidence`。`gji_monitor` はそのとき GJI の監視を外し(`gji_monitor_ok=false`、`gji_*` の値も 0 に戻す)、接続しない。literal 判定は走らない(Mozc 単独環境と同じ)。外す向きは 1 回の観測で即時。GJI 系でない TIP は従来どおり GJI。また、アクティブな TIP の問い合わせを新しい STA スレッドで行う(ADR-269 D1a。起動時の `mgr` は起動後の GJI → Mozc の切り替えに追随しなかった。CI で切り替えの約 1.5〜1.8 秒後に監視を外すことを確認)。副次: GJI と Mozc が両方ある環境で、GJI の無関係な I/O が Mozc の belief を ON に書く汚染(`observe_gji_after_focus`)も止まる。

**回帰テスト:** `converter_target.rs` の単体テスト(Linux)、`architecture_guard::gji_monitor_drops_gji_evidence_when_mozc_family_is_active`。これらは純関数と文字列だけを見る。元の条件で develop が落ちるテストは CI の `ts-{edit,tsf}-mozc-gji-*`(同名のダミー変換サーバー、および実 GJI + Mozc アクティブ、ADR-269 順序 2)で作った。結果: develop(run 39179709667)は tsf INVALID ×4(`attached to GJI process`、疑い 1・諦め 2)、修正後(run 39179706704)は tsf PASS ×4(接続なし、誤判定 0)。実 GJI をインストールして Mozc をアクティブにした `ts-tsf-mozc-gjireal-*` でも同じ: develop(run 39180505943)は INVALID ×4、修正後(run 39180466125)は PASS ×3(残り 1 本は GJI の chocolatey インストール失敗で未実行)。`ts-tsf-mozc-*`(Mozc 単独)は develop でも PASS するので再発防止にならない。

**未確認:** 実機での確認。症状の「Mozc だけにした」と「GoogleIMEJaConverter も動いていた」は一見食い違う(GJI の TIP を一覧から外しても変換サーバーが残ったのか、アンインストールされず常駐していたのかは未確認)。TIP 切替後、GJI → Mozc は最大約 2 秒(外す向きは即時)、Mozc → GJI は最大約 4 秒(付ける向きは 2 連続)。
