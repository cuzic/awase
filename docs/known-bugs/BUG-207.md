# BUG-207: Mozc Readable で `raw-tsf-literal` の誤判定により、入力直後の文字が消される

**状態(2026-10-18):** 修正を PR にした(CI 待ち)。実機での確認は未実施。原因は実機ログとコードの読みによる推定で、「監視を `mozc_server` に向けると直る」ことは実機では確かめていない。

**症状(利用者の報告):** Mozc Readable(日本語の入力方式を Mozc だけにした状態)で入力すると、入力した直後に awase にバックスペースで消されて入力できない。

**証拠(dragonflyg4、`awase.log`、develop 64b65541 相当、UTC 2026-10-18 23:04:03〜14):**
- ひらがなキー(`vk=0xF2`)→`S`(`vk=0x53`)→ `KeyInput(tsf): romaji="a" ime=GJI`。0.5 秒後に `[comp-probe] setopen-per-vk-literal cold=1 ... profile=TsfNative himc_null=true`、`WARN output::probe_io: [raw-tsf-literal] cold=1 raw TSF literal suspected → backspace + re-send "a" scheduled`。
- 以降 `cold=2 consecutive raw-tsf-literal (count=2) → giving up, backs=1 cleanup only` が約 0.5 秒ごとに cold=8 まで。`FocusProbe ... gji_io=18860ms`(GJI の I/O が 18.9 秒前のまま)。
- 同時に `GoogleIMEJaConverter`(GJI)と `mozc_server.exe`(Mozc Readable)が動いていた。`[gji-monitor] attached to GJI process`。

**原因(推定):**
1. `tsf/gji_monitor.rs` の監視対象は `GoogleIMEJaConverter`/`GoogleJapaneseInputConverter` の接頭辞に固定。`mozc_server` は対象外。
2. `probe_io` の raw-tsf-literal 判定は、`gji_write_bytes()`(その変換サーバーの書き込み量)が送信前のベースラインから増えないことを「リテラル」の証拠にする。
3. ADR-265/#663 で Mozc 系の TIP は `ActiveImeKind::GoogleJapaneseInput` になるが、証拠の I/O だけは GJI 専用のまま。Mozc が正しく変換していても GJI の変換サーバーは静止しているので「書き込みなし = リテラル」と誤判定する。

**修正(PR):** アクティブな TIP で変換サーバーを選ぶ(`awase-windows-core/src/tsf/converter_target.rs` の `converter_target`/`is_converter_process`、純関数。GJI 系で `TipIdentity::Gji` でないものは `mozc_server`、それ以外は従来どおり GJI)。`gji_monitor` は 2 tick 連続で同じ対象が観測されたら付け替える。GJI と Mozc の両方が動いていても、最初に見つかったものでなく TIP で選ぶ。

**回帰テスト:** `converter_target.rs` の単体テスト(Linux で走る。Mozc 系は `mozc_server`、GJI/非 GJI 系は従来どおり、両方が動いていても互いを拾わない)と、`architecture_guard.rs::gji_monitor_selects_converter_by_active_tip`(監視が GJI の接頭辞に固定され直さないこと)。

**未確認:** 実機で、監視を `mozc_server` に向けると `[raw-tsf-literal]` が出なくなること。`mozc_server` の `WriteOperationCount`/`WriteTransferCount` が打鍵で十分に増えるか(350B 閾値で足りるか)。Chrome など TSF ネイティブの窓での挙動。
