# BUG-228: LR 判定器が数字キー単打を強く「非日本語」の証拠として学習していた

**状態(2026-11-08):** 原因はコードと学習データの両方から特定、修正を PR にした(実機は未確認)。

**症状:** dragonflyg4(`mode=ime_on_eisu`・`scope=all`・`decider=lr`・`eisu_threshold=4.0`)で
msedge を約 20 秒操作せずに置いた後、数字キー「8」を 1 打しただけで `lr_llr=-4.46` となり
`eisu_threshold` を超えて `ime_on_eisu`(半角英数トグル、不可逆)の入りが実行された。実 MS-IME が
Eisu(英数)conv mode に確定し、以後エンジンは正しく `reason=Inactive(NotRomajiInput)` で非活性の
まま、ローマ字がそのまま出力され続ける(見た目は「親指シフトが効かない」不具合)。

**原因:** `tools/lang-detect-model/ldm/build_dataset.py::ja_episodes` が ASCII トークン(数字含む)に
当たった時点で日本語側の学習エピソードを切るため、数字キーは「ja」クラスにほぼ出現せず、
ほぼ無正則化(`l2=1e-6`)の学習で `lr.rs` の数字キー重みが極端に負(例: `uni['8']≈-2.59` nats)になる。
これは学習データの構成に起因する構造的な偏りで、同じ手順で再学習しても再発しうる。

**修正:** 学習データ/重み表には触らず、判定ロジック側で既存の `KanaModel::delta`(ADR-280/#819、
記号・数字など仮名に読めないキーを中立(0)として扱う既存の原則)と同じ基準を LR にも適用する。
`EpisodeDetector::on_char_down` で `model.key_kana.contains_key(&pos)` が false のキーは
`lr_llr`/`lr_trace` に 0 を加え `lr_ctx` を BOS にリセットする(`src/lang_detect.rs`)。

**回帰テスト:** `lang_detect.rs::tests::lr_decision_treats_lone_digits_as_neutral`(数字単打後に
`lr_llr` が 0 のまま・`NotJapanese` に倒れないことを確認。`"windows10"` のような英字混在列は
数字の中立化後も正しく `NotJapanese` と判定されることも確認)。
