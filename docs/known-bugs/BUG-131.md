# BUG-131: `kana_mode_restore_key_down` ラッチがDown/Up vk非対称で解除されず固着する（確認済みの設計欠陥、本報告の直接原因は未確定）

**発端:** 不具合報告 `01M29KDNZ22KNY1FPXSKBGMW7V`（2026-09-12、v1.19.0、GJI、JISキーボード、
`force_tsf`設定でWindowsTerminal.exe強制TSF化）:「なぜか、カタカナで状態が固着してしまった」。
Shift+物理「カタカナ ひらがな ローマ字」キー(scan=0x70)でカタカナへ入った後、同じ物理キーの
ひらがな側を5回以上押し直してもひらがなへ戻らない、という報告。

**確認済みの設計欠陥（コード読解で確定）:** ADR-137(BUG-116)決定2
(`key_pipeline.rs::kp_restore_hiragana_for_suppressed_mode_key`)は、物理ひらがな側
(`VK_DBE_HIRAGANA`=0xF2)が`transport.rs::PhysicalKeyDisposition::plan`にSuppressされた
埋め合わせとして`VK_DBE_HIRAGANA`を能動注入する。このM-2リピート防止ラッチ
`kana_mode_restore_key_down`の解除条件は、旧実装では`event.vk_code == VK_DBE_HIRAGANA`の
KeyUpのみを離鍵と認めていたが、**実機ではこの物理キーのKeyUpは常に`VK_DBE_ALPHANUMERIC`
(0xF0)で届く**（5/5件で確認。KeyDownは切替先モードに応じ0xF1/0xF2、scan_codeはDown/Up
双方とも0x70で一致）。Windowsのキーボードレイヤーが押下時と離鍵時で別々に現在のIMEモードを
見てvkを合成するための非対称性。結果、解除条件が構造的に一度も成立せず、条件を満たした
KeyDownでラッチがセットされた場合、プロセス生存中ずっと解除されなくなる。この欠陥自体は
実機ログを介さずコードを読むだけで確定できる。

**本報告の直接原因かどうかは未確定（opus-adversarial-consult検証）:** ラッチをセットする
唯一の箇所は`send_gji_half_width_alnum_toggle`呼び出し直後の無条件`tracing::info!`だが、
報告のapp_log（1157行、`awase.log`の末尾200KB切り出し、`bug_report.rs::truncate_text_tail`）
中にこの成功ログが1件も無い。切り出しがプロセス起動行（`"Keyboard Layout Emulator
starting..."`）を含んでいればラッチが一度も立たなかったと確定できるが、本報告のexcerptは
この行を含んでおらず（末尾切り出しのため、より早い時点での成功が窓の外に落ちた可能性を
排除できない）、ラッチ説を確定的に排除することも確証することもできなかった。加えて、他に
4つの無ログ早期return候補（`is_configured_thumb_key`/`half_width_alnum_toggle_before`/
`conv_mutation_allowed`(M-4)/ラッチ自身）が同じ「ログ0件」という観測と区別なく両立する。
さらに`plan()`自体にも独立した未解決candidate機序（[ADR-166](../adr/166-physical-key-disposition-decision-table.md)
M-2節: Shift+`VK_DBE_KATAKANA`のDownがAllowされる一方、対応するUpは常にSuppressされ、
GJI自身がこの物理押下のKeyUpを一度も受け取らない）が見つかっている。したがって本報告の
症状に対するBUG-131の因果関係は**有力仮説の一つ**に留まる。

**修正（確認済み設計欠陥への対応、本報告の因果とは独立に正当）:**
1. ラッチの型を`bool`から`Option<ScanCode>`に変更し、KeyDown時に発火した`scan_code`を
   保持、**同じscan_codeのKeyUp**で解除する（vk_code系列判定ではなくscan_code一致——
   `rewritten_vk`によるキー役割代入(ADR-140/143)でUp側のvkが書き換わる構成にも頑健）。
2. `runtime/focus_tracking.rs`のフォーカス遷移ハンドラでもラッチを解除する。disable_apps
   バイパス等でKeyUpがパイプライン自体に到達しない残存経路（opus-adversarial-consult
   指摘M-3）への保険。単一の物理押下中にフォーカスが変わることはないため、M-2のリピート
   防止効果は損なわれない。タイムアウト方式（ラッチに経過時間で自然失効させる）は、
   `tuning-constants.md`の実測義務が発生する上、長押し中に失効してM-2の重複発火保護が
   復活するリスクがあるため不採用。

**テスト:** 解除条件を`should_clear_kana_mode_restore_latch(armed_scan_code, keyup_scan_code,
injected) -> bool`という純粋関数に切り出し、ユニットテスト4件を追加（`key_pipeline.rs`）。
本体の`kp_restore_hiragana_for_suppressed_mode_key`はRuntime全体を要するため単体テスト
困難（ADR-137実装m-1で既知）。あわせて`transport.rs::plan_tests`にADR-166の全数決定表
テストと、M-2のDown/Up非対称を固定するpinテストを追加した。いずれも`runtime/`配下のため
`#[cfg(windows)]`でLinux上では実行不可、`cargo check --target x86_64-pc-windows-msvc -p
awase-windows --tests --lib`でコンパイルのみ確認済み。**windows-build CIでの実行結果、
実機JISキーボードでの`[kana-mode-restore]`ログ出力確認、および本報告の実際の原因特定
（本BUGかADR-166 M-2か他の無ログ候補か）は次回セッションでの確認事項。**
