# BUG-131: `kana_mode_restore_key_down` ラッチがDown/Up vk非対称で解除されず固着する（確認済みの設計欠陥、本報告の直接原因は未確定）

**発端:** 不具合報告`01M29KDNZ22KNY1FPXSKBGMW7V`（GJI、JIS、force_tsf）:
物理「カタカナ ひらがな ローマ字」キーでカタカナへ入った後、ひらがな側を
5回以上押し直しても戻らない。

**根本原因（コード読解で確定）:** ADR-137決定2のM-2リピート防止ラッチは
`event.vk_code == VK_DBE_HIRAGANA`のKeyUpのみを離鍵と認めていたが、
実機ではこの物理キーのKeyUpは常に`VK_DBE_ALPHANUMERIC`で届く（5/5件で確認、
scan_codeはDown/Up双方0x70で一致）。Windowsが押下時と離鍵時で別々に
現在のIMEモードを見てvkを合成する非対称性のため、解除条件が構造的に
一度も成立しない。

**本報告の直接原因かは未確定:** ラッチ成功ログが報告のapp_log excerptに
無く、他に無ログ早期returnの候補4件、および`plan()`自体の独立した
Down/Up非対称（[ADR-166](../adr/166-physical-key-disposition-decision-table.md)
M-2）も候補として残るため、本BUGは有力仮説の一つに留まる。

**修正:** (1) ラッチの型を`bool`→`Option<ScanCode>`にし、KeyDown時の
`scan_code`を保持、同じscan_codeのKeyUpでのみ解除（vk系列ではなくscan_code
一致、キー役割代入でUp側vkが書き換わる構成にも頑健）。(2)
`focus_tracking.rs`の`on_focus_process_changed`と
`apply_app_disable_transition`の両方でラッチを解除（disable_appsバイパス等で
KeyUpが届かない残存経路への保険）。

**テスト:** `should_clear_kana_mode_restore_latch`を純粋関数に切り出しユニット
テスト4件追加、`transport.rs::plan_tests`にADR-166全数決定表テストと
M-2非対称のpinテストを追加。`#[cfg(windows)]`のためLinuxではコンパイル
確認のみ、windows-build CI・実機での`[kana-mode-restore]`ログ確認は未実施。

**関連ファイル:** `runtime/key_pipeline.rs`
（`kp_restore_hiragana_for_suppressed_mode_key`,
`should_clear_kana_mode_restore_latch`）、
`state/platform_state.rs::GateStore::kana_mode_restore_key_down`、
`runtime/focus_tracking.rs`、`runtime/transport.rs`。

**関連バグ:** ADR-166 M-2（`plan()`自体のDown/Up非対称、未解決）、
BUG-132（同型の非対称が`hook.rs`にも影響しうる件、別途起票）。
