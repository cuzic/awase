# BUG-231: ADR-290適用後も、かなキー押下からEngine再活性まで最大約5.3秒ローマ字がリテラルで漏れる

**状態(2026-11-11):** 原因は2つとも特定済み(下記)。修正は[ADR-291](../adr/291-mozc-shm-push-notify-and-engine-recheck.md)で提案・Opusレビュー予定。実装は未着手。

**症状:** dragonflyg4(ADR-290/BUG-230の修正を含むビルドを投入済み)で、左Shift単独タップで半角英数
トグルをONにしたあと、ひらがなキー(vk=0xF2)を押して日本語入力に戻したつもりでも、実際にEngineが
活性(Active)に戻るまで最大約5.3秒かかり、その間に押した打鍵がNICOLA変換されずローマ字のまま
リテラルで出力され続けた。ADR-290が対処した「toggle_heldが解除されない」問題とは別の、ADR-290の
修正(mozc-shmの観測ベースの2段ラッチ)自体が持つ新しい遅延特性。

**タイムライン(UTC, awase.log 2026-11-11T05:47:16〜05:47:24, dragonflyg4):**
1. `05:47:16.733` 左Shift単独タップ → `[shift-conv-guard]` 半角英数トグルON。
2. `05:47:16.869` `Engine deactivated (reason=Inactive(NotRomajiInput))`。
3. `05:47:18.911` ひらがなキー(vk=0xF2)押下1回目 → `[mode-key-follow]` PassThrough、
   `[key-effect-predict]` は `mode=None`(このモードキー予測は`input_mode`軸に触れない)。
4. `05:47:20.544` (約1.63秒後) `[shift-conv-guard] mozc-shmの観測でかなへの追随を確認 → 半角英数
   トグルを手放す` — `ir_do_abandon_half_width_alnum_from_mozc_shm`が発火し、
   `apply_input_mode_correction`で`input_mode`をromaji-capableへ補正。**この時点でEngineの
   再チェックは一切呼ばれない。**
5. `05:47:20.544`〜`05:47:24.195` の間、バックスペース(vk=0x08)×4・T(0x54)×2・Space(0x20)・
   Enter(0x0D)等、複数の物理キーが押された。**これらは`[key-effect-predict]`だけでなく
   `Engine::on_input`→`check_active_transition`も毎回実際に再実行していた**
   (Opusレビューで訂正。`key_pipeline.rs`の特殊キー以外は全て`engine.on_input`を通り、
   `on_input_body`のPhase2が非活性の早期returnより前に`check_active_transition`を呼ぶ)。
   それでも非活性のままだったのは、再チェックした先の belief 自体が古かったため(下記原因2)。
6. `05:47:24.195` ひらがなキー(vk=0xF2)押下2回目(ユーザーが再度押したと見られる) →
   `[key-effect-predict]`発火。
7. `05:47:24.231` (手放しから**約3.65秒後**) `Engine activated (reason=Active)`。

**合計: かなキー押下1回目(18.911)からEngine活性(24.231)まで約5.32秒。**

**原因(2つ、独立。Opusレビューで原因2を訂正・確定):**

1. **mozc-shm観測の検知遅延(〜約1.6秒、うち大半はMozc自身の切替時間)**: ADR-290 D1″の2段ラッチは
   専用タイマー`TIMER_MOZC_SHM`(`MOZC_SHM_TIMER_MS = 500ms`、
   `crates/awase-windows-base/src/tuning.rs:65`)による定期ポーリングでしか共有メモリを読まない。
   mozc-readable側は実際には`TipStatePublisher::Pulse()`(`SetEvent`+`ResetEvent`、Local名前付き
   イベント`Local\mozc-readable-ime-changed`)で変化を即時シグナルしているが、
   `crates/awase-windows/src/observer/mozc_shm.rs`はこのイベントを一切使っていない(`grep`で0件)。
   ただし、ポーリング間隔が足せるのは最大500ms(平均約250ms)のみで、今回の1.63秒のうち
   **少なくとも約1.13秒はMozc自身の実際の切替時間**([BUG-230](BUG-230.md)の実測、F2押下から
   `hiragana`表示まで約2秒、と整合)。ADR-291のD2(Pulse通知)はこの軸を縮められない。
2. **belief_v2(候補Z)がトグルの手放しを受理しない(〜約3.7秒、今回の主要因)**:
   `general.belief_v2`は既定で`true`([ADR-282](../adr/282-per-scope-latched-ime-belief-zero-base.md)
   V2-3、所有者決定O8)で、この設定が真の間、Engineが読むbeliefは旧`ImeModel`ではなく候補Z
   (`scope_shadow`、`platform_state.rs::engine_belief()`)。`ir_do_abandon_half_width_alnum_from_mozc_shm`
   が書く`ImeEvent::InputModeApplied { strategy: UserTurnOnEisuReset }`は、Zの変換表
   (`crates/awase-ime-core/src/state/scope_belief.rs::scope_event_of`)で`UserHalfWidthAlnumToggle`・
   `PanicReset`以外の`InputModeApplied`を`_ => None`として**無視する**。そのため旧`ImeModel`は
   即座にromaji-capableへ補正されるが、**Zは英数(Eisu)の主張のまま変わらない**。
   `Engine::on_input`は実際には毎キー`check_active_transition`を再実行していた(上記観測5の
   訂正どおり)が、読む先のZが古いEisuのままなので非活性の判定が変わらなかった。2回目のかな
   キー押下(24.195)で`key_pipeline.rs`の打鍵時予測(`scope_shadow_key`)がZを直接`kana`へ動かし、
   直後の`notify_engine_refresh()`呼び出しでEngineが初めて活性化する(24.231)。
   **[ADR-244](../adr/244-bug186-msime-chrome-persistent-toggle-follow.md)のD3(直接観測による追随、
   `ir_follow_direct_mode_key_read`)は同じ目的だが`InputModeObserved`(Zが受理する`ScopeEvent::
   Observed`に変換される)を書くため、この穴に落ちない**。[BUG-222](BUG-222.md)の
   `kp_exit_lang_detect_toggle_on_hiragana`も同じ`UserTurnOnEisuReset`を書くため、Z有効時は
   同じ穴を持つ(本バグと同じ原因、未検証)。

**ADR-290/BUG-230との関係:** BUG-230は「Mozcの実際の切替完了より前にawaseが楽観的にローマ字を送って
しまう」(早すぎる)問題だった。本バグは逆に「ADR-290が実際の切替完了を待つよう直したことで、待ち方
(観測の検知・反映)自体に数秒の遅延が乗っている」(遅すぎる)問題。両者は同じ根(Mozcの切替完了を
確認する仕組みの精度)の表と裏。
