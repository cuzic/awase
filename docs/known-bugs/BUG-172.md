# BUG-172: msime-ready ゲートが開閉ではなく conv の NATIVE で ON と判断する

**状態(2026-10-04、v2.0.0 時点):** 一部解決(GJI × 実 Chrome は解決済み・CI検証済み、MS-IME 側は修正せず) — 実 Chrome × GJI の「外部注入で閉じられても belief が ON のまま」は ADR-205(`fd41bf88`、PR #377)で修正され、v2.0.0 に含まれる(CHANGELOG「修正」)。CI で追随 10/10、実機(X5、`docs/tasks/v2-device-verification-results-2026-09-30.md`)でも #377 の効果を確認。ただし実機の Edge で初回セッションのみ出る偽 OFF 疑いは [BUG-176](BUG-176.md) で別管理。題名の msime-ready ゲートの NATIVE 誤認は「ゲート修正は見送り」と本文で結論済みで、ゲート(`tsf/warmup/ms_ime_ready_coro.rs` の `[msime-ready]`)は現行コードにも残る。MS-IME × 実 Chrome は外部注入の `VK_IME_OFF`/0xF3 自体が閉じず再現できていない(未対応)。ADR-178 領域A(reassert/force-on)は ADR-179 系の撤去済み。

(以下は当時の記述)

**発見経緯:** 2026-09-29。ADR-178 領域A撤去後の観測 `cal-driftrec-tsf-msime-native`（PR #352）。ハーネスが実 IME を閉じた後に
かな単打（`ka`）を打つと、生ローマ字 `ka` が入力欄に残った（30/30、run 36510380572・36511231753・36512047169）。

**症状:** IME が閉じている（`ImmGetOpenStatus`=false、3秒間変わらず）のに、awase が `"ka"` を送り、`ka` のまま確定する。

**原因（ログで確認）:** `output/vk_send.rs:535` の `[msime-ready] ... IME mode 未確認 (state=Hiragana confirmed=false) → defer` の後、
`output/probe_io.rs:621` の `IMC ポーリング: NATIVE 確認 → 終了` → `ms_ime_ready_coro.rs:95` の `IME mode NATIVE 確認 → 送信 "ka"`。
確認しているのは conv の NATIVE ビット（`conv=0x19`）で、開閉ではない。conv は IME が閉じても NATIVE のまま残る
（`runtime/ime_refresh.rs:862-866` のコメント自身がそう書いている）。「conv-mode を actuation のゲートに使わない」方針と同型。
awase.log: run 36512047169 の `result-cal-driftrec-tsf-msime-native-1`、`dist/awase.log` の `02:22:09.237`〜`.257`。

**未確認（実機・CI）:**
- 実 Chrome（TsfNative）で、IME を閉じたときも conv が NATIVE のまま読めるか。CI の入力先は RichEdit を Chrome のクラス名へスーパークラス化したもの（ADR-193）。
- どの経路で閉じられたか（今回はハーネスの `WM_IME_CONTROL`）。実運用の外部要因（他アプリ・OS）との対応は未確認。
- GJI では同じゲートを通らない（tsf × GJI は literal 検出 → GJI reinit が開け直す）。

**修正方針（未着手）:** ゲートは開閉（`ImmGetOpenStatus` 等）と conv の両方を要求する。開閉が取れない TsfNative では、
送信を止めるより literal 検出（BUG-33 系）へ落とす方が安全か、要検討。`fix-requires-evidence` により、修正時は回帰テスト（journal replay か
`cal-driftrec-tsf-msime-native` の not_recovered→recovered への変化）を添える。conv mode ファミリー。

**再現(CI):** `gh workflow run e2e-ime.yml --ref ci/adr178-tsfnative-on-recovery -f only='cal-driftrec-tsf-msime-native'`。
summary の `not_recovered=10`、`conv_read=10`、`observed=0`。

**実 Chrome での確認結果（2026-09-29、GitHub windows CI、run 36524071258、`cal-driftrec-chrome-msime-native`、`chrome_probe --close-ime=10 --msime`）:**
- 症状（閉じたままローマ字 `kiu`）は実 Chrome でも 9/9 で再現（残り1回はフォーカス外れで INVALID）。GJI 対照（run 36518453739）も 10/10 で `kiu`。
- ただし**このゲートは経由していない**: `[msime-ready]` は最初の準備打鍵の3件のみ（`mode=Unknown` のまま期限切れ→give-up latch）。閉じた後の打鍵にゲート通過の記録なし。
- 実 Chrome 窓は `profile=Imm32Unavailable` で開閉観測を捨て、awase は「閉じた」ことを観測できず belief ON のまま NICOLA ローマ字を送る（`IMC_GETOPENSTATUS` 自体は 1→0 と読める）。原因は NATIVE 誤認ではなく観測不能（drift correction が判断に届かない領域、`observed=0`）。
- 結論: 「ゲートに開閉を要求」する修正は実 Chrome の症状を直さず、TsfNative では開閉が信頼できないため副作用も大きい。**ゲート修正は見送り**。実 Chrome の症状は「外部から閉じられたことを awase が観測できない」問題として別途扱う。
- 前提: CI の閉じ方は `WM_IME_CONTROL`（外部要因の再現）で、実運用の閉じ方との対応は未確認。

**実 Chrome × GJI（外部注入の 0xF3/VK_IME_OFF で閉じても belief が ON のまま）の修正（2026-09-29、ADR-205、`fd41bf88`）:**
- 原因（run 36545236017 の trace で確認）: 注入 0xF3 の KeyDown から 32ms 後の最初の prefetch 読みで既に `open=0`。しかしその refresh は打鍵中扱い（`SkipTyping`）で Blacklist 分岐に届かず、
  明示意図があるとポーリングも止まり、届いても毎回 prefetch している `IMC_GETOPENSTATUS` を捨てていた（`observed=0` の内訳）。
- 修正: 目印なしの外部注入 IME キーで監視窓（既存 `MODE_KEY_PASS_MARK_WINDOW_MS`=300ms）を開き、窓内に prefetch 済みの読みが基準値（arm 前の直近の読み）から変わったときだけ、
  実状態へ追随（`ObserverPoll` 記録 + `IntentStore` 意図削除 + `ModeKeyPassedThrough` で desired を揃え食い違う `applied` を未確認へ）。awase は IME を開け直さない。開く方向（0→1）は GJI のみ。
- 検証: `cal-driftrec-chrome-real-imeoff-ext-gji`（run 36547215222）は追随 10/10（`[external-change]` 10件、observed 0→10）、打鍵は `kiu`（不整合）→ `ka`（IME OFF と一致）。ハーネスの PASS 定義は「開け直して NICOLA」なので FAIL 表示のまま。
- 固着の定義（所有者）: 何度押しても状態が変わらないこと。トグル系の 2 回押しは許容。絶対指定キーが古い `applied` で省略され続ける未検出ケースは ADR-208（草稿）。
- 未確認: MS-IME × 実 Chrome（awase 自身の `VK_IME_OFF` が閉じない測定あり）、実機、追随後のモードキー押下の CI 検証。


**別窓方式のフォーカス変更を挟んだ実 Chrome 測定(2026-09-29、`ci/bug172-refocus-window`、run 36537797446、`cal-driftrec-chrome-refocus-*`、各10試行):**
- ハーネス修正: `chrome_probe --refocus` はタスクバーでなく自前の `STATIC` 窓(AttachThreadInput 経由)を前面にする。全20試行で `REFOCUS away=true back=true`(フォーカス変更が実際に起きた。awase.log に `FocusChange [Chrome→Static]`/`[Static→Chrome]` が各10往復)。
- 結果: 実 Chrome × MS-IME 0/10(`kiu` 相当のローマ字のまま)、実 Chrome × GJI 0/10(先頭 `k` が生のまま)。`open_at_probe=Some(0)` で実 IME は閉じたまま。
- **observed 件数(Chrome の開閉を ImeModel が観測した回数)= 0**。`ObserverPoll` は全体で1件だけで、それも別窓 `Static`(ImmCross)側の読み。Chrome へ戻るたび `Imm32Unavailable` で `hard pre-sync applied`、HwndCache が Chrome の `ime_on=true` を restore し belief ON のまま(`Skipping IMM query for known-broken class`)。drift は1件のみ(Static 側、`授権が下りない`)。観測経路に乗っていない、が「起きなかった」の実体。
- 対照(撤去前相当、`ci/bug172-pre-teardown`、run 36538290846): `f83084b3`(reassert)は後続変更と衝突して復元できず、`621bf93c`(force-ON)のみ復元。同じく MS-IME 0/10・GJI 0/10。force-ON は起動時に1回発火しただけで、フォーカス復帰時は `focus-settle ... skipped (settling)` 15件。よって reassert 側の対照は**未実施**。force-ON の有無では差が出ない。
- 結論: フォーカス変更を挟んでも撤去の有無に関わらず回復しない。原因は回復手段の欠如でなく、**Chrome 系の開閉が観測できず belief が古い ON のまま残る**こと。
- 次の一手の選択肢: (a) 観測の代替: Chrome 窓でも `ImmGetDefaultIMEWnd` 経由の `IMC_GETOPENSTATUS` は 1→0 と読める(probe 側で確認済み)。`Imm32Unavailable` の全面スキップでなく、打鍵直前など限定点だけ読み取り専用で照合する(判断は belief 更新の reduce 経由、書き込みはしない)。(b) `WM_IME_NOTIFY`/TSF compartment 通知(`GUID_COMPARTMENT_KEYBOARD_OPENCLOSE`)を購読する(通知2〜5ms の実測あり)。(c) フォーカス復帰時に HwndCache の ON を鮮度切れとして扱い、次打鍵まで belief を「未知」にする。(d) 何もしない(閉じ方の実運用対応が未確認のため)。(a)〜(c) は Chrome の閉じ方が実運用で起こるかを先に確認してから。
- 限界: 閉じ方は `WM_IME_CONTROL`(外部要因の再現)。1台の CI 実機、各10試行。

**実運用に近い外部 IME OFF の測定(2026-09-29、`ci/bug172-realistic-close`〈`chrome_probe --close-via`〉、run 36540419485、`cal-driftrec-chrome-real-*`、各10試行):**
- 閉じ方: (a) `SendInput` で 半角/全角(VK_OEM_AUTO 0xF3)・VK_IME_OFF(0x1A)を Chrome 前面へ注入(目印なし=他プロセス注入相当。0xF3 は awase の目印付き=物理キー相当も)、(b) メモ帳を前面で IME ON→OFF(0xF3 注入/`WM_IME_CONTROL`)してから Chrome へ戻す。
- **GJI × 実 Chrome は外部注入で 10/10 再現**: 0xF3・0x1A とも IME は 1→0 に閉じ(`IMC_GETOPENSTATUS`)、3秒後も閉じたまま(`open_at_probe=Some(0)`)、打鍵は `kiu`(ローマ字のまま。Engine は ON のまま=直接入力に落ちる症状)。
- **awase の観測件数(Chrome の開閉を ImeModel が観測した回数)= 0**(`ObserverPoll`=0、`Imm32Unavailable` 39件)。awase は注入キーを hook で見ている(`injected=true extra=0x0`)が、`[shadow-toggle] injected IME キー ... ユーザー意図に昇格させない (BUG-14) — belief 追従は may_change_ime refresh 観測に委譲` で昇格せず、委譲先の refresh が Chrome では読めないため belief は ON のまま。
- 対照(0xF3 に awase の目印付き=物理キー相当): GJI は awase が `[shadow-toggle] ... true→false` で Engine も OFF にし `ka`(直接入力で一貫、**症状ではない**。ハーネス上は FAIL 表示)。MS-IME は 10/10 で閉じず NICOLA 継続。
- **MS-IME × 実 Chrome は再現できず**: 外部 0xF3 は 9/10 で IME が閉じず(`open_after=Some(1)`、NICOLA 継続)、閉じた1/10だけ `kiu`。外部 0x1A は 10/10 閉じず。MS-IME は注入の 0xF3/0x1A を効かせない(理由は未特定)。
- **メモ帳経由(アプリ間共有)は 0/10 で影響なし**: メモ帳で IME を閉じた(`open_after_close=Some(0)`)間も Chrome は `open=Some(1)` のまま、戻ると NICOLA 継続。GJI/MS-IME とも同じ(IME 開閉は窓/スレッドごと)。`WM_IME_CONTROL` のメモ帳版も同じ。
- 結論: 「外部から閉じられたのを awase が観測できず belief が古い ON のまま」は、**他プロセスが注入した 半角/全角・IME OFF で GJI × 実 Chrome に再現する**(C1 の `WM_IME_CONTROL` 版が実運用と乖離する懸念は解消)。物理キー押下(awase 経由)では起きない。実際にユーザーが遭遇するのは AutoHotkey 等の注入やモード切替アイコン操作だが、頻度は未確認。
- 次の一手: 前任の (a) 打鍵直前だけ読み取り専用で照合、(b) `GUID_COMPARTMENT_KEYBOARD_OPENCLOSE` 通知購読(通知2〜5ms)を、`cal-driftrec-chrome-real-hz-ext-gji`/`imeoff-ext-gji` の FAIL 10/10 が PASS に変わるかで効果判定する。MS-IME は閉じ方の再現が先(トレイ操作等)。
- 限界: 1台の CI 実機、各10試行。IME 側ホットキー(Alt+~)やモード切替アイコンは未測定。
