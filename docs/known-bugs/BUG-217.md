# BUG-217: Zoom のチャットで注入キーの一部(主に母音)が落ちる

**状態(2026-10-24):** 修正済み(#832、ユーザーの実機で入力できることを確認)。Zoom のチャット窓のときだけ、キーを 1 つずつ順に、↓のあと 10ms 待ってから↑を送る。**続きの PR で、待ちをメッセージループのブロック(`thread::sleep`)から、キューとタイマーによる非ブロックの送信(`key_pacer`)へ変えた。20 キーの上限も不要になり撤去した。**

**症状:** Zoom のチャット入力欄で「かくにんをおねがいします」と打つと、「かｋにんをんぎします。」のように、一部の母音が落ちる。落ちる場所は毎回違う。BUG-215(リテラル化の誤判定で Backspace が出る)を直した後でも残った。

**切り分け(実機 dragonflyg4、GJI):**
- awase のログでは、想定どおりのローマ字を送っていた(`ka`・`ku`・`ni`・`nn`・`wo`・`o`・`ne`・`ga`・`i`・`si`・`ma`・`su`)。疑い・回収・諦めは 0 件。
- ユーザーの実際の打鍵(`awase.log` から取り出した 36 イベント)を、awase を通して同じタイミングで再生すると、同じ症状が出た(落ちる母音は毎回違う = タイミングの競合)。
- 入力欄を「Shift+Enter で確定 → 全選択 → コピー」で読んで、自動で各 8 回比べた。IME が OFF の状態の試行でも英字の母音が落ちたので、IME の手前(Zoom がキーを受ける段階)で落ちている。

| 送り方(一致 = 期待の文字列または変換後 `確認をお願いします。`) | 一致 |
|---|---|
| 従来(全キーの↓を送ってから↑、1 回の SendInput) | 0/8 |
| キーを 1 つずつ順に(待ち 0ms) | 0/8 |
| 順に、↓↑の後に 2ms | 0/8 |
| 順に、押している時間 5ms | 2/8 |
| **順に、押している時間 10ms** | **8/8**(別の日も 8/8、目視 2/2) |
| 全キーの↓ → 10ms → 全キーの↑(重ねる) | 0/8 |
| 順に、↑の後だけ 10ms | 6/8 |

**原因:** awase の注入キーは「↓から↑まで」がほぼ 0 秒で、キーが重なる場合もある。Zoom のチャット入力欄は、それを一部取りこぼす。人間の打鍵は押している時間が数十 ms あるので起きない。

**修正:** `class_names::needs_key_hold_window`(Zoom のチャット 2 クラス)のときだけ、`KeyInjector::send_vk_run_batch` と `send_vk_pair` が、キーを 1 つずつ順に「↓ → `tuning::ZOOM_KEY_HOLD_MS`(10ms)待つ → ↑」で送る。ほかの窓は変えない。待ちは `key_pacer.rs`(純粋な状態機械 `state/paced_queue.rs`〈Idle/Pacing、札つき〉+ `win32_async::sleep_ms`)で進める。待ちが 1 秒進まなければ、次の送信が溜まった分を流して復帰する(安全弁。測定値ではなく設計上の値)。待っている間は、`win32::send_input_safe` の口で他の送信もキューの後ろに回し(順序を守る)、`OutputActiveGuard` で物理キーを保留する(Enter が並んでいる文字を追い越さない)。

**本番の修正だけを入れたビルドでの確認(環境変数なし、2026-10-24):** 自動の比較 7/8(従来 0/8)。失敗の 1 回は、IME が OFF の状態の試行で `a` が 1 つ落ちた(`kakuninnwoonegaisimsu.`)。IME が OFF の状態で、なぜ落ちるかは未調査。

**条件を交互に混ぜた再測定(2026-10-24、実験ビルド `da2a1a84`、3 周 × 各 8 試行):** 従来 0/24、hold10(↓→10ms→↑)24/24、gap10 24/24。順番を混ぜても差は変わらない。**本番ビルド(`eaf0e179`、環境変数なし)は 3 回 × 8 = 24/24。**

**非ブロック版(`key_pacer`、`c42163e0`)の実機再生(2026-10-24、環境変数なし):** 3 回 × 8 = **24/24**(#832 のブロック版と同じ)。

**単体の注入器での掃引(補足、結論には使わない):** 母音だけ・1 キーは、押している時間 0〜20ms のどれでも 40/40 で落ちない。子音+母音(`k`→`a`)は、落ちるのは常に**母音(2 キー目)**で、子音は落ちない(`k` が残って次の組の `k` と合わさり「っ」になる)。ただし同じ条件でも実行ごとに 42/60 と 60/60 に割れ、落ち方は固まって出る(3〜4 連続)。区切りに入れた `1`(12ms 押下)も落ちる。IME が OFF の直接入力でも落ちる。つまり、**押している時間や間隔の規則は取り出せず、Zoom 側の一時的な状態に左右される**。10ms が効く理由(原理)は未解明。

**Mozc readable の共有メモリ(`key_seq`)で測った、落ちたキーの行き先(2026-10-24、dragonflyg4、Zoom のスレッドは Mozc Readable v5):** `key_seq`(TIP が受け取ったキーダウンの数)は Zoom で動く(Chrome では動かなかった)。`k`→`a` を 40 組(80 キー)順に送ると、押下 0ms は TIP に 53・56 キーしか届かず(か 13・16/40)、2ms は 48・58(8・18/40)、12ms は 80・79(40・39/40)。**落ちたキーは TIP まで届かない = Zoom か OS が TSF に渡す前に捨てている**(「Zoom 自身のフックが詰まる」という仮説と矛盾しない。未検証)。**フィードバック式(↓の後、`key_seq` が増えるまで待ってから↑)では直らない**: 3 回とも 80 キー中 24・35・28 キーが 100ms 待っても届かず(か 16・5・12/40)、届いたキーの待ちは中央 0.3〜0.4ms(p95 約 17ms、最大約 21ms〈約 15.6ms のタイマーの刻みに近い〉)。落ちるかどうかは、そのキー自身の押下時間ではなく、直前のキーの押下が短かったことで決まるように見える。検出して再送する案も、検出に 20ms 以上待つので固定の 10ms より遅い。実験ブランチ `exp/romaji-send-mode`(`da2a1a84`、`AWASE_ROMAJI_SEND`)は測定の再現用にリモートへ残してある。

**限界:**
- 10ms が最小とは言えない(6〜9ms は未測定。単体の掃引では 5ms 前後でも通る日があり、結果が揺れた)。測定は、ユーザーの 1 つの文(13 音)の再生。
- 待ちは `SetTimer`(約 15.6ms 単位)で進めるので、実効の待ちは 10ms 以上になる(1 つの音で約 30ms 前後)。待っている間に来た物理キーは保留され、キューが空になってから流れる。フックのスレッドが直接送るもの(修飾キーのマスク・カナリア)はキューを通らない。
- 窓のクラスで判定している。ポップアップのチャット窓での再測定は未了。
