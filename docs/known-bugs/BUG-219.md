# BUG-219: 打鍵中に belief が約 1 秒 OFF に倒れ、その間の NICOLA 打鍵が素通りする

**状態(2026-10-26):** 経路は確定、偽の「閉」の出所は未解明。Mozc 系を IMM の追随から外す変更を PR #840(`09f4ac294`)でマージした(実機未確認)。特性テストは PR #839(`bc3938508`)。

**症状:** dragonflyg4(Mozc Readable、Chrome)で「かんけいできますか？」と打つと「かんけいできますw１」になった(2026-10-25 17:49 JST)。末尾の「か」「？」が NICOLA の W・`1` のまま IME に入り、`w` は子音待ち、`1` は全角「１」。

## 観測されたこと(`awase.log.old`、08:49 UTC)
- 02.530〜.796 `[direct-follow]`(`ime_refresh::ir_follow_direct_mode_key_read`、ADR-188/244)が 5 回連続で `open=Some(false)`(conv=25=0x19、ひらがな)へ追随し、`ObserverPoll(false)` を書いた。17:48:50.995 にも同じ追随がある。
- 04.340 `[skip-typing-read] ime_on=Some(false) conv=0x19`。この読みは窓ハンドル 0xa670f3a(利用者の Chrome 本体)を対象にしていた。
- 04.475 `effective-open-flip → false decided_by=DeriveMedium{ObserverPoll}`、Engine が `deactivated (ImeOff)`。04.582 / 04.815 の W と `1` が `PassThrough`。
- 05.476 `[mozc-shm] follow external change open=true` → 05.623 `flip → true decided_by=DeriveHigh(MozcShm)`。OFF は約 1.15 秒。実際の IME は ON のまま(共有メモリが ON を報告、17:49:09 の字形も `kana`)。
- 同じ「OFF へ倒れて約 1 秒後に MozcShm が戻す」が 17:48:50 / 48:53 / 49:00 / 49:04 に繰り返された。17:46〜17:50 の W・`1` の素通り(KeyDown)9 回のうち `ObserverPoll` 由来は 3 回(`ExplicitIntent` の OFF が 3 回、belief が ON のままの別原因が 3 回)。

## 原因の経路(確定)
`resolve_open_at` は High が無いと Medium の単独(`DeriveMedium`)を採る。`MozcShm`(High)は `MOZC_SHM_OBSERVATION_TTL_MS=1000` で失効し(ADR-268 の status も「TTL=1000ms は不足」と既知)、直前の `[direct-follow]` が書いた新鮮窓(3 秒)の `ObserverPoll(false)` が単独で勝った。`[direct-follow]` は `Imm32Unavailable` の窓で GJI／同定済み MS-IME のときに働く設計で、Mozc 系は PR #663 で GJI 系に分類されたため対象に入っている。

## 未解明: IMM が偽の「閉」を返した理由
実機のログでは `ime_on=Some(false)` なのに conv=0x19 で、共有メモリは ON だった。しかし次の 3 つの制御した測定では、偽の「閉」を再現できなかった。
- GitHub CI(run 40233934917、ブランチ `ci/imm-read-matrix`): 87 構成(24 入力先 + 標準 5 種 × GJI・MS-IME・Mozc)で、各構成 144 回(開 72・閉 72)の読みに偽の「開」「閉」は 0 件。実 Chrome のページも別プロセスの窓も含む。Windows Terminal は awase 方式の読み(`prod`)が門前払いで全回 `None`、素の読み(`raw`)は一致。WPF は閉の試行ができなかった(IME OFF キーで閉じない)。
- dragonflyg4 の専用 Chrome × Mozc(別プロセスの読み手、20ms 刻み): IME キー直後の追随は 13〜35ms。連続打鍵中の 526 回は全て「開」。
- 同上で A(Chrome)=開・B(別プロセスの EDIT)=閉にして素早く交互に前面化(36 回、820 回の読み): ハンドル指定の読みも前面を読む awase 方式の読みも全て期待どおり。窓の切り替えの過渡の瞬間は拾えていない。
- 副次: IMM の開閉は Mozc の「ひらがな」と「半角英数」を区別できない(半角英数で英字しか入らない状態でも読みは「開」)。
- 未測定: 実際に使う窓の組(Windows Terminal ⇄ Chrome など)、Chrome の要素フォーカス移動に伴う入力コンテキストの切り替え。

## 対応
- PR #840: Mozc 系(`gji_evidence_absent()`)を `[direct-follow]` と外部変化の監視の対象から外す。Mozc 系の開閉は共有メモリ(High)が担う。GJI・MS-IME の追随は変えない(CI の測定では誤読が無い。ただし BUG-176 の疑いは残る)。
- 候補(未着手): 「直前に High で確認した値」を別の High が来るまで Medium 単独が覆さない。打鍵中の Medium 単独の OFF 反転を保留する。字形(ADR-273)を倒す前の拒否権に使う。
- 参考: `ObserverPoll` 由来の OFF 反転 12 件(全ログ)のうち Chrome 3 件・LINE 5 件は 5 秒以内に MozcShm が ON へ戻した。窓の種類は直前の `FocusChange` からの近似で、1 台 12 件。

**関連:** BUG-218 の「限界・別件」(Mozc が閉と報告しても ON のまま)は逆向きの同根。`ime_refresh` が打鍵中を理由に観測を飛ばす点も共通。
