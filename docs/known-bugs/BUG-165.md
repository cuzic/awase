# BUG-165: TsfNative + GJI の高速打鍵で defer キューが上限超過し文字が消える

**発見経緯:** 2026-09-25。Zoom チャットで高速タイピングすると崩れる報告の切り分けのため、`ci/e2e-typing-stress` ブランチに高速打鍵E2E(`ts-*` 構成、`typing_stress.rs`)を作り、windows-latest で回したところ検出された。Zoom 本物の症状と同一かは未確認。

**症状:** `ts-tsf-gji-2ms`(TsfNative 相当の RichEdit スーパークラス化入力欄〈ADR-193〉、GJI、注入間隔 2ms)の 1 回(run 36209255447 の run1)で、12試行が全滅し 182 文字が消えた(単打・親指シフト・混在の全種別)。同じ awase.log に `[pending-deferred] count limit exceeded, degrading to immediate send` が 182 件あり、消失文字数と一致。

**再現率:** 同構成の他 8 回(2ms ×7、5ms/3ms 計12回)では再現せず。約 1/8。40〜3ms は全て PASS(41万イベントの注入で `SendInput` の落ち 0、自プロセスの LL フックに全件到達)。cold 状態を作る条件は未特定。

**原因(推測、未検証):** cold probe/recovery の実行中は後続キーが `pending_deferred` に退避される(awase.log で cold probe/recovery 中の defer は確認済み)。probe が長引くと上限 32 VK を超え、超過分が immediate send に落ちて GJI が受け付けず消える。BUG-038 と同じ defer/replay キュー系統(`output/tsf_warmup_coord.rs`、`output/vk_send.rs`)。

**注意:** 2〜3ms は実注入間隔が名目値にならず(遅れの中央値 約1〜1.6ms)、人間の打鍵速度では起きにくいと推測している。Zoom がこの経路かは、実機の journal に `count limit exceeded` が出ているかで判断できる。記録時点で run の artifact を私(記録者)が直接再確認していない(報告値を転記)。

**次の一手:** (a) アイドル後の最初の連打など、cold 状態を意図的に作る構成で再現し閾値を実測する。(b) 実機 Zoom の journal に `count limit exceeded` があるか確認する。修正時は `fix-requires-evidence` により、`ts-tsf-gji-*` 構成か journal replay を回帰の根拠にする。
