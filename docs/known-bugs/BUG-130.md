# BUG-130: grace expiry テストが `GetTickCount64` の量子化で稀にflake

**症状:** `crates/awase-windows/tests`ではなく`tsf/probe.rs`内の
`#[cfg(test)]`ユニットテスト
`check_now_show_only_confirm_becomes_stale_after_grace_expires`が、
windows-build CI（run `34659416676`、PR #202、2026-09-11）で1回だけ
`probe.rs:1171`の`assert!`で失敗した。期待値`Some(StaleConfirm)`に対し
実際は`None`。`gh run rerun --failed`で同ジョブは即green、
`probe.rs`自体はそのPRで無変更（`git diff`で確認済み）。

**根本原因（解析、実機再現はできていないため未確定・状況証拠ベース）:**
`LiteralDetector::check_now`（`tsf/probe.rs:689`）の猶予判定
（`grace_hold_verdict`、`EPOCH_FENCE_GRACE_MS = 20ms`）は
`crate::hook::current_tick_ms()`（`GetTickCount64`実測、既定タイマー
分解能 ~15.6ms）を基準にする。当該テストは
`EPOCH_FENCE_GRACE_MS + 10ms`（=30ms）だけ`thread::sleep`してから
再判定していたが、実経過30msに対しマージンが10msしかなく、tick分解能
(~15.6ms)の量子化ぶれ次第では観測される`tick差分`が20ms未満に丸まり
うる。CI runnerが負荷でスケジューリングジッタを伴うと発生頻度が上がる
と推測される。

**修正（テストのみ、production挙動は無変更）:** sleepマージンを
`+10ms`→`+50ms`に拡大し、tick量子化を確実に吸収する。
`EPOCH_FENCE_GRACE_MS`自体（tuning.rs由来の値ではないが同種の
タイミング定数）は変更していない。

**テスト:** Linuxではこのテスト自体が`#[cfg(windows)]`配下のため
実行できない（`cargo check --target x86_64-pc-windows-msvc -p
awase-windows --tests --lib`でコンパイルのみ確認）。実機側の再現頻度が
低い（develop直近CI runは大半success）ため、windows-build CIでの
再発有無を継続監視する。

**関連ファイル:** `crates/awase-windows/src/tsf/probe.rs`
（`check_now`/`grace_hold_verdict`/該当テスト）。
