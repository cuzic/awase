# BUG-137: explicit_ime_action_targetのKeyDown/KeyUpステートレス再評価が、押下中にbeliefが変化すると孤立KeyUpを漏らしうる

**状態(2026-10-04、v2.0.0 時点):** 機構撤去済み — 対象の`explicit_ime_action_target`によるKeyDown/KeyUpステートレス再評価は、ADR-206(`669b784e`)で撤去された。無変換/変換の開閉はエンジンの特殊キー照合へ合流し、生キーの抑止は`Decision::Consume`(Down)と`UpDuty::Consume`(Up)が対で負う。`tests/architecture_guard.rs::forced_thumb_path_lives_in_the_engine_special_key_match`が、`key_pipeline.rs`に`explicit_ime_action_target`等が再導入されないことを固定している。

(以下は当時の記述)

**症状（コード監査で発見、実機未確認。複数の独立レビューが同じ結論に
収束）:** ADR-153決定1・BUG-124対策の「ケース3改」は、無変換/変換の
KeyDownとKeyUpの両方から`explicit_ime_action_target(vk_code)`を
ステートレスに再評価し、両方が`SuppressOnly`を返した場合のみ
KeyDown/KeyUp双方を抑止する（`kp_stage_shadow_ime_toggle`）。ラッチで
はなく再評価にしているのは、ステートフルなラッチが取り出し漏れによる
恒久残留リスク（BUG-14と同型）を持つため、と設計コメントに明記されて
いる。

**根本原因:** `explicit_ime_action_target`は`effective_open()`
（belief）を見て判定するため、KeyDownとKeyUpの間でbeliefが変化する
と、同じ物理キー押下に対して両者の評価が食い違いうる。例:
KeyDown時点でbelief=OFFかつ設定が"off"なら`SuppressOnly`（KeyDown抑止、
マーカー設定）。押下中に他の経路（別の親指キーのcase2、非同期
actuation完了、フォーカス変更等）でbeliefがONに変化すると、KeyUp時点
の再評価は`current`ガードにより`None`（Inactive）を返し、マーカーが
立たない→`transport.rs::plan`がKeyUpをAllowする→KeyDownが抑止された
のに対応するKeyUpだけが生でGJIへ届く。これはこのメカニズム自身が
防ごうとしていた「孤立KeyUpがGJIへ漏れる」症状（BUG-113/BUG-124の
根本原因＝GJI自身のTSFキー横取り）の逆方向再発にあたる。設計コメント
は「KeyDownとKeyUpの間でbeliefが変化しない限り同じ結論になる」とこの
前提を明記しているが、強制する仕組みはない。

**影響の見積もり:** 押下時間（数十〜数百ms）内にbeliefが変化する必要
があり、窓は狭い。

**対応:** 未修正。恒久対策の候補はKeyDown時点の判定をscan
code等でラッチしKeyUpで消費する形だが、それ自体がBUG-14型の残留
リスクを持つため、単純な置き換えでは済まない（設計検討要）。

**関連ファイル:** `crates/awase-windows/src/runtime/key_pipeline.rs::
explicit_ime_action_target`/`kp_stage_shadow_ime_toggle`、
`crates/awase-windows/src/runtime/transport.rs::plan`。
