# BUG-232: 明示IME OFF直後にmozc-shmの古い読みが候補Zを再度ONへ上書きする

**状態(2026-11-12):** 原因は確定(mozc-readableフォーク実機ソースで直接確認、かつGitHub Windows CI
の実機mozc-readableでも再現確認済み)。修正は
[ADR-291](../adr/291-mozc-shm-push-notify-and-engine-recheck.md) D5(案E1)としてコード実装済み、
Linux単体テスト(全774件)・windows target check/clippy/fmtともグリーン。実機再現用の新規CIシナリオ
`tickchurn`は[PR #934](https://github.com/cuzic/awase/pull/934)(developへ、未マージ)として提出済み
(run [43145173691](https://github.com/cuzic/awase/actions/runs/43145173691)で
`update_tick_ms`がstate不変のまま進むことを確認)。D5の修正コード自体は
`docs/adr291-mozc-shm-push-notify-and-engine-recheck`ブランチにあり、別PRでdevelopへ提出予定。

**症状:** dragonflyg4、Chrome(Chrome_WidgetWin_1、GJI)で半角英数の"mermaid"を入力しようとし、
明示的にIME OFFキーを押した直後、"m"を押した瞬間にbeliefが一瞬ON(Japanese変換)に化け、
Backspaceで消して再度IME OFFを押し直す羽目になった("marm"あたりで突然IME OFF・Nicola ONの表示)。

**タイムライン(UTC, awase.log 2026-11-12T01:40:37〜01:40:39, dragonflyg4、Chrome_WidgetWin_1):**
1. `01:40:37.620` 明示的にIME OFFキー押下 → `effective-open-flip → false decided_by=ExplicitIntent`
   (shadow_model=false、候補Zも含めて正しくOFF)。
2. `01:40:37.717` `[belief-v2] 食い違い開始` z=(open=false basis=z-explicit)。
3. `01:40:37.732`(明示OFFから+112ms) `[mozc-shm] follow external change open=true` →
   `effective-open-flip → true decided_by=DeriveHigh(MozcShm)`(shadow_model=true) —
   mozc共有メモリの読みがZを再びtrueへ上書き。
4. `01:40:37.741`(+9ms) "M"キー押下(vk=0x4D) — この瞬間effective_openは誤ってtrue。
5. `01:40:38.479`〜`39.004` Backspace(vk=0x08)×5連打 — 誤変換された文字を削除していると見られる。
6. `01:40:38.765`(収束) `effective-open-flip → false decided_by=MostRecentTrusted`、
   `[belief-v2] 食い違い終了`。
7. `01:40:39.208` 再度明示的にIME OFFキー押下(was_open_before=false — 確認のため再押下と見られる)。

**原因(確定):** `state::mozc_shm::decide_use`/`read_is_after_baseline`(ADR-268 D3 R3')は
「`update_tick_ms > baseline_ms`なら`tsf_open`自体が変化した確実な証拠」という前提で、
`settle_ms`(`KEY_EFFECT_SETTLE_MS`=170ms)未満でも高速に受理する設計だった。mozc-readableフォーク
実機ソース(`~/mozc-readable-release/repo/src/win32/tip/tip_state_publisher.cc::ThreadSlot::
Flush()`)を直接確認したところ、`update_tick_ms`は**ブロック全体のdirtyタイムスタンプ**で、
`key_seq`等の高頻度フィールド(ほぼ毎打鍵で変わる)のどれかが変わるだけで更新される——
`tsf_open`自体が変わっていなくても新しくなる。本エピソードでは、明示OFF直後に送った"M"キー
自体がMozcの`key_seq`を進め、`update_tick_ms`を再スタンプしたため、まだ古い`open=true`の読みが
settle窓(170ms)を素通りして`Use`になった。

**修正(ADR-291 D5/案E1、実装済み):** `decide_use`で、読みがbelief(`effective_open`)と**食い違う**
ときは`update_tick_ms`の高速路を使わず`settle_ms`の無条件経過のみを要求する(一致する読みは
高速路を維持、副作用ゼロ)。`crates/awase-ime-core/src/state/mozc_shm.rs`、新規テスト2件
(`bug232_stale_update_tick_does_not_bypass_settle_when_it_disagrees_with_belief`・
`decide_use_still_fast_paths_a_read_that_agrees_with_belief`)含め全774件グリーン。
検討した他案(OR条件を単純に外す・`KEY_EFFECT_SETTLE_MS`を上げるだけ・mozc-readable側に専用
タイムスタンプを追加)との比較はADR-291「案E」節参照。

**ADR-291との関係:** ADR-291のD1'は**mode軸**(`InputModeApplyStrategy`がZの`scope_event_of`に
無視される穴)を修正する。本バグは**open軸**の既存settle機構(`decide_use`/R3')自体の穴で、
D5として同じADR-291に追記した(別軸・別決定)。

**[BUG-231](BUG-231.md)との関係:** BUG-231はbelief_v2(Z)がmozc-shm追随後の書き込みを**受理しない**
(反映欠落)方向の遅延。本バグは逆に、mozc-shmの**古い**読みが明示意図を**上書きしてしまう**方向の
誤り。根は同じ(mozc-shm観測とawase自身の意図/操作タイミングの整合)だが症状と経路は別。
