# BUG-153: 撤去後に英数・カタカナが握りつぶされて効かなくなる疑い

**発見経緯:** 2026-09-21、ADR-191の撤去ブランチ(`feat/adr191-remove-hardcoded-mode-keys`)でADR-189の半角/全角トグルを復元した際、
`transport.rs::PhysicalKeyDisposition::plan`の`is_dbe_mode_key_down`(BUG-52/BUG-116/ADR-091 §D3.6)が英数(0xF0)・カタカナ(0xF1)を
VKで列挙して`shadow_toggled`に関わらずSuppressしていることに気づいた。**CI・実機での確認は未了**(疑いの段階)。

**症状(疑い):** 撤去前は英数・カタカナにawaseの`shadow_action`(TurnOff/TurnOn)があり、awaseが代行するのでSuppressしてよかった(素通しすると
awaseの書き込みと実IMEの処理が二重になる、BUG-46/BUG-52)。撤去後はawaseが代行しない(`ImeKeyKind::shadow_effect`が`None`)ので、
Suppressすると「OSにもawaseにも誰も何もしない」二重の空振りになり、英数・カタカナキーが効かない。

**現状の挙動(コード確認):** 実イベントの英数・カタカナは`shadow_action`を持たず、`plan()`の`is_kanji_event`判定で既にAllowになる。
つまり実害は`is_dbe_mode_key_down`の列挙が「合成イベント(`shadow_action`あり)」でだけ効く死んだ分岐として残っていた点で、
実イベントの挙動は変わらない可能性が高い。ただし将来`shadow_action`を持たせる変更(表からの予測など)が入ると、この列挙が再び握りつぶしを起こす。

**修正(この記録と同時):** Suppressの対象を、VK列挙ではなく`ImeKeyKind::is_open_toggle_for(ImeKindId)`(awaseが開閉トグルとして書くキー=
GJI・MS-IME本体の0xF3/0xF4)だけにした。英数・カタカナ・ひらがなはSuppressせずIMEへ素通しする。`dbe_mode_key_policy=Passthrough`の挙動は変えない。
BUG-116/ADR-137のShift+0xF1の特例(`shift_katakana_passthrough`)は、0xF1が常にAllowになったため撤去した。
残るSuppress: 0xF3/0xF4のKeyDown(policy=Suppress)、`shadow_toggled`のKeyDown、KANJI系のKeyUp、ImmCrossの`shadow_action`付き全キー。

**検証:** `transport.rs::plan_tests`は`#[cfg(windows)]`配下でLinuxでは走らない。Linuxで走る固定は`vk.rs`の`is_open_toggle_for`のテストと
`architecture_guard`の静的スキャン。plan_testsの新テスト3件(英数/カタカナはSuppressでも素通し、0xF3/0xF4はGJI・MS-IME両方でSuppress)は
windows-build CIで初めて実行される。実機での英数・カタカナ・半角/全角の動作確認は未了。

**実機検証(2026-09-21、追記):** ユーザー実機(MS-IMEプリセットのGJI、本番config、hands-off注入)で、撤去版(BUG-154の再注入scan修正後)の `sc-dbe`(suppress)/`sc-kanji`/`sc-shift` が
**ALL PASS**。英数(0xF0)は変換モード 0x10(半角英数)へ、カタカナ(0xF1)は 0x1B(全角カタカナ)へ、実IMEが実際に変化した(`check_consistency`)。
英数・カタカナが握りつぶされて効かない、という疑いは実機では起きていない。修正前の撤去版でこれらが失敗したのは、Suppressではなく再注入の`wScan=0`(BUG-154)が原因だった。
