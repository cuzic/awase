# BUG-140: `right_thumb_key`と同じキーを`keys.ime_detect.on`に登録すると、変換キー単独タップ毎にIME再適用が暴発し、GJI自身の変換機能と競合+「あ」混入

**症状（不具合報告 `01M21JQY0PQPE3PQYDKSX8JAZS`、2026-09-08、GJI、`right_thumb_key=変換`）:**

> KB232あの親指右／変換をGoogle日本語入力の変換にしています。（中略）ところか変換キーでは変換がきかず、いまはあスペースで変換しています。（中略）なにかトラブルっぽいことが起きると、入力していない「あ」が入ってしまうようです。

（BUG-095「症状1について: 撤回した仮説」で真因未確定のまま持ち越されていたのと同一症状——`docs/bug-reports-triage.md`の`01M13EACMQ7D2VETW75N0BTZ9C`行、GitHub issue #144。）

**原因（journalで実測、確定）:** `config.toml`が

```toml
[general]
right_thumb_key = "変換"

[keys.ime_detect]
on = ["IMEオン", "変換"]
```

となっており、「変換」（`VK_CONVERT`、NICOLAの右親指キーでもある）が`keys.ime_detect.on`（シャドウ追跡キー、README「IMEが自動でON/OFFされる」節）にも登録されていた。この結果、`runtime/key_pipeline.rs::kp_stage_shadow_ime_toggle`で`event.ime_relevance.sync_direction`（`IntentKind::SyncKey`）が最優先で採用され、**変換キーを単独タップするたびに**（IMEが既に開いていても`was_open_before=true`のまま）`apply_ime_open(true)`が再送される。実機ログでは約300〜400ms間隔の連続タップで、そのたびに

```
[shadow-toggle] intent 昇格: vk=0x1C ... action=TurnOn kind=SyncKey ... true→true
IME open axis delegated (solo tap, key semantics absorption) → true
[apply-ime] ImmCross async: open=true ...
```

が発火し、GJIの変換候補ウィンドウが`candidate SHOW`→`HIDE`→`SHOW`と明滅していた。**この再適用がGJI自身の「変換」キーバインド（ユーザーが確認候補表示に割り当てている）と同じ物理キー押下から同時に発火するため、awase側の再適用処理がGJIの変換候補表示を割り込み的に乱し、変換が効かないように見える。**

さらに、この再適用の最初の1回（cold復帰直後）は`[unicode-cold-warmup]`の犠牲キー機構
（`VK_IME_ON+VK_A+BS`でGJIを起こしてすぐ消す設計、issue #144既出の仮説と同型）を
誘発することも実機ログで確認した。この犠牲`あ`+Backspaceの取り消しがGJI側の
candidate明滅と競合するタイミングでは、`あ`が消し切れずに残留しうる——「意図しない
『あ』混入」の具体的な発火経路の一つ。

**対応:** コード変更は保留（このユーザーの`config.toml`が原因のため、まず設定変更で
解消を試みる）。GitHub issue #144へ回答済み: `keys.ime_detect.on`から`"変換"`を削除する
（`ime_detect`はawaseが直接制御しないIME切替キーの状態追跡専用であり、`right_thumb_key`
と同じキーに設定する必要はない）。恒久対策として、`right_thumb_key`/`left_thumb_key`と
`keys.ime_detect.{on,off,toggle}`が同一VKを指す組み合わせを設定画面で警告する
バリデータの追加が考えられるが未実装。
