# BUG-203: IME を閉じた直後の GJI の I/O を「ON の証拠」と読んで、Engine を有効化する

**状態(2026-10-18):** 未修正。**実 Chrome+GJI では flip が再現せず、優先度を下げた**(下記「実アプリでの測定」)。CI(windows-latest、awase debug)で観測の無い窓の近似(自前の TSF text store の窓、`cache.toml` で unavailable)に限って確認。実機・実アプリでの頻度は未確認。

**症状(ログ):** 入力インジケーターの右クリックメニューで **Direct Input(IME 閉)を選ぶ**と、選択(`POPUPEND`)の 9〜14 ms 後に GJI が I/O を起こし(`[gji-io] WRITE: w_ops=+1`)、0.05〜0.4 秒後の定期観測で
`[gji-poll] GJI I/O observed 406ms ago … → observer_poll=true` → `[effective-open-flip] → true decided_by=DeriveMedium { first: ObserverPoll }` → `Engine activated (ime=true …)` → `[startup-align] desired_open … desired=true`。
実際の IME は**閉**(メニューを再度開くと `Item 10`=Direct Input が選ばれている)なのに、awase は ON と判断して Engine を有効にする。

**再現(CI):** ブランチ `ci/indicator-menu-verify`、run 39081235242、成果物 `result-gji-full` の `gji-tsf-hover/awase.log`(選択は `events.log` の `POPUPEND` 00:06:38.602、上のログは 00:06:38.611〜39.016)。
run 39079041821(`result-gji` の `gji-tsf-awase`)でも同じ向きの `effective-open-flip → true` が出た(`POPUPEND` 23:31:01.797 → `[gji-io] WRITE` 01.811 → `[gji-poll] observer_poll=true`・flip 01.845。**選択から 48 ms 後**)。
GJI の通常の窓(IMM が読める)では選択後に `true→false` で実状態と一致した。**MS-IME には該当する観測(GJI の I/O 推論)が無く、メニューで IME を閉じる操作も測っていない**(測った MS-IME の選択は `103`=開)。

**影響(想定。未確認):** 利用者がずれに気づいてメニューから「直接入力」を選ぶと、次の打鍵が NICOLA のローマ字として送られ、直接入力の窓にローマ字が出る。
メニューに限らず、**GJI が I/O を起こす操作全般**(設定の書き込みなど)の直後、IME が閉でも ON と推論しうる(GJI の I/O 推論が「開いている間の I/O」と「閉じる操作に伴う I/O」を区別しない)。

**原因(読解):** `gji_observer` は「直近の GJI プロセス I/O」を ON の証拠(Medium)として扱う。IME を閉じる操作そのものが I/O を起こすため、閉じた直後の I/O が ON の証拠に見える。

**方針案:** 利用者の明示の閉じる操作(物理キー・メニュー選択)の直後の一定時間(N ms。選択から flip まで 48〜413 ms の実測を踏まえ、測って決める)は、GJI の I/O を開閉の証拠にしない。メニュー選択の検知は、`MENUSTART`〜`MENUEND` の間に非 0 の `idChild` が出たかで足りる([ADR-264](../adr/264-indicator-menu-mode-evidence.md) 決定 5)。ADR-264 の**証拠(メニューの読み)には依存させない**が、抑止に要る `MENUSTART`〜`MENUEND` の WinEvent の登録(ADR-264 決定 1 の範囲 0x4〜0x7)には依存する(オプトインが無効でも登録は要る。カーソル位置のフィルタは要らない)。BUG-202 の修正(ADR-264 決定 7)と共通の前提。キーボード選択で非 0 の `idChild` が出るかは未測定で、物理キーで閉じた直後の I/O は、既存の予測(`KeyEffectPredicted`)と GJI の I/O 推論のどちらが勝つかを調査で確かめる。
`state/`・`observer/gji_observer.rs` は再発ファミリー([fix-requires-evidence](../../.claude/rules/fix-requires-evidence.md)、IME belief)なので、直す際は golden か journal のテストを足す。観測の無い窓の近似以外(実アプリ)で出るかを先に確かめる。

**実アプリでの測定(2026-10-18):** 実 Chrome(`strategy=Blacklist`)+GJI で、IME ON の後にメニューから `Item 10`(Direct Input)を選ぶ測定を 3 回行った(ブランチ `ci/bug203-chrome-verify`、run 39120996108、`tools/ci/bug203_chrome/run.ps1`)。
3/3 とも、選択の約 10 ms 後に `[gji-io] WRITE`、その 125〜265 ms 後に `observer_poll=true` が出たが、belief は元から ON で `effective-open-flip` は出なかった。メニューの再読では `Item 10` が選択済み(実状態は閉)で、awase の belief は ON のまま。
つまり I/O 推論は発火するが、belief が ON なら flip を起こさない。食い違いの本体は GJI の I/O 推論ではなく、メニューによる閉じを awase が観測していないこと(ADR-264 段階 2 の領域)。柵を進める修正は見送り。
**未測定:** belief が OFF で実状態が ON の状態から選ぶ場合、キーボードでの選択、GJI 以外。

**修正履歴:** なし(柵を進める案は上の測定を受けて見送り)。
