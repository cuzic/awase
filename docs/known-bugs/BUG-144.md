# BUG-144: 較正probeループがフォーカス不一致時にtracker.tick()をスキップし、settle window外の値がpostとして混入しうる（ADR-176 176-T9a）

**発見経緯:** 実機での不具合報告ではなく、ADR-176 T8〜T10のコードレビュー
（Codex CLI、2026-09-17）で発見。実機での再現は未確認。

**症状（理論上）:** 較正モード中、対象キー押下後のsettle window
（`CALIBRATION_TRIAL_SETTLE_WINDOW_MS`、既定3秒）中にawase-settingsの
テキスト入力欄からフォーカスが外れ、期限超過後にフォーカスが戻ると、
戻った直後のprobe結果がそのまま`post`として採用され、誤った
`ConfirmedOn`/`Rejected`が確定しうる。「計測中は常にテキスト欄に
フォーカスを保持し続ける」というT9/T10の前提が破られていても、
`TrialTracker`側は気づかない。

**根本原因:** `spawn_calibration_probe_loop`
（`crates/awase-windows/src/runtime/focus_tracking.rs`）が、
フォーカス不一致（`focus_pid != session_pid`等）を検知すると
`continue`でループの残りをスキップし、`TrialTracker::tick()`を
一切呼んでいなかった。`tick()`は呼ばれたときにのみ
`deadline_ms`超過を判定する純粋関数のため、呼ばれない間は
進行中の試行（`ActiveTrial`）が`active`のまま凍結され、期限超過の
判定自体が起こらない。フォーカス復帰後に`tick()`が呼ばれると、
その時点のprobe結果が（実際にはwindow外で観測されたにも関わらず）
`post`として採用されてしまう。

**修正:** フォーカス不一致時もprobe自体は行わず`probe_result = None`
のまま、必ず`tracker.tick(press_seq, now_ms, None, ...)`を呼ぶよう
制御フローを変更した。これにより期限超過が正しいタイミングで
評価され、window中フォーカスが戻らなければ`TrialTick::Discarded`
（`press_with_no_successful_probe_during_window_is_discarded`が
既にこの経路を純粋関数レベルでカバー済み）が確実に返る。
