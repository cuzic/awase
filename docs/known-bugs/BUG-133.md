# BUG-133: Standardプロファイル×ImmCross失敗フォールバック時、随伴warmupがGjiDirectStrategyの実送信直後に重複する

**症状（コード監査で発見、実機未確認）:** ADR-149（PR #180）は随伴eager TSF
warmupの送信を`should_send_accompanying_warmup(outcome)`でゲートし、
「戦略が今回の`apply`で実際に`SendInput`した場合は随伴warmupを重ねない」
とした。ただしStandardプロファイル（ImmCross対応アプリ）だけは
`profile.can_use_imm32_cross_process() || should_send_accompanying_warmup(..)`
という無条件例外を持っていた。

**根本原因:** `ImmCrossProcessStrategy`が`Failed`を返した場合（`SendMessage
Timeout`、または書込み後の再観測が`desired`と不一致等、`open_chain.rs`の
`ActuationOutcome::Failed`分岐）、strategy chainは`GjiDirectStrategy`へ
フォールスルーし実際に`SendInput`する（outcomeは`Applied`）。旧実装は
Standardプロファイル全体を無条件例外にしていたため、GjiDirectの実送信
直後に随伴warmupがもう1回SendInputし、ADR-149が解消したはずの「1打鍵に
対する即時連続SendInput」（「@」の確立済み必要条件）を再現しうる。

**修正（ADR-167、2026-09-12）:** `ImeOpenOutcome`に`AppliedWithoutSendInput`
variantを新設し、`ImmCrossProcessStrategy`（sync: `ime_controller.rs`、
async: `runtime/open_chain.rs::imm_cross_write`）の成功時だけこれを返す
ようにした。`should_send_accompanying_warmup`はロジック変更不要（新
variantは自然に「送る」側になる）——呼び出し元（`platform.rs::
on_ime_applied_inner`）のプロファイル軸の例外を削除するだけで済む。
opus-adversarial-consultで、選択肢A（`ActuationDecisionRecord`経由で
実送信有無を伝播）は非同期経路がWMメッセージ（`wparam`/`lparam`
ビットパック）越しのため対象バグに届かない設計ミスだったと判明し、
選択肢B（本variant追加）を採用。

**実機ソーク未実施:** 発火条件は「Standardプロファイル×GJIアクティブ×
Tsf注入×ImmCross Failed×open=true」の積で、既存の実機証拠（ADR-149の
「@」ログ）はTsfNative（この例外分岐が効かない側）で取られたもの。
Standardプロファイルで同一症状が出るかは未検証。

**関連ファイル:** `src/platform.rs`（`ImeOpenOutcome`/
`should_send_accompanying_warmup`/`wrote_open_state`）、
`crates/awase-windows/src/ime_controller.rs`、
`crates/awase-windows/src/runtime/open_chain.rs`、
`crates/awase-windows/src/platform.rs::on_ime_applied_inner`。
