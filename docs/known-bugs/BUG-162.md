# BUG-162: `baseline`構成でEngineが直接入力中に spurious activate する

**発見経緯:** `.github/workflows/e2e-ime.yml`のCI高速化作業中、変更前後の比較検証として
`baseline`構成(runs=3)を実行したところ全runでFAILした。CI構造の変更が原因かを切り分けるため、
未改修の`develop`(旧ワークフロー構造、変更コミットなし)で同じ構成を単独実行しても同一の
失敗が再現したため、**ワークフロー変更ではなくdevelop本体の回帰**と判断した。

**症状:** `check.py`(構成`check='expect'`)の判定で、10ステップ中2ステップが
`outcome=Unwarranted`でFAIL:

```
2 open=1 conv=0x10 activated@+1ms; deactivated@+146ms  FAIL: 実IME期待 open=0 conv=0x10 / Engineがactivatedになった(OFFのままの期待)
5 open=1 conv=0x19 (なし)                                FAIL: 実IME期待 open=0 conv=0x19 / delegate → false が出ない
6 記録なし → FAIL
8 open=1 conv=0x10 activated@+1ms; deactivated@+161ms   FAIL: 実IME期待 open=0 conv=0x10 / Engineがactivatedになった(OFFのままの期待)
結果: 5 件 FAIL
```

実IME側は直接入力(open=0)のままであるべき局面で、Engineがspurious activateし、
約140〜160ms後にdeactivateする、という同一パターンが3run全てで再現した。

**再現:** `only=baseline`でCI実行(GitHub-hosted windows-latest、GJI+ATOKプリセット)。
`docs/adr/186-*.md`のADR-186撤去実験マトリクスにおける無撤去(baseline)構成。

**検証:** CI実行ログ(旧ワークフロー構造、develop HEAD)
[35857737369](https://github.com/cuzic/awase/actions/runs/35857737369)。

**未解明:** 直近develop(2026-09-23)にADR-195/196関連の多数のマージが並行して入っており、
どのコミットが原因かは未特定。IME belief/actuation関連の変更が疑わしいが、本BUGの発見者は
CI速度改善作業中の副産物として報告するのみで、原因調査・修正は行っていない。

**追記(2026-09-23、未検証):** [ADR-191](../adr/191-ime-is-source-of-truth-observe-not-write.md)
(IMEを書き込まず観測・予測に追随する設計転換、PR #240でdevelop統合済み)もIME belief/actuation周りの
大きな変更であり、bisect対象に含めて確認すべき(BUG-149/150で見たとおり、ADR-191は「Engineが実IMEに
追随しない」系の症状を解消する側に働く変更だが、本BUGは逆に「直接入力中にEngineがspurious activateする」
という別方向の症状であり、ADR-191が原因側である可能性も解消側である可能性も排除できていない)。
どちらかは`git bisect`で確認する必要がある。

**追記(2026-09-25、CI実測):** ADR-191 の撤去実験（#313、強制OFF撤去）は原因ではない。#313 の直前 `c82b1d3d`（run
[36104015748](https://github.com/cuzic/awase/actions/runs/36104015748)、検証専用ブランチ `ci/verify-05-pre313`）でも
`baseline`×3 が全て同じ5件FAIL（`outcome=Unwarranted`が2件）で、#313 を含む `f2a875cd`（run
[36103384502](https://github.com/cuzic/awase/actions/runs/36103384502)）と同一。同じ run の `atok-passthrough-cold`×3 はPASS（rc=0）。
e2e-ime は PR ごとには回らないので、赤が入った時期は未特定のまま（原因調査は別途）。

**原因調査（2026-09-25、Opus。#240 で 3 つの原因が重なって始まったと推定。確度は有力）:**
- A（コードの回帰）: `k`→Esc で、ATOK 表に（入力中・Esc）のセルが無い（保持/破棄が割れて生成時に除外）ため予測が返らず、追跡した
  段階が `Typing` のまま残る→次の無変換が「入力中の無変換」と誤予測される→Engine が活性化し `SetOpen(true)` が warrant 付きで IME を
  書き戻す（GJI が無変換で OFF にした状態を ON に戻す）。`outcome=Unwarranted` も同じ「予測→活性化→書き込み」経路。
- B（期待表の更新漏れ）: 手順5・6 の `delegate → false` は ADR-191 で撤去された仕組み。無変換/変換の単独タップは既定設定で Suppress される。
- C（`check.py`）: 1 件の Unwarranted が 2 行に出るので「2 件」と数える。時間枠にかかわらず全体で数える。
- 最後に PASS した run は 35504455792（`69491a22`、2026-09-20）、最初の FAIL は 35857737369（`f74c8633`）。間に baseline を回した run は無い。

**修正（A の 1 段目、`state/key_effect_predictor.rs`）:** 表にセルが無い**入力中（`Typing`）の Esc**で、開閉・入力モードは予測しないまま、
追跡した段階を `Stage::None` へ落とす。変換中（`Conv*`）の Esc は保持/破棄が実際に割れるので従来どおり。回帰テスト:
`typing_esc_without_a_table_cell_drops_the_tracked_stage`。残る限界: MS-IME 本体で候補ウィンドウだけが閉じて入力中が残る場合、
読めない窓では取りこぼす（読める窓は観測の `composing` が直す）。A の 2 段目（Engine 活性化に伴う `SetOpen` を IME に書かない）、B、C は未着手。
