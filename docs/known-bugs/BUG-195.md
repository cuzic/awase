# BUG-195: アクティブ TIP の誤同定(GJI → MS-IME)

**状態(2026-10-09):** 起票。原因は仮説のみ(未検証)。報告 `01M4FJV2M52W30VG98YNBETMK8`(v2.0.0、[bug-reports-triage.md](../bug-reports-triage.md))。

**症状:** Windows Terminal で「のと」を打つと「noと」。所有者が GJI 使用を確認。

**証拠(報告のログ・journal):**
- awase の同定は約3.3時間ずっと MS-IME: `GjiFsmTransition` 1246件すべて `MsImeStrategy`、`ActuationDecision` は `kind=MsIme`、`FocusProbe` は `ime=MicrosoftIme`、`ime_product_name` は `Microsoft IME`。
- 実際は GJI: `[gji-obs] candidate SHOW`(クラス `GoogleJapaneseInputCandidateWindow`)が40件。
- 症状の経路: 物理ひらがなキー(0xF2)PassThrough の約0.93秒後に `[msime-ready] IME mode 未確認 → defer` → 16ms 後に conv の NATIVE を確認して `"no"` を送信([BUG-172](BUG-172.md) 型)。GJI として扱えば別の戦略(literal 検出 → GJI reinit)になる。

**仮説(CI で再現、報告者の条件=OFF + 上書き MS-IME でも再現):** `tip_detector.rs::query_active_kind` は監視スレッド(`gji-io-monitor`)の `GetActiveProfile` で種別を決める。
「入力設定をアプリ ウィンドウごとに異なる値にする」(`SPI_GETTHREADLOCALINPUTSETTINGS`)が有効だと、監視スレッドが見るプロファイルは前面窓の IME と食い違いうる。報告にこの設定値は無い。

**CI 観測(2026-10-09、`ci/bug195-tip-scope`、run 37893206030、`examples/tip_scope_probe.rs`、windows-latest、MS-IME 既定 + GJI 有効):**
- 窓のスレッドで `ActivateProfile`(GJI、`FORSESSION` なし)すると、そのスレッドの `GetActiveProfile` は GJI、窓を持たない別スレッド(awase の監視スレッド相当)は Microsoft IME のまま(8秒間、毎秒)。
- (訂正)上の「設定に依存しない」は同一プロセス内の比較でしか見ておらず、不十分だった。次の2回の run で修正する。
- 「アプリウィンドウごと」ON(`readback=1`)、run 37894682558: awase を Microsoft IME の状態で起動(`initial IME kind: MicrosoftIme`)→ 別プロセスの窓スレッドで GJI を有効化 → 窓スレッドは GJI、同プロセスの別スレッドと**起動済みの awase は約25秒間 Microsoft IME のまま**(`IME kind →` の行なし)。**ON なら誤同定を再現した。**
- 同設定 OFF: 窓スレッドの GJI 有効化が次に起動したプロセス(awase 含む)から GJI に見えた(`initial IME kind: GoogleJapaneseInput`)。ただし reset 直後にも GJI に戻っており汚染が疑われ、**起動済みの awase が追随するかは未検証**。
- 実利用の Win+Space は CI で効かなかった(run 37893901031・37894307630、4回送っても窓スレッドは Microsoft IME のまま)。報告者は Win+Space で切り替えている(所有者確認)。
- 報告者の環境(所有者確認、2026-10-09): 「アプリウィンドウごと」は **OFF**、既定の入力方式の上書きは **Microsoft IME**、切り替えは Win+Space。
- 上の条件に合わせた run 37895475336(OFF 固定、`Set-WinDefaultInputMethodOverride` を切り替え、awase 起動後に別プロセスの窓スレッドで GJI を有効化):
  - 上書き=Microsoft IME: awase は `initial IME kind: MicrosoftIme`、窓スレッドが GJI でも監視スレッドは12/12回 Microsoft IME、awase に `IME kind →` の変化なし(約23秒)。**誤同定を再現。**
  - 上書き=GJI: awase は `initial IME kind: GoogleJapaneseInput`、監視スレッドも12/12回 GJI。
  - よって窓を持たない監視スレッドは、前面窓の切り替えでなく**既定の入力方式の上書き**を見ている可能性が高い。報告者の回避策案: 上書きを GJI にする(Microsoft IME へ切り替えると逆方向に誤同定するはず、未検証)。
- 未達: Win+Space の実操作(CI では効かない)、逆方向(上書き=GJI で窓が MS-IME)、実機での回避策の確認。

**未確認:** 報告者の設定値、起動時の `[tip-detect] EnumProfiles(JA)` / `initial IME kind`(ログ抜粋に無い)、他の GJI ユーザーでの再現頻度。

**修正方針(未着手):** 種別の同定を前面窓のスレッドの HKL/TIP から取るか、`GoogleJapaneseInputCandidateWindow` の表示を GJI 稼働の独立証拠として照合する。
