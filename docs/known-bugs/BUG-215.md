# BUG-215: Zoom チャット欄で raw-tsf-literal が誤判定され Backspace で文字が消える

**状態(2026-10-24):** 修正を PR にした(案 A・B)。実機再確認は未了。

**症状:** Zoom のチャット欄で入力すると、文字が欠ける(「謎の Backspace で削られる」)。

**再現(実機 dragonflyg4、awase debug 版):** Zoom のチャット欄を前面にして、冷えた状態(3 秒空け)から `k`(き)を 12 回打つ。12/12 で `SuspectedLiteral`(`since_vk_sent_ms` 312〜313)になった。1 回目は Backspace ×1 + `ki` 再送、2 回目以降は `consecutive raw-tsf-literal (count=2…13) → giving up, cleanup only (no re-send)` で、Backspace ×1 だけを毎回送った。連続カウントは 3 秒空けても戻らなかった。窓の IME は `himc_null=true`(全項目 `-`)。

**原因(部分的に確認):** 約 313ms 以内に GJI の書き込み・候補窓が見えず、literal と判定される。文字が実際に literal だったのか、正しく入っていたのかは、入力欄の本文を読んでいないため未確認。ただ、同じ窓で `CompositionConfirmed` になる例もあり、判定が不安定。「諦める」分岐の Backspace は再送なしで文字を消すだけで、literal の証拠も要らなかった。

**追加の観測(2026-10-24、メイン会議ウィンドウ内のチャットタブ `ConfMultiTabContentWndClass`):** ポップアップ(`ZConfChatPopupContainerWndClass`)だけでなく、こちらでも毎回 `SuspectedLiteral`。ここでは入力欄を目で見てもらえた。`k` キー(親指シフトで「き」)を 4 回打った後の表示は「っっっｋkkkkkkkkｋっっっっっっっｋ」で、`ki` の `i` が届かず `k` だけが出ていた。per-VK の確認は疑いが出ると**残りのキーを送らずに終わる**ため。なお、IME が OFF のウィンドウ(awase の belief も IMM の実読みも `ime_on=false`)ではエンジンが動かず、打鍵は素通しになる(これは別の話)。

**原因の調査(2026-10-24、dragonflyg4、GJI):** Zoom でも GJI の書き込みは起きている(`[gji-io] WRITE` が打鍵の約 14ms 後、`w_KB=+0.3`)。ただ、per-VK の判定の閾値 `COMPOSITION_BYTES_THRESHOLD`(350B、`tsf/probe.rs`)の直下で、候補窓(`GoogleJapaneseInputCandidateWindow` の WinEvent SHOW)も子音 1 文字では出ないため、証拠が 0 とみなされて `SuspectedLiteral` になる。ログ全体の書き込み量(`w_KB`)の分布は +0.0〜0.4KB に集中している(+0.3KB が 174 件)。Windows Terminal(`InputSite.WindowClass`)でも同じ型の誤判定が出ているので、Zoom 固有ではない可能性が高い(未確認)。

**書き込み量の実測(2026-10-24、dragonflyg4、GJI、Zoom のメイン会議ウィンドウ内のチャット、`GetProcessIoCounters` で `GoogleIMEJaConverter` の `WriteTransferCount` を 1ms おきに採取):**
- awase を止めて生の `k`・`i` を打つと、打鍵の 20ms 以内に **462B(`k`)・463B(`i`)が 1 回の書き込みで**入り、24 打鍵とも同じ値(閾値 350B を超える)。
- awase を動かしたまま同じ打鍵をすると、1 打鍵あたり **148〜560B(多くは 150〜290B)**、書き込みは 1〜2 回で、打つたびに約 12B ずつ増える傾向があった(12 回目で 350B 前後に届く)。閾値 350B の手前の例が多い。
- 推測(未検証): 書き込みの大きさは入力欄の中身(直前の文字列)に比例する。入力欄が短いと閾値に届かず、長いと届く。awase を止めた時の 462B は、入力欄に残っていた文字列の長さによる可能性がある。
- 結論: 書き込み量は 150〜560B と幅が広く、閾値 350B をどこに置いても誤判定は残る。**閾値は動かさない**(`tuning-constants.md` の「実測なしに値を動かさない」。この実測は新しい値を導くものではない)。Zoom のチャットは、上の「修正(最終)」の窓単位の扱いで対処する。
- 自前の Edge 窓(`data:` URL の textarea)での比較は、IME が ON にならず書き込みが 0 で、測れなかった。

**修正の経緯:** 最初は Zoom のクラスだけ回収をやめたが、per-VK の確認は疑いが出ると残りのキーを送らずに終わるため、「っっっｋkkk」になった。次に per-VK を外してまとめて送る案を試したところ、入力欄は「kいききき」で、2 回目以降は正しいが**最初の 1 文字(IME を ON にした直後)は本物のリテラル化**だった。per-VK はこれを正しく検知していたので、per-VK は残す(所有者の指摘)。さらに、1 打鍵で `ki` が 6 回再送される連鎖(再送した `ki` の `i` が疑われ、ESC + 全体の再送を繰り返す)を見つけた。

**修正(最終):** (1) 諦める分岐(連続 2 回目以降)で Backspace を送らず、疑いが出た VK より後ろのキーは送る(`probe_io.rs::romaji_after`)。(2) Zoom のチャット 2 クラスでは、2 番目以降の VK の疑いを信用せず確認済みとして進む(`class_names.rs::is_later_vk_literal_check_unreliable_window`、`probe_fsm.rs`)。1 番目の VK の判定は変えない。回帰テスト: `romaji_after_returns_the_vks_after_the_failed_one`、`chrome_per_vk_later_vk_suspicion_is_ignored_in_unreliable_window`、`zoom_chat_windows_have_unreliable_later_vk_literal_check`。

**実機確認(メイン会議ウィンドウ内のチャットタブ):** 「k」×4 → 「きききき」。K・E・T ×6 ラウンド → ひらがなが正しく並ぶ(目視、所有者)。ポップアップのチャット窓(`ZConfChatPopupContainerWndClass`)は今回の修正後は未確認。

**残り:** 書き込み量が閾値の直下になる原因(GJI が子音 1 文字で書く量が約 300B)と、閾値 350B の見直し(`tuning-constants.md` の実測が要る)。CI での再現(模擬窓)は、`gji_write_bytes` / 候補窓の値を差し替える単体テストが確実。
