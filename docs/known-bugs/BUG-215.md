# BUG-215: Zoom チャット欄で raw-tsf-literal が誤判定され Backspace で文字が消える

**状態(2026-10-24):** 修正を PR にした(案 A・B)。実機再確認は未了。

**症状:** Zoom のチャット欄で入力すると、文字が欠ける(「謎の Backspace で削られる」)。

**再現(実機 dragonflyg4、awase debug 版):** Zoom のチャット欄を前面にして、冷えた状態(3 秒空け)から `k`(き)を 12 回打つ。12/12 で `SuspectedLiteral`(`since_vk_sent_ms` 312〜313)になった。1 回目は Backspace ×1 + `ki` 再送、2 回目以降は `consecutive raw-tsf-literal (count=2…13) → giving up, cleanup only (no re-send)` で、Backspace ×1 だけを毎回送った。連続カウントは 3 秒空けても戻らなかった。窓の IME は `himc_null=true`(全項目 `-`)。

**原因(部分的に確認):** 約 313ms 以内に GJI の書き込み・候補窓が見えず、literal と判定される。文字が実際に literal だったのか、正しく入っていたのかは、入力欄の本文を読んでいないため未確認。ただ、同じ窓で `CompositionConfirmed` になる例もあり、判定が不安定。「諦める」分岐の Backspace は再送なしで文字を消すだけで、literal の証拠も要らなかった。

**追加の観測(2026-10-24、メイン会議ウィンドウ内のチャットタブ `ConfMultiTabContentWndClass`):** ポップアップ(`ZConfChatPopupContainerWndClass`)だけでなく、こちらでも毎回 `SuspectedLiteral`。ここでは入力欄を目で見てもらえた。`k` キー(親指シフトで「き」)を 4 回打った後の表示は「っっっｋkkkkkkkkｋっっっっっっっｋ」で、`ki` の `i` が届かず `k` だけが出ていた。per-VK の確認は疑いが出ると**残りのキーを送らずに終わる**ため。なお、IME が OFF のウィンドウ(awase の belief も IMM の実読みも `ime_on=false`)ではエンジンが動かず、打鍵は素通しになる(これは別の話)。

**修正:** (1) 判定を信用できない窓(`is_literal_recovery_unreliable_window`: 上の 2 クラス)では、`Output::step_probe` が `gji_active` を偽にして per-VK の確認をやめ、ローマ字を全部まとめて送る。(2) 諦める分岐(連続 2 回目以降)から Backspace を外す。回帰テスト: `class_names.rs` の `zoom_chat_windows_are_literal_recovery_unreliable`、`probe_io.rs` の諦める分岐のテスト(Backspace なしの期待値)、既存の `chrome_without_gji_active_skips_literal_detect`(`gji_active` が偽なら直接送信)。

**残り:** 実機で同じ手順を再実行し、入力欄に「き」が並び、Backspace が出ないことを確認する。他の Zoom ウィンドウ(`ZPControlPanelClass` など)は未測定。
