# BUG-128: Chrome で Ctrl+無変換 直後に explorer.exe 内の別 UWP 入力面へフォーカスが移ると、無関係な cached ON が復元され force-ON まで誤発火する

**アプリ:** msedge.exe（Chrome_WidgetWin_1）→ explorer.exe の UWP InputSite
系フライアウト（`Windows.UI.Input.InputSite.WindowClass`）。**IME:** Google
日本語入力。

**再現手順 / 症状（不具合報告 `01M27VXD4SPAD4STQ9TG1PZSCD`、2026-09-11）:**
Chrome で Ctrl+無変換 を押して IME-OFF（`desired_open=false`）にした約3.6秒後、
フォーカスが explorer.exe がホストする別の UWP 入力面（タスクバー検索等、
`Windows.UI.Input.InputSite.WindowClass` は複数の無関係な入力面が共有する
汎用クラス名）へ移動。`on_focus_process_changed` の TsfNative キャッシュ復元
分岐（`(pid, class_name)` キー、`35230fd` 由来）が、無関係な過去の
`ime_on=true` キャッシュを「Imm32Unavailable 汚染の修正」と誤認して
`desired_open` を強制的に true へ復元し、続けて `apply_force_on_for_imm_broken`
が `force-ON (ImmBrokenForceOn)` を発火。ユーザーは半角のつもりが親指シフト
入力（ひらがな）のままになった。

**原因・設計:** [ADR-165](../adr/165-tsf-cache-restore-recency-guard.md) 参照。
`HwndImeCache`（`(pid, class_name)` キー、1時間 TTL）が実際にはウィンドウ
インスタンスを一意に特定できておらず、`35230fd` の復元ヒューリスティックが
明示 OFF の新しさもキャッシュ対象の同一性も見ていなかった。

**対応（案E、実機検証済み）:** `HwndImeSnapshot` に hwnd を追加し、TsfNative
窓への ON 復元は hwnd 一致を無条件で要求するよう修正
（`focus/hwnd_cache.rs`・`focus/tracker.rs`・`runtime/focus_tracking.rs`）。
opus-adversarial-consult round1〜round6（実機検証込み）で設計収束。dragonflyg4
実機で、修正前のコードで実際の誤発火を再現し、修正後に再現しないこと、かつ
`35230fd` の救済シナリオ（Windows Terminal 自身への復帰）は引き続き正しく
機能することを確認済み。回帰テストは `runtime/focus_tracking.rs` の
`should_restore_tsf_cache_on` ユニットテスト。

**関連:** BUG-63（同型の belief/actuation 分離不備）、BUG-107（別キャッシュの
`class_name` 単独キー問題、同型の設計課題）、BUG-110/ADR-157（同じ
`is_eligible_for_ime_force_on()` 合流点、発火源は別）。
