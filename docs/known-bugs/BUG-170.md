# BUG-170: 他プロセスの`WH_KEYBOARD_LL`が`CallNextHookEx`を呼ばず握りつぶすとキー入力が完全消失する（issue #165、自己修復を追加）

**症状:** GitHub issue #165。不具合報告`01M3JTVDPMW35MF81DGRKW10MQ`で、他アプリ間の
フォーカス往復直後にUWP系入力面へフォーカスが移り、その直後の約6.4秒間`awase.log`に
`KeyInput`が一件も記録されないまま`Hook watchdog: no activity for 6468ms（OS全体の
最終入力は187ms前 → フックにイベントが届いていない疑い）`が発火した。「能動的」と
入力しようとして「うどうてき」（先頭モーラ「の」欠落）になる`WrongCharacterOutput`
と結びついた。

**原因確定（PR #347、CI実証実験）:** `crates/e2e-uwp-inputsite-probe`が自前で
`WH_KEYBOARD_LL`をawaseより後にインストールし、一定時間`CallNextHookEx`を意図的に
呼ばずマーク付きキーを握りつぶす実験を行い、windows-latest CI上で issue #165 と
同一のwatchdogシグネチャ（`stale_ms=6938ms, os_idle_ms=47ms`、実報告の
`6468ms/187ms`とほぼ同じ桁）を確定的に再現した。さらにawase自身のログで、握り
つぶされたキーは遅延ではなく`[engine-input]`から完全に消失する（ブロック窓の間
一件も出現しない）ことを確認した。`WH_KEYBOARD_LL`はLIFO（最後に登録したフック
が最初に呼ばれる）で配送されるため、awaseより後に別プロセスのフックが割り込むと
確実に発生しうる。自然発生条件（実環境で何が実際にそのフックを詰まらせるか、
PowerToys Keyboard Manager等）は未特定のまま。

**対応（自己修復）:** watchdogがhook_starved（`stale_ms>5000`かつ`os_idle_ms<5000`）
を検知した時点で、`UnhookWindowsHookEx`→`SetWindowsHookExW`により自分のフックを
チェーンの先頭へ戻す（`Runtime::reinstall_keyboard_hook_for_watchdog`）。失われた
打鍵は戻せないが、同じ停止が続くのを防ぐ。install失敗時もpanicせずログのみ（次の
watchdog tickで再試行）。

**検証（CI、run 36394214484）:** 上記の握りつぶし実験を25秒間に延長し、自己修復
無しなら25秒間（またはブロック窓の自然終了まで）続くはずの消失が、watchdog検知後
**約7.2秒で復帰**することを確認した。ブロック用フックは残り約18秒間も有効のまま
だったが、awase側は再インストール後チェーン先頭に戻ったため以後は正常に受信し
続けた。

**未対応（残存）:** 自然発生条件は依然未特定。再インストールが頻発する場合の
バックオフは未実装（3秒周期のwatchdogが停止中は毎tick再試行する）。実環境での
発生頻度・自己修復の効果は次の同種報告で確認する。

**関連ファイル:** `crates/awase-windows/src/runtime/mod.rs`
（`reinstall_keyboard_hook_for_watchdog`/`set_hook_guard`/`drop_hook_guard`）、
