# BUG-179: CI の MS-IME 構成で新規 Chrome の初回入力が `kiu` になる

**症状:** awase 起動後に起動した実 Chrome へ、IME 操作なしで `k,a` を打つと
`kiu` になる。belief は ON、実 IME は閉。awase なしの対照は `ka` 5/5。

**再現:** CI run 36803095123 と最終 head の run 36805640317 の `sc-p2-initial-chrome-msime`（observe）は各 0/5。
`sc-p2-initial-chrome-msime-noawase` を対照にする。

**原因:** Chrome の TSF-native 経路では開閉を読めず、belief が ON の placeholder のまま残る。PR #406 の
新スレッド=閉は GJI または同定済み MS-IME 本体が条件だが、CI 構成の TIP は
`MicrosoftIme (Other)`（IMM32 HKL）と同定されるため適用されない。

**修正:** `tsf/` の同定で、アクティブが HKL 型(IMM32 HKL)のとき、有効(`TF_IPP_FLAG_ENABLED=0x2`、`0x1` は ACTIVE)な
日本語 TIP が MS-IME 本体 1 件だけなら `MsImeNative` と同定する(`3e3a4ca9`・`518b62ee`、PR #409)。
`sc-p2-initial-chrome-msime` は 0/5 → 5/5。GJI 経路は PR #406 の `fix(ADR-212 P2)` で修正済み。

**不変条件の超過(2026-10-01 調査):** 修正後、`sc-adr209-chrome-msime(-stale)` で `i2_unwarranted` が 3 件(上限超過)。
修正の副作用ではなく、**修正を含まない develop(`59a5072c`)でも同じ 3 件**で、`sc-follow-chrome-*`・
`sc-reopen-tsf-*msime*`(最大 17 件)等にも出る既存の現象。`awase.log` では全て
`[set-open] origin=ActivationSync … outcome=Unwarranted`(`eff=false conf=true`、`execute_from_loop`)で、
belief が ON のまま実 IME が閉の窓へ Engine の loop 経路が SetOpen(true) を出し、`apply` が棄却している。
ActivationSync を止める検証スパイク(ADR-213 P2a+P2b)では i2 が全構成で 0 になった。BUG-179 としては追加の修正は不要で、
ADR-213 P2b で解消する。

**残作業:** `table_ime_kind` を使う ADR-189 の半角/全角 belief トグル等の CI カバレッジへの影響、
`sc-hz-msime-native` が observe である理由(yml のコメントは F3/F4 静的モデル)が同じ原因かは未確認。
実機(Windows 11)で `[thread-scope] applied=true ime_kind=Some(MsIme)` → `ka` の確認も残る。
