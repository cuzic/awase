# BUG-175: eager warmup が修飾キー押下中に注入される

**発見経緯:** 不具合報告 `01M3NJYRQ5ZBYTKV55FV06KETP`(v1.21.0、GJI、Windows Terminal + PowerShell)「Ctrl+Shift の操作で @ が出る」。調査は BUG-174 / PR #358(Ctrl↑ 契機の warmup 撤去)。

**確認できた事実(実機 A/B、2026-09-29、dragonflyg4、DEBUG ログ):** Ctrl+Shift を 1 回押すと、Ctrl↑ 受信直後に awase が `VK_IME_ON`(scan=0xF2)を SendInput し、その時点で Ctrl・Shift は押されたまま(アプリには Ctrl+Shift+`VK_IME_ON` の順序で届く)。「@」が 1 個出た。CtrlUp warmup を撤去したビルドでは同操作で「@」は出ず、注入も無かった。n は少数の手動操作。

**原因(コードで確認):** `tsf/send.rs::send_eager_warmup_vk_pair` の押下中スキップは `hook::win_key_held()` のみ(BUG-32 / BUG-48 の対策)。Alt(別途 `hook::ime_mode_key_injection_blocked_by_modifier` は Win+Alt)・Ctrl・Shift は素通しだった。報告者のログでも、注入 10 件が全て `gas_ctrl=true`、うち 3 件は Alt 押下中だった。PR #358 は Ctrl↑ 契機だけを撤去したため、確定キー(Ctrl+Enter)・物理 F2(Ctrl+F2)等、他契機の warmup が修飾キー押下中に発火する経路は残る。

**修正:** `hook::eager_warmup_blocked_by_modifier()`(Win/Alt/Ctrl/Shift のいずれか押下中で true)を `send_eager_warmup_vk_pair` の判定点にした。判定は純粋関数 `state::win_key_guard::eager_warmup_blocked`(Linux で単体テスト)。stale 判定は既存の `is_held_fresh` + `WIN_KEY_HELD_STALE_MS` を再利用(新規タイミング定数なし)。スキップ時は `None`(呼び出し側は「未送信」扱いで `eager_warmup_sent_ms` を更新しない、BUG-32 の既存契約)。
回帰テスト: `state::win_key_guard::tests::eager_warmup_*`(3 件)。

**対象外(意図的):** `ime.rs::send_ime_mode_key` 等の IME OFF/ON 注入は本修正で触っていない。Ctrl+無変換 の IME OFF ショートカットは Ctrl を押したまま IME 制御を注入する必要があり、Ctrl をブロック対象に含められない。A のログには Ctrl↓ の約 50ms 後の `VK_IME_OFF`(scan=0)注入も 1 件あるが、「@」との関係は未確認。

**未確認:** (1) 本ガード単体での実機確認(PR #358 と本 PR を両方入れた場合の A/B)は未実施。(2) 確定キーの 2 連送(ConfirmKeyDown + reinject、修飾キーなしでも `VK_IME_ON` が 63ms 間隔で 2 回)は未対応。(3) スキップした warmup の代替(物理 F2 の Suppress の埋め合わせ)が修飾キー押下中に必要になるケースの影響は未検証(rare と推定)。
