# BUG-142: Windows Terminal + GJI、物理半角/全角キーがIMEをONから戻せなくなる（「IME ON固着」）。再現条件・因果関係とも未確定

**アプリ:** Windows Terminal（`WindowsTerminal.exe`）+ PowerShell。
**IME:** Google 日本語入力（GJI）。

## 症状

物理半角/全角キーを押しても IME が OFF に戻らなくなる（「IME ON固着」）。
GJIのキーマップ設定はプロファイル依存で可変（既定/MS-IME互換/ATOK互換等）
であり、無変換/変換キーの役割（ひらがな⇔カタカナ⇔半角カナの巡回、直接
入力への切替等）もプロファイルによって異なる（ユーザー指摘）。

## 経緯（2026-09-15、1セッション内の複数の観測・実験）

### 発見1: 物理半角/全角キーが TurnOn 方向でしか認識されなくなる

実機ログ解析（別調査、BUG-033/BUG-113の「@」再発調査中に偶然発見）で、
`ir_apply_drift_correction` の `Blind` ポリシーが
`DRIFT_CORRECTION_BLIND_REARM_COOLDOWN_MS=3000` のクールダウンを無視して
150ms間隔で連続 GiveUp するバースト（本来あるべきでない挙動）の直後から、
物理半角/全角キー（`vk=0xF2`）が `TurnOn` 方向でしか認識されなくなる
（`[shadow-toggle] no-op: ... 見送り` が繰り返される）パターンを観測した。
ユーザーは「GJIはおかしくなかった（awase側だけがおかしい）」と証言。

### 発見2: 無変換/変換の単独タップが引き金という新しい再現手順

ユーザーが独立に「PowerShellで、半角モードで無変換や変換を押すと再現する
（『@』・『IME ON固着』とも）」という再現手順を報告。**awase.exeを完全に
停止した状態でも両方とも再現する**ことをユーザーが実機確認——このため
「@」はGJI自身のTSFキー横取りが真因（BUG-113と同一機構）と判断し、本BUG
の対象から切り離した。「IME ON固着」についても当初は同一機構と推定した。

### 実機ログでの部分確認（2026-09-15）

半角モード（`ime_on=false`）中の無変換キー単独タップは、`[shadow-toggle]`
ログを一切出さず`decision="PassThrough"`でGJIへ生キーがそのまま渡る
ことを実機ログで確認した（`explicit_ime_action_target`が未設定なら
`Inactive`、コアエンジンの活性ゲートが`!ime_on`で無条件`PassThrough`
にするため）。**この打鍵に対してawaseのbeliefは一切更新されない**。

### ADR-153方式（生キー抑止）での実機検証

[ADR-173](../adr/173-scope-solo-tap-ime-action-by-process-name.md)
（`app_overrides.solo_tap_ime_action_apps`によるプロセス名限定機構、
実装・opus-adversarial-consult round1-2収束済み・PR #219）を使い、
`muhenkan_solo_tap_ime_action = "off"` + アプリ限定設定を実機に投入した
ところ、**「IME ON固着」は解消した**（ユーザー確認）。一方
`henkan_solo_tap_ime_action = "on"`（変換キーを明示的にIME ON actuation
へ置き換える）は、ユーザーにより設計として却下された
（「無変換/変換の本来の役割〈巡回〉を固定的な意味〈IME ON〉に置き換える
のは乱暴」——GJIのキーマップはプロファイル依存で可変であり、awase側が
特定の意味を決め打ちすべきでない、という設計原則）。

### ADR-174（パススルー + belief再観測）の起草とopus-adversarial-consult

ユーザー要望「生キーはパススルーし、GJIの実際の結果をawaseが観測して
beliefに反映する」を受け、[ADR-174](../adr/174-solo-tap-passthrough-belief-reobservation.md)
を起草。opus-adversarial-consult round1で**Blocker 6件**を検出:

- **B1（最重要）**: 「belief乖離→固着」という因果関係自体が実機ログで
  一度も証明されていない。少なくとも2つの対抗仮説がある——(a) トグルの
  位相ズレ（1回空振りするだけで恒久固着ではない）、(b) 物理配送そのもの
  が二重に空振りしている（BUG-37/ADR-121 `reassert_explicit_physical_key`
  と同型、beliefを直しても直らない）。
- B2: 提案した設計（既存`ConvOpenInference`経路への合流）を実装すると、
  20ms後にdrift correctionが実際にVK_IME_OFFを送ってしまい、ADR-173より
  悪い結果（巡回を殺した上に送信も増える）になることが判明。
- B3: `observed`側を書くだけでは`desired_open`が変わらず、「beliefに
  反映する」という目的を構造的に達成できない。
- B4/B5/B6: 既存機構（ガード5、`kp_trigger_focus_resync`、
  `probe_actuation_fence`）の転用は、目的の不一致・自己干渉ループ等の
  問題を抱える。
- 詳細は `opus-review-adr174-round1.md`（ADR-174起票時のワークツリー、
  破棄済みのため本文は残らない。要点は上記に集約）。

opusは「まずB1を実機で確定してから設計すべき、確定すればADR-174自体が
不要になる可能性がある」と提案した。

### 実機再検証（2026-09-15 続き）——再現せず、原因未確定のまま持ち越し

develop（config未設定、ADR-173適用前の状態と機能的に同一——後述）で、
半角モードのまま無変換キーを単独タップする再現を**複数回試みたが、
一度も「IME ON固着」（あるいはIME ONへの遷移そのもの）を再現できなかった**:

1. develop + 素のconfig: 無変換タップ → GJI表示は「半角のまま」変化なし。
2. GJI関連プロセス（`GoogleIMEJa*`）を強制終了して再起動、再度同じ手順 →
   結果は同じ（半角のまま変化なし）。

**コード差分で「ADR-173ブランチかdevelopか」の違いを排除済み**:
`git diff origin/develop origin/adr/173-hankaku-zenkaku-stuck-on` を確認
した結果、`explicit_ime_action_target`へのADR-173の変更は
`muhenkan_solo_tap_ime_action`/`henkan_solo_tap_ime_action`が**明示的に
設定されている場合にのみ**実行される分岐に置かれており、config未設定
（今回の再検証環境）では develop と ADR-173 ブランチの挙動は**完全に
同一**であることをソースレベルで確認済み。したがって「ブランチが違った
のでは」という仮説は排除できる。

### 実機再現（2026-09-15 続き）——変換キーで再現、無変換キーでは再現せず

同セッション内でさらに検証したところ、**無変換キーでは（develop・GJI再起動後とも）IME ON への遷移が再現しなかったが、変換キーの単独タップでは再現するようになった**（ユーザー視認確認）。実機デバッグログで裏付けを取った:

```
[engine-input] vk=0x1C KeyDown ... [diag-ctx] ime_on=false ...
key input seq=1852 vk_code=28 ... state_before="Idle" state_after="Idle" decision="PassThrough" physical="Allow"
[engine-input] vk=0x1C KeyUp ... [diag-ctx] ime_on=false ...
key input seq=1853 ... decision="PassThrough"
```

同型のイベントが3回（05:47:22, 05:47:25, 05:47:42）記録されており、いずれも
`[shadow-toggle]`ログ・`[apply-ime]`（actuation）ログとも**一切出ていない**
——awaseはこの打鍵に対して完全に無反応（生キーがそのままGJIへ渡るだけ）で
あることを確認した。GJIが実際にIME ONへ遷移したのだとすれば、それは純粋に
GJI自身のネイティブな処理によるものであり、beliefは一切追従しない。

**注意点（過大解釈しないこと）**: 同じログに「desired=false observed=true」
という乖離検出が`duration_ms=59578`〜`61232`（約60秒間、同一
`intent_at_ms`）と連続して記録されている。この乖離自体は今回の変換タップ
より前から存在していた可能性が高く（BUG-26が記録するとおり、GJIのconv
NATIVEビットはIMEを閉じても消えない持続的な設定であるため）、**この特定の
`[drift]`ログ行を「変換タップが新たに引き起こした乖離」と結びつけて解釈
してはならない**。確実に言えるのは「変換の単独タップにawaseが一切反応
しない」という事実のみ。

**未確認のまま残る点**: この状態（変換タップでGJIがONになったと仮定した
状態）で物理半角/全角キーを押すと実際に「固着」するかどうかは、今回もまだ
検証していない。次のセッションでの優先確認事項。

### 実機再現（2026-09-15 続き）——固着の完全な再現とログでの機序特定

ユーザーが一連の操作を再現させ、症状を明確に言語化した:
「IME OFFで変換を押して、IME ONになるけどEngine OFF。半角全角を押すと
IME ON・Engine ONになって、そこから半角全角を何回押してもIME ON・
Engine ONに固着した」。この一連の流れを実機デバッグログで裏付けた
（`target/debug/awase.log`、時刻は全て2026-09-15）:

```
05:53:46.611  [hook] IME-mode vk=0xF2 down (物理半角/全角キー)
              [shadow-toggle] intent 昇格: vk=0xF2 action=TurnOn false→true
              [apply-ime] GJI direct: send 0x0016 (open=true) → belief ON
05:53:47.188  [apply-ime] GJI direct: send 0x001A (open=false)
              → belief が再び OFF へ（reason=EngineDecision、経路未特定）
05:53:48.856  ir_apply_drift_correction: target_open=false attempts=5
              policy=Blind action=GiveUp
05:53:48.982  ir_apply_drift_correction: 同上 GiveUp
              ← 前回よりわずか126ms後（DRIFT_CORRECTION_BLIND_REARM_
              COOLDOWN_MS=3000のクールダウンが機能していない）
05:53:49.614  [hook] IME-mode vk=0xF2 down (物理半角/全角キー2回目)
              [shadow-toggle] intent 昇格: vk=0xF2 action=TurnOn false→true
              → belief ON
05:54:00.659  [hook] IME-mode vk=0xF2 down (物理半角/全角キー3回目)
              [shadow-toggle] intent 昇格: vk=0xF2 action=TurnOn true→true
              [shadow-toggle] no-op: ... effective_open は既に true
              → apply-ime 見送り
              （別経路のapply_mechanismが無条件でsend 0x0016も実行——
              二重ディスパッチ）
              ↑ この時点から半角/全角キーは vk=0xF2（TurnOn方向）しか
              二度と現れない（本ログの残り全体で vk=0xF0/0xF3 は皆無）
05:54:08.269〜08.720  ir_apply_drift_correction GiveUpが5連発
              （間隔126〜145ms、cooldown無視が再発）
05:54:09.278  [hook] IME-mode vk=0xF2 down (物理半角/全角キー4回目)
              → 依然としてTurnOn方向のみ
05:54:13.634  drift give-up interval ended reason="FocusChanged"
              （フォーカス変更でようやくリセット）
```

**この機序整理から得られる仮説（未検証、次の優先調査対象）**: 「IME ON
固着」の直接の引き金は、beliefがネイティブ遷移を追従できないこと自体
ではなく、**`DRIFT_CORRECTION_BLIND_REARM_COOLDOWN_MS=3000ms`のクール
ダウンが実際には守られておらず、`VK_IME_OFF`のBlind送信が126〜145ms
間隔で連発している**ことである可能性が高い。この連射の直後から、物理
半角/全角キーが一貫してTurnOn方向のVK（0xF2）しか報告しなくなる——
OS/ドライバ側のキーボードレイアウト処理が持つ「次にどちらの方向のVKを
送るか」というトグル記憶が、この連射によって破壊されているように見える
（BUG-113が確立した「awase自身のSendInput連射がGJI/OS側の内部状態を
乱す」という同系統の機構の、キーボードレイアウト層での新しい現れ）。

この仮説が正しければ、対策候補は「beliefの再観測・追従」（ADR-174）
より遥かに小さく的を絞れる: **なぜクールダウンが無視されているのかを
特定し、実際に3000ms間隔を守らせる**こと。次のセッションで最優先の
調査対象とする。

## 未解決・次のアクション

1. **因果関係（B1）は実機ログで確定した（上記「固着の完全な再現」節）。**
   引き金は「無変換/変換パススルー由来のbelief非追従」そのものではなく、
   **`DRIFT_CORRECTION_BLIND_REARM_COOLDOWN_MS=3000ms`のクールダウンが
   実際には守られておらず、Blindポリシーの`VK_IME_OFF`送信が126〜145ms
   間隔で連発している**ことであり、この連射の直後から物理半角/全角キーが
   TurnOn方向のVK（0xF2）しか報告しなくなる（OS/ドライバのキーボード
   レイアウト層のトグル記憶が破壊されていると見られる）。
2. **最優先の次の調査**: なぜクールダウンが無視されているのかを
   `ir_apply_drift_correction`/`DRIFT_CORRECTION_BLIND_REARM_COOLDOWN_MS`
   の実装箇所（`runtime/ime_refresh.rs`）で確認する。今回のログでは
   `attempts=5`の`GiveUp`が同一 target で繰り返し発火しており、
   `decide_conv_inference_drift`のエピソードラッチ（`intent_at_ms`ベース）
   がこのケース（`reason=EngineDecision`由来の反復belief変化）を捕捉
   できていない可能性がある。
3. この仮説が正しければ、**ADR-174（パススルー+belief再観測）より
   遥かに小さく的を絞った修正**（クールダウンを実際に機能させる）で
   BUG-142が解決する可能性が高い。ADR-174は当面保留とし、まずこちらを
   優先する。
4. **GJIのキーマップ設定を確認・記録すること。** 無変換/変換の役割は
   プロファイル依存で可変（既定/MS-IME互換/ATOK互換等）であり、
   「無変換=巡回」「無変換=直接入力」のどちらか一方に決め打ちしないこと
   （ADR-174 round1 S3が指摘した、リポジトリ内docの記述間の見かけ上の
   矛盾は、実際にはプロファイル違いによるものと判明している）。今回の
   実機では**無変換キーの単独タップではIME ONへの遷移が再現せず、
   変換キーでのみ再現した**（同一セッション内、develop・GJI再起動後）。
5. [ADR-173](../adr/173-scope-solo-tap-ime-action-by-process-name.md)
   （生キー抑止方式、プロセス名限定機構）はコードとして実装・レビュー
   収束済みだが、`henkan_solo_tap_ime_action = "on"`という具体的な設定は
   ユーザーにより却下済み。[ADR-174](../adr/174-solo-tap-passthrough-belief-reobservation.md)
   （パススルー+再観測方式）はopus-adversarial-consult round1でBlocker
   6件が残ったまま、優先度を下げて保留（上記2・3参照）。
