# BUG-142: Windows Terminal + GJI、物理半角/全角キーの繰り返し押下でIME ON/Engine ONに固着（「IME ON固着」）。原因はshadow-toggleの固定方向no-op誤判定、keys.ime_detect.toggleでToggle解決に変えると実機A/Bで解消確定（ADR-175、2026-09-15）。恒久修正（config既定値変更）は未実装

**アプリ:** Windows Terminal（`WindowsTerminal.exe`）+ PowerShell。
**IME:** Google 日本語入力（GJI）。

## 症状

物理半角/全角キーを押しても IME が OFF に戻らなくなる（「IME ON固着」）。
GJIのキーマップ設定はプロファイル依存で可変（既定/MS-IME互換/ATOK互換等）
であり、無変換/変換キーの役割（ひらがな⇔カタカナ⇔半角カナの巡回、直接
入力への切替等）もプロファイルによって異なる（ユーザー指摘）。

## 経緯（2026-09-15、1セッション内の複数の観測・実験）

### 発見1: 物理半角/全角キーが TurnOn 方向でしか認識されなくなる

実機ログ解析（別調査、BUG-033/BUG-113の「@」再発調査中に偶然発見）で、
`ir_apply_drift_correction` の `Blind` ポリシーが
`DRIFT_CORRECTION_BLIND_REARM_COOLDOWN_MS=3000` のクールダウンを無視して
150ms間隔で連続 GiveUp するバースト（本来あるべきでない挙動）の直後から、
物理半角/全角キー（`vk=0xF2`）が `TurnOn` 方向でしか認識されなくなる
（`[shadow-toggle] no-op: ... 見送り` が繰り返される）パターンを観測した。
ユーザーは「GJIはおかしくなかった（awase側だけがおかしい）」と証言。

### 発見2: 無変換/変換の単独タップが引き金という新しい再現手順

ユーザーが独立に「PowerShellで、半角モードで無変換や変換を押すと再現する
（『@』・『IME ON固着』とも）」という再現手順を報告。**awase.exeを完全に
停止した状態でも両方とも再現する**ことをユーザーが実機確認——このため
「@」はGJI自身のTSFキー横取りが真因（BUG-113と同一機構）と判断し、本BUG
の対象から切り離した。「IME ON固着」についても当初は同一機構と推定した。

### 実機ログでの部分確認（2026-09-15）

半角モード（`ime_on=false`）中の無変換キー単独タップは、`[shadow-toggle]`
ログを一切出さず`decision="PassThrough"`でGJIへ生キーがそのまま渡る
ことを実機ログで確認した（`explicit_ime_action_target`が未設定なら
`Inactive`、コアエンジンの活性ゲートが`!ime_on`で無条件`PassThrough`
にするため）。**この打鍵に対してawaseのbeliefは一切更新されない**。

### ADR-153方式（生キー抑止）での実機検証

ADR-173（本文はdevelop未収録。git タグ `archive/adr173-solo-tap-ime-action-by-process-name`〈`cbb412cf`〉にレビュー記録のみ保存）
（`app_overrides.solo_tap_ime_action_apps`によるプロセス名限定機構、
実装・opus-adversarial-consult round1-2収束済み・PR #219）を使い、
`muhenkan_solo_tap_ime_action = "off"` + アプリ限定設定を実機に投入した
ところ、**「IME ON固着」は解消した**（ユーザー確認）。一方
`henkan_solo_tap_ime_action = "on"`（変換キーを明示的にIME ON actuation
へ置き換える）は、ユーザーにより設計として却下された
（「無変換/変換の本来の役割〈巡回〉を固定的な意味〈IME ON〉に置き換える
のは乱暴」——GJIのキーマップはプロファイル依存で可変であり、awase側が
特定の意味を決め打ちすべきでない、という設計原則）。

### ADR-174（パススルー + belief再観測）の起草とopus-adversarial-consult

ユーザー要望「生キーはパススルーし、GJIの実際の結果をawaseが観測して
beliefに反映する」を受け、[ADR-174](../adr/174-solo-tap-passthrough-belief-reobservation.md)
を起草。opus-adversarial-consult round1で**Blocker 6件**を検出:

- **B1（最重要）**: 「belief乖離→固着」という因果関係自体が実機ログで
  一度も証明されていない。少なくとも2つの対抗仮説がある——(a) トグルの
  位相ズレ（1回空振りするだけで恒久固着ではない）、(b) 物理配送そのもの
  が二重に空振りしている（BUG-37/ADR-121 `reassert_explicit_physical_key`
  と同型、beliefを直しても直らない）。
- B2: 提案した設計（既存`ConvOpenInference`経路への合流）を実装すると、
  20ms後にdrift correctionが実際にVK_IME_OFFを送ってしまい、ADR-173より
  悪い結果（巡回を殺した上に送信も増える）になることが判明。
- B3: `observed`側を書くだけでは`desired_open`が変わらず、「beliefに
  反映する」という目的を構造的に達成できない。
- B4/B5/B6: 既存機構（ガード5、`kp_trigger_focus_resync`、
  `probe_actuation_fence`）の転用は、目的の不一致・自己干渉ループ等の
  問題を抱える。
- 詳細は `opus-review-adr174-round1.md`（ADR-174起票時のワークツリー、
  破棄済みのため本文は残らない。要点は上記に集約）。

opusは「まずB1を実機で確定してから設計すべき、確定すればADR-174自体が
不要になる可能性がある」と提案した。

### 実機再検証（2026-09-15 続き）——再現せず、原因未確定のまま持ち越し

develop（config未設定、ADR-173適用前の状態と機能的に同一——後述）で、
半角モードのまま無変換キーを単独タップする再現を**複数回試みたが、
一度も「IME ON固着」（あるいはIME ONへの遷移そのもの）を再現できなかった**:

1. develop + 素のconfig: 無変換タップ → GJI表示は「半角のまま」変化なし。
2. GJI関連プロセス（`GoogleIMEJa*`）を強制終了して再起動、再度同じ手順 →
   結果は同じ（半角のまま変化なし）。

**コード差分で「ADR-173ブランチかdevelopか」の違いを排除済み**:
`git diff origin/develop origin/adr/173-hankaku-zenkaku-stuck-on` を確認
した結果、`explicit_ime_action_target`へのADR-173の変更は
`muhenkan_solo_tap_ime_action`/`henkan_solo_tap_ime_action`が**明示的に
設定されている場合にのみ**実行される分岐に置かれており、config未設定
（今回の再検証環境）では develop と ADR-173 ブランチの挙動は**完全に
同一**であることをソースレベルで確認済み。したがって「ブランチが違った
のでは」という仮説は排除できる。

### 実機再現（2026-09-15 続き）——変換キーで再現、無変換キーでは再現せず

同セッション内でさらに検証したところ、**無変換キーでは（develop・GJI再起動後とも）IME ON への遷移が再現しなかったが、変換キーの単独タップでは再現するようになった**（ユーザー視認確認）。実機デバッグログで裏付けを取った:

```
[engine-input] vk=0x1C KeyDown ... [diag-ctx] ime_on=false ...
key input seq=1852 vk_code=28 ... state_before="Idle" state_after="Idle" decision="PassThrough" physical="Allow"
[engine-input] vk=0x1C KeyUp ... [diag-ctx] ime_on=false ...
key input seq=1853 ... decision="PassThrough"
```

同型のイベントが3回（05:47:22, 05:47:25, 05:47:42）記録されており、いずれも
`[shadow-toggle]`ログ・`[apply-ime]`（actuation）ログとも**一切出ていない**
——awaseはこの打鍵に対して完全に無反応（生キーがそのままGJIへ渡るだけ）で
あることを確認した。GJIが実際にIME ONへ遷移したのだとすれば、それは純粋に
GJI自身のネイティブな処理によるものであり、beliefは一切追従しない。

**注意点（過大解釈しないこと）**: 同じログに「desired=false observed=true」
という乖離検出が`duration_ms=59578`〜`61232`（約60秒間、同一
`intent_at_ms`）と連続して記録されている。この乖離自体は今回の変換タップ
より前から存在していた可能性が高く（BUG-26が記録するとおり、GJIのconv
NATIVEビットはIMEを閉じても消えない持続的な設定であるため）、**この特定の
`[drift]`ログ行を「変換タップが新たに引き起こした乖離」と結びつけて解釈
してはならない**。確実に言えるのは「変換の単独タップにawaseが一切反応
しない」という事実のみ。

**未確認のまま残る点**: この状態（変換タップでGJIがONになったと仮定した
状態）で物理半角/全角キーを押すと実際に「固着」するかどうかは、今回もまだ
検証していない。次のセッションでの優先確認事項。

### 実機再現（2026-09-15 続き）——固着の完全な再現とログでの機序特定

ユーザーが一連の操作を再現させ、症状を明確に言語化した:
「IME OFFで変換を押して、IME ONになるけどEngine OFF。半角全角を押すと
IME ON・Engine ONになって、そこから半角全角を何回押してもIME ON・
Engine ONに固着した」。この一連の流れを実機デバッグログで裏付けた
（`target/debug/awase.log`、時刻は全て2026-09-15）:

```
05:53:46.611  [hook] IME-mode vk=0xF2 down (物理半角/全角キー)
              [shadow-toggle] intent 昇格: vk=0xF2 action=TurnOn false→true
              [apply-ime] GJI direct: send 0x0016 (open=true) → belief ON
```

**この機序整理から得られる仮説（未検証、次の優先調査対象）**: 「IME ON
固着」の直接の引き金は、beliefがネイティブ遷移を追従できないこと自体
ではなく、**`DRIFT_CORRECTION_BLIND_REARM_COOLDOWN_MS=3000ms`のクール
ダウンが実際には守られておらず、`VK_IME_OFF`のBlind送信が126〜145ms
間隔で連発している**ことである可能性が高い。この連射の直後から、物理
半角/全角キーが一貫してTurnOn方向のVK（0xF2）しか報告しなくなる——
OS/ドライバ側のキーボードレイアウト処理が持つ「次にどちらの方向のVKを
送るか」というトグル記憶が、この連射によって破壊されているように見える
（BUG-113が確立した「awase自身のSendInput連射がGJI/OS側の内部状態を
乱す」という同系統の機構の、キーボードレイアウト層での新しい現れ）。

この仮説が正しければ、対策候補は「beliefの再観測・追従」（ADR-174）
より遥かに小さく的を絞れる: **なぜクールダウンが無視されているのかを
特定し、実際に3000ms間隔を守らせる**こと。次のセッションで最優先の
調査対象とする。

### コード調査で判明（2026-09-15、静的解析のみ・実機未検証）——クールダウン自体は機能しており、上記「連射」の正体は journal ログの重複記録

`runtime/ime_refresh.rs::ir_apply_drift_correction`を読んだ結果、
**`DRIFT_CORRECTION_BLIND_REARM_COOLDOWN_MS`のクールダウン判定
（`blind_rearm_cooldown_elapsed`、`ime_refresh.rs:747`）自体は正しく
機能しており、実際の`VK_IME_OFF`再送（`Send`分岐、`ime_refresh.rs:822`
以降）はこのクールダウンの間は起きない**ことをソースで確認した。

`GiveUp`のjournal記録（`self.platform_state.ime.journal.record(...
ImeActuation {...})`、`ime_refresh.rs:680-689`）は、`match act_gave_up_at`
（`None`/`Some(gave_up_at)`でクールダウンを見る分岐、`:692`）に入る**前**、
`action == ActuationAction::GiveUp`が真になった時点で無条件に実行される。
`FeedbackPolicy::Blind::decide_action`（`state/ime_actuation.rs:44-55`）は
`attempts >= max_attempts`の間ずっと`GiveUp`を返し続ける純関数で、
`attempts`自体は`Send`分岐（`advance_epoch`、`:902-904`、`GiveUp`側では
到達しないので加算されない）でしか増えない。つまり**一度`GiveUp`で
parkedになった後は、`ir_apply_drift_correction`が呼ばれるたび
（`ir_stage_notify`からの周期リフレッシュ、`ime_refresh.rs:226-235`）に
同じ`GiveUp`のjournal記録が無条件で再生成される**——クールダウン判定は
「再武装（discard_actuationしてattempts=0からやり直す）してよいか」だけを
制御しており、「`GiveUp`ログをもう一度出すかどうか」は制御していない。

BUG-142.mdが引用した「05:53:48.856と05:53:48.982、126ms間隔で2回連続の
`GiveUp`」は、この**ログ生成側の重複**である可能性が高い——両方とも
`target_open=false attempts=5`と同一値なのは、実際に2回送信を試みた
からではなく、同じparked状態を2回連続のリフレッシュtickで記録した
だけと読める。**「Blindポリシーの`VK_IME_OFF`送信が126〜145ms間隔で
連発している」という前回の解釈は、journal記録の反復と実際の
SendInput/IMC書き込みの反復を混同していた可能性が高く、訂正が必要。**

### より有力な代替候補: ADR-121 D1（`reassert_explicit_physical_key`）にデバウンスが無い

BUG-142.mdの実機ログが明記していた「no-opのはずが、別経路の
apply_mechanismが無条件でsend 0x0016も実行——二重ディスパッチ」
（05:54:00.659、3回目の0xF2押下）は、上記のjournal重複とは別物で、
**`runtime/key_pipeline.rs:1639-1652`の`reassert_explicit_physical_key`
呼び出し（ADR-121 D1、`docs/adr/121-...md`）そのものと一致する**:

- 発火条件（`key_pipeline.rs:1639-1645`）: `!delegate_owned && vk ==
  VK_DBE_HIRAGANA(0xF2) && action == TurnOn && kind == PhysicalImeKey
  && !can_use_imm32_cross_process() && !half_width_restore_fired`。
  GJI direct（Blacklistプロファイル）はこの条件を満たす。
- `reassert_explicit_physical_key`（`runtime/mod.rs:1184-1228`）は
  `order.would_have_blocked()`（実質shadowモードでほぼ常にfalse、
  ADR-090 §2.A参照）を通過すれば**毎回無条件に`apply_ime_open_with_view`
  を呼び、実際にVK_IME_ON(0x0016)を送る**。しかも
  `reassert_ime_apply_complete_without_belief_write`という名前が示す
  とおり、**この送信はbelief（`applied`）を一切更新しない**（ADR-121
  round3決定、BUG-69型のbelief偽装を避けるため意図的）。
- **ADR-121のD2（このパスへのデバウンス/クールダウン新設）は
  「実機でVK_DBE_HIRAGANAのKeyDownがauto-repeatするか未確認」を理由に
  明示的に未実装のまま**（同ADRステータス節「D2は実機未確認のため
  未実装のまま」）。つまり**このパスには現状レート制限が一切無い**。

belief を更新しないため、OSが0xF2（TurnOn方向）を報告し続ける限り
（＝物理半角/全角キーのトグル記憶が壊れている間）、**このno-op分岐と
無条件reassert送信が押すたびに何度でも繰り返される**——ドリフト補正の
`GiveUp`クールダウンとは完全に独立した経路で、実際のVK_IME_ON送信が
無制限に連発しうる。BUG-142.mdの「OS/ドライバのキーボードレイアウト層の
トグル記憶が破壊される」という仮説の引き金としては、こちらの方が
（ログ上も条件上も）drift correctionのGiveUp連発より一致度が高い。

**注意（過大解釈しないこと）**: 上記はいずれも2026-09-15時点でのソース
読解のみに基づく仮説であり、実機ログでの検証はまだ行っていない。次回は
実機で`[explicit-reassert] apply_ime_open(true) → ...`ログが「IME ON
固着」再現時に繰り返し出ているかを確認すること。

## 実機検証（2026-09-15、6フェーズ・1セッション）で因果関係を確定

上記の「コード調査で判明」節が立てた2つの仮説（drift correctionのクール
ダウン無視／ADR-121 D1の未デバウンス）を、1回の実機検証で切り分けるため
6フェーズの手順（Phase A〜F、詳細は本セッションのやり取り参照）を計画し、
実行した。環境は前回と同じ Windows Terminal + PowerShell + GJI だが、
**`can_use_imm32_cross_process()`のprofileは`TsfNative`**（前回セッションが
暗黙に前提としていた`Blacklist`ではない）であり、物理半角/全角キーが
実際に生成するVKも**`VK_DBE_SBCSCHAR(0xF3)`/`VK_DBE_DBCSCHAR(0xF4)`**
（`ADR-121`が対象とする`VK_DBE_HIRAGANA(0xF2)`とは別のペア）であることが
判明した——この環境特定の事実だけで、ADR-121 D1仮説は成立しないと確定した
（後述）。

### Phase A（awase停止、対照群）: 物理キー10連打、10/10回とも正常に交互切替

OS/GJIネイティブのトグル記憶自体は壊れていない。awaseの関与なしでは症状は
一切起きない。

### Phase B・C（awase起動、半角/全角キー連打のみ・変換キー無し）: 固着せず

15回・10回それぞれ連打しても固着しなかった。ログで確認したところ、
`explicit-reassert`（ADR-121 D1）は**0件**——この環境の物理キーは
`0xF3/0xF4`であり、`VK_DBE_HIRAGANA(0xF2)`専用のADR-121 D1はそもそも
発火条件に合致しない。OFF方向は`ShadowToggleOff`が直接1回実送信、ON方向は
Engineの`DispatchImeSetOpen`（`engine_decision_sync`）が1回実送信し、
互いに`shadow_on`ゲートで重複を防いでいる（二重送信なし）。**ADR-121仮説は
この環境では棄却**。

### Phase D（変換キー→タイピング→半角/全角→タイピング→半角/全角連打）: 固着を再現

固着の直前のログ（`docs/known-bugs/BUG-142.md`本文の別セッション記録と
条件は異なるが、機序は同型）:

```
半角/全角キー押下 → 正常にON（vk=0xF4, TurnOn, false→true）
[TSFプローブ: StartComposition → per-VK confirmed(vk=0x4B, vk=0x49) → セッション確認 → Warm]
1文字タイプ（"a" → romaji "u" → "う"、正常に合成）
半角/全角キー押下（OFFにするつもり）
  → [hook] vk=0xF4 down（本来は0xF3のはずが、TurnOn方向のまま）
  → [shadow-toggle] intent 昇格: action=TurnOn true→true（同方向、変化なし）
  → [shadow-toggle] no-op: effective_openは既にtrue → apply-ime 見送り
（以後、20回以上の連打すべてが同じ vk=0xF4 / no-op のまま固着）
```

**重要な否定的事実**: 固着中、`explicit-reassert`は0件、`[drift]`の
`GiveUp`バーストも0件（drift correctionは`ConvOpenInference`由来で1回だけ
送信し、既存のエピソードラッチで正しく抑止されただけ）。つまり**固着後は
awase側から一切の実送信が発生していない**——固着は「awaseが送り続けて
いる」ことの結果ではなく、「OSが物理キーの方向を1回だけ間違えた後、
awaseのbeliefがその間違った方向と一致してしまい、双方が動かなくなる」
という静的なロックである。

### Phase E（固着中にawase.exeを強制終了、押下は継続）: 即座に正常な交互切替に復帰

**最も決定的な結果。** 押し続けたまま`taskkill /f /im awase.exe`を実行した
直後から、ユーザーの報告により物理キーは正常に交互切替するようになった。
これは以下を意味する:

- **OS/キーボードドライバのトグル記憶が恒久的に破壊されたのではない。**
  破壊されているように見える状態は、**awaseのフック（プロセス）が生きて
  いる間だけ**発生する現象であり、フックを外す（プロセスを殺す）だけで
  即座に消える。
- 前回セッションの中心仮説（「OS/ドライバのキーボードレイアウト層の
  トグル記憶が破壊される」という**恒久的な**破損）は誤りだったと確定した。

### 診断コードのバグ: F9ダンプが素の`ImmGetContext(hwnd)`を使っており、

### 新しい決定的発見: charsetc(FULLSHAPE)軸は物理DBEキー押下では一切
動かないが、`WM_IME_CONTROL`（`IMC_SETCONVERSIONMODE`）による直接書き込み
では確実に動く

```
open_raw=0 conv=0x0019(FULLSHAPE=true)  ← open は false に変化、conv は不変
```

**open軸は物理DBEキー押下のたびに正しく交互反転した**（今回のセッションでは

ベース、`IME_KANJI_MARKER`）で`VK_DBE_SBCSCHAR`を注入する方式だったが、
今回`WM_IME_CONTROL`直接書き込みでは確実にconvが動いたことから、

注入がGJIのcharset処理に届いていない」ことの証明だった可能性が高い**
（反証ではなく手法上の偽陰性の疑い）。

## 続報（2026-09-15、同日中の追加セッション）——ユーザー指摘で判明: 送信経路は
生きている、原因は「送信を試みていないこと」自体

### 再現手順の再確認とユーザーによる修正

ユーザーが実際の状態遷移を明確に言語化した:
「IME OFF, Engine OFF => 変換 => IME ON, Engine OFF => 半角全角=> IME ON,
Engine ON => 半角全角 => IME ON, Engine ON 以降何回半角全角をおしても
IME ON Engine ONで固着します」。この固着はタスクバー表示ではなく**実際に
文字を打って**確認したとのこと（「変換を押してから半角全角を何度押しても
ずっとIME ONです」「きうきうきう→かなになりますね」）。

上記「H1決定的検証セッション」節で試した`Home`（`WM_IME_CONTROL`/
`IMC_SETOPENSTATUS`直接書込）は、APIとしては成功（`open_ok=true`）を
返すにもかかわらず、**直後に実タイピングで確認したところ依然としてかな
のまま**だった——この書込みは実際のGJI TSFエンジンには効いていない
ことを実タイピングで確認した（前回セッションの`VK_DBE_SBCSCHAR`
SendInput注入の「反証」と合わせて、awase側が持つ2つのIME制御経路
（`WM_IME_CONTROL`メッセージ、物理DBEキーのVK直接SendInput）が
いずれもこの固着状態では実TSFエンジンに届いていないことになる）。

### 決定的な発見: Ctrl+無変換（`GjiDirectStrategy`の`VK_IME_OFF`送信）は
固着中でも実際に効く

ユーザー指摘「Ctrl+無変換、Ctrl+変換は効果があるわけだから、そっちと
同じ方法にしたらいいんじゃないかな」を受け、固着状態で実際に**Ctrl+
無変換**を押してもらったところ、**実タイピングでローマ字（直接入力）に
戻ることを確認した**。

Ctrl+無変換/Ctrl+変換は`ime_controller.rs::GjiDirectStrategy`が送る
`VK_IME_ON`(0x16)/`VK_IME_OFF`(0x1A)の単発SendInputという、**通常の
GJI direct actuationと全く同じ送信経路**を使う（`docs/adr/`の既定
キーバインド、`state/platform_state.rs`の`UserIntentSource::Command`
経由）。この経路が固着中も実際にGJIへ届き実TSFエンジンを動かせることが
確認された以上、**「awaseからGJIへの送信チャネルが壊れている」という
これまでの作業仮説（H1、`WM_IME_CONTROL`・物理DBEキーSendInputの
両方が効かないという観測から導いていた）は誤りだったと判明した。**

### 修正された結論: 固着の原因は送信の失敗ではなく、送信が試みられて
いないこと自体

`BUG-142.md`が当初から記録していた通り、固着中は
`[shadow-toggle] no-op: effective_open は既に true → apply-ime 見送り`
のログが繰り返され、`[apply-ime]`（実際の`GjiDirectStrategy`送信）は
一度も発火していない。今回Ctrl+無変換で確認した「送信経路自体は生きて
いる」という事実と合わせると、**根本原因は「OSが物理半角/全角キーに
対して同じ方向のVK（TurnOn方向）を繰り返し報告し、awaseの
shadow-toggleロジックがこの報告された方向を無条件に信用して
『すでに目的の状態＝変更不要』と判断し、`GjiDirectStrategy`の送信
自体を呼び出していない」ことに絞り込まれた。** OS側のVK生成が
なぜ同じ方向に固定されるのか（本BUGの初期セッションが追った論点）は
依然未解明だが、**修正のターゲットは「OSの報告方向を信用しない
shadow-toggleロジックへの変更」に絞り込める**——具体的には、物理
半角/全角キーの繰り返し押下に対し、OSが報告する方向（TurnOn/TurnOff）
ではなく現在のbeliefからの反転を基準に`GjiDirectStrategy`を呼ぶ
（Ctrl+無変換/Ctrl+変換が既にそうしているのと同じ「現在状態に関わらず
明示的に設定する」方式）ことが有力な修正候補になる。

**次のアクション**: この修正案（shadow-toggleのno-op判定をOS報告方向
ではなくbelief反転ベースに変える）はIME actuation合流点・キー選択の
再発ファミリーに該当するため、実装前にADRを起票し
opus-adversarial-consultで設計を収束させてから進めること
（`.claude/rules/fix-requires-evidence.md`「キー選択」行参照）。
[ADR-175](../adr/175-physical-dbe-key-stuck-direction-recovery.md)として起票済み。

## 続報（2026-09-15、opus-adversarial-consult round1で解決策を発見・実機A/Bで確定）

ADR-175のopus round1レビューが、当初案（no-op N回連続検出→フォールバック
送信）のBlocker 5件・Major 8件を検出した過程で、コード変更なしで検証できる
代替案を提示した: `config.toml`に以下を追加し、`VK_DBE_SBCSCHAR`/
`VK_DBE_DBCSCHAR`を固定方向（TurnOn/TurnOff）ではなく`Toggle`として
解決させる。

```toml
[keys.ime_detect]
toggle = ["VK_DBE_DBCSCHAR", "VK_DBE_SBCSCHAR"]
```

`crates/awase-windows/src/runtime/focus_tracker.rs::enrich_ime_relevance`が
これを`event.ime_relevance.sync_direction = Some(ShadowImeAction::Toggle)`
として設定し、`kp_stage_shadow_ime_toggle`の`intent_kind`解決で
（`shadow_action`より優先度が高い）`IntentKind::SyncKey`として採用される。
`Toggle.resolve(current) = !current`となるため、OSがどちらのVKを報告
しても常にbeliefが反転し、no-op分岐に落ちなくなる。

**実機A/Bで確定**: dragonflyg4でこの設定を投入しawaseを再起動、BUG-142の
再現手順（変換キー1回→半角/全角キーを2〜3回）を再試行したところ、
**固着が解消し、正しく交互切替するようになった**（ユーザー確認）。

これによりADR-175の当初案（no-op N回連続検出、round1でN=1がToggle化と
数学的に同値と指摘済み）は不要と判明し、決定は「`VK_DBE_SBCSCHAR`/
`VK_DBE_DBCSCHAR`を固定方向マッピングではなくToggleとして解決する」に
一本化される見込み。詳細はADR-175 round1レビュー（Blocker/Major全件）を
反映して更新中。
