## Blocker（v5で新規）

### B8. 決定2フェーズ3の文が「存在しない`.yab`のみを埋め込み既定値から書き戻す」と限定してしまい、**`.yab`についてB1（MSI再インストール後のバックアップ復元）が再び発火しなくなっている**

決定2の中に、`.yab`の復元について**互いに矛盾する2つの規則**がある。

(A) フェーズ3（150-163行）:
> フェーズ2: 上記「書き込み」節の条件を満たす場合に`.yab`の復元を行う。
> 復元は**存在しない**同梱`.yab`のみを埋め込み既定値から書き戻す形で行い、
> **既存の（壊れた）ファイルは上書きしない**（決定5参照）。

(B) 「復元条件」（173-175行）:
> ファイルが「存在しない」**または**「内容が埋め込み既定値とバイト一致し、
> かつバックアップが存在し、かつバックアップの内容が既定値と異なる」場合に
> 復元する。

(A)を読むと、`.yab`の復元は「**存在しないものだけ**」「**埋め込み既定値から**」の
2重の限定になる。これはB1が対象としているケース——

```
MSI アンインストール → 再インストール
→ layout\*.yab は 6本とも「存在する」（MSIが工場出荷値で再配置した）
→ (A)の「存在しない`.yab`のみ」に該当しない → 復元されない
→ さらに「埋め込み既定値から書き戻す」なのでバックアップを見ない
→ 配列編集タブで作り込んだユーザーの `.yab` は復元されない
```

——を**完全に除外する**。`config.toml`だけが復元され、`layout/*.yab`は
工場出荷値のまま残る。本ADRのコンテキスト（24-28行）が明示的に守ろうとしている
「配列編集タブで作り込んだ`layout/*.yab`」がそのまま失われるので、
これは主目的の半分が達成できない状態である。

原因は、round4 M5（救済手段の曖昧さ）への対応文をフェーズ3に書いたこと。
M5が明確化を求めたのは**決定5の救済**（「有効な`.yab`が1本も無い＝起動不能
という緊急事態を、埋め込み既定値で救う」）という**別の機構**であって、
通常の復元規則ではない。2つを同じ文に混ぜたため、より狭い救済側の条件が
一般規則を飲み込んでしまった。

**要求**: 決定2フェーズ3を、2つの機構を分けて書き直すこと。

> 3. フェーズ2: 上記「書き込み」節の条件を満たす場合、同梱6ファイルの
>    それぞれについて「復元条件」（後述）を評価し、満たすものを復元する。
>    復元元は、バックアップが存在しかつ妥当ならバックアップ、無ければ
>    埋め込み既定値。
>    （**別機構**）決定5の救済は、上記の復元を行ってもなお有効な`.yab`が
>    1本も無い場合にのみ発動し、**存在しない**同梱`.yab`を埋め込み既定値から
>    書き戻す。既存の（パースできない）ファイルは上書きしない。

決定5側の文（224-235行）は正しく書けているので、フェーズ3から「存在しない
`.yab`のみ」「埋め込み既定値から」の限定を外し、決定5への参照だけを残せばよい。

決定7のテスト項目も、現状「B1の直接再現」は`config.toml`しか想定していない
読み方ができる。**「`layout\*.yab`が工場出荷値で存在し、バックアップに
ユーザー編集版がある状態から、`.yab`が復元されること」を独立した項目として
明記**すること（B8はこの項目が無いために生まれた欠落でもある）。

### B7. 「復元先は常に`resolve_next_to_exe()`」という規則が、`cargo run`での開発フローを壊し、**リポジトリのトラッキング済みファイルへ書き込む**経路を作る

決定2は復元先を次のように定めている。

- `config.toml`: 常に`resolve_next_to_exe("config.toml")`（136行）
- `layout/*.yab`: `layouts_dir`が相対なら`resolve_next_to_exe(layouts_dir)`（137-148行）

一方、**読み取り**は`resolve_relative_to_exe()`のままで、これは
「exe隣 → ワークスペースルート（`target`の親） → CWD」の順に**存在する
パスを探す**（`src/paths.rs:38-53`）。`cargo run`実行時は exe が
`<root>/target/debug/awase.exe`、リソースは`<root>/config.toml`・
`<root>/layout/`にある——これは`src/paths.rs`のモジュールコメントが
明示する2大サポート形態の一方であり、テスト
`falls_back_to_workspace_root_when_run_from_cargo_target_dir`が
「実際に踏んだ回帰」として固定している挙動である。

この構成で`ensure_user_data_present()`が走ると:

```
1. 復元先 = resolve_next_to_exe("config.toml") = <root>/target/debug/config.toml
2. そこには何も無い → 復元条件「存在しない」を満たす → 埋め込み既定値を書き込む
3. 以後、読み取り resolve_relative_to_exe("config.toml") は
   **exe隣を最優先**（paths.rs:38-43）するため <root>/target/debug/config.toml を返す
4. 開発者が <root>/config.toml をいくら編集しても、アプリはもう読まない
   （cargo clean するまで恒久的に）
```

`layout/`についても同様に`<root>/target/debug/layout/`に6本が書き出され、
以後ワークスペースルートの`layout/*.yab`は読まれなくなる。**「編集している
ファイル」と「アプリが読んでいるファイル」が無言で乖離する**——これは
ADR-099 F5（2026-07-19実機確認）としてリポジトリに記録されている事故
そのものであり、`src/paths.rs:54-58`のコメントが「典型的な事故」と
名指ししている失敗モードでもある。`scripts/run-e2e.ps1`経由のe2eも同じ影響を受ける。

さらに、これを「見つかった既存パスへ復元する」形に直すと、今度は逆向きの
危険が生まれる: 開発時は`<root>/config.toml`が**埋め込み既定値と
バイト一致する**（`include_str!`が同じファイルを読んでいるので当然一致）ため、
バックアップが存在すれば復元条件を満たし、**gitのワーキングツリーにある
トラッキング済みファイルがバックアップの内容で上書きされる**。
気づかずコミットする事故につながる。

**要求**: 決定2に、開発ビルドを除外する規則を明記すること。推奨:

> 復元（および決定5の救済）は、`current_exe()`の祖先に`target`という名前の
> ディレクトリが含まれる場合（＝`cargo run`/`cargo build`での実行）には
> **行わない**（ログ警告のみ）。`src/paths.rs`が既に同じ条件でワークスペース
> ルートへのフォールバックを判定しているので、判定ロジックは共用できる。

加えて、`resolve_next_to_exe()`しか使わない現行の規定は
「既存ファイルがワークスペースルート側にある」ケースを無視するため、
除外規則を入れない限りどちらの合成でも破綻する点を決定文に残しておくこと。
決定7に「`cargo run`相当（exeが`target/`配下）で復元が発火しないこと」の
自動テストを追加すること（`ensure_user_data_present()`が純粋関数なので、
exeパスを引数化すればホストターゲットで検証できる）。

## Major

### M1. 「`config.toml`を消して初期化する」が効かなくなる。既定値へ戻す操作がバックアップによって巻き戻される経路が残っている

v5のM1ルール（決定1、94-103行）は「内容が既定値と一致する場合はバックアップを
作成・更新しない（**既存のバックアップも上書きしない**）」である。この
「既存も上書きしない」により、次が起きる。

- **意図的に既定へ戻した編集が復活する**: ユーザーが`nicola_keytop.yab`を
  カスタマイズ（バックアップ作成）→ 後日、工場出荷版に戻したい/戻した
  → 内容が既定値と一致するのでバックアップは**カスタマイズ版のまま残る**
  → 次にMSI再インストールすると、戻したはずのカスタマイズ版が復元される。
- **「設定を初期化したい」操作が無効化される**: 「`config.toml`を消して
  起動し直す」は最も素朴な初期化手段であり、`crates/awase-windows/src/main.rs`の
  起動エラーヒントも「`config.toml`が見つかりません…同梱の
  `config.sample.toml`をコピーして使えます」と、ファイル差し替えによる
  復旧を前提にした文面になっている。v5以降は削除しても次回起動で
  バックアップから**元に戻る**。ユーザーから見ると「消しても設定が消えない」
  という挙動になり、原因（`backup\`の存在）はUIからは見えない。

決定6の通知（「バックアップから復元しました」）があるので気づけはするが、
**どうすれば初期化できるか**の逃げ道が設計に無い。

**要求**: 以下のいずれかを決定文に入れること。
- (a) 決定6の通知文に「既定値に戻したい場合は`backup\`フォルダも削除して
  ください」を含める（最小コスト）。
- (b) `awase-settings`に「既定値に戻す」操作を用意し、本体とバックアップの
  両方を同時に処理する（決定5で既に「バックアップから復元しますか？」という
  UIを足すと決めているので、その隣に置ける）。
- (c) M1ルールを「既定値と一致する場合は既存バックアップを**削除**する」に
  変える（初期化は自然に効くようになるが、一時的に既定値相当になった瞬間に
  バックアップが消えるリスクがある。採るなら理由を書くこと）。

「解決されないこと」にもこの制約を明記すること。

### M2. 決定7から**MSI実機での「バイト一致」確認**が落ちている。B1修正が依拠する唯一の前提が未検証のまま

v4の決定7にあった「MSIインストール→設定編集→`msiexec /x`→**同じMSIを
再インストール**→起動→復元されることを確認」という実機項目が、v5では
`ensure_user_data_present()`の単体テスト（決定7の「B1の直接再現」、
287-289行）に置き換わっている。単体テストの高速化・自動化自体は正しい方向
（round4 m5で推奨した内容）だが、**単体テストでは検証できない前提**が1つ残る。

B1修正の全体は「MSI再インストール時、`%LOCALAPPDATA%\awase\config.toml`と
`layout\*.yab`が、**埋め込み既定値と（正規化後）バイト一致する内容**で
再配置される」という前提の上に成り立っている。この前提は round1〜2 の
机上推論（アンインストールでKeyPathレジストリ値も消えるので、次の
インストールは真の新規インストールとして扱われ`NeverOverwrite`が効かず
ファイルが配置される）に基づくもので、**誰も実機で観測していない**。
ADR-177の実機検証もアンインストール後の削除までしか見ておらず、
その後の再インストール結果は見ていない（「検証の限界」7）。

前提が外れた場合（例: MSIが何らかの理由でファイルを配置しない、
BOM/改行が変わる、`config.toml`のタイムスタンプ由来で別内容になる）、
**復元条件が永久に満たされず、全ての自動テストが緑のまま本ADRは無効化される**。

**要求**: 決定7に実機項目を1つだけ明示的に残すこと。

> MSIインストール → `config.toml`/`nicola_keytop.yab`を編集 → `msiexec /x` →
> **同じMSIを再インストール** → 起動前に`%LOCALAPPDATA%\awase\config.toml`と
> `layout\*.yab`を採取し、リポジトリの`config.toml`/`layout/*.yab`と
> （改行正規化・BOM除去後に）バイト一致することを確認する。その後起動し、
> 編集内容が復元されることを確認する。

「起動前に採取して比較する」ところまで手順に書くのが重要で、
起動後に確認すると復元が済んでいて前提の検証にならない。

### M3. 決定1の「プロセスローカルフラグ」を**いつ立てるか**が未規定。立て方次第で、ユーザーが直した直後の設定がバックアップされない

決定1の実行ゲート（111-123行）は
「`ensure_user_data_present()`が**完了したことを示す**フラグが立っている場合に
限りバックアップ書き込みを実行する」だが、「完了」の定義が無い。決定2には
早期に抜ける経路が複数ある:

- フェーズ2の`AppConfig::load()`が失敗（`Dangerous`）→ フェーズ2と契機3を
  スキップ（155-160行）
- 復元の書き込み自体が失敗 → インメモリ既定値で起動継続（185-188行）
- B6ゲート不成立（`layouts_dir`が絶対パス）→ `.yab`復元を行わない

これらで「完了」とみなさない実装にすると、たとえば
「`config.toml`を壊した → 起動 → `Dangerous`でスキップ → ユーザーが
`awase-settings`で修正して保存」という最も自然な復旧フローで、
**修正後の正しい設定がバックアップされない**（フラグが立っていないため
契機1が抑制される）。次回起動でようやく契機3が拾うことになり、その間に
MSIアンインストールが挟まると保護されない。

**要求**: 「フラグは`ensure_user_data_present()`から**復帰した時点で、
結果（復元した／しなかった／失敗した）に関わらず立てる**」と明記する。
「復元をスキップした」ことと「復元ステップを一度も通っていない」ことは
別物であり、ゲートが防ぎたいのは後者だけである
（`Dangerous`時に契機1がバックアップを汚す危険は無い——工場出荷の
`config.toml`はパースできるので`Dangerous`にならず、`Dangerous`になるのは
ユーザー自身が壊した内容だけだから）。

### M4. 決定5のシグネチャ`layouts_dir_if_relative: Option<&Path>`だと、B6のゲート判定が**呼び出し元2クレートに分散**し、決定5が狙った「1箇所に閉じる」が崩れる

決定5（244-261行）は「埋め込みリスト・復元対象リスト・テストを1箇所に書けば済み、
2バイナリ間のロジック乖離を構造的に防ぐ」ことを配置の根拠にしている。ところが
提示されたシグネチャは`layouts_dir_if_relative: Option<&Path>`——
**「相対パスかどうかを判定して`None`/`Some`を作る」というB6の核心ロジックが
呼び出し元（`awase-windows`と`awase-settings`）側に残る**。

これは`find_config_path()`が2クレートに同型実装されて実機バグを起こした
（`crates/awase-settings/src/main.rs:5284-5289`のコメントが
「ズレていると実機バグの原因になる（2026-07-19に実際に発生）」と警告）
のと同じ構図であり、round4 M5で配置をコアに寄せた理由そのものを損なう。

**要求**: 判定に必要な**生の入力**を渡し、判定はコア側で行う形にする。例:

```
pub fn ensure_user_data_present(
    exe_dir: &Path,                 // OS依存の解決結果だけを呼び出し元から受け取る
    layouts_dir_setting: &str,      // validate() 後の生の設定値
    backup_dir: &Path,
) -> RestoreOutcome
```

「`layouts_dir_setting`が相対なら`exe_dir.join(...)`へ復元、絶対なら復元しない」
「`exe_dir`が`target`配下なら復元しない（B7）」の両方がコア側の1箇所に収まり、
決定7のテストもそこで書ける。

## Minor

### m1. 「この設計で解決されること・されないこと」節が本文から消えている

v5の当該節（313-318行）は「（v4から変更なし。…以下を追加）」となっており、
**v5のADRを単体で読んでも内容が分からない**。ADRは後から1ファイルだけ開いて
読む前提の文書（`.claude/rules/docs-frontmatter-convention.md`が
「索引だけ読めば概要が分かり、必要なときだけ本文を開く」構成を規定）なので、
差分参照ではなく全文を復元しておくこと。M1・B7・B8の結論もここに反映される。

### m2. 契機3の`.yab`側は実質`awase.exe`でしか走らないことを明記すること

決定1の契機3は`.yab`の「パース成功」を`awase-windows`の
`LayoutEntry::scan_all`と定義した（m2対応、87-92行）。しかし
`awase-settings`は起動時に全`.yab`をパースせず、`ensure_layout_loaded()`
（`crates/awase-settings/src/main.rs:1802-1816`）で
`default_layout`の1本だけを遅延ロードする。したがって契機3の`.yab`半分は
実質`awase.exe`側でのみ機能する。仕様としてそれでよい（常駐アプリは必ず
起動する）が、「`awase-settings`だけを起動した場合は`.yab`の手編集捕捉は
行われない」ことを1行書いておかないと、実装者が`awase-settings`側に
全`.yab`パースを足す方向（起動時間の悪化、`ensure_layout_loaded`を
遅延にした経緯と逆行）へ進みうる。

### m3. 決定2の復元条件の第3節（「バックアップが既定値と異なる」）は、決定1のM1ルール導入後は冗長

決定1のM1ルールにより「内容が既定値と一致するならバックアップを作らない」ため、
存在するバックアップは定義上すべて既定値と異なる（作成時点の既定値との比較
ではあるが）。復元条件に残しておいても害はなく、バージョン跨ぎの安全弁として
機能するが、**なぜ二重に書いてあるのか**の一言があると、将来「冗長だから
消そう」と判断されたときに（バージョン跨ぎの穴が開くことに）気づける。

### m4. `ConfigLoadState::NotFound`の扱い（未解決事項3）は、B7の除外規則次第で結論が変わる

「復元後は`config.toml`が必ず存在するので`NotFound`は到達不能」という前提は、
B7対応で開発ビルドを復元対象から外すと崩れる（`cargo run`で
`target/debug/config.toml`が無い状態＝`NotFound`が正規の経路として残る）。
また復元の書き込みが失敗してインメモリ継続する経路（185-188行）もある。
未解決事項3を判断する際の材料としてこの2点を書き添えておくこと。

### m5. 決定7の「4箇所同期」は、決定5の配置確定後は実質3箇所

決定5で「埋め込みリスト」と「復元対象リスト」がコア`awase`の同一定数に
なる想定なので、同期を要するのは
