# ADR-095: タスクトレイからの不具合報告機能 — Cloudflare Workers + R2 による非公開受付

## ステータス

提案中（設計のみ。実装未着手）。

## コンテキスト

これまで不具合報告はユーザーが手動で `docs/known-bugs.md` 相当の情報
（アプリ・IME・再現手順、[experiment-logging](../../.claude/rules/experiment-logging.md)
参照）を書き起こす前提だったが、一般ユーザーには負荷が高く報告が集まりにくい。
タスクトレイから直接、症状発生時の内部状態（app kind・IME 種別・
warm/cold・直近イベント列など）を自動添付して報告できる機能を検討した。

検討の過程で以下を決定した。

1. **受け口に GitHub Issues は使わない。** 公開リポジトリの Issue に
   投稿すると、添付ログに含まれうる composition テキストやウィンドウ
   タイトル等が全世界に公開されてしまう。プライバシー上許容できない
   ユーザーが一定数いると判断し、非公開のフォーム受付を別途用意する
   方針にした。
2. **報告時点での AI（LLM）による自動要約・トリアージは行わない。**
   将来的な拡張候補ではあるが、今回のスコープには含めない。
3. **受付バックエンドは Cloudflare（Workers + R2）を GCP より優先する。**
   awase の CI 基盤（GitHub Actions self-hosted runner）は既に GCP
   （[project_gcp_windows_spot_ci]）上にあり、その意味では GCP に寄せる
   方が管理主体を一本化できる利点はあった。しかし本用途（低頻度・
   突発的なフォーム送信を非公開ストレージに保存するだけ）では経済性が
   決め手になった:
   - Cloudflare Workers/R2 の無料枠はクレジットカード登録なしで
     利用開始でき、この規模のトラフィックなら実質恒久的に $0。
   - R2 はエグレス（ダウンロード）課金が無いため、後日ログを何度
     読み返しても追加コストが発生しない。GCS はエグレスに課金される。
   - Cloudflare はエッジ側でリクエストを捌くため、スパム/フラッドが
     無料枠上限に達する前に弾かれる。GCP は課金アカウント（カード）
     前提で動くため、予算アラート/クォータを事前設定しない限り
     乱用時に実費が発生しうる。
   - スパム対策には Cloudflare Turnstile をそのまま使える（追加の
     サービス契約が不要）。
4. **awase.cc 本体（GitHub Pages）は移行しない。** 「フォーム受付が
   必要 = 静的サイト全体を Cloudflare Pages 等へ移行しなければならない」
   と当初想定していたが、必要なのは POST を受けるエンドポイントだけ
   であり、`report.awase.cc` のようなサブドメインを Cloudflare Workers
   に向けるだけで足りる。awase.cc 本体の GitHub Pages ホスティングは
   変更しない。

## 決定

### 全体構成

```
タスクトレイ「不具合を報告...」
  → ダイアログ（自由記述 + 自動添付ログのプレビュー/編集）
  → report.awase.cc (Cloudflare Workers) へ POST
  → Cloudflare R2 に非公開保存（一般公開しない）
```

- `awase.cc`（GitHub Pages）: 変更なし。
- `report.awase.cc`（新設）: Cloudflare Workers。POST を受理し、
  Turnstile でスパム検証したうえで R2 に書き込む。
- 保存先: Cloudflare R2（非公開バケット）。閲覧はメンテナ側の手動確認を
  前提とし、この ADR の時点では自動処理（AI 要約等）を行わない。

### 選ばなかった選択肢

- **GitHub Issues**: 公開性がプライバシー要件と相容れないため不採用。
- **GCP Cloud Functions + GCS**: 技術的には成立するが、経済性
  （無料枠利用へのカード前提、R2 に対する GCS のエグレス課金、
  乱用時の実費リスク）で Cloudflare に劣ると判断し不採用。CI 基盤との
  管理主体一本化という利点はあったが、それを上回る決め手にはならなかった。
- **報告時 AI トリアージ（Claude API 等）**: 今回のスコープ外。将来
  追加する場合も、Workers から Claude API を叩く形で疎に追加できる
  はずで、今の設計を阻害しない。

## 保持するもの（変更しないもの）

- `awase.cc` の GitHub Pages ホスティングと DNS 設定。
- 既存の `docs/known-bugs.md` ベースの手動記録運用（フォーム経由の報告は
  これを置き換えるのではなく補完する）。

## 既知の限界・未決定事項

- 添付するログ/内部状態の範囲（直近何秒・どのイベント種別を含めるか）は
  未確定。[fix-requires-evidence](../../.claude/rules/fix-requires-evidence.md)
  が要求する「アプリ×IME×再現手順」を機械的に満たせる粒度を今後詰める。
- 送信データの形式（JSON か multipart か、添付ファイルの上限サイズ）は
  未確定。
- R2 に溜まった報告をメンテナがどう閲覧・トリアージするか（ダッシュボード
  無しで手動 DL するのか、簡易ビューアを別途作るか）は未確定。
- `report.awase.cc` の DNS 委譲・Cloudflare アカウントのセットアップは
  未実施。
- タスクトレイ側 UI（ダイアログのレイアウト、保存前プレビュー/編集の
  実装箇所）は未設計。
- Windows 実機での動作確認は当然ながら未実施（実装がまだ無い）。
