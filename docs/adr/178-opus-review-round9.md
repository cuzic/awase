## Blocker（v9で新規）

### B13. `.yab`の妥当性検証基準を「`awase::yab::lint`で致命的エラーが無いこと」に変更したが、**`lint`には「致命的エラー」という概念が無く、しかも構造的に不正な行を意図的に読み飛ばす**。この基準では検証として機能せず、壊れたバックアップが健全な工場出荷ファイルを上書きする

決定2「バックアップの妥当性検証」（224-235行）とチェックリスト#12は

> `.yab`は`YabLayout::parse`（`keyboard_model`に依存…）を使わない。代わりに
> `awase::yab::lint`（`keyboard_model`非依存）で**致命的なエラーが無いこと**
> のみを基準とする

としている。しかし実装を見ると成立しない。

1. **`lint`は「致命的エラー」を返さない**。シグネチャは
   `pub fn lint(input: &str) -> Vec<String>`（`src/yab/mod.rs:237`）で、
   返るのは警告文字列の`Vec`のみ。致命/非致命の区別が型にも戻り値にも存在しない。
   「致命的エラーが無いこと」を実装しようがない。
2. **`lint`は構造的に不正な行を意図的に読み飛ばす**。`src/yab/mod.rs:246-248`の
   コメントがそう明言している:
   > 構造的に不正な行（`process_yab_line` が `Err` を返す）は lint の対象外として
   > 読み飛ばす。lint はパースの成否から独立に動作する設計であり、
   > **構造検証そのものは `YabLayout::parse` の責務**。

   つまり、truncateされたファイル・まったく別形式のテキスト・バイナリ断片でも
   `lint`は**警告0件**を返しうる。これを「妥当」と判定して復元すると、
   round5 M2で塞いだはずの穴——「壊れたバックアップで健全な工場出荷ファイルを
   上書きし、復元機構自身が起動不能を作り出す」——がそのまま再発する。
   バックアップは`write_atomic`で書かれるが、それは「書きかけを読まない」ことしか
   保証せず、「中身が`.yab`として妥当」は保証しない（ディスクフルで0バイト、
   ユーザーが`backup\`へ別ファイルを置いた、等）。
3. 加えて、逆方向に「`lint`の警告0件」を基準にすると**同梱ファイル自身が
   弾かれうる**。`lint`はクォート不整合等を警告する設計で、ユーザーが
   カスタマイズした`.yab`が警告付きでも正常動作するのは通常のケースである
   （`awase-settings`は警告を表示しつつ保存を許す、`main.rs:1611-1614`）。

**M3の懸念自体は正しい**（`YabLayout::parse`は`keyboard_model`に依存し、
US配列環境では同梱JIS配列が列数超過で失敗しうる——`crates/awase-settings/src/main.rs`の
診断スキャンが`parse`を避けている理由そのもの）。しかし解決策が
「構造検証を一切しない」方向に振れてしまっている。

**要求**: 「構造検証はする、ただし`keyboard_model`に依存させない」形にすること。
具体案（いずれかを決定文に明記）:

- (a) **最も寛容なモデルでパースする**: `YabLayout::parse(text, KeyboardModel::<最大列数のモデル>)`
  で検証する。M3が問題にした失敗（US環境でJIS配列が列数超過）は、
  厳しい側のモデルで検証したときだけ起きるため、寛容な側で検証すれば
  環境非依存に構造だけを見られる。
- (b) **全モデルで試し、いずれかが成功すれば妥当**とする。`KeyboardModel`の
  バリアント数は少なく、コストは無視できる。
- いずれの場合も`lint`は**警告の表示・ログ用にのみ**使い、妥当性のゲートには
  しない（警告付きファイルを弾かない）。

チェックリスト#12もこの内容に書き換えること。あわせて**チェックリスト#13の
「`awase::yab`のパース関数（コア）でパース成功したものだけを」という表現と、
#12の「`lint`のみを基準とする」が現状矛盾している**ので、同じ基準に統一すること
（契機3の判定と復元前の妥当性検証は同じ関数を使う、と決定2も書いている）。

## Major

### M1. チェックリスト#1（両バイナリが必ず呼ぶ）に、`awase-settings.exe`の**非GUIサブコマンド経路**の除外が無い。`main()`先頭に置く実装だと、不具合報告を開くだけでユーザーのファイルが書き換わる

`crates/awase-settings/src/main.rs`には、`SettingsApp`を構築せずに早期
リターンする経路が少なくとも2つある。

- `main.rs:344-345`: `if args.iter().any(|a| a == "--bug-report") { return bug_report::run(..); }`
  ——タスクトレイの「不具合を報告」（ADR-095）から`launch_bug_report()`
  （`crates/awase-windows/src/app/mod.rs:595`）が起動する経路。
- `main.rs:354`付近: レジストリ操作のみ行い終了コードで結果を返すモード。

決定2は呼び出し位置を「`awase-settings`側は`SettingsApp::new`より前」と
書いており、これに**厳密に**従えば上記経路は自然に除外される。しかし
チェックリスト#1は「両方が、load/saveより前に呼ぶ」としか書いておらず、
チェックリストは「決定文が変わっても参照される独立節」という位置づけである
（38-39行）。実装者が`main()`の先頭に置く——上記早期リターンより**前**に
なる——のは自然な読み方であり、そうすると:

- 「不具合を報告」を開いただけで、`config.toml`/`.yab`がバックアップから
  復元される、あるいは埋め込み既定値で生成される。
- 「設定が勝手に既定値に戻った」という不具合を報告しようとしたユーザーの
  環境が、報告ダイアログを開いた時点で書き換わり、**再現しなくなる**。
  round2 M8で「不具合報告は現状を採取するのが目的であり、採取行為が状態を
  変えてはならない」として`find_config_path()`から副作用を外した判断と
  矛盾する。

（なお添付内容そのものは`awase.exe`側の`read_bug_report_attachments()`が
採取済みなので、添付が差し替わるわけではない。実害は「ユーザー環境の状態が
報告操作で変わる」ことと、調査の再現性が失われることにある。）

**要求**: チェックリスト#1に除外を明記すること。

> ただし`--bug-report`等、`SettingsApp`を構築せずに早期リターンする
> サブコマンド経路では呼ばない（呼び出し位置は`main()`先頭ではなく
> `SettingsApp::new`の直前）。

### M2. チェックリスト#3「呼び出し元は自分で改めて`AppConfig::load()`を呼ばない」が広すぎる。文字どおり適用すると、**意図的にディスクから読み直している既存実装**（`save_auto_start`）を壊す

チェックリスト#3（48-52行）は例外なしに
> 呼び出し元はこの戻り値を使い、自分で改めて`AppConfig::load()`を呼ばない

としているが、このリポジトリには**意図的にディスクから読み直す**実装がある。

- `AppConfig::save_auto_start`（`src/config.rs:912`）は内部で`Self::load(path)`を
  行う。doc コメント（`src/config.rs:895-906`）がその理由を明記している:
  > 自動起動のON/OFFはトレイメニュー（`awase.exe`）と設定画面
  > （`awase-settings.exe`、別プロセス）の両方から独立に切り替えられる。
  > どちらも「フォームで編集中の他の未保存の変更」を巻き込まないよう、
  > in-memory の `AppConfig` をそのまま保存するのではなく、この関数を
  > 通して都度ディスクから読み直す

  呼び出し元は`crates/awase-windows/src/tray.rs:1046`と
  `crates/awase-settings/src/main.rs:2043`。
- `awase-settings`は「適用」時に`AppConfig::load`で最新を読み直す経路も持つ
  （`main.rs:677`）。
- `update_check.rs:40`も独自に`AppConfig::load`する。

チェックリスト#3を文字どおり実装すると、`save_auto_start`をメモリ上の
`AppConfig`ベースに書き換えることになり、上記docが防いでいる
「未保存の編集を巻き込む」回帰が復活する（2プロセスが独立に
auto_startをトグルする、という本来の設計意図が壊れる）。

**要求**: #3の適用範囲を「**起動シーケンスにおける初期ロード**」に限定すると
明記すること。

> 起動時の初期ロードを呼び出し元が独自に行ってはならない（B10・B9対策）。
> 起動後の意図的な再読み込み（`AppConfig::save_auto_start`のディスク
> 読み直し、設定画面の「適用」時のリロード、更新チェック）はこの制約の
> 対象外であり、従来どおりでよい。

### M3. `UserDataGuard`が**スレッドを越える**必要がある。`awase-settings`の`config.toml`保存はワーカースレッド上で行われる

決定1の能力トークン方式は良い設計だが、`awase-settings`の保存経路は
UIスレッドではなくワーカースレッドで走る:

```
crates/awase-settings/src/main.rs:786-828
    std::thread::spawn(move || {
        ... config.toml.bak 退避 ...
        match clone.save(&config_path) { Ok(()) => tx.send(PendingSaveResult::Saved{..}) ... }
    });
```

契機1（`AppConfig::save()`成功後にバックアップ）をこのスレッド内で行うなら、
`UserDataGuard`は`Send`でなければならず、`SettingsApp`が保持する1個を
`move`するとUIスレッド側から失われる。素直な実装は
**`UserDataGuard`を実体のないゼロサイズの`Copy + Send`トークンにする**こと
（構築手段を`ensure_user_data_present()`だけに限る、という保証は
`Copy`でも維持できる——非公開フィールドを持つ unit-like struct にすればよい）。
もう一案は「バックアップはワーカースレッドで行わず、既存の
`PendingSaveResult`チャネルで結果をUIスレッドへ戻してから行う」。

**要求**: どちらを採るかを決定1に1行書くこと。書かずに実装に入ると、
`Send`でないトークンを`Arc`で包む／`unsafe impl Send`する／契機1を
「保存成功後」ではなく「次回起動時（契機3）」に先送りする、といった
場当たりの回避策が入りうる（最後のものは決定1の契機1そのものを無効化する）。

## Minor

### m1. チェックリスト#12と#13が異なる基準を書いている

#12は「`lint`のみを基準とする」、#13は「パース関数でパース成功したものだけ」。
B13の要求に沿って統一すること（決定2本文も「この基準は契機3の
『パース成功』判定にも同じ基準を使う」としており、3箇所の表現を揃える必要がある）。

### m2. 決定5の「純粋関数を**1つだけ**置く」が、決定1の`backup_config`/`backup_layout`と矛盾

決定1の能力トークン節（126-131行）はコアに3つの公開関数
（`ensure_user_data_present`・`backup_config`・`backup_layout`）を置く前提で
書かれている。決定5の「1つだけ」という表現は「復元のエントリポイントは1つ」の
意図だと読めるが、字面どおりだと矛盾する。「復元のエントリポイントは
`ensure_user_data_present()`ただ1つ」と書き換えること。

### m3. 復元書き込みが失敗してインメモリ既定値で継続する場合の戻り値と、契機3スキップの関係が未記載

決定2「失敗時の挙動」（239-241行）は「埋め込み既定値をインメモリで使って
起動を継続する」としているが、その場合の戻り値`AppConfig`が
「インメモリの既定値」であること、および決定2ステップ2の中断条件
（ロード失敗 → `.yab`復元と契機3をスキップ）が同時に成立することを
明記しておくこと。実装者が「インメモリで有効な設定が得られたのだから
`.yab`復元も進めてよい」と解釈すると、`layouts_dir`が既定値由来のまま
書き込みに進む（決定2が禁じたケース）。

### m4. チェックリスト#10の「CLI引数でconfigパスが明示されているか」の判定が、2クレートに重複している既存ロジックに依存する

`find_config_path()`は`crates/awase-windows/src/app/mod.rs:153-171`と
`crates/awase-settings/src/main.rs:5290-5300`に同型実装されており、後者の
doc コメントが「ここがズレていると実機バグの原因になる（2026-07-19に実際に
発生し確認済み）」と警告している。チェックリスト#10はこの判定に新たな
依存を1つ増やす。判定を共通化する（例: `awase::paths`に
`explicit_config_path_from_args()`を置く）か、少なくとも
「2箇所を同時に変更すること」を決定文に注記すること。

### m5. 移動したレビュー記録が`docs-frontmatter-convention`を満たしていない

`docs/adr/178-opus-review-round1.md`〜`round8.md`は移動済みだが、
`.claude/rules/docs-frontmatter-convention.md`が求める
「`docs/adr/`直下の補助資料は`type: companion-doc`のfrontmatterを持ち、
`docs/adr/index.md`の『補助資料』節に一覧がある」を満たしていない
（現状はfrontmatter無しで`# ADR-178 敵対的レビュー round1`から始まり、
index.md 333-344行の補助資料テーブルにも未登録）。8ファイル追加するので、
テーブルには1行でまとめる（例: 「178-opus-review-round1〜8.md ｜
ADR-178 敵対的レビュー記録 ｜ ADR-178」）のが index を肥大化させない書き方。

## 総評

v9でB11・B12は解消され、round8のMajor 3件も反映されている。B11対応の副産物として
「契機3の`.yab`捕捉が`awase.exe`限定だった」制約まで消えており、設計としては
むしろ改善している。チェックリストは15項目まで育ち、圧縮による欠落への対策として
機能している。

残るB13は、**round8 M3（`keyboard_model`依存で正当なバックアップが弾かれる）への
対応が、振り子の反対側に振れすぎた**もので、「構造検証はするが`keyboard_model`に
依存させない」（寛容なモデルでパース、または全モデルで試す）という中間解に
すれば両方の懸念を同時に満たせる。`lint`の実装（`src/yab/mod.rs:237-248`）が
「構造検証は`YabLayout::parse`の責務」と明言している以上、`lint`を検証ゲートに
することはできない。

Majorはいずれも「決定文は正しいが、チェックリストの表現が広すぎる／
既存実装との接続が書かれていない」種類で、数行で閉じる。特にM2
（`save_auto_start`のディスク読み直し）は、文字どおり実装すると
**2026-09-07に統合したばかりの実装を壊す**ため、適用範囲の限定を
明記しておくこと。

B13とMajor 3件を反映すれば、**次ラウンドは確認のみで収束し、実装フェーズへ
進んでよい**水準にある。
