# ADR-178: MSIアンインストール時のユーザーデータ喪失を自己修復（バックアップ+復元）で無害化する

## ステータス

**起草中v8（2026-09-17）。opus-adversarial-consultによるレビュー継続中
（round1〜7で計12件のBlockerを段階的に検出・解消、v8で反映）。**

## コンテキスト

[ADR-177](177-msi-restart-manager-graceful-shutdown.md)の実機検証で、MSIの
アンインストール（`msiexec /x`）が`%LOCALAPPDATA%\awase\config.toml`/
`layout/*.yab`を削除することが判明した。[ADR-099](099-config-preservation-on-upgrade.md)
決定1がZIP版に定めた「既定では残す」方針と非対称であり、ユーザーから
「ユーザーデータ削除するのおかしいね。残してほしい」との要望があった。

過去のADR-177実機検証・過去のOpusレビューでも繰り返し確認されている通り、
**この種の自己修復機構は「良い意図の修正がそのまま新しい重大バグを作る」
失敗パターンを何度も踏む**。本ADRはopus-adversarial-consultで7ラウンド、
計12件のBlockerを検出・解消してきた（詳細な経緯は本ファイルのgit履歴、
または各ラウンドの`opus-review-adr178-round*.md`を参照——ラウンドごとの
要約をこの節に逐一残すと、過去に実際に「v4にあった1文がv5・v6の圧縮で
落ちてBlockerが復活する」という事故が起きたため、**本節では経緯を圧縮
せず、決定文本体および下記「実装チェックリスト」に要件を直接持たせる**
方針に変更した）。

## 実装チェックリスト（圧縮による欠落を防ぐための独立節）

以下は決定文全体から導かれる、実装時に必ず満たすべき制約の一覧。
決定文の記述が変わっても、この一覧との整合を確認すること。

1. `awase.exe`・`awase-settings.exe`の**両方**が、`AppConfig::load()`／
   `.yab`の読み込み／`AppConfig::save()`のいずれよりも**前**に
   `ensure_user_data_present()`を呼ぶ（決定2）。
2. `ensure_user_data_present()`は`config_path`（exe隣の絶対パス）と
   `exe_dir`と`backup_dir`のみを引数に取り、**内部で**`AppConfig::load()`
   → `validate()`を行って`layouts_dir`を得る。呼び出し元が先に
   `AppConfig::load()`を呼んで`layouts_dir`を渡す設計は**禁止**
   （B10。呼び出し元が2重にロードすると、検証した内容と実際に使われる
   内容がずれ、B9の損失経路が復活する）。
3. `ensure_user_data_present()`の戻り値には、**検証済みの設定
   （`AppConfig`）自体を含める**。呼び出し元はこの戻り値を使い、
   自分で改めて`AppConfig::load()`を呼ばない。
4. バックアップの書き込み（保存成功時・起動時ロード成功時）は、
   `ensure_user_data_present()`が返す**能力トークン**を持つ場合にのみ
   実行できる（グローバルな`OnceLock<bool>`等の暗黙フラグは使わない
   ——`cargo test`のスレッド並列実行でテスト間の状態漏れが起き
   フレーキーになるため。トークンは型で強制する、決定1参照）。
5. バックアップ対象は`config.toml`と同梱6ファイル
   （`nicola.yab`・`nicola_keytop.yab`・`nicola_us.yab`・`nicola_f.yab`・
   `nicola_kb232.yab`・`nicola_kakutei.yab`）**のみ**。ユーザー自作の
   `.yab`（`layouts_dir`内だが同梱名でないもの）はバックアップ・復元
   いずれの対象にもしない（MSIが配置・削除しないファイルはそもそも
   本ADRが守る対象外、決定1参照）。
6. `config.toml`の復元条件と`.yab`の復元条件は**異なる**
   （`config.toml`はファイル欠落自体を既定値で救う、`.yab`は
   バックアップが無ければ欠落を放置する——決定2参照）。
7. `.yab`が1本も有効でない場合の救済（決定5）は、復元条件とは別機構
   であり、存在しない同梱ファイルのみを埋め込み既定値から書き戻す
   （既存の壊れたファイルは上書きしない）。
8. 復元・救済のいずれも、`exe_dir`の祖先に`target`という名前の
   ディレクトリが含まれる場合は行わない（開発ビルド除外、決定2）。
9. `GeneralConfig::default()`のserializeを埋め込み既定値の代用にしない
   （決定3）。`validate()`前の生の設定値を復元判定に使わない
   （決定2フェーズ2）。

## 決定

### 決定1: バックアップ対象を絞り込んだ上で、保存の都度と起動時ロードの都度にMSI管理外へバックアップする

**バックアップ先**: `<exe_dir>\backup\`（`INSTALLDIR`配下、例:
`%LOCALAPPDATA%\awase\backup\`）。MSIの`File`/`RemoveFile`テーブルに
載らないためアンインストールを生き延びる。

**バックアップ対象範囲（M2対応、契機・復元側を統一）**: `config.toml`と
同梱6ファイルの`.yab`**のみ**。契機（下記1〜3）・復元（決定2フェーズ3）
のすべてでこの範囲に揃える。ユーザーが`layouts_dir`に自作した
`my.yab`等はバックアップ対象にしない——MSIが配置・削除するのは同梱
ファイルのみであり、本ADRが解決したい問題（MSI由来の喪失）の範囲を
超えないようにするため（自作ファイルをMSIが消すことはそもそも無い）。

**バックアップ契機**（いずれも「実行のゲート」節の対象）:

1. `config.toml`: `AppConfig::save()`成功後。保存先パスが
   `resolve_next_to_exe("config.toml")`と一致する場合のみ。
2. `layout/*.yab`: `layout_write_to_path()`成功後。保存先が現在の
   `layouts_dir`配下であり、かつファイル名が同梱6ファイルのいずれかと
   一致する場合のみ。
3. 起動時、`ensure_user_data_present()`が内部でロードした
   `config.toml`/`.yab`（同梱6ファイル名のみ、`LayoutEntry::scan_all`が
   読む全`.yab`のうち同梱名と一致するもの限定）の内容がバックアップと
   異なれば、バックアップを更新する。

**バックアップを作成・更新しない条件**: 対象ファイルの内容が
（決定3の正規化後）現在の埋め込み既定値と一致する場合は、バックアップを
作成・更新しない（既存のバックアップも上書きしない）。未カスタマイズ
ユーザーのバックアップに旧バージョンの工場出荷値が保存され続け、
将来の既定値改善が届かなくなるのを防ぐ。

**この副作用と、初期化操作を残す方法**: 「既存も上書きしない」ことに
より、意図的に既定値へ戻す／削除して初期化する操作が、バックアップが
残っている限り無効化される。決定6の通知に、**どのファイルを復元したか**
を含め、「該当ファイルを`backup\`から削除してください」という個別の
案内を示すことで、初期化の逃げ道を確保する（フォルダ単位の削除案内
だと、他のカスタマイズしたファイルのバックアップまで巻き添えで失われる
ため、ファイル単位で案内する）。

**書き込み方式**: `crate::fs_atomic::write_atomic`を使う。

**実行のゲート（M1対応、能力トークン方式）**: バックアップ書き込みは、
グローバルな暗黙フラグ（`OnceLock<bool>`等）ではなく、
`ensure_user_data_present()`が返す**明示的な能力トークン**を要求する
形で実装する。

```
pub struct UserDataGuard { /* 非公開フィールド、構築手段は下記のみ */ }
pub fn ensure_user_data_present(..) -> (RestoreOutcome, UserDataGuard)
pub fn backup_config(guard: &UserDataGuard, ..)   // トークンなしでは呼べない
pub fn backup_layout(guard: &UserDataGuard, ..)
```

`awase.exe`側は`AppState`に、`awase-settings`側は`SettingsApp`にこの
トークンを保持させる。これにより「復元ステップを通らないプロセスは
バックアップを汚さない」という保証がコンパイル時に効き、`cargo test`の
スレッド並列実行下でもテスト間の状態漏れが起きない（トークンを作る／
作らないかだけで両ケースを独立に検証できる）。

（開発ビルドでの実際の挙動、M3対応・記述を実態に合わせる: 上記の対象
限定〈`resolve_next_to_exe`との一致判定〉と既定値一致判定の両方により、
`cargo run`実行時は実質的に**バックアップもほとんど動作しない**
——`cargo run`では実際に読み書きされるのは`resolve_relative_to_exe()`の
ワークスペースルートフォールバックが指す`<root>/config.toml`であり、
これは`resolve_next_to_exe("config.toml")`＝`<root>/target/debug/config.toml`
とは異なるパスなので契機1のゲートを満たさない。さらに`<root>/config.toml`
は`include_str!`が読む埋め込み既定値そのものなので、内容が既定値と一致し
契機3もバックアップを作らない。「開発ビルドで機構を動作確認できる」という
効果は実際には無く、これは意図した挙動ではなく単なる帰結として正直に
記載する——実害はない。）

### 決定2: 復元は「読み取り」と「書き込み」を分離した単一関数として実装し、両バイナリの起動シーケンスから必ず呼ぶ

**呼び出し要件**: `awase.exe`・`awase-settings.exe`の**両方**が、起動
シーケンスの中で、`AppConfig::load()`／`.yab`の読み込み／
`AppConfig::save()`のいずれよりも**前**に`ensure_user_data_present()`を
1回だけ呼ぶ。`awase.exe`側は`bootstrap.rs`の起動シーケンス先頭、
`awase-settings`側は`SettingsApp::new`より前とする。

**呼び出し元が改めて`AppConfig::load()`を呼ぶ設計は禁止する（B10対応、
決定5のシグネチャと整合させる）**: `ensure_user_data_present()`は
**内部で**`AppConfig::load()`→`validate()`を行い、`layouts_dir`を含む
検証済みの設定を**戻り値として返す**。呼び出し元はこの戻り値を使い、
自分で改めてロードしない。理由:

- 呼び出し元が別途`load()`する設計だと、`layouts_dir`（`validate()`後の
  値）を`ensure_user_data_present()`の**呼び出し前に**知る必要があるが、
  それは`ensure_user_data_present()`自身がロードする前には存在しない
  値であり、両立しない。
- 仮に「呼び出し元が先にload」という順序で実装すると、
  `ensure_user_data_present()`がバックアップから復元した内容と、
  呼び出し元が先に読んでいた（復元前の）内容がずれる。ユーザーが
  この「先に読んだ古い内容」を基準に1項目だけ変更・保存すると、
  復元済みのファイルが古い内容で上書きされ、以後バックアップも
  同じ内容で汚染される——B9で解消したはずの損失経路が再発する。
- 2プロセス（`awase.exe`・`awase-settings.exe`）が同時に起動する
  経路（`warn_layout_fallback`経由）があるため、「関数内で検証した
  内容」と「呼び出し元が別途読んだ内容」がプロセス間の書き込み
  タイミング次第でずれるリスクも避けられる。

**読み取り（既存パスの解決）は変更しない**: `resolve_relative_to_exe()`
をそのまま使う。

**開発ビルドの除外**: 復元（および決定5の救済）は、**引数で渡された
`exe_dir`**の祖先に`target`という名前のディレクトリが含まれる場合には
行わない。`current_exe()`の呼び出しは呼び出し元（`awase-windows`/
`awase-settings`）に残し、コア関数は`exe_dir: &Path`を受け取るだけに
する——`cargo test`実行時のテストバイナリも`target`配下にあるため、
コア関数内部で`current_exe()`を直接呼ぶ実装だと決定7の自動テストが
軒並み除外規則に引っかかってしまう。この判定は開発ビルド検出の
ヒューリスティックであり、万一インストール先パスに`target`という
名前のディレクトリが偶然含まれる場合は自己修復が無効になる
（安全側に倒れるため許容する）。

**書き込み（復元先の決定）**: 開発ビルドでない場合に限り、
`resolve_next_to_exe()`（`src/paths.rs`新設、存在チェックなしでexe隣の
絶対パスを構成する）を使う。

- `config.toml`の復元先: `resolve_next_to_exe("config.toml")`。
- `layout/*.yab`の復元先の可否判定: `validate()`後の
  `config.general.layouts_dir`が相対パスである場合に限り、復元先を
  `resolve_next_to_exe(layouts_dir)`とする。復元先ディレクトリが
  存在しなければ`create_dir_all`で作成する（この手順は決定5の救済
  経路が発動する場合にも共通して適用される）。

**実行順序（関数内部）**:

1. `config.toml`の復元（後述「`config.toml`の復元条件」を満たす場合。
   引数不要、常にexe隣固定。**復元元は、バックアップが存在しかつ
   妥当ならバックアップ、無ければ埋め込み既定値**）。
2. `AppConfig::load()` → `validate()`。**このロードが失敗した場合
   （分類を問わず——`NotFound`・`Dangerous`いずれでも）、以降の`.yab`
   復元と決定1の契機3は共にスキップする。** `.yab`復元は`validate()`
   が成功して得られた`layouts_dir`の値でのみ実行し、
   `AppConfig::default()`の値で代用してはならない。
3. 上記「書き込み」節の条件を満たす場合、同梱6ファイルそれぞれに
   ついて後述「`.yab`の復元条件」を評価し、満たすものを復元する。
   復元元は、バックアップが存在しかつ妥当ならバックアップ、無ければ
   埋め込み既定値。
   （**別機構**、決定5参照）上記の復元を行ってもなお有効な`.yab`が
   1本も無い場合にのみ、決定5の救済が発動し、存在しない同梱`.yab`を
   埋め込み既定値から書き戻す。既存の（パースできない）ファイルは
   上書きしない。
4. 決定1の契機3（バックアップ更新）を実行する。
5. 検証済みの設定（`AppConfig`）と`RestoreOutcome`（ファイルごとに
   「何もしなかった／バックアップから復元した／既定値から生成した／
   失敗した」を持つ、決定6が要求する粒度）と`UserDataGuard`を返す。

これら1〜5を単一の関数（`ensure_user_data_present()`）としてコア`awase`
クレートに実装する（決定5参照）。`find_config_path()`はパスを解決する
だけの純粋な関数のまま維持する。

**復元条件は`config.toml`と`.yab`で異なる**:

- **`config.toml`の復元条件**: ファイルが「存在しない」**または**
  「内容が埋め込み既定値とバイト一致し、かつバックアップが存在し、
  かつバックアップの内容が既定値と異なる」場合に復元する（ファイルが
  無ければ実質的に埋め込み既定値へ落ちる——これが無いとアプリが
  起動できないため）。
- **`.yab`の復元条件**: **「バックアップが存在し妥当である」場合に
  限り**復元する（＝「存在しない＋バックアップあり」または「既定値
  一致＋バックアップ差分」）。**バックアップが無い`.yab`は、存在しな
  くても復元しない**（ユーザーが意図的に削除した同梱配列を毎起動
  復活させないため。起動不能は決定5の救済が別に担う）。

**バックアップの妥当性検証**: 復元の直前に、バックアップの内容を
パースして妥当性を確認する（`config.toml`は`toml::from_str`、`.yab`は
`YabLayout::parse`）。不正な場合は復元せず警告ログのみとする。

**書き込み方式**: `crate::fs_atomic::write_atomic`を使う。

**失敗時の挙動**: 復元の書き込みが失敗しても`panic`せず、ログ警告の
うえ既存のエラーダイアログ経路に委ねる。書き込みが失敗した場合でも
埋め込み既定値をインメモリで使って起動を継続するフォールバックを持つ。

### 決定3: 埋め込み既定値はビルド時にリポジトリのファイルから直接取り込み、生成元を`AppConfig::default()`にしない

`include_str!("../config.toml")` / `include_str!("../layout/nicola.yab")`
等、コア`awase`クレート（`src/`直下）からリポジトリルートの実ファイルを
直接参照する。`GeneralConfig::default()`のフィールドをserializeして
生成する実装は禁止する。

**バイト一致の頑健化**: 比較前に改行正規化（`\r\n`→`\n`）とBOM除去を
行う。`.github/workflows/release.yml`に「`dist/config.toml`がリポジトリの
`config.toml`とバイト一致すること」「`dist/layout/*.yab`が`layout/*.yab`
とバイト一致すること」を検証するCIステップを追加する。

### 決定4: 「完全に削除したい」場合の案内を更新する

MSI版・ZIP版ともに、完全削除の案内を「`%LOCALAPPDATA%\awase`を削除
してください」に更新する。案内先は`docs/index.html`・`docs/index.en.html`
にアンインストール手順の節を新設する。ZIP版`scripts/uninstall.ps1 -Purge`
は変更不要。

### 決定5: `.yab`側の救済手段と、実装配置

**`.yab`のDangerous相当ケースの救済手段**: `layouts_dir`に有効な`.yab`
が1本も無い場合、`show_no_layouts_dialog`で起動を諦める**前に**、
埋め込み既定値からの復旧を試みる（決定2の「別機構」節参照）。救済後も
なお有効な`.yab`が0本なら従来どおり`show_no_layouts_dialog`。

**`config.toml`のDangerous分類**: `classify_load_error`が`Dangerous`に
分類した場合は自動復元しない。既存の`config.toml.bak`退避に加えて、
`awase-settings`のUIで「バックアップから復元しますか？」とユーザーに
提案する。`ConfigLoadState::NotFound`分岐は、開発ビルドや復元の書き込み
自体が失敗した場合には決定2導入後も到達しうるため、削除しない。

**実装配置（B10対応、シグネチャを決定2のフェーズ構成に合わせる）**:
コア`awase`クレートに、埋め込み既定値（`include_str!`群）と、以下の
純粋関数を1つだけ置く。

```
pub fn ensure_user_data_present(
    exe_dir: &Path,       // OS依存の解決結果（current_exe().parent()）のみ呼び出し元から
    config_path: &Path,   // 復元・ロード対象。exe隣の絶対パス（resolve_next_to_exe の結果）
    backup_dir: &Path,
) -> (RestoreOutcome, ValidatedConfig, UserDataGuard)
```

（正確なシグネチャ・型名は実装時に詰める。）`layouts_dir_setting`を
引数として受け取る設計は**採らない**——`layouts_dir`は関数内部の
`AppConfig::load()`→`validate()`で得る値であり、呼び出し元がこれを
関数呼び出し**前**に知ることはできない（B10）。`AppConfig::load`も
`validate()`もコア`awase`クレート（`src/config.rs`）にあるため、これを
関数内部で呼んでもADR-019（コアのOS非依存）には抵触しない。相対/絶対の
判定・`target`配下判定はいずれもコア側の1箇所に閉じる。

### 決定6: 復元・生成をユーザーに通知する

`tracing::info!`に加えて、トレイ通知または`awase-settings`のステータス
欄で、`RestoreOutcome`が示す**ファイルごとの結果**（例:「`config.toml`を
バックアップから復元しました」「`nicola_keytop.yab`を既定値で生成しま
した」）を表示する。既定値に戻したい場合は、通知に含めたファイル名を
使って「`backup\<ファイル名>`を削除してください」と案内する（フォルダ
単位の削除案内はしない、決定1参照）。MSI`LaunchApplication`による
インストール直後の自動起動では、復元時点でトレイアイコンがまだ生成
されていない可能性が高いため、トレイ生成後に通知をdeferする処理を
持たせるか、`awase-settings`側のステータス欄に残す形にするかを実装時に
決める。

### 決定7: 回帰テスト

原則としてホストターゲット（Linux、`cargo test --lib`）で実行できる
自動テストとして書く（`ensure_user_data_present()`が純粋関数であり、
能力トークン方式〈決定1〉によりテスト間の状態漏れが起きない設計の
ため）。ただしB1修正が依拠する唯一の実機前提だけは自動化できないため、
実機確認を1件残す。

- 埋め込み既定値をparseすると`layouts_dir == "layout"`かつ
  `default_layout`が埋め込み`.yab`リストに存在するという不変条件。
- 3箇所同期テスト（コア`awase`の定数・`layout/`の実ファイル・
  `wix/main.wxs`のコンポーネント）。
- **B1の直接再現（config.toml）**: 工場出荷値の本体＋ユーザー設定入り
  バックアップの状態から復元し、本体がユーザー設定になることを確認する。
- **B1・B8の直接再現（.yab、バックアップ有りの一般規則経路）**:
  `layout/*.yab`が6本とも工場出荷値で「存在」し、バックアップにユーザー
  編集版がある状態から復元し、`.yab`がバックアップの内容に復元される
  ことを確認する。
- **B6の直接再現（バックアップ無し、決定5の救済経路と明示的に分離）**:
  `layout\`ディレクトリごと存在せず、かつバックアップも無い状態から
  復元し、ディレクトリが作成され6本とも埋め込み既定値から書き戻される
  ことを確認する（この経路は決定5の救済であり、一般規則ではないことを
  テスト名に明記する）。
- **B4の直接再現**: B1テストの初期状態から、復元後に本体がユーザー
  設定になっていることに加え、バックアップ側が上書きされていないこと
  を確認する。
- **B7の直接再現**: `exe_dir`が`target/debug`相当のパスである場合、
  復元が一切発火しないことを確認する。
- **B9の直接再現（能力トークンで型的に保証）**: `UserDataGuard`を
  持たない状態でバックアップ書き込み関数を呼ぶコードが**コンパイル
  できない**ことを確認する（型システムによる保証のため、実行時テスト
  としては「トークンを経由しないバックアップ経路が存在しない」ことの
  確認に限定される）。
- M1の直接再現: バックアップの無い同梱`.yab`を削除した状態で起動しても
  復活しないことを確認する。一度も編集していない`config.toml`を保存
  してもバックアップが作成されないことも確認する。
- B2（CWD誤書き込み）の直接再現。
- B3（バックアップ汚染）の直接再現。
- B5の回帰確認: `src/paths.rs`の既存テスト
  （`absolute_path_is_returned_unchanged`、
  `falls_back_to_workspace_root_when_run_from_cargo_target_dir`）が
  変更されないことを条件とする。
- 手編集した`config.toml`が、次回起動時のロード成功をトリガーに
  バックアップへ捕捉されることを確認する。
- release.ymlに、`dist/`配下と埋め込み既定値のバイト一致を検証する
  ステップを追加する。

**実機確認（自動化不可）**: B1修正は「MSI再インストール時、
`%LOCALAPPDATA%\awase\config.toml`と`layout\*.yab`が、埋め込み既定値と
（正規化後）バイト一致する内容で再配置される」という前提の上に成り
立つ。この前提は実機で確認されていない。以下の手順を実機で1回行う:

> MSIインストール → `config.toml`/`nicola_keytop.yab`を編集 →
> `msiexec /x` → **同じMSIを再インストール** → **起動前**に
> `%LOCALAPPDATA%\awase\config.toml`と`layout\*.yab`を採取し、
> **検証に使ったMSIをビルドしたコミット時点**の`config.toml`/
> `layout/*.yab`と（改行正規化・BOM除去後に）バイト一致することを
> 確認する。その後起動し、編集内容が復元されることを確認する。

「起動前に採取して比較する」ことが重要——起動後に確認すると復元が
既に済んでおり、前提の検証にならない。

## この設計で解決されること・されないこと

**解決されること**:
- MSIアンインストール→再インストール後、`config.toml`/`layout/*.yab`が
  出荷時の既定値で再配置されても、次回起動時にバックアップから実質的に
  復元される。
- `layouts_dir`に有効な`.yab`が1本も無い状態でアプリが起動不能になる
  事態を、埋め込み既定値からの復旧で防ぐ。
- ユーザーが使わない同梱配列を削除して整理しても、毎起動復活しない
  （バックアップが無い`.yab`は復元対象外）。
- テキストエディタでの手編集も、次回起動時のロード成功をトリガーに
  バックアップへ捕捉される。
- `awase.exe`・`awase-settings.exe`のどちらを先に起動しても、両方が
  復元ステップを通り、かつ関数の戻り値だけを使う設計により、片方だけが
  復元前の古い内容を基準に保存してバックアップを汚染する事態を防ぐ。
- バックアップの書き込みが能力トークンによって型レベルでゲートされ、
  復元ステップを通らないプロセスはバックアップを一切汚せない。
- 開発ビルドでは復元・救済が一切動作せず、リポジトリのトラッキング
  済みファイルを汚染しない（バックアップも実質的に動作しない）。

**解決されないこと**:
- MSIのアンインストール自体は引き続き`config.toml`/`layout/*.yab`を
  削除する。
- `Dangerous`分類のケースは自動復元されない。
- ユーザーが`layouts_dir`を明示的に別ディレクトリへ向けている場合、
  そのディレクトリへの自動復元は行わない。
- ユーザーが`layouts_dir`に自作した（同梱6ファイルに含まれない）
  `.yab`は、バックアップ・復元いずれの対象にもならない。
- ユーザーがconfig.tomlを壊したまま再起動を繰り返す間は、`.yab`復元も
  連動してスキップされる。
- ポータブルZIP運用でexeごと別の場所へ移動すると、`backup\`もその
  exeに付随して移動するため、旧場所のバックアップは参照されなくなる。
- 「`config.toml`/`layout/*.yab`を意図的に既定値へ戻す」「削除して
  初期化する」という操作は、バックアップが残っている限り無効化される
  （決定6の通知案内で該当ファイルの`backup\`削除手順を示す）。
- インストール先パスに`target`という名前のディレクトリが偶然含まれる
  場合、自己修復機構全体が無効になる（安全側に倒れるため許容）。
