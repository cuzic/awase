# ADR-222: 不具合報告のログは ring の中身を圧縮して送る(打鍵は最低 10 分)

## 背景(実測、report `01M42BME26GDQ3CJ4F5DMGT0MP`。Opus round1 で照合済みの値)

- 打鍵(KeyInput)は 165 秒・73 件しか残らなかった。他レーンは 13〜16 分残っていた(GjiFsmTransition 966 秒、ConvClassifyCall 786 秒)。
- **主因はダンプ時のバイト配分**: `journal_policy.rs` の `RESERVED_PERCENT` で打鍵は 15%、さらに余り予算の配分優先度(`lane_priority`)も最下位。
  (204,800−2)×0.15 = 30,719B ÷ 打鍵 1 件約 418B ≒ 73 件。ring(512 件)には 512 件あり、うち 439 件を予算が落とした。
  ring の大きさが主因だったかは、この報告からは判定できない。
- 訂正: 「追い出し 17,464 件」は打鍵レーンだけの件数(全レーン合計は 28,966 件)。打鍵 1 件は平均 418B(旧記述の 460B は誤り)。
  journal 複製行は awase.log の 9.8%(旧記述 8% は誤り)。
- 切り詰めは 2 段ある: `journal.rs::to_json_capped`(レーン配分あり)と、`bug_report.rs::truncate_journal_json_tail`(レーンを区別しない末尾切り)。
- 打鍵頻度(`awase.log.old`、1 分最大 475 件。`journal: key input` 行の件数)。5 分間の最大 1,167 件は未再確認。
- 圧縮率(journal 204,753B): gzip -9 15,886 / xz -9e 10,876(preset 6 は 12,112)。awase.log 204,800B: gzip 19,867 / xz -9e 14,288。差は約 1.4 倍。
- LINE への最初のフォーカスは、クリックの約 8.8 分前(T−529s)にもあった(旧記述の「約 6 分前」は別の回)。10 分では余裕が約 71 秒しかない。
- awase.log が DEBUG 行で埋まるのは `RUST_LOG` を設定した環境だけ(既定は `info`、`bootstrap.rs:152`)。この報告は開発者本人の環境。
- 512KiB は ADR-095 実装時の暫定値で、Cloudflare 側の制約や費用の実測に基づかない。

## 決定

- **D1 予算で絞らず、ring の中身を全部ダンプする**: `RESERVED_PERCENT` / `select_tail_within_budget` / `to_json_capped` / `DumpTruncated` を削除した(実装済み)。
  圧縮すれば journal 全体で数 KB〜十数 KB で、絞る理由が無い。`DumpTriggered` に**レーンごとの ring 内最古の時刻**(`oldest_elapsed_ms_*`)と追い出し件数を記録する。
  `truncate_journal_json_tail`(レーンを区別しない末尾切り)は、本体が上限を超えたときの**最終手段**として残した(圧縮前の上限を半分ずつ縮めて再圧縮。
  当初案の「時間窓を短くして再圧縮」は、打鍵以外のレーンが時間でなく件数で ring に入るため採らなかった)。縮めたことは journal の `ReportEdited` の印に残す(D11)。
- **D2 打鍵 ring を最低 10 分に広げ、ダンプ時は打鍵だけを直近 10 分に絞る**: ring は最大頻度(約 4,750 件/10 分)でも溢れない 8,192 件(他レーンは State/Timing 2,048・Actuation 1,024)。
  ただし通常の頻度では ring に 10 分をはるかに超えて(平均で約 104 分、報告直前の頻度で約 5.4 時間)溜まるので、**ダンプ時に KeyInput だけを直近 10 分に絞る**
  (`journal_policy::REPORT_KEY_INPUT_WINDOW_MS`。所有者が許容したのは「直近 10 分」の全打鍵。Opus round2 B-E1)。窓の判定は、畳み込まれた自動リピート(ADR-169)の
  `elapsed_ms`(最初の押下)ではなく `max(elapsed_ms, last_elapsed_ms)` で行う。他のレーンは打鍵の内容を含まないので全件出す
  (FocusTransition のウィンドウ情報などは長時間ぶんになる)。事前確保は 512 件までに抑えた。ダンプ時間(メインスレッドで数 MB を serde)は実機ログ
  `[journal] report dump: N entries, M bytes, T ms` で測る(未測定)。外部注入の打鍵(畳み込まない)で ring が溢れた場合は、`oldest_elapsed_ms_key_input` で範囲が分かる。
- **D3 gzip で圧縮して送る**(所有者決定 2026-10-04): `flate2`(既存依存)。xz は約 1.4 倍小さいが、2MiB に対して決め手にならず、新クレートが要るため採らない(旧版の xz 方針を撤回)。
  **Worker は解凍しない**(無料プランの CPU 時間と解凍爆弾を避けるため。当初案の「Worker が `DecompressionStream('gzip')` で解凍して中身を検証」は採らなかった。したがって
  「gzip なら Worker で中身を検証できる」という選定理由は、現状では使っていない)。形式(長さ上限・4 の倍数・先頭 `H4sI`・先頭 4KiB の文字種・末尾のパディング。全文の文字種は見ない)だけを検証し、展開は調査側で
  展開後 64MiB 上限・途中切れ検出つきで行う。圧縮は送信スレッドで 1 回だけ行う(説明欄の入力ごとの再圧縮は禁止)。1 本の上限 `MAX_LOG_GZ_BASE64_CHARS` はクライアントも同じ値を持ち、超えたら縮める。
- **D4 schema_version を 4 に上げる**: 古い Worker は新フィールドを黙って捨てて 201 を返す(`index.ts:608-638` は許可項目だけで組み直す)ため、
  上げないと「ログだけ消えた報告」が気付かれずに溜まる。新 Worker は 3 と 4 の両方を受理し、**Worker を先にデプロイ**してからクライアントを出す。
  ボディ上限 2MiB の引き上げも同じ順序(クライアントが先だと 413)。
- **D5 ボディ上限を 2MiB に引き上げる**(所有者決定): 試算(Opus): 打鍵 4,750 件 ≒ 125KB(xz)、journal 他 ≒ 11KB、awase.log(DEBUG)10 分 ≒ 270KB で、
  base64 込み約 545KB。一般ユーザー(`info`)ならさらに小さい。2MiB には 2.6〜4 倍の余裕がある。
- **D6 専用バイナリ形式は採らない**: xz に対する効果が約 1/2 に留まり、`jq`/`grep` で直接読めなくなる(標準の `base64 -d | xz -d` で読める範囲に留める)。
- **D7 Worker は旧フィールドの報告も無期限に受理する**: v1 保守ライン(`v1-main`/`v1-develop`)の旧クライアントは今後も旧フィールドで送り続ける。
  新フィールドの検証: base64 の文字種・`length % 4 == 0`・長さ上限・圧縮形式のマジック(xz なら `/Td6WFoA`、gzip なら `H4sI`)・`attach_log=false` のとき null。
  旧フィールドと新フィールドが両方あれば拒否する。
- **D8a Worker の CPU 時間(Workers Free は 10ms/リクエスト)**: プランは API で確認できなかった(OAuth トークンに権限なし)。ADR-095 の記録(無料枠を理由に選定・R2 有効化でカード登録なし)から Free を前提とする。
  CI(GitHub ランナー、Node/V8)での計測は、本体 1.75MiB で旧処理(全文の正規表現 + 整形つき直列化)13.3ms → 現行(先頭 4KiB と末尾だけの検証 + compact な直列化)11.4ms(warm、比 0.86)。
  復号・解析・直列化の基本コストだけで約 11ms あり、本体上限いっぱいの報告は Free の 10ms 前後かそれ以上になりうる。コストは本体の大きさにほぼ比例し、
  現実的な報告(10 分ぶんの打鍵 + ログを gzip。0.3〜1MiB)は約 2〜6ms の見込み。実測は本番デプロイ後に `wrangler tail` の `cpuTime` で行い、超えるなら
  Paid プラン / 本体上限の引き下げ(1MiB 等)/ 検証の軽量化から選ぶ(手順は `services/report-worker/README.md`)。R2 に保存する JSON は整形(インデント)しない。
- **D8 R2 には JSON 1 オブジェクトのまま保存する**: 巨大フィールドは base64 のまま保存し、調査スクリプトが解凍する(書き込みを分けると一部だけ失敗する状態が生じる)。
  調査スクリプト側は、解凍後のサイズに上限を設ける(解凍爆弾対策、例 64MiB)。
- **D9 旧 D3(awase.log の間引き)・旧 D4(KeyInput の省略表現)は今回見送る**: 間引き対象([ime-io]、Timer set/killed、MSAA 分類)は
  BUG-027/031/054/111/113/126 などで決定的な証拠だった。間引いても圧縮後で約 35% しか減らず、2MiB に対して不要。
  代わりに考えた (a) `[actuation-record]` の長い固定文言を出力元で短くする、(b) `awase::journal` の複製行だけは除く、は**今回は実装していない**(後続の候補)。
  KeyInput の省略は、プレビューのサイズが問題になった場合に、情報を落とさない形式(往復変換テストつき、平均約 67B/件)としてだけ採る。
- **D10 awase.log の時間窓**: 時間(行頭の RFC3339)で切り、`awase.log` と `awase.log.old` の両方を読む(ローテーション直後は新ファイルがほぼ空)。
  時刻の無い継続行は直前の行に付ける。**基準はログ自身の最後の時刻ではなく壁時計の `now`**(既定の `info` ではログがまばらで、最後の行が数十分前のことがあり、
  journal と時間帯がずれるため。Opus round2 M-C1)。窓内の行が少なくても末尾 200 行は残す(`APP_LOG_MIN_ROWS`)。最大 40MB の読み込みと解析は
  ウィンドウ生成の中で同期実行すると初回表示が遅れて背面で開く(BUG-73)ので、別スレッドで行い、読み込み中は送信できない。
- **D11 送信内容とプレビューの関係(Opus round1 B1・round2 B-A1/B-E2/M-A2/M-E3/M-E4)**:
  ログは読み取り専用の一覧(**既定で開く**。ADR-095 決定4 条件2)。切り詰められた行・複数行の行は、**マウスを乗せると全文が出る**。削除は 1 行ずつのほか、
  「これより前をすべて削除」と journal の「打鍵の行をすべて削除」。ログを送るかは**チェックボックスの値とプレビューの `attach_log` の両方が true のときだけ**
  (プレビューを編集済みだと古い値が残り、チェックボックスを外してもログが送られる事故を防ぐ)。送信内容の journal の先頭に、削除件数と縮めたかを記した
  `{"type":"ReportEdited","journal_rows_deleted":N,"app_log_rows_deleted":M,"shrunk":bool,...}` の印を入れる(調査側が「awase がキーを落とした」と誤読しないため。
  JSON 配列の中なので Worker の変更は要らない)。プレビューの `log_excerpt_gz` には、送信時に何が入るかを示す文言を表示する。
- **D12 一時ファイルの削除**: journal のダンプ(`%TEMP%/awase_journal_*.json`、直近 10 分の全打鍵が平文)と診断情報は、ウィンドウを閉じるときに送信の成否に関わらず削除する。
  送信失敗時の再送用ファイル(`awase_bug_report_failed_*.json`)は別。

## 所有者決定(2026-10-04)

1. 圧縮方式は **gzip**(D3)。
2. プレビューは **ログを読み取り専用表示にし、行の削除だけを許す。送信時に表示中の内容から圧縮する**(消した行は圧縮データに含まれない)。
   ADR-095 決定4 の条件2「送信する全文をダイアログ内で表示する」は、「ログ部分は圧縮前の内容を表示し、送信するのはその圧縮」に読み替える。
3. **10 分ぶんの全打鍵を送ることを許容する**(条件: プレビューで確認・削除できること)。チェックボックスのツールチップを「直近約 10 分のすべてのキー入力」に変更する。

## 旧・未決(上で解決済み)

1. **圧縮方式**: Opus は gzip(`flate2` は既存依存、Worker が `DecompressionStream` で解凍して中身を検証できる)を第一候補に推奨。
   xz は約 1.4 倍小さいが、新クレート(`lzma-rust2`、動作確認済み)と、Worker が解凍できないことによる検証の弱さが代償。数 MB の実データで両方を測ってから決める。
2. **プレビューの作り直し**: 現状は「プレビューの文字列そのものを送る」(`awase-settings/src/bug_report.rs:397`)で、ユーザーが行を消せる。
   圧縮して送ると、消した行が圧縮データの中に残る。ログは読み取り専用の表示(必要な行だけ描画)にして、送信時に表示中の内容から圧縮する案を第一とする。
3. **10 分ぶんの全打鍵を送ること**(この間に打ったパスワードも文章として復元できる)は、ADR-095 決定4(生の打鍵はマスクしない代わりにプレビューで確認できる)の前提が変わるため、所有者の再確認が要る。
