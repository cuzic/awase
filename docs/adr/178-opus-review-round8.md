## Blocker

### B11. 決定1の契機3が`LayoutEntry::scan_all`に依存しているが、これは**コア`awase`クレートから呼べない**（`awase-windows`の`#[cfg(windows)]`配下の`pub(super)`関数）。決定2でこの契機がコア関数の内部ステップになったため、そのままでは実装不能

決定1の契機3（102-105行）:
> 起動時、`ensure_user_data_present()`が内部でロードした`config.toml`/`.yab`
> （同梱6ファイル名のみ、**`LayoutEntry::scan_all`が読む全`.yab`のうち**
> 同梱名と一致するもの限定）の内容がバックアップと異なれば…

そして決定2の実行順序（207-228行）は、この契機3を`ensure_user_data_present()`の
**ステップ4**として関数内部に置き、決定5はその関数を**コア`awase`クレート**に
実装すると定めている。しかし:

- `LayoutEntry`は`crates/awase-windows/src/runtime/mod.rs:113`で定義されている
  （コアではなく`awase-windows`）。
- `scan_all`は`crates/awase-windows/src/app/bootstrap.rs:795`の
  **`pub(super) fn`**——`awase-windows`の外からはそもそも見えない。
- さらに`crates/awase-windows/src/runtime/mod.rs`はモジュールツリー全体に
  `#[cfg(windows)]`が付いている（CLAUDE.md「Concurrency model」節・Testing節が
  明記）。つまり**Linuxホストターゲットではこの型自体が存在しない**。

したがって:

1. コア`awase`クレートは`LayoutEntry::scan_all`を呼べない（依存方向が逆。
   コア→プラットフォームの依存はADR-019が禁じている構造でもある）。
2. 仮に呼べたとしても、決定7が前提にしている
   「ホストターゲット（Linux、`cargo test --lib`）で自動テストできる」が
   崩れる（`cfg(windows)`配下の型に触れた時点でLinuxビルドから消える）。

**要求**: 契機3の`.yab`読み込みを、コアで完結する形に書き換えること。具体的には

> 契機3の`.yab`側は、`ensure_user_data_present()`が**同梱6ファイル名を
> 直接読み**、`awase::yab::YabLayout::parse`（`src/yab/mod.rs:843`、コア）で
> パース成功したものだけをバックアップ対象とする。`LayoutEntry::scan_all`
> （`awase-windows`側・`cfg(windows)`・`pub(super)`）には依存しない。

なお決定1が契機3の判定基準として`LayoutEntry::scan_all`を名指ししていたのは
round6 Minor（「`.yab`の読み込み成功＝パース成功と定義せよ」）への対応であり、
**意図（read+lintだけの診断スキャンと区別する）は正しい**。同じ意図は
`YabLayout::parse`を直接使うことで満たせるので、参照先を差し替えるだけでよい。
併せてB12（下記）と同様に、`keyboard_model`が必要になる点に注意すること
（→M3）。

### B12. `ensure_user_data_present(config_path: &Path, ..)`という単一引数では、「読み取り先」と「復元（書き込み）先」を兼ねられない。呼び出し元が何を渡しても、B2（CWD誤書き込み）か開発ビルドの起動不能のどちらかが再発する

v8の決定5シグネチャ（293-299行）は`config_path`を1つだけ取り、コメントは
> `config_path: &Path,   // 復元・ロード対象。exe隣の絶対パス（resolve_next_to_exe の結果）

としている。一方、決定2は

- 復元先: **常に**`resolve_next_to_exe("config.toml")`（200行）
- 読み取り（既存パスの解決）: **`resolve_relative_to_exe()`をそのまま使う**（182行）
- 開発ビルドでは復元を行わない（185-194行）

と定めており、この2つは**同じパスではない**。呼び出し元が渡せる候補は2つしかなく、
どちらも既に解消したはずの問題に戻る。

**候補(a): `resolve_next_to_exe("config.toml")`を渡す**（決定5のコメントどおり）

```
cargo run 実行時:
  config_path = <root>/target/debug/config.toml（存在しない）
  → 開発ビルド除外により復元は行われない
  → ステップ2の AppConfig::load(config_path) が NotFound で失敗
  → 中断条件により以降スキップ、戻り値に有効な設定が入らない
  → 呼び出し元は「自分で load してはならない」（チェックリスト#3）
  → **cargo run でアプリが起動できなくなる**
```
`<root>/config.toml`（`resolve_relative_to_exe`が返す実際の読み取り先）は
一度も読まれない。

**候補(b): `find_config_path()`／`resolve_relative_to_exe()`の結果を渡す**

```
本番環境で config.toml が存在しない場合（MSIアンインストール後にZIP版exeを
起動した等）:
  resolve_relative_to_exe("config.toml") はどこにも見つからず
  → PathBuf::from("config.toml")（CWD相対の裸パス、src/paths.rs:59-64）
  → この値を config_path として渡すと、復元先が CWD になる
  → **B2（Runキー起動時に C:\Windows\system32 へ書き込む）が再発**
```
「復元先は常に`resolve_next_to_exe()`」という決定2の規定を関数内部で守るなら
今度は「復元した先」と「`config_path`から読む先」が食い違い、
**復元は成功したのにロードは別の（存在しない）パスを見て失敗する**。

**要求**: `config_path`引数を廃し、コア関数が`exe_dir`から**読み取り先と
書き込み先の両方を自分で導出する**形にすること。`src/paths.rs`はコア
クレートにあるので、解決ロジックをコア側に置いてもADR-019に反しない
（`resolve_relative_to`は既に「exeパスを引数で受け取る」形の内部関数として
存在する——`src/paths.rs:33`）。規則は:

> - 書き込み（復元）先: `exe_dir.join("config.toml")`（＝`resolve_next_to_exe`相当）。
> - 読み取り先: 復元が発火した場合は上記の復元先から読む。復元が発火しなかった
>   場合（既にファイルがある／開発ビルド除外／復元失敗）は、従来の読み取り解決
>   （exe隣 → ワークスペースルート → 見つからなければ諦める）の結果から読む。
>   **CWD相対の裸パスへは決して書き込まない**（B2の不変条件を維持）。

この形なら`cargo run`（ワークスペースルートの`config.toml`を読む）も、
本番の復元経路も、B2の禁止事項も同時に満たせる。実装チェックリストにも
「読み取り先と書き込み先は別物であり、1つの引数で兼ねてはならない」を
1行追加しておくこと（これは過去にB2・B5・B6と3回形を変えて現れた論点である）。

## Major

### M1. 戻り値を`ValidatedConfig`だけにすると、`awase-settings`の既存挙動（ユーザーが書いた値をそのまま表示・保存する）が変わる。チェックリスト#3とも食い違っている

- 決定5のシグネチャ（298行）: `-> (RestoreOutcome, ValidatedConfig, UserDataGuard)`
- 実装チェックリスト#3（54-56行）: 「**検証済みの設定（`AppConfig`）自体**を含める」

型が違う（`ValidatedConfig`と`AppConfig`は`src/config.rs`の別の型）。
そして実務上は`AppConfig`側が必要である:

- `awase-settings`は`SettingsApp::new`で**生の`AppConfig`**を保持し、
  UIに表示・編集し、保存する（`crates/awase-settings/src/main.rs:542-556`）。
- `validate()`は正規化を行う（例: `confirm_mode = "speculative"`を
  `two_phase` + `speculative_delay_ms = 0`へ、`layouts_dir`に`".."`が
  あれば`"layout"`へ）。`ValidatedConfig`しか返さないと、設定画面が
  **ユーザーが書いた値ではなく正規化後の値を表示**することになり、
  その状態で保存すれば`config.toml`が正規化後の内容で書き換わる。
  現状は`AppConfig::from(validated)`を「適用」操作のときだけ通す設計
  （`main.rs:700`）であり、ロード時点では生の値を保つ。挙動が変わる。
- `validate()`は`(ValidatedConfig, Vec<String>)`を返し、後者の警告を
  `awase-settings`が表示している。`ValidatedConfig`だけでは警告が失われる。

**要求**: 戻り値に**生の`AppConfig`**を含めることを決定5・チェックリスト#3の
両方で統一すること（`validate()`は純粋なので、`ValidatedConfig`や警告が必要な
呼び出し元は戻り値の`AppConfig`から自分で再度`validate()`すればよい。
`awase.exe`側は今も`validate()`を通してから`init_engine_validated`へ渡している）。
関数内部で`validate()`するのは`layouts_dir`を得るためであり、その結果を
外へ出す必要はない。

### M2. CLI引数でconfigパスを指定した場合の扱いが、v8で決定文から消えている（チェックリスト#1と衝突する）

round2 M6以降、「CLI引数で明示されたパスには復元を発火させない」という規則が
あった（v3〜v6の決定2に明記）。v8ではシグネチャ変更に伴いこの記述が消え、
代わりにチェックリスト#1が「**両バイナリが**load/saveより前に
`ensure_user_data_present()`を呼ぶ」と無条件に要求している。

`find_config_path()`はCLI第一引数をそのまま返す（`crates/awase-windows/src/app/mod.rs:153-171`、
`awase-settings`側も`main.rs:5290-5300`で同型）。`awase.exe D:\tmp\test.toml`の
ような起動で何が起きるべきかが未定義であり、実装者が取りうる解釈は両方とも問題がある:

- ensure を exe 隣のパスに対して呼ぶ → **実際に使う`D:\tmp\test.toml`とは別の
  config が復元・ロードされ、戻り値（チェックリスト#3により呼び出し元は
  これを使わねばならない）が誤ったものになる**。
- ensure を `D:\tmp\test.toml` に対して呼ぶ → 別インストールのバックアップが
  ユーザー指定の任意パスに実体化する（round2 M6で塞いだ問題の再発）。

**要求**: 決定2とチェックリスト#1に例外条項を戻すこと。

> CLI引数で config パスが明示されている場合、`ensure_user_data_present()`は
> 呼ばない（または「復元・バックアップを行わない」モードで呼ぶ）。その場合
> 呼び出し元は従来どおり指定パスを`AppConfig::load()`する。自己修復機構は
> 「自動解決されたexe隣の config」のみを対象とする。

このとき`UserDataGuard`が得られないため、決定1のゲートによりバックアップも
自動的に抑止される——能力トークン方式がこの例外とも自然に噛み合う点は
設計として良い。その旨も1行書いておくとよい。

### M3. バックアップ妥当性検証に`YabLayout::parse`を使うと、`keyboard_model`依存で**正当なバックアップを「不正」と判定して復元しない**ケースが生じる

決定2「バックアップの妥当性検証」（247-249行）は`.yab`を`YabLayout::parse`で
検証するとしているが、この関数のシグネチャは
`pub fn parse(input: &str, model: KeyboardModel) -> Result<Self>`
（`src/yab/mod.rs:843`）であり、**`keyboard_model`に依存して失敗しうる**。

`crates/awase-settings/src/main.rs:1607-1614`のコメントが、まさにこの依存を
理由に診断スキャンで`parse`を避けている:

> パースまで行うと、同梱の JIS用レイアウトが `keyboard_model = "us"` 環境で
> **列数上限超過**により恒久的に警告される（US配列ユーザーには対処しようが
> ない誤警告になる）

つまり US 配列環境のユーザーが JIS 用同梱配列をカスタマイズしていた場合、
そのバックアップが検証で弾かれ、**MSI再インストール後に復元されない**
（本ADRが守るはずのユーザーが守られない）可能性がある。しかも失敗は
「警告ログのみ」（決定2）なので、ユーザーには「復元されなかった」としか
見えない。

**要求**: `.yab`の妥当性検証基準を決め直すこと。候補:

- (a) UTF-8として読めること＋`awase::yab::lint`（`src/yab/mod.rs`、
  `keyboard_model`非依存）が致命的エラーを返さないこと、までに留める。
- (b) `YabLayout::parse`を使うが、`keyboard_model`は**復元先環境の設定値**
  （フェーズ2で得た`config.general.keyboard_model`）を渡し、かつ
  **列数超過のような`keyboard_model`起因の失敗は「不正」と扱わない**。

いずれにせよ「どの`keyboard_model`で検証するか」を決定文に書くこと
（現状は引数の存在自体に触れていない）。同じ問題はB11の要求で
`YabLayout::parse`を契機3の判定に使う場合にも生じるので、両方で同じ基準を
使うこと。

## Minor

### m1. 「能力トークンにより復元を通らないプロセスはバックアップを汚せない」は正しいが、**B9の損失そのものは防がない**

「解決されること」（399-400行）の記述は事実だが、B9で問題にした損失
（片方のバイナリが復元前の内容に1項目重ねて保存 → もう一方の復元条件が
成立しなくなり、契機3が正しいバックアップを工場出荷値＋1項目で上書き）は、
**トークンを持つ`awase.exe`側の契機3が行う**ため、トークンでは止まらない。
これを止めているのはチェックリスト#1（両バイナリが必ず呼ぶ）と
チェックリスト#3（戻り値を使う）である。

将来「トークンがあるからチェックリスト#1は保険では」と判断されないよう、
両者の役割分担（トークン＝復元を通らないプロセスからの汚染防止、
呼び出し要件＝復元前の内容で上書きされることの防止）を1行で書き分けること。

### m2. 決定7の「B9の直接再現（コンパイルできないことを確認する）」は、通常の`#[test]`では書けない

型で防ぐ設計にした以上、「トークン無しで呼べないこと」の自動確認は
`trybuild`のようなcompile-failテスト、またはdoc-testの
` ```compile_fail ` 属性でしか書けない。決定7の項目としてどちらを使うかを
書くか、「型システムで保証されるためテスト項目からは外す（レビュー観点として
残す）」と明示すること。現在の書き方（「実行時テストとしては…限定される」）
だと、実装者が何を書けばよいか判断できない。

### m3. 実装チェックリストに決定6（通知）・決定7（実機確認1件）の要件が入っていない

チェックリストの目的は「圧縮による欠落を防ぐ」ことなので、圧縮で落ちると
痛い要件はすべて載せるべき。特に:

- 決定6の「通知は**ファイル単位**で行い、`backup\<ファイル名>`の削除を案内する」
  （フォルダ単位の案内に戻すと、他のバックアップを巻き添えで失わせる）。
- 決定7の「**実機確認1件**（MSI再インストール後の内容が埋め込み既定値と
  バイト一致することを、**起動前に**採取して確認）」——これはB1修正が依拠する
  唯一の未検証前提であり、落とすと自動テストが全て緑のままADRが無効化される。

現在のチェックリスト9項目は決定1〜3・5に偏っている。

### m4. ADRが参照している`opus-review-adr178-round*.md`が**未追跡ファイル**で、このままではリポジトリに残らない

コンテキスト節（33-34行）は「詳細な経緯は本ファイルのgit履歴、または各ラウンドの
`opus-review-adr178-round*.md`を参照」としているが、これらは現時点で
`git status`上`??`（未追跡、かつ`.gitignore`対象でもない）。ADR本文から
参照する以上、(a) コミットしてリポジトリに残す、(b) 参照を外して必要な要点を
ADR本体（実装チェックリスト等）に持たせる、のどちらかを決めること。
経緯の圧縮で要件が落ちる事故を3回起こしている経緯からすると、(a)（レビュー
記録をリポジトリに残す）のほうが本ADRの趣旨に合う。

## 総評

v8でB10は解消され、round7のMajor 3件（能力トークン化・バックアップ範囲の統一・
開発ビルド説明の訂正）も的確に反映されている。「実装チェックリスト」節の新設は、
このADRが繰り返してきた失敗（圧縮で要件が落ちる）への構造的対策として有効で、
今後の改訂でも維持すべき。

残る2件のBlockerは、いずれも**「決定文をコアクレートの実装に落とす」段階で
初めて見える型・クレート境界の問題**である:

- **B11**は、契機3の判定基準として名指しした`LayoutEntry::scan_all`が
  `awase-windows`の`cfg(windows)`・`pub(super)`であり、コアから到達できない
  （かつLinuxホストターゲットに存在しない＝決定7の自動テスト前提も崩れる）。
  参照先を`awase::yab::YabLayout::parse`へ差し替えるだけで解消する。
- **B12**は、`config_path`という1つの引数に「読み取り先」と「復元先」という
  性質の違う2つの役割を持たせてしまったもの。これはB2・B5・B6で3度形を変えて
  現れた論点（読み取り解決は存在依存、書き込み先は存在非依存でなければならない）
  の4度目の現れであり、`exe_dir`のみを受け取って関数内部で両方を導出する形に
  すれば恒久的に閉じる。

Majorの M1（戻り値の型）・M2（CLI引数の例外）・M3（`YabLayout::parse`の
`keyboard_model`依存）も、いずれも決定文の数行で解消できる。

これらを反映すれば、**次ラウンドは確認のみで収束し、実装フェーズへ進んでよい**
と考える。8ラウンドで検出したBlocker14件はすべてコードを1行も書く前に潰せて
おり、`.claude/rules/fix-requires-evidence.md`が言う「再発ファミリー」への
事前対策としては十分な密度に達している。
