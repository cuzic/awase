# ADR-270: Mozc の「入力中の文字ができない区間」の検知

## 背景

実機(dragonflyg4、Mozc Readable + Windows Terminal)で、ローマ字はひらがなになるのに、変換候補にならない症状が頻発する(利用者の報告。体感では頻繁)。awase のログには異常が出ない(awase は ON と判断し、ローマ字を普通に送っている)。

**実測(2026-10-19、version 3 の共有メモリを 20ms ごとに記録する道具で、awase のログの打鍵時刻と突き合わせた。打鍵の中身は記録していない)**:

- 14 分間の打鍵の塊 40 件のうち、入力中の文字が空の状態から始まったものが 34 件。うち 32 件は、最初の打鍵から入力中の文字(`phase>=1`)ができるまでが **0.01〜0.06 秒**(最初の打鍵で、すでに `phase=1`・`preedit_utf16_len=1`・`candidate_category=1`)。
- 残る 2 件が失敗で、**7.15 秒**と **2.76 秒**(UTC 06:47:00.7〜06:47:07.8 の同じ区間。この間、awase は 18 打鍵を送り、記録は `phase=0`・`preedit_utf16_len=0`・`candidate_category=0` のまま。窓・スレッドの変化も IME の ON/OFF の変化もなく、7 秒後に何も操作せず戻った)。利用者の見え方は「ひらがなにはなるが、変換候補にならない」。
- 利用者の指摘: ローマ字がひらがなになっている以上、キーは Mozc に届いている。したがって、失敗は「届かなかった」ではなく「入力中の文字として保持されていない」(1 打鍵ごとに確定されている可能性が高い。rust-nicola-89 のコード調査の H1: `OnEndEditImpl` の selection 変化、`OnCompositionTerminated`、composition の範囲が空のときの REVERT による SUBMIT。未実機確認)。

## 決定

### D1. 失敗の判定: 「入力中の文字が空の状態から、awase が 1 回送信してから 0.3 秒たっても、`phase` が 0 のまま」

- 主な条件は `phase >= 1`。`candidate_category`(候補窓)は補助にとどめる(出れば成功の追加の証拠。出ないことは失敗の根拠にしない)。理由: サジェストの有無は Mozc の設定や読みで変わり、候補窓が出ない正常がありうる。入力中の文字ができるかは、Mozc が正常なら必ず成り立つ。
- 「1 送信」は、awase がローマ字を IME へ送った 1 回(親指シフトの 1 物理キー。ひらがな 1 文字ではない)。1 送信が 2 キー(`ka`)でも、判定は 1 回。
- 検査は、次の**すべて**が成り立つ送信にだけ行う: 共有メモリが採れる(`active=1`、読み取りが accepted)、`effective_open=1`、直前の読みで `phase=0`、送ったのが文字(Enter・Space・矢印などの操作キーではない)。IME が閉じているとき、入力欄が IME を閉じる指定のとき(`scope_forced_mode=1`)は検査しない(入力中の文字が出ないのが正常)。

### D2. しきい値は 0.3 秒

利用者の許容(「0.3 秒程度なら待たせてもよい」、2026-10-19)。正常の最大は 0.06 秒(n=32)なので約 5 倍の余裕。失敗は 2.76 秒以上。**実測の母数が小さい(失敗 2 件、正常 32 件、いずれも 1 台・1 アプリ)ので、`tuning.rs` に置くときは `#[measured(pending = true)]` とし、記録が増えたら見直す。**

### D3. 段階

1. **段階 1(観測のみ)**: awase の共有メモリの読み取りを version 4(80/112 バイト、ADR-267 D9 の規約)へ拡張し、D1 の条件が成り立ったときに journal へ記録するだけ。belief・送信・キーの保持は動かさない。打鍵の中身は記録しない(時刻・`phase`・`preedit_utf16_len`・ADR-267 の追加項目だけ)。**目的は、検知が誤っていないこと(正常な打鍵で出ない)と、頻度の確認。**
2. **段階 2(回復)**: 検知したら、最初の 1 送信で文書に出た文字(0〜1 文字の想定)を Backspace で消し、入力中の文字が復帰するまで待ってから再送する。続くキーは、検査の間(最大 0.3 秒)保持する。**数える機構は作らない**: 最初の 1 送信で検知するので、消す文字は高々その 1 回分で、「何文字目か」を数える必要がない(GJI の `ze_bs_count` とは別物)。着手の条件は、下の「未確認」の 1〜3。

### D4. やらないこと

- 候補窓の有無を失敗の主な条件にしない(D1)。
- 失敗中に Mozc へ働きかけて状態を直す動作は、原因が分かるまで入れない。
- GJI の I/O 監視を証拠にしない(ADR-269)。

## 未確認(段階 2 の前提)

1. 失敗中の最初の打鍵が、文書にどう出るか(英字・何も出ない・ひらがな)。利用者の感覚では、英字が見えたことはない。消す文字数が 0 か 1 かを決める。
2. 失敗の状態が、何をきっかけに始まり、何をきっかけに終わるか。今回は約 14 秒の無操作の後に始まり、約 7 秒で自然に戻った。TIP 側に 7 秒のタイマーや再試行は無い(rust-nicola-89 のコード調査)ので、Windows Terminal 側の変化と考えられるが、未確認。
3. 失敗の間に、再送が効くか(失敗の状態が続くなら、再送も失敗する)。
4. 20ms ごとのポーリングは、数ミリ秒の `phase=1` を取りこぼす(H1 が正しければ、失敗中にも `phase=1` が瞬間的に出ている)。ADR-267 に version 4 として足す観測項目(`composition_start_count`・`submit_count` と、SUBMIT の経路別のカウンタ)で確かめる。
5. 他のアプリ(Chrome・WezTerm)や他の窓でも起きるか。現在の測定は Windows Terminal(`Windows.UI.Input.InputSite.WindowClass`)だけ。

## 却下した案

- **打鍵のたびに、何文字目かを数えて Backspace の数を決める案**: 利用者の指摘どおり、最初の 1 送信で検知できるなら不要。
- **候補窓の有無を主な判定にする案**: サジェストの設定や読みで変わるため、誤検出になりうる(D1)。
