# ADR-264: 入力インジケーターの右クリックメニューを開いたときだけ、メニューの現在のモードを読んで証拠にする

## ステータス

起草(2026-10-17)。実装なし。測定は使い捨てのスパイクブランチ(`ci/indicator-menu-verify`、develop にはマージしない)の GitHub Actions による。
決定は**案**で、Opus レビューと所有者判断を経ていない。測っていない範囲(一太郎の実機・awase 起動時の影響・選んだ項目の検知)は「未測定・リスク」に分けて書く。

## 背景

不具合報告 `01M4QSFH1B02DQ9B8AXBYVRQ39`(GJI・一太郎、issue #623)は、窓内の IMM が読めない窓(観測の無い窓)で、belief が実 IME とずれる
(「タスクバーは OFF なのに入力は全角」「IME ON にするとローマ字」)ことを訴える。観測の無い窓には、読んで直す手段が無い。

観測の無い窓への備えは、1 つに絞らず、複数の証拠の組み合わせでカバーする(所有者の方針、2026-10-17)。取れたら使い、取れなければ諦める。現在の候補:

| 手段 | 向き | 書き込み | 本 ADR との関係 |
|---|---|---|---|
| [ADR-261](261-taskbar-indicator-glyph-observation-for-unreadable-windows.md) | 字形(画像)を周期的に取り込んで読む | 無し | 別の「読む」証拠。併用する |
| [ADR-262](262-nicola-intent-evidence-for-unobserved-windows.md)・[ADR-263](263-episode-start-key-hold-and-language-decision.md) | 親指シフトの打鍵(意図)の証拠から、IME ON を 1 回送る | 有り(ADR-212 の例外) | 独立。本 ADR は読むだけ |
| **本 ADR** | **利用者が右クリックでメニューを開いたときだけ、メニューの現在のモードを読む** | **無し** | — |

所有者の案: 「ユーザーが右クリックメニューを表示する操作をしたときに、それをすかさず撮影して、モードずれを直す」。画面を撮らなくても、メニューは UI Automation で読める(下の実測)。

## 実測(GitHub Actions windows-latest = Windows Server 2025・Win11 型タスクバー・1024×768・DPI 100%・en-US)

自前の窓(`indicator_scenario`)にフォーカスを置いて状態を作り、`SendInput` 相当の右クリックでインジケーターのメニューを開く。WinEvent(`SetWinEventHook`)と UI Automation のイベントで開閉を記録し、
メニューの項目を UI Automation で読む(`tools/ci/indicator_menu/run.ps1`)。

| 項目 | 結果 |
|---|---|
| 開いた瞬間の検知 | **WinEvent の `EVENT_SYSTEM_MENUSTART`・`MENUPOPUPSTART` と、UI Automation の `MenuOpened` が、全 15 状態で各 1 回ずつ発火**した。閉じるときは `MENUPOPUPEND`・`MENUEND`・`MenuClosed` |
| どの窓のメニューか | **`MENUSTART` の hwnd はフォーカス中の入力欄そのもの**で、メニューはその窓のスレッドで出る。窓の識別がイベントだけで分かる。メニューのクラスは `#32768`(標準の Win32 メニュー) |
| フォーカスの副作用 | 前面窓の変化(`EVENT_SYSTEM_FOREGROUND`)は出なかった。awase を起動した状態は未確認 |
| 読み取り | UI Automation で `MenuItem` が読め、**現在のモードの項目に `SelectionItemPattern.IsSelected=True`** が付く |
| MS-IME の項目 | `AutomationId` = `Item 101`(ひらがな)・`102`(全角カタカナ)・`103`(全角英数)・`104`(半角カタカナ)・`105`(半角英数)。本物の MS-IME は閉と半角英数が同じ |
| GJI の項目 | `Item 11`(ひらがな)・`12`(全角カタカナ)・`14`(全角英数)・`15`(半角カタカナ)・`13`(半角英数)・**`10`(Direct Input = IME 閉)**。開閉まで読める |
| 通常の窓(IMM が読める。5 状態) | MS-IME のひらがな・カタカナ・半角英数、GJI の ON・OFF で、選ばれた項目が設定した状態と一致 |
| **観測の無い窓の近似(10 状態)** | 自前の TSF text store の窓。`assoc` = 窓の IMM コンテキストなし、`disable` = スレッドで `ImmDisableIME`(IMM の読みは常に open=0/conv=0)。MS-IME 3 状態 × 2 + GJI 2 状態 × 2 の**全 10 状態で、`IsSelected` の項目が窓の実状態と一致**した。実状態は、キーで状態を作り、打った出力で読んだ(MS-IME: ひらがな→「か」・カタカナ→「カ」・英数→何も入らない、GJI: ON→「か」・OFF→何も入らない) |
| 言語依存 | 項目名は表示言語で変わるが、**`AutomationId` は変わらない**(IME ごとに別の体系) |

MS-IME の項目数は測定により 17 件と 18 件があった(状態や表示によって、モード以外の項目が増減する)。項目の判定は件数でなく `AutomationId` で行う。
**IMM が読めない窓でも、メニューは窓自身の実状態を示す**(メニューは TSF の状態から作られるため)。これは、報告の「belief が実機とずれる」を直接直せる証拠源になりうる。

## 決定(案。Opus レビュー前)

### 決定 0: 原則 — 読むだけ・利用者の操作が起点・取れなければ何もしない

メニューは**利用者が開いたときだけ**読む。awase がメニューを開く・右クリックを送る・フォーカスを動かすことはしない(却下案)。IME へは何も書かない(actuation を足さない。ADR-212 の方針、ADR-261 決定 0 と同じ)。
メニューが読めない・入力インジケーターのメニューと同定できない・IME が未知・フォーカスがずれた、のときは何もしない。位置づけ(複数の証拠の 1 つ・取れなければ諦める)は ADR-261 と同じ。

### 決定 1: 検知は WinEvent(新しいフックは足さない)

`EVENT_SYSTEM_MENUSTART`(hwnd・スレッドでフォーカス窓を知る)と `EVENT_SYSTEM_MENUPOPUPSTART`(メニューの hwnd を知る)を受ける。既存のフォーカス検知と同じ `SetWinEventHook` の仕組みに相乗りし、
**マウスフック(`WH_MOUSE_LL`)は新設しない**(ADR-261 決定 5 と同じ理由。遅延とウイルス対策の面で重い)。
**`#32768` のメニューはどのアプリの右クリックメニューでも出る**ので、入力インジケーターのメニューかどうかは、決定 2 の中身で同定する(クラスだけでは足りない)。

### 決定 2: 読み取りは 1 回だけ。IME のモード項目の集合に当たったときだけ採る

メニューが開いたら、UI Automation で**メニュー項目の `AutomationId` と `IsSelected` を 1 回だけ**読む(`focus/uia.rs` の専用ワーカースレッド(STA + mpsc)に相乗り。固まりに備えてタイムアウトを置く。
`run_with_timeout` は使わない理由は ADR-261 決定 1 と同じ)。
- **同定**: 読んだ `AutomationId` の集合が、同定済みの IME(`TipIdentity`)の「モード項目の集合」(決定 3)を含むときだけ採る。含まなければ破棄する(他のアプリの右クリックメニューは採らない・保存しない)。
- **無駄な読み取りの抑止**: 観測の無い窓(`ImmCapability::Unavailable` と学習された窓)で、IME が GJI または本物の MS-IME のときだけ読む(読める窓では直接の読みがあるので不要。段階 1 の shadow だけ例外)。
  回数の上限と最短間隔を置く(値は D0 の実測。tuning 定数にして ms を添える)。

### 決定 3: 対応表は `AutomationId` で引く(名前は使わない)

| IME | `AutomationId` → 状態 |
|---|---|
| 本物の MS-IME | `Item 101` = 開・ひらがな、`102` = 開・全角カタカナ、`103` = 開・全角英数、`104` = 開・半角カタカナ、`105` = 閉(= 半角英数。本物の MS-IME は同じ) |
| GJI | `Item 11` = 開・ひらがな、`12` = 開・全角カタカナ、`14` = 開・全角英数、`15` = 開・半角カタカナ、`13` = 開・半角英数、`10` = 閉(Direct Input) |

ID は実測した版(Windows Server 2025 build 26100 の MS-IME、CI の GJI)のもの。**IME の更新で ID が変わりうる**ので、**表に無い ID は採らない**(`Miss`)。表示名・並び順は言語・版で変わるので、判定に使わない
(並び順は ID が取れなかったときの診断にだけ記録する)。表は内蔵でよい(字形と違い、DPI・テーマに依らない)。他の IME(ATOK 等)は測っていないので対象外。

### 決定 4: どの窓の状態か — `MENUSTART` の hwnd とフォーカス世代

`MENUSTART` の hwnd(フォーカス窓)・スレッドを、awase のフォーカス追跡の窓と照らし、**読んだ時点と適用時点で `FocusGen` が変わっていれば捨てる**(await をまたぐ失効判定、ADR-261 決定 5 と同じ作法)。
メニューを開いている間にフォーカスが動くことは通常無い(メニューが開いている)が、読み取りの完了前に閉じた場合も捨てる。

### 決定 5: belief への入れ方(案)

- **段階 1(shadow)**: belief には入れない。journal と不具合報告に `indicator_menu { read, 同定の成否, 読んだ状態, その時点の belief, 一致/不一致 }` だけを出す(ID・状態のみ。他のアプリのメニューの名前・内容は出さない)。
  読める窓で、直接の読み(High)と突き合わせて**一致率**を出せる(正解のある一致率)。観測の無い窓の正解は、メニューで選ばれた項目と、利用者の打ち直し・打った出力でしか取れない(一太郎の実機)。
- **段階 2(belief 配線)**: 新しい `ObservationSource::IndicatorMenu`、`confidence` は High 相当(IME 自身の UI の読み)。入力モードは `InputModeObserved`、開閉は `ObserverReported` の規約に従い、
  **`authority() = BeliefOnly`**(`derive_actuating` に入れない。drift correction の書き込みを引き起こさない。ADR-261 決定 6 の入口条件 2 と同じ理由)。
  ADR-261 決定 6 の入口条件(古い値で正しい予測を覆さない・`Miss` の後に古い `Hit` を残さない)は、**メニューは「今」の状態を読む**ので遅れの問題は小さいが、
  awase の書き込み(ADR-262/263 の ON)の直後は組にしない・採らない、を同様に置く。本 ADR では配線を決めない(別レビュー)。

### 決定 6: 他の証拠との関係

字形(ADR-261)・打鍵起点の ON(ADR-262/263)・直接の読み(読める窓)と**併用**する。食い違ったときの優先順位は、段階 2 で、他の証拠の設計と合わせて決める。
メニューは**利用者が開いた瞬間の IME 自身の UI の読み**なので、他に比べて新しく確かな証拠になりうる(High 相当の根拠)。ただし、開いた時にしか取れない(頻度が低い)ので、**主な証拠にはならず、取れたら信頼する補助**という位置づけにする。

### 決定 7: プライバシー・安全・オプトイン

- **画面を撮らない**(ADR-261 と違い、画素を取り込まない)。読むのはメニュー項目の `AutomationId` と `IsSelected` だけで、同定に失敗したメニュー(他のアプリの右クリックメニュー)の内容は破棄し、保存しない。
- 他のアプリのメニューに対して UI Automation を呼ぶことになる(同定の前に項目の ID を見る)ので、**既定はオプトインにして ADR-261 と同じスイッチに揃える案**(所有者判断 Q)。
  UI Automation(アクセシビリティ API)は画面の取り込みより穏当だが、「低レベルフック + 他アプリの UI の走査」はウイルス対策の行動検出に当たりうるので、D0 で確かめる。
- UI Automation の探索が固まる恐れ(ワーカーとタイムアウト、連続失敗でそのセッションの停止)。

## 却下案

- **awase が周期的・契機でインジケーターを右クリックしてメニューを開いて読む**: メニューが利用者の画面に出て、フォーカスを奪い、入力を妨げる。読むのは利用者が開いたときだけ(決定 0)。
- **メニューの画面を撮って画像で読む(ADR-261 の字形と同じ手法)**: `IsSelected` が UI Automation で直接読めるので不要。
- **項目名(「ひらがな」等)で判定する**: 表示言語で訳される。`AutomationId` を使う(決定 3)。
- **`WH_MOUSE_LL` で右クリックを検知する**: 遅延とウイルス対策の面で重い。WinEvent で足りる(決定 1)。
- **項目の並び順で判定する**: 版・言語・状態で項目数が変わる(MS-IME で 17〜18 件)ので不安定。ID が取れないときの診断にだけ使う。

## 未測定・リスク(段階 0 = D0)

| ID | 内容 | 測り方 |
|---|---|---|
| M0-1(go/no-go) | **一太郎の実機**で、右クリックメニューが出て、`IsSelected` が実際の入力と一致するか。一太郎が TSF 経由でメニューを出す窓かは実機でしか分からない | 実機(報告者への依頼、または一太郎を持つ環境) |
| M0-2 | **awase を起動した状態**でのフォーカス追跡・belief・`HwndCache` への影響(メニューが開いている間・閉じた直後) | CI(awase あり) |
| M0-3 | **利用者が選んだ項目の検知**(UI Automation の `InvokedEvent`、または閉じた後の再読)。選んだ時点で窓のモードが確定する | CI |
| M0-4 | 他のアプリの右クリックメニューを読むコスト・固まり、同定に失敗したときの破棄 | CI(多数のメニュー) |
| M0-5 | IME の版による `AutomationId` の変化(MS-IME の以前のバージョン互換モード〔ADR-254〕、GJI の版、Windows 10 の言語バー) | 構成を増やす |
| M0-6 | 他の IME(ATOK 等)・複数言語・「アプリごとに入力方式を切り替える」設定でのメニュー | — |
| M0-7 | インジケーターの左クリック(トグル)・Win+Space など、メニューを開かない操作は対象外(別の証拠で補う) | — |

リスク: ①開いた時にしか取れない(頻度が低い。主な証拠にならない)。②IME の更新で `AutomationId` が変わる(表に当たらなくなるだけで、決定 0 により害は無い)。③他のアプリのメニューを走査する副作用(コスト・固まり・ウイルス対策)。
④一太郎でメニューが出ない・状態が実状態でない(M0-1)。⑤利用者がメニューを開いても項目を選ばずに閉じる(読んだ状態は有効。選んだ項目は M0-3)。

## 段階

- **段階 0**: M0-1(一太郎の実機)を最優先。M0-2・M0-3 は CI。M0-1 が否定的なら、本 ADR は #623 には効かない(他の窓には使える)。
- **段階 1**: `observer/` に WinEvent の検知と UI Automation の読み取り、`state/` に純粋な同定・対応表、shadow(journal・不具合報告)。読める窓で直接の読みとの一致率を見る。
- **段階 2**: belief への配線(決定 5 の入口条件を満たす別 ADR/追記でレビュー)。
- **段階 3**: 設定画面にオプトインの説明(ADR-261 と同じスイッチ)。
