# ADR-264: 入力インジケーターの右クリックメニューを読んで、字形の表の正解ラベルと shadow の証拠にする

## ステータス

起草(2026-10-17)。実装なし。測定は使い捨てのスパイクブランチ(`ci/indicator-menu-verify`、develop にはマージしない)の GitHub Actions による。
Opus レビュー round 1(Blocker 2・Major 8・minor 9)を反映して書き直した(レビューの全文はセッションのスクラッチパッド。要点は本文の該当箇所に取り込んだ)。決定は**案**で、所有者判断を経ていない。

## 背景

不具合報告 `01M4QSFH1B02DQ9B8AXBYVRQ39`(GJI・一太郎、issue #623)は、窓内の IMM が読めない窓(観測の無い窓)で、belief が実 IME とずれる
(「タスクバーは OFF なのに入力は全角」「IME ON にするとローマ字」)ことを訴える。観測の無い窓には、読んで直す手段が無い。

観測の無い窓への備えは、1 つに絞らず、複数の証拠の組み合わせでカバーする(所有者の方針、2026-10-17)。取れたら使い、取れなければ諦める。現在の候補:

| 手段 | 向き | 書き込み | 本 ADR との関係 |
|---|---|---|---|
| [ADR-261](261-taskbar-indicator-glyph-observation-for-unreadable-windows.md) | 字形(画像)を周期的に取り込み、表に当たったときだけ読む | 無し | 本 ADR の読みは、この**表の正解ラベル**になる(決定 5) |
| [ADR-262](262-nicola-intent-evidence-for-unobserved-windows.md)・[ADR-263](263-episode-start-key-hold-and-language-decision.md) | 親指シフトの打鍵(意図)の証拠から、IME ON を 1 回送る | 有り(ADR-212 の例外) | 独立。本 ADR は読むだけ |
| **本 ADR** | **利用者が右クリックでメニューを開いたとき、メニューの現在のモードを読む** | **無し** | — |

所有者の案: 「ユーザーが右クリックメニューを表示する操作をしたときに、それをすかさず撮影して、モードずれを直す」。画面を撮らなくても、メニューは UI Automation で読める(下の実測)。

**前提の取り違えに注意(レビュー M4)**: 報告者は「タスクバーは IME オフになっているものの、入力は全角」「IME オフと、ひらがな入力のモード表示がちょうど逆転している」と書いている。
ADR-261 は、これを H1(インジケーターが別スレッド/別コンテキストの状態を映す)・H2・H3 に切り分けている。**メニューのチェックも、インジケーターの字形と同じ言語バー項目(入力モード)の状態から作られる**ので、
H1 なら一太郎ではメニューも「閉」を示し、**誤った証拠**になる。本 ADR の「報告の状況に当たる」は、**一太郎で一致することを M0-1 で確かめるまで仮定**にすぎない。

## 実測(GitHub Actions windows-latest = Windows Server 2025・Win11 型タスクバー・1024×768・DPI 100%・en-US・ライトテーマ。いずれも 1 環境・各状態 n=1)

自前の窓(`indicator_scenario`)にフォーカスを置いて状態を作り、`mouse_event` の右クリックでインジケーターのメニューを開く。WinEvent(`SetWinEventHook`)と UI Automation のイベントで開閉を記録し、
メニューの項目を UI Automation で読む(`tools/ci/indicator_menu/run.ps1`。ハーネスは PowerShell の `DoEvents` で WinEvent を拾うので、awase の実装〔WinEvent コールバック → STA ワーカー〕とは別物)。

## 決定(案。Opus レビュー round 1 を反映。round 2 以降は未)

### 決定 0: 原則 — 読むだけ・利用者の操作が起点・取れなければ何もしない・belief へは直接入れない

メニューは**利用者が開いたときだけ**読む。awase がメニューを開く・右クリックを送る・フォーカスを動かすことはしない(却下案)。IME へは何も書かない(actuation を足さない。ADR-212 の方針、ADR-261 決定 0 と同じ)。
同定できない・IME が未知・フォーカスがずれた・インジケーターの上で開かれたメニューでない、のときは何もしない(`Miss`)。位置づけ(複数の証拠の 1 つ・取れなければ諦める)は ADR-261 と同じ。
**メニューの読みを belief へ直接入れる配線は、本 ADR では決めない**(決定 5・段階)。

### 決定 1: 検知は WinEvent(`WH_*` フックは足さない)。インジケーターの上で開かれたメニューだけを読む

- **WinEvent の範囲を 1 つ足す**: `EVENT_SYSTEM_MENUSTART`〜`MENUPOPUPEND`(0x4〜0x7)。既存の `SetWinEventHook` は `EVENT_OBJECT_FOCUS` 単独(`bootstrap.rs`)と NAMECHANGE・SHOW/HIDE(`win_event_obs.rs`)だけなので、**この範囲の登録は新規**(新しい `WH_*` フックは足さない。**マウスフック `WH_MOUSE_LL` は新設しない**。ADR-261 決定 5 と同じ理由)。
- **前置きのフィルタ(レビュー M2 の代案を採る)**: `MENUSTART` のコールバック内で `GetCursorPos` を 1 回呼び、**カーソルが入力インジケーターの矩形(ADR-261 決定 1 で取る)の中にあるときだけ**読む。右クリックで開いたメニューは、カーソルがインジケーター上にある。
  これで、**他のアプリの右クリックメニューを UI Automation で読むことが、そもそも無くなる**(決定 6 のプライバシー・EDR の懸念と M0-4 がほぼ消え、`#32768` は誰のメニューでも出る問題も解消する)。
  メニューキー・Shift+F10 で開かれたメニュー(カーソルが別の場所)は対象外(読まない)。
- クラス `#32768` でメニュー窓を絞る(MS-IME の候補窓でも `POPUPSTART` が出るため)。

### 決定 2: 読み取りは 1 回だけ。同定は「完全一致」

- メニュー窓の hwnd(`POPUPSTART`)を `AutomationElement.FromHandle` で引き、**その配下の `MenuItem` と `IsSelected` を 1 回だけ**読む(デスクトップ全体の `FindAll` は使わない)。`focus/uia.rs` の専用ワーカースレッド(STA + mpsc)に相乗りし、固まりに備えてタイムアウトを置く(`run_with_timeout` は使わない。理由は ADR-261 決定 1 と同じ)。
- **同定**: `AutomationId` は `Item`+コマンド ID で IME 固有ではない(実測)ので、**モード項目の集合を含むだけでは足りない**。**「IME のモード項目の集合の全部 + その IME 固有の非モード項目(MS-IME: 116/118/120/122/536、GJI: 20/21/22/30/31)が揃い、モード項目のうちちょうど 1 つが `IsSelected`」の完全一致**のときだけ採る。
  `TipIdentity` の誤同定(BUG-179 で CI の MS-IME を Other と同定した前例)と重なって別 IME の表で読む失敗を避けるため、決定 1 のインジケーター上のフィルタと併用する。
- 無駄な読み取りの抑止: 観測の無い窓(`ImmCapability::Unavailable` と学習された窓)で、IME が GJI または本物の MS-IME のときだけ読む(読める窓では直接の読みがあるので不要。段階 1 の shadow だけ例外)。回数の上限と最短間隔を置く(値は D0 の実測。tuning 定数にして ms を添える)。

### 決定 3: 対応表は `AutomationId` で引く(名前は使わない)。測った行と推定の行を分ける

| IME | `AutomationId` → 状態 | 根拠 |
|---|---|---|
| 本物の MS-IME | `Item 101` = 開・ひらがな | **静的に観測**(通常の窓・近似の窓) |
| | `Item 102` = 開・全角カタカナ | **静的に観測**(近似の窓。通常の窓は再読のみ) |
| | `Item 105` = **入力モード=英数。開閉は不明** | **静的に観測**(IMM で open=0/conv=0x10 に書いた状態)。ただし本物の MS-IME は閉と開+半角英数(0x00)が同じ表示(ADR-261 の `GlyphClass`)なので、**`105` を「閉」とは読まない**(開閉の軸へ入れない) |
| | `Item 103` = 開・全角英数、`104` = 開・半角カタカナ | **推定**(名前から。選んだあとの再読でのみ観測。`104` は一度も観測していない) |
| GJI | `Item 11` = 開・ひらがな、`Item 10` = 閉(Direct Input) | **静的に観測**(通常の窓・近似の窓) |
| | `12` = 開・全角カタカナ、`14` = 開・全角英数、`15` = 開・半角カタカナ、`13` = 開・半角英数 | **推定**(名前から。一度も観測していない) |

**推定の行は、段階 1 の shadow(読める窓の直接の読みとの突き合わせ)で一致を確かめるまで採らない**。表は実測した版(Windows Server 2025 build 26100 の MS-IME、CI の GJI)のもので、IME の更新で ID が変わりうるので、**表に無い ID・完全一致しない集合は採らない**(`Miss`)。
表示名・並び順は言語・版で変わるので判定に使わない。表は内蔵でよい(字形と違い DPI・テーマに依らない)。他の IME(ATOK 等)は対象外。

### 決定 4: どの窓の状態か — `MENUSTART` の hwnd とフォーカス世代

`MENUSTART` の hwnd(フォーカス窓)・スレッドを、awase のフォーカス追跡の窓と照らし、**読んだ時点と適用時点で `FocusGen` が変わっていれば捨てる**(await をまたぐ失効判定、ADR-261 決定 5 と同じ作法)。
**注意(レビュー M7)**: [BUG-202](../known-bugs/BUG-202.md) のとおり、ホバーするとメニュー窓への `focus-sync` で awase のフォーカス窓が `#32768` に切り替わり、`FocusGen` が変わる。
**決定 7(BUG-202 の修正)が入る前は、ホバーを挟む操作で読みが必ず世代の食い違いで捨てられる**。開いた直後の読み(ホバー前、29〜109 ms)は、世代が変わる前に完了するので影響を受けない。

### 決定 5: 読みの使い道 — 字形の表の正解ラベルと shadow。belief へは直接入れない(レビュー M8・M7)

- **字形の表の正解ラベル(主)**: 開いた瞬間のメニューの読み(選ぶ前の状態)を、**同じ瞬間の字形(ADR-261)と組にして、その環境(DPI・テーマ)の表の正解ラベルにする**。観測の無い窓では正解が無いという ADR-261 の最大の課題(所有者判断 Q1)を、
  利用者が開いたときだけ補える。選んだ項目の検知(`idChild`)は要らない(選択後の状態は、`MENUEND` を契機に字形を読めば取れる。ADR-261 実測で切替の遅れは中央約 0.2 秒)。
- **段階 1 の shadow**: belief には入れない。journal と不具合報告に `indicator_menu { read, 同定の成否, 読んだ状態, その時点の belief, 字形のクラス, 一致/不一致, 非 0 の idChild が出たか }` だけを出す(ID・状態のみ。他のアプリのメニューの名前・内容は決定 1 により読まない)。
  読める窓では直接の読み(High)と突き合わせて**正解のある一致率**が出る。**メニュー読み × 字形 × belief の三つ組**を観測の無い窓でも取れる(上の「メニューが報告型のずれを捕まえた例」)。
- **選んだ項目の検知は採らない**(レビュー M3): 測ったのは「最後にホバーした項目をそのままクリック」の 1 パターンだけで、(a)項目をホバーしてからメニューの外・ESC・Alt+Tab で閉じると、最後の非 0 の `idChild` が残って「選んだ」と誤判定する、
  (b)サブメニュー(MS-IME の `Input Method`〔ローマ字/かな入力の切替〕等)は入れ子の `#32768` で、`idChild` を hwnd ごとに分ける必要があり、かな入力の切替は決定 3 の表にも無い、
  (c)`idChild` は区切り線を数えるのに、読み取りは `MenuItem` だけ(区切り線を除く)なので、区切り線より後の項目で 1 つずれる(現状のモード項目は両 IME とも最初の区切り線より前なので、測定では表に出なかっただけ)。
  段階 1 では「**非 0 の `idChild` が 1 度でも出たか(= 選択した可能性。出ていれば読みの状態は古い可能性)**」だけを記録する。
- **belief への直接配線は本 ADR では決めない**(別 ADR/ADR-261 の段階 2 と一本化)。決めるべき未決の問題(レビュー B1・M7):
  1. **観測ストアの新鮮さ**: `derive_filtered`(`observation_store.rs`)は High を「新鮮(`OBSERVATION_FRESH_WINDOW_MS = 3_000`)な最新の 1 件」でしか採らない。メニューの読みは 3 秒で落ち、観測の無い窓では後続の High が無いので、その後は Medium や `desired_open` に戻る。
     持続させるなら `desired_open` を揃える専用の経路(`ModeKeyPassedThrough { align_desired }` 型)が要るが、それは `ime-belief-architecture.md` の「直接書き込みの正当な例外」の追加で、dylint `ime_event_guard` と `architecture_guard` の件数固定の更新を伴う。
  2. **GJI の I/O 推論との順序**: メニューで IME を閉じた直後は GJI の I/O 推論が ON を立てる([BUG-203](../known-bugs/BUG-203.md))。**メニュー選択の直後の GJI I/O は開閉の証拠にしない**を入口条件に入れる。
  3. **新しい `ObservationSource`・`InputModeObserved` の作り方**: `observation_source_guard` と `architecture_guard.rs::input_mode_observed_construction_sites_are_accounted_for` の更新、`classify_*` 経由の純粋関数化が要る(規約)。
  4. **confidence**: H1(インジケーターが実状態と逆)が否定されるまで、High にしない(Medium 以下、または shadow のみ)。
  5. `authority() = BeliefOnly`(`derive_actuating` に入れない。drift correction の書き込みを引き起こさない)。ADR-262/263 の書き込み直後の読みは採らない。

### 決定 6: プライバシー・安全・オプトイン

- **画面を撮らない**(ADR-261 と違い、画素を取り込まない)。決定 1 により、**インジケーターの上で開かれたメニューだけ**を読み、他のアプリの右クリックメニューは UI Automation で読まない(カーソル位置の判定だけ)。
  読むのはメニュー項目の `AutomationId` と `IsSelected` だけで、同定に失敗したものは破棄し、保存しない。
- **既定はオプトインにして ADR-261 と同じスイッチに揃える案**(所有者判断 Q)。UI Automation(アクセシビリティ API)は画面の取り込みより穏当だが、「WinEvent の監視 + UI Automation の読み取り」はウイルス対策の行動検出に当たりうる。D0 で確かめる。
- UI Automation の読み取りが固まる恐れ(ワーカーとタイムアウト、連続失敗でそのセッションの停止)。

### 決定 7: メニューの間は、メニュー窓へのフォーカスを窓の切替として扱わない([BUG-202](../known-bugs/BUG-202.md))— 決定 4 の前提

メニューの項目がハイライトされる(マウスのホバー・キーボード)と、メニュー窓(クラス `#32768`)への `EVENT_OBJECT_FOCUS` が出て、awase の focus 追跡がそれを窓の切替として拾い、`tsf-gate` の `PendingWarmup`(保持キーの解除)と UIA 分類が走る
(上の実測。メニューを開く・読むだけでは起きない)。**`MENUSTART`〜`MENUEND`(同じスレッド)の間は、`#32768` のクラスの窓へのフォーカスを、`focus-sync`・`HwndCache` の保存/復元・`tsf-gate` の遷移の対象にしない**
(メニューの間は元の窓にフォーカスが残っているものとして扱う)。これは本案に固有でなく、**どのアプリの右クリックメニューでも項目をホバーすれば起きうる既存の挙動**で、本案の有無に関わらず直す価値がある。
**決定 4・5 の belief 配線の前提**(ホバーを挟む操作で `FocusGen` が変わるため。レビュー M7)。`focus_tracking.rs` 系は再発ファミリー(`fix-requires-evidence`)なので、直すときは golden か journal のテストを足す。

## 却下案

- **awase が周期的・契機でインジケーターを右クリックしてメニューを開いて読む**: メニューが利用者の画面に出て、フォーカスを奪い、入力を妨げる。読むのは利用者が開いたときだけ(決定 0)。
- **メニューの画面を撮って画像で読む(ADR-261 の字形と同じ手法)**: `IsSelected` が UI Automation で直接読めるので不要。
- **項目名(「ひらがな」等)で判定する**: 表示言語で訳される(ja-JP は未測定)。`AutomationId` を使う(決定 3)。
- **`WH_MOUSE_LL` で右クリックを検知する**: 遅延とウイルス対策の面で重い。WinEvent で足りる(決定 1)。
- **項目の並び順で判定する**: 版・言語で並びが変わりうる。ID が取れないときの診断にだけ記録する(メニュー窓配下の項目数は、測定した範囲では MS-IME 16 件・GJI 11 件で一定。「状態で増減する」という以前の主張は測定の誤りだった)。
- **選んだ項目を `idChild` で検知する**: 決定 5(クリックを示すイベントが無く、区切り線・サブメニュー・ホバー後の取り消しで誤判定する)。段階 1 では採らない。
- **メニューの読みを belief へ直接入れる**: 決定 5(新鮮さの窓・GJI の I/O 推論・FocusGen・H1 の未確認)。ADR-261 の段階 2 と一本化して別レビュー。

## 段階

推奨の順(レビュー M8):

1. **決定 7(BUG-202)を独立に直す**(本 ADR と無関係に価値がある)。BUG-203 の調査も同時に。
2. **段階 0**: M0-1(一太郎の実機)と M0-8(管理者権限)を最優先。M0-3(物理キー相当の再測定)・M0-2 の取り直しは CI。M0-1 が否定的なら、本 ADR は #623 には効かない(他の窓には使える)。
3. **段階 1(shadow)**: `observer/` に WinEvent の検知(決定 1)と UI Automation の読み取り(決定 2)、`state/` に純粋な同定・対応表(決定 3)。**メニュー読み × 字形 × belief の三つ組を journal に出す**(決定 5)。belief には入れない。
4. **段階 2**: belief への配線は、ADR-261 の段階 2 と一本化し、決定 5 の未決の問題を解く別 ADR/追記でレビューする。
5. **段階 3**: 設定画面にオプトインの説明(ADR-261 と同じスイッチ)。
