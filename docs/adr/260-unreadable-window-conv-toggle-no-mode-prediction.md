# ADR-260: 読めない窓の状態依存のトグルキー(英数)は、入力モードを予測しない(B1)

## ステータス

起草(2026-10-15)。Opus 敵対的レビュー前。コードは変えていない。測定は使い捨てのスパイクブランチ `exp/mode-key-recheck`
(develop にはマージしない)の GitHub Actions(`sc-exp-modekey-*`、run 38669329177・38670546888・38674632947)による。

## 背景

不具合報告 `01M4QSFH1B02DQ9B8AXBYVRQ39`(GJI・一太郎、issue #623)に 2 つの問題がある。

1. 実 IME の状態と awase の belief がずれる(app log: 別アプリで IME OFF にして一太郎へ移ると、141 秒前の ON を `HwndCache` から復元する)。
2. **英数を押しても入力モードのずれが解消しない**(タスクバーは OFF なのに入力は全角、IME ON にするとローマ字。ちょうど逆転する)。本 ADR は 2 を扱う。

### 機序(CI の awase.log と、コードの読解で確認した)

- 英数の予測は、belief の開閉と変換モード(`track.conv` → 観測の `conv_raw` → belief の入力モードから推定、の順)からの表引きである
  (`key_effect_predictor.rs::predict_in_table`)。窓の読めなさ(`unreadable`)で変わるのは変換(0x1C)の規則だけで、英数には何もしない。
- 開状態の英数は、プリセット(MS-IME・ATOK)でかな(C19)↔半角英数(C10)を入れ替えるトグルである。belief の入力モードが実機と逆位相だと、
  予測も実機も同じ向きに反転し続け、逆位相が固定される。
- awase は実 conv を**読んでいる**のに採らない。CI の awase.log(`tsf`・`sync` の 1 試行): 英数の 30ms 後から約 300ms、
  `[skip-typing-read] conv=0x00000010`(半角英数)を読み続けたが、belief は「かな」と予測したまま Engine を活性化した。理由は 3 つ:
  - 打鍵時点の予測が付いたキーは、直接観測の窓内の読みを採らない(`follow_direct_read_in_scope`、ADR-188 追記6。
    IME の処理が窓より遅いと窓内の読みは処理前の古い値で、正しい予測を覆してしまうため)。
  - 打鍵中(`TYPING_IDLE_MS`=500ms 未満)の読みは `SkipTyping` で捨てる(`decide_read_strategy`)。
  - 窓が閉じた後は、読めない窓ではポーリングが止まり、誰も読み直さない。
- つまり、予測が外れたときにそれを直す経路が無い。ADR-188 追記6 の懸念(古い読みで正しい予測を壊さない)を優先した結果である。

### 実測(GitHub Actions windows-latest、GJI の MS-IME プリセット)

`typing_stress --mode=keymatrix` / `chrome_probe --keymatrix` で、英数(0xF0)を belief と実 IME のずれ(`close`=awase が ON を書いた後に外から閉じる /
`fresh`=awase 再起動で未知 / `sync` / `open`)で押し、直後のかな単打の結果から Engine と実 IME の組み合わせを読む(`tsf` の読み方:
`か`=Engine ON+かな〔正常〕、`ｗ`=Engine OFF+かな〔ずれ〕、`w`=Engine OFF+英数/閉〔一致〕、`ka`=Engine ON+英数/閉〔ずれ〕)。
読める窓(`edit`)は常に追随した。読めない窓では、従来は `tsf` で 120/180(3 run)、実 Chrome で 74/180 がずれた(下表)。

## 決定

### 決定1: 読めない窓の開状態のトグルキーは、入力モードを予測せず、追跡も捨てる(B1)

`predict_in_table` で、次をすべて満たすとき、`effect.mode = None`・`track.conv = None` にする。

- `input.unreadable`(読めない窓。窓の種類の判定は ADR-209 と同じ `cannot_verify_real_ime_state` かつ `InputRelay` でない)。
- 開状態(`input.open`)で、押した後も開(`c.after_open`)。
- **表のデータから**、この打鍵が変換モードを入れ替えるトグルと判定できる: 現在の変換モードの行の `after_conv` が反対側(C19↔C10)で、
  反対側の変換モードの行の `after_conv` が現在の変換モード(`is_conv_toggle`)。キー名(英数)を決め打ちしない。

開閉の予測(`effect.open`)は変えない(開のまま)。閉状態の英数(閉→開・かな)は対象外(開閉の軸は予測が正しい多数派)。

効果: 開閉・入力モードとも変わらず、追跡も変わらない打鍵は `apply_key_effect_prediction` が何もしない。`ImeEvent::KeyEffectPredicted` が
fence を進めず、`key_effect` に予測が残らないので、「予測が付いたキーは予測に任せる」の対象から外れ、**既存の直接観測の窓が働く**
(読める窓では、読んだ実 conv で belief が直る)。読めない窓では観測が無いので、belief は動かない。

### 決定2: 範囲

- 新しい設定項目は足さない。`unreadable` の条件(`predict_henkan_open_in_unreadable_windows`、既定 true)をそのまま使う。設定の名前は変換規則由来だが、
  「読めない窓の予測」を止める 1 つの設定として扱う(`false` なら従来どおり)。
- 学習表(`predict_with_override`)の予測にも同じ判定をかける(`predict_in_table` を通るので、表の出どころによらない)。
- CUSTOM の表に英数の行があると同梱表の予測は打ち切られ(ADR-209 決定4)、学習表のセルがあるときだけ予測が付く。その場合も同じ判定が働く。

## 実測(B1 の効果と、却下した案)

ずれの試行数(`f0=tog:close/fresh/sync/open`・`on:sync`・`on:fresh` の 6 セル × 3 run = 180 試行)。2〜3 周目。

| 案 | `tsf`(読める)1文字目 | 実 Chrome(読めない)1文字目 |
|---|---|---|
| 従来 | 132 | 75 |
| **B1** | **0** | **30**(`close`・`on:fresh` は 0) |
| A(窓が閉じた後に 1 回読み直す) | 0 | 66(`close` が 15→23 に悪化) |
| Z(A の読み直しを入力モードの軸だけ) | 1 | 70(`close` が 24 に悪化) |
| B2(入力モードを不明に戻す) | 25/40(1周目) | 30/40(悪化) |
| X(打鍵の結果から推定) | 102 | 90 |
| B1 + X | 0(2文字目は 45 に悪化) | 31 |
| B1 + Z | 0 | 18(各セル 20 試行) |

- 報告の症状に一番近い実 Chrome の `close`(belief が古い ON、実 IME は閉)は、従来 15/30 → B1 0/30。
- 実 Chrome の `tog:open`(belief が OFF、実 IME は開)は、B1 でも 30/30 ずれる(下の「残る穴」)。

## 却下した案

- **A / Z(窓が閉じた後に 1 回読み直し、予測と食い違えば観測を採る)**: 読める窓では B1 と同じく 0 にするが、実 Chrome では悪化した(読みが信頼できない。ADR-205 の知見と同じ)。
  開閉の軸を外した Z でも悪化したので、開閉の読みだけが原因ではない。B1 と併用しても利益は無い。
- **B2(入力モードを `Unknown` に戻す)**: `effect.mode = Some(Unknown)` は予測として `key_effect` に残るので、直接観測が採られない。さらに次の打鍵で予測器が
  `Unknown` を種としてかな(Engine ON)にする(`seeded`)ので、実機が英数だと「英数なのに Engine ON」になる。
- **X(GJI の候補ウィンドウの SHOW を打鍵の結果の証拠にする)**: 実 IME が英数の試行でも SHOW が来て、belief を「英数→かな」に誤って直した
  (B1 に足すと `tsf` の 2 文字目が 0→45 に悪化)。SHOW は組み立て中の信頼できる証拠ではない。作り直すなら別の信号が要る。
- **Y(読めない窓の古い ON のキャッシュを復元しない)**: **未検証**。CI の再現手順(外から閉じてフォーカスを外して戻す)が `HwndCache: restore` を通らず、
  `[exp-y]` が 0 件で、5 構成とも結果が同一だった。ADR-165(「時間条件は設けない」、仮想デスクトップ往復の復帰が根拠)と衝突するので、
  報告の流れ(別アプリで OFF → 一太郎へ戻る)を再現できる手順ができてから別に扱う。
- **ユーザーへの案内(冪等キー・警告)**: Ctrl+無変換/Ctrl+変換による強制の解消が既にあるので、この ADR では何もしない。

## 検証(実装時)

- 純粋関数の単体テスト(Linux): 読めない窓の開状態の英数(MS-IME・ATOK の両プリセット、C19・C10 の両方)は `effect.mode`・`track.conv` が `None`。
  読める窓・閉状態の英数・トグルでないキー(ひらがな 0xF2 など)・変換モードが表に無い場合は従来どおり。`is_conv_toggle` は表のデータで決まること
  (スパイクで追加した単体テストを持ち込む)。
- 既存の goldens・journal replay・`architecture_guard` が通ること。
- CI に `sc-eisu-km-{tsf,chrome}-*`(本 ADR の測定構成)を残し、観測のまま継続。判定を付けるのは、読める窓の `tsf` の `typed` がすべて正常のとき。

## 残る穴・未確認

- **実 Chrome の `tog:open`**(belief が OFF、実 IME は開): 予測で見分けられない。多数派(belief OFF と実 IME が一致)に合わせた現状が妥当で、観測が要る。
- **実 Chrome の 2 文字目の `fresh`**(従来でも 29/30 ずれ): 1 文字目の `ka`(英数)の後に、別の仕組み(literal 回収など)が Engine を ON に戻すためと思われる。B1 の範囲外。
- belief が一致していて実機がトグルしたとき(`sync`)、読めない窓の belief がどう追随したかは**未特定**(実 Chrome の `tog:sync` は従来も B1 も 0/30)。ADR-238 の英数候補など、
  既存の観測が働いた可能性があるが、ログで確かめていない。
- 測定は MS-IME プリセットの表(`keymap=2`)と、`ime_toggle` 付きの構成だけ。ユーザーの CUSTOM 表+学習表の組み合わせ・一太郎(`ImmCapability::Unavailable`で読み自体が不可)は未測定。
- 1 回の環境(`windows-latest`)・試行間の状態の引き継ぎ(5/5 に割れる偶奇)。実機の確認は未実施。
