# ADR-261: 観測の無い窓の IME 状態を、タスクバーの入力インジケーターの字形から読む

## ステータス

起草(2026-10-15)。実装なし。ADR-259(PR #624)・ADR-260(PR #626/#627)とは独立に書いているが、`docs/adr/index.md` の同じ位置に行を足すので、
後からマージするものに軽い衝突が出る。測定は `exp/mode-key-recheck`(HEAD `9cf0ae0f`)の run 38717579288・38761351107・38810058235・38810649639・38811194999・
38811705842・38812641962 による。

## 背景

不具合報告 `01M4QSFH1B02DQ9B8AXBYVRQ39`(GJI・一太郎、issue #623)に 2 つの問題がある。

1. 実 IME の状態と awase の belief がずれる。app log: 別アプリで IME OFF にして一太郎へ移ると、`HwndCache: restore ime_on=true (141688ms ago)` で古い ON を復元し、
   `FocusProbe: ime_on=true(shadow)` と belief が ON のまま。一太郎(`taro36.exe`/`JsTaroCtrl`)は `[imm-learning] 降格: Standard → Imm32Unavailable`
   (`ImmCapability::Unavailable`)で、窓内の IMM が読めない。journal の観測は `ObserverPoll` 1 件のみ(`FocusChanged.profile` は降格前の `ImmCross` を記録するので、journal だけでは読み違える)。
2. 英数を押しても入力モードのずれが解消しない。所有者は 2 を重く見ている(「英数を押してモードずれが解消しないことの方を問題視」)。

**報告者自身の記述(本 ADR の前提を左右する)**: 「他のアプリで IME オフの状態で一太郎に移動すると、**タスクバーは IME オフになっているものの、入力は全角**。IME オンにすると、
ローマ字入力になる」「IME オフと、ひらがな入力のモード表示が**ちょうど逆転している**ようです」。この文面は、(H1)一太郎ではインジケーターが映すスレッド/コンテキストが実際の入力と別物である、
(H2)一太郎(アプリ側)の挙動である、(H3)awase の belief だけがずれている、のどれとも読める。H1 なら字形は誤った証拠を足すだけで、本 ADR は #623 に効かない。
**一太郎の実機で、インジケーターの表示と実際の入力が一致するかを先に測る(D0-2)ことを、段階0 の最初の go/no-go とする。**

[ADR-260](260-eisu-toggle-no-mode-prediction-when-observable.md) は、窓内の IMM の読みが**効く**窓(`tsf` フォーム・実 Chrome。プロファイルは `Imm32Unavailable` でも
`[direct-follow]` が約 25ms で追随する)で、英数トグルの入力モードを予測しないようにして 2 を直す。**観測の無い窓**(報告の一太郎のように
`ImmGetDefaultIMEWnd` が NULL で読み自体ができない窓)には効かない(ADR-260 の測定で、観測の無い窓を模した `noread` は従来と変わらなかった)。#623 はこの窓の問題であり、
ADR-260 だけでは閉じない。

観測の無い窓で awase が頼れる情報は、打鍵時の予測(ADR-191)・`HwndCache` の古い値・間接観測(GJI プロセス I/O、`ObservationSource::GjiIoInference`、`ObservedEisu→AssumedRomaji` の
一方通行のみ)だけで、**実 IME の現在の状態を直接読む手段がない**。ADR-191 の実測では、GJI の開閉・変換モードは TSF スレッド単位で保持され、窓を離れている間に変化しない。
つまり「窓を移ったときの推測が悪い」より、離れる時点の belief が窓内の操作と逆位相になっていることが多い。直接読めれば、推測ではなく証拠で直せる。

### 着想と、所有者の判断

Windows のタスクバーは入力インジケーター(「あ」/「A」など)を描いており、これは別プロセスの TSF スレッドの状態を反映する。画面上の矩形を読む案は所有者が出した
(「画面上の矩形を使うアイデアはありませんでした。脆いというのはそうだけど、今のどうしようもない状況が少しでも改善できるんだったら使っていい」)。さらに、
字形と状態の対応は「**IME キー学習で作る**」案(所有者)、読む場面は「**観測の無い窓だけ。マウス操作・Alt+Tab・タイピングのときに、抑止機構つきで**」(所有者)。
本 ADR はこの 2 つを設計に落とす(表の作り方は、レビューで見つかった DPI・settle・失効の問題から、受け身の収集を主・学習を補助とする案に直した。所有者判断 Q1)。

### 実測(GitHub Actions windows-latest。いずれも 1 環境: 1024×768・DPI 100%・既定テーマ・en-US)

- **UIA の Name・HelpText・LegacyIAccessible は状態では変わらない**(`IME is disabled`/`Right click to show IME options` の 2 値が、フォーカスとプロファイルの有効化で替わるだけ)。
  読めるのは画面上の字形だけ。
- **字形ハッシュは実 IME の状態に追随する**。インジケーター要素(`SystemTray.NormalButton`、名前 `Tray Input Indicator…`)の矩形 32×48 を取り込み、
  背景との差が閾値を超える点で 2 値化して FNV でハッシュした。
  - **GJI(run 38761351107、自前の窓 26 押下 + キー列 61 押下 × 2 プリセット)**: この環境では 6 モードが衝突せず別のハッシュ(各状態 3〜26 件)。ひらがな `d49577`・カタカナ `385e42`・全角英数 `069551`・
    半角カナ `9812cd`・半角英数 `0bbfa6`・閉 `def643`。MS-IME プリセットでも ATOK プリセットでも同じハッシュ(字形は IME の入力モードの表示で、キー配置に依らない)。
    全角英数と半角カナは通常のキーでは届かないので、GJI のカスタムキー表で `InputModeFullAlphanumeric`/`InputModeHalfKatakana` を F5〜F9 に割り当てて作った。
  - **本物の MS-IME(run 38810058235、IMM の書き込み 30 + キー注入 36)**: 別のハッシュ体系。ひらがな `eb8708`・カタカナ `c6b2e9`・全角英数 `37fb64`・半角カナ `490507`・閉 `691729`。
    **本物の MS-IME では半角英数と閉が同じ状態・同じ字形**(半角英数を書くと閉になる)。区別できるのは 5 つ。本物の MS-IME は IMM の書き込みが効く(GJI では効かない)。
  - **`Imm32Unavailable` プロファイルの窓(実際には IMM が読める)でも追随する**: 実 Chrome×本物の MS-IME 34 押下で字形は API の開閉と全件一致、tsf フォーム×本物の MS-IME 18 押下も全件一致。
    **`ImmGetDefaultIMEWnd`=NULL の窓(観測の無い窓、一太郎)では 1 件も測っていない**。
    実 Chrome×GJI カスタム表(run 38811194999・38811705842・38812641962)は ひらがな 9/9・カタカナ 3/3・半角カナ 3/3・全角英数 3/3・半角英数 2/3
    (1 件は閉の字形、タイミングの疑い)。
  - **遅れ**: 押下から字形が最初に変わるまで、中央 0.18 秒・最大 0.68 秒(60 件。run 38717579288、実 Chrome・tsf フォーム×GJI の 2 プリセット、awase 起動あり。**フォーカス切替後の遅れではない**〔D0-1〕)。
- 字形の 64bit FNV ハッシュのうち、本文の 6 桁は先頭だけ(表には 64bit 全部を持つ)。2 値化の閾値(背景の平均との差が 20 超)の感度は未測定(D0-5)。
- **環境依存**: 矩形は GJI の run で (822,720)–(854,768)、本物の MS-IME の run で (778,720)–(810,768) と、トレイの並びで位置が変わる(UIA で毎回探す必要がある)。

### 測定で踏んだ罠(同じ失敗を繰り返さないために記録する)

- **2 値化を「平均より明るい点」だけにしたため、明るい背景に暗い字形(本物の MS-IME の黒い「A」)が全部空白になった**。その結果「GJI は区別できるのは 3 クラス、
  カタカナ・全角英数・半角カナ・閉は空白で同一」「本物の MS-IME では動かない」と**誤結論を出した**(報告済み)。画面を実際に保存して見て(`--shots`)発覚し、
  `abs_diff(mean) > 20` に直して 6 モードが分かれた。**結論を出す前に画像を見る**。
- IMM(`WM_IME_CONTROL`)で変換モードを書いても、GJI では読み戻しは変わるが**字形は動かない**(GJI の内部状態と食い違う)。状態はキーか GJI のカスタムキー表で作る。
- 1 回目の集計で「ずれ 16/93」と見えたのは、押下から 1.8 秒後の字形を取ったため、keymatrix のセットアップが約 1.3 秒後に状態を戻す変化を拾ったノイズ。
  時系列で見ると字形は押下の 0.1〜0.2 秒後に追随していた。
- 学習(`awase-keymap-learn-win`)は自前の EDIT を `ImmGetOpenStatus`/`ImmGetConversionStatus` で読むだけで IMM に書かないので、「GJI では IMM で書いても字形に出ない」罠は学習には当たらない。
- `ime_key_matrix_spike` の `--seq` は、フックが認識するキー(F5 等は無し)しか記録しない。本物の MS-IME で F5/F6(ローマ字)を押すと入力欄のフォーカスを奪い、以後の IMM 読み取りが失敗した。

## 決定

### 決定 0: 原則 — 書かない・推論しない・表に当たったときだけ

字形は**実 IME の状態を読む証拠**であり、IME へは何も書かない(actuation を足さない。ADR-212 の方向、所有者の「窓に移ったときの強制書き込みはやめる」と整合)。
**表に無いハッシュ・環境指紋が合わないとき・矩形が見つからないとき・タスクバーが覆われているとき・フォーカスがずれたとき・IME が無効のとき・点の数が少なすぎるときは何もしない**
(否定的な証拠から閉を推論しない、ADR-227 の所有者方針)。「空白=閉」のような決め打ちは置かない。
**前提**: 狙う窓(一太郎)でインジケーターが実際の入力を映していること。これは D0-2 で確かめるまで仮定にすぎない(背景の報告者の記述)。

### 決定 1: 観測 — `observer/` の新 probe と、`state/` の純粋な分類

- `observer/`: インジケーター要素を探して矩形を得る。**表示言語に依存しない探し方にする**(測定のプローブは `Name.starts_with("Tray Input Indicator")` の英語名で探しており、日本語 Windows では
  名前が訳される。クラス名 `SystemTray.NormalButton`・AutomationId・トレイ内の位置関係で探す。D0-4 で ja-JP を測る)。
  UIA は既存の `focus/uia.rs` の専用ワーカースレッド(STA + mpsc)に相乗りさせ、要素をキャッシュして `CurrentBoundingRectangle` だけを取り直す(`FindAll(Descendants)` を毎回払わない。
  `run_with_timeout` はスレッドを毎回作り、固まりでリーク上限 8 を食うので使わない)。層ルール(`architecture_guard`/dylint)で `observer/` から UIA を呼べるかを実装時に確かめる。
- 取り込む前に、矩形の中心が**タスクバー自身**であること(`WindowFromPoint` が `Shell_TrayWnd` 系)を確かめる。全画面アプリ・自動非表示では UIA の矩形は取れても BitBlt は前面アプリの画素を取る。
  ロック画面・セキュアデスクトップ・RDP 切断・explorer 再起動で GetDC/BitBlt が黒や失敗になる場合も `Miss` にする。
- 画面の矩形を GDI で取り込み、明暗の両側で 2 値化(背景の平均との差の絶対値が閾値超)し、64bit の FNV ハッシュにする。**2 値化後の点が最小数に満たないとき(一様な画像・黒・覆われた領域)は
  `Miss(EmptyGlyph)`**(測定の誤結論のとき、空白と閉が同じハッシュになった)。
- UIA の Name(`IME is disabled`/`Right click to show IME options` 型の「IME が有効か」の 2 値、実測)は、IME 無効の窓(パスワード欄等)で閉の字形と取り違えないための前提条件の候補。
  文字列そのものは表示言語で変わるので、**2 値のどちらが「有効」かは、読める窓で IME が開いている(直接の読み)ときに出ていた値として実行時に覚える**(言語に依らない)。
  覚えるまでは判定に使わず、shadow の記録(journal)にだけ残す。無効の判定を決定0 の「何もしない」へ組み込むのは段階2 の入口条件とする。
- 戻り値は `GlyphSnapshot { hash, dots, rect_size, taken_at, focus_gen, focus_thread }` だけ(画素は保持しない)。**字形はキーボードフォーカスのスレッド(`GetGUIThreadInfo.hwndFocus` のスレッド)の状態を映すのか、
  前面スレッドか、入力方式の既定か**は未測定(D0-2/D0-10)なので、両方のスレッド ID を記録する。
- `state/`(OS 非依存の awase-windows-core、Linux でテストする): `classify_glyph(&GlyphTable, &Env, &GlyphSnapshot) -> GlyphReading`(`Hit { class }`/`Miss(理由)`)。
  判断はここだけに置く(観測側に `if` を書かない。`.claude/rules/ime-belief-architecture.md` の Observe → classify → reduce)。`Env`(DPI 等)は observer が取り、`classify_glyph` へ値で渡す。

### 決定 2: 表のキーは `GlyphClass`。表は「受け身の収集」を主、IME キー学習を補助にする

**表のキー**: 学習の `Status { open, mode: raw & 0x0B, composing }` は字形と 1 対 1 ではない(閉でも mode を持ち、composing は idle と同じ字形になり、本物の MS-IME では半角英数と閉が同じ字形)。
そこで表のキーを `GlyphClass`(写し方: **閉は mode を落として 1 つ**、composing は落とす、MS-IME では {閉, 開+0x00} を 1 クラス、GJI は 閉(1 クラス)と 開 × {ひらがな,カタカナ,全角英数,半角カナ,半角英数})とする。
衝突の判定は `GlyphClass` の単位で行い、**同じハッシュが異なる `GlyphClass` に付いたときだけ**そのハッシュを無効にする(同じクラスの Status が複数あっても衝突ではない。閉の字形を消さない)。
写し方は実データで検証する(閉×各 mode が同じハッシュか、composing が idle と同じか。D0-11)。ハッシュは 64bit 全部を持つ。

**作り方(案、所有者判断 Q1)**:
- **主案: 受け身の収集**。`direct-follow`/`idle-conv-check` が効く窓(読める窓)で、直接の読み(High)から (開閉, 変換モード) が確定したときに、同時に読んだ字形を `GlyphClass` と組にして記録する。
  **組にする条件(B-R2-1・B-R2-2)**: ① 字形の安定化: 直接の読みは約 25ms で変わるが、字形は 0.18〜0.68 秒遅れる。直接の読みが変わった直後の字形は前の状態を映すので、
  **直接の読みが変わってから、字形のハッシュが最大遅れ(実測 0.68 秒)に余裕を足した時間以上同じ値で続いたとき**だけ組にする(または「直接の読みが T 秒以上変わっていない状態で読んだ字形」だけ)。
  T は D0-9 の実測から tuning 定数にする。② **awase 自身の書き込みの直後は組にしない**: awase は今も `IMC_SETCONVERSIONMODE` を送る(`imm.rs`、唯一の送信点は `conv_mutation.rs` で世代を上げる)。
  GJI では、IMM で書くと読み戻し(直接の読み)は変わるが字形は動かない(測定の罠)ので、`conv_mutation` の世代と awase の actuation(`apply_sync`・open chain)から一定時間内の組は、収集にも
  段階1 の一致率の正解にも使わない。
  利点: 学習の操作が要らず(既存の利用者も、学習し直すまで表が無い問題がない。学習は設定画面のボタンからしか走らない)、**awase.exe 自身が取るので DPI の扱いが実行時と同じ**
  (学習プロセスは DPI 非対応で動き、awase.exe は PerMonitorV2 のため、125%/150% で学習時と実行時のハッシュが食い違いうる)、環境が変わっても自動で作り直せ、普段使うモードが自然に集まる。
  欠点: 利用者が使わないモード(GJI の全角英数等)は集まらない。表に無い状態は `Miss` になるだけで害はない。
- **補助案: IME キー学習への相乗り**(所有者案)。学習は各状態に到達した時点で (開閉, 変換モード) を知っているので、字形も記録できる。ただし、そのままでは前の状態の字形に次の状態の名前が付く:
  学習の `settle()` は約 44〜53ms・上限 150ms(`driver.rs`・`settle_tuning.rs`)で、字形の遅れ(中央 0.18 秒・最大 0.68 秒)より短い。**IMM が settle した後、ハッシュが X ms 変わらないこと**を記録の条件にする
  (X は D0 の実測)。1 押下あたり最大約 0.7 秒が足され、学習時間が最大約 10 倍になりうるので、(a)各状態に初めて着いたときに 1 回だけ読む、(b)巡回の後に状態ごとの短い確認の巡回を別に回す、のどちらかにする。
  学習プロセスの取り込み処理は、awase.exe と**共有のクレート**に置き、DPI の扱いをそろえる(D0-4 に「学習プロセスで作った表が awase.exe で当たるか」)。
- **永続化**: 学習表の `CURRENT_SCHEMA_VERSION`(= 2、`from_json` は版が違えば拒否し、staleness で内蔵表へ戻る)を**上げない**。字形の表は**別ファイル**にする
  (版を上げると、学習済みの利用者全員のキー効果予測が内蔵表へ戻る)。保存の単位は TIP ごとではなく `TipIdentity`(`driver.rs`)ごとのエントリにする(学習表は 1 ファイルで IME 種別をタグとして混ぜるだけ)。

### 決定 3: 環境指紋 — 表を作ったときと違う環境では使わない。ただし厳しさより「当たらない・空白を拒否する」を効かせる

`EnvFingerprint` = DPI スケール、インジケーター矩形のサイズ、タスクバー背景の明暗、OS の**メジャービルド番号のみ**(UBR まで入れると月例更新で毎月失効する)、`TipIdentity` と IME の版
(GJI Converter の版は `env_version.rs` が既に持つ)、**取り込み方式の版**(2 値化の閾値・矩形の取り方。変えると全部の表が無効になる)。一致しなければ表を使わない。
誤ヒットの実害は「旧環境の状態 A のハッシュが、新環境の状態 B のハッシュと偶然一致する」ときだけで、実質は空白・一様な画像の場合に限る。したがって指紋より、**決定 1 の最小点数の拒否**と、
**読める窓での継続的な突き合わせによる表の自動失効**(決定 2 の受け身の収集で、**決定 2 の安定化・書き込み直後の除外を通った**組が直接の読みと食い違う状態が続けば、該当エントリを失効)のほうを効かせる。失効の回数/割合と、失効したエントリの再収集を許すか(許さないと、遅れの残りの誤組 1 回で恒久的に消える。許す前提)は D0 の実測から tuning 定数にする。

### 決定 4: 使う窓

- **段階 1(shadow)では、読める窓でも読む**(直接の読み High と字形を突き合わせて「正解のある」一致率を出すため。決定 6)。
- **段階 2 で belief に入れるのは観測の無い窓だけ**。判定の述語は、`ImmGetDefaultIMEWnd(hwndFocus)`=NULL、または「この `FocusGen` で `direct-follow` の読みが N 回失敗」とする
  (`ImmCapability::Unavailable` は実 Chrome にも付くので使えない。静的な「読める/読めない」の分類はコードに無い。N は D0 の実測)。読める窓では直接の読みが優先で、二重に解釈しない(ADR-260 と重ならない分担)。

### 決定 5: 読む場面と抑止(数値は D0 の実測で決める)

- 読む場面: ①フォーカス/前面の変化(`SetWinEventHook` の `EVENT_SYSTEM_FOREGROUND`/`EVENT_OBJECT_FOCUS`。**マウスフック `WH_MOUSE_LL` は新設しない**。遅延と AV の両面で重い)から settle 後、
  ②その窓の最初の打鍵まわり。マウスでインジケーターを直接クリックした直後は、ホバーの強調で背景が変わって `Miss` になりやすく、効く場面が減る(害は無い)。
- **字形の遅れの前提**(中央 0.18 秒・最大 0.68 秒): 読んだ時点の字形は、実 IME の最新状態とは限らない。打鍵の判断を待たせない(結果は次の判断から効く)。
- 抑止: 具体的な回数/分の上限、最短読み取り間隔、同一 `FocusGen` で結果が変わらなければ再読しない、連続 `Miss` のバックオフ、UIA・GDI の連続失敗でそのセッションを停止、
  インジケーターが見つからない(自動非表示・トレイのオーバーフロー・「デスクトップ言語バーを使用」設定)ときは停止。**値は tuning 定数にし、D0 の実測 ms/回数を添える**
  ([tuning-constants](../../.claude/rules/tuning-constants.md))。await をまたぐ失効判定は `FocusGen` で行い、読んだ時点と適用時点でフォーカスが変わっていれば捨てる。
- 字形が前面スレッドとフォーカススレッドのどちらを映すかは D0-2/D0-10 で決まるまで未確定なので、**段階 1 では「前面窓が対象窓でないとき捨てる」を置かず、両方のスレッド ID を記録する**。捨てる条件は D0-10 の結果で決める(段階 2)。

### 決定 6: belief への入れ方 — 段階 1(shadow)と、段階 2 の入口条件

- **段階 1(shadow)**: belief には入れない。journal と不具合報告(ADR-148 型の allowlist: `glyph_probe { env_match, hits, misses, reason 別件数 }`。ハッシュは環境固有で個人情報ではないが、
  未知ハッシュは `WindowFromPoint` でタスクバーと確認できたものだけ、最大 3 件)にだけ出す。
  **一致率の正解**は belief ではなく(観測の無い窓の belief はずれが既知の量)、①**読める窓での、直接の読み(High)との一致**(ただし決定 2 の安定化と、awase 自身の書き込み直後の除外を通った組だけ)。
  ②観測の無い窓の正解は、自動では取れない(ADR-188 の窓内の読みは IMM が読める窓が前提で、raw TSF リテラル検出も一太郎で働くかは未確認、残るのは利用者の打ち直しだけで弱い)。
  **観測の無い窓の一致は D0-2 の手動の記録(実機で、実際に打った出力)でしか取れない**。段階 2 へ進む判断は、読める窓の一致率と、一太郎の実機での手動の確認の 2 本立てにする。
- **段階 2 の入口条件(別 ADR/追記でレビュー。本 ADR では配線を決めない)**:
  1. **遅れによる予測の上書きを防ぐ(B3)**。`ime_model.rs` の `reconcile_key_effect_open`/`_mode` は、予測時刻から `KEY_EFFECT_SETTLE_MS`(170ms)を過ぎて Medium 以上の観測が来ると予測を消し、
     `most_recent_trusted`(`observation_store.rs`、Medium 以上 → 時刻の順で選ぶ=新しい Medium が古い High にも勝つ)へ落ちる。字形の遅れ(最大 0.68 秒)は、押す**前**の状態を映した字形を
     押下より新しい時刻で届け、正しい予測を消して古い状態を belief に入れる。**(b)同じハッシュが最大遅れ以上続いたときだけ `GlyphSnapshot` を出す(安定化。observer 側で完結し、reduce を変えずに済む。決定 2 の収集の安定化と同じ仕組み)を第一にする**。
     (c)打鍵後 N ms 以内の字形は報告しない(N は D0-9 の実測。tuning 定数)を併用してよい。(a)観測時刻を「読んだ時刻 − 最大遅れ」にする案は、`reduce` が envelope の時刻
     (`ime_model.rs` の `ObserverReported` アーム、`observation_store.rs` の `record_replayed`)を使うので、observer が時刻を遡らせても fence にも `most_recent_trusted` の順位にも効かない。
     (a)を採るなら `ObserverReported` が内容の時刻を持ち reduce がそれを使う変更(reduce の唯一の書き込み点への変更でレビューが重い)が要るので、採らない。入力モード側(`InputModeObserved` の fence、同じ 170ms)も同じ。
  2. **drift correction 経由の書き込みを塞ぐ(B4)**。`evaluate_drift`(`drift_correction.rs`)が除外するのは `ConvOpenInference` だけで、明示意図の直後に古い字形が届くと補正が書き込まれ、決定 0 が破れる
     (トグル系のキーなら二重トグル)。新しい `ObservationSource::TaskbarGlyph` は `authority() = BeliefOnly`(`derive_actuating` に入れない)とし、`evaluate_drift` の除外リストに足す
     (`ime_event.rs` の「新しいソースを足したら `check_drift_correction` 側も更新する」注意書きに従う)。
  3. **`Miss` 後に古い `Hit` が残らない**(M4): 観測の有効期限(`expires_at`)をこのソースでは短くするか、Hit の後の Miss は前の Hit を失効させる。
  4. `confidence: Medium`、`state/` の `classify_glyph` 経由の `ObserverReported`。入力モードは `InputModeObserved`(Medium 以上のみ `input_mode` を上書き)の規約に従う。観測を偽装した内部補正にしない。

### 決定 7: プライバシー・安全・EDR

- 取り込むのはタスクバーの 32×48 の矩形だけ。メモリ上で 2 値化してハッシュだけを保持し、**画素・画像は保存しない**(診断の ASCII アートは明示の診断モードだけ)。画面全体は取り込まない
  (スパイクの `--shots` は測定専用で、製品には入れない)。
- **「低レベルキーボードフック + 周期的な画面取り込み」は、EDR/ウイルス対策の行動検出(キーロガー + スクリーングラバー)に当たる恐れがある**。32×48 でも同じで、GDI の BitBlt には Windows の
  「画面の取り込み」権限の確認も出ないので、利用者には「知らないうちに画面を読んでいる」になる。企業環境で awase ごと隔離されると害が上回る。対処: **既定で無効にしてオプトイン**(所有者判断 Q2)。**オプトインの単位は、収集と読み取りで同じスイッチ**(受け身の収集は普段の使用中に字形を取り込むことそのものなので、収集の段階で既に懸念が生じる)。
  決定 5 の回数上限、README/設定画面で説明。段階 1 の一致率は、オプトインした利用者・CI・実機(dragonflyg4)からしか集まらないので、**報告者(#623)にオプトインを依頼する**(依頼の手順は段階 1 で決める)。
  D0 で Defender の反応を確かめるが、「Defender で検出されない」は必要条件にすぎず(企業 EDR の行動検出の閾値は別)、オプトインの既定はこの結果に依らず維持する。

## 却下案

- **UIA の Name・HelpText・LegacyIAccessible で状態を読む**: Name は「IME が有効か」の 2 値しか運ばない(実測)。状態は運ばないので字形が要る。
- **IMM(`WM_IME_CONTROL`)で読む/書く**: 観測の無い窓では読めない。GJI では書いても字形に出ない。
- **窓に移った最初の 1 回だけ、ひらがな/カタカナ/英数のキーで actuation する案**: 所有者が議論の末に取り下げた(推論・書き込みでなく、証拠を読む方向へ)。
- **ずれたらユーザーに別のキー(MS-IME プリセットのひらがな、半角全角)を押してもらう案内**: 保留。字形が読めれば、案内より先に自動で直せる。残すなら別の小さな UI 変更。
- **内蔵のハッシュ表**: ハッシュは DPI・テーマ・矩形・IME で変わり、GJI と本物の MS-IME で体系も違う。決定 2・3 のとおり実行環境で作る。
- **OCR・画像認識**: 重く、脆さが増える。2 値化ハッシュで足りることを実測した。
- **マウスフック(`WH_MOUSE_LL`)でマウス操作を読む場面にする案**: 新しい低レベルフックは遅延と AV の面で重い。フォーカス/前面の変化のイベントで足りるかを先に見る(決定 5)。
- **`ITfLangBarMgr` による言語バーのモードボタンの文字列の読み取り(字形より正確で、DPI・テーマ・覆い・言語に依らない可能性)**: **却下せず、D0-0′ で先に測る**。
  BUG-025 追補4 は `ITfLangBarItemSink` の cross-process 到達性を未検証のままにしている。**既存のスパイク(`spike_langbar_input_mode.rs --watch-langbar`)は `CoCreateInstance(CLSID_TF_ThreadMgr)` →
  `ITfLangBarItemMgr` で awase 自身のスレッドの項目を見るだけで、他プロセスの状態は測れない**(そのまま CI で回すと「読めない」という誤結論になる。2 値化で誤結論を出したのと同じ型)。
  正しい測り方は `ITfLangBarMgr::GetThreadLangBarItemMgr(フォーカスのスレッド ID)` → `GUID_LBI_INPUTMODE` の `ITfLangBarItemButton::GetText`/`GetTooltipString`/`GetIcon` を、状態の違う 2 窓で読む
  (`ITfLangBarEventSink::OnSetFocus(dwThreadId)` でフォーカススレッドの変化も受ける)。読めれば字形の案は置き換えるか併用を再検討する。(ADR-138 は言語バー経路の放棄を述べておらず、
  `spike_langbar_input_mode.rs` が長く続いた唯一の例として名前が出るだけ。)

## 段階

- **段階 0**: D0 を表の順に。**D0-2 が否定的なら、本 ADR は #623 には効かないので、CI での D0-1/3/4/5 は打ち切る**。D0-0′ で言語バーの文字列が読めるなら、字形の案は置き換える/併用を再検討する。
- **段階 1**: `observer/` の probe、`state/` の `classify_glyph`、受け身の収集(必要なら学習への相乗り)、shadow(journal・不具合報告)。読める窓で直接の読みとの一致率を見る。
- **段階 2**: belief への配線(決定 6 の入口条件を満たす別 ADR/追記でレビュー)。#623 の本体の解消はここ。
- **段階 3**: 設定画面に字形の収集状況を出す(環境指紋が変わったら自動で作り直す旨)。

## 所有者に決めてほしいこと

- **Q1(表の作り方)**: 受け身の収集(主案、学習の操作が要らず DPI が実行時と一致)か、IME キー学習への相乗り(先に所有者が示した案)か、併用か。**推奨: 受け身を主、学習は受け身で集まらない状態の補助**(理由は決定 2)。
- **Q2(既定の有効/無効)**: 画面取り込みを含むので EDR の懸念(決定 7)。**推奨: 既定は無効のオプトイン(収集と読み取りで同じスイッチ)**。
