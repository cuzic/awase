## Blocker

### B1. 「実害が無い」の根拠が未測定であり、その測定手順が ADR-132 の未完了タスクとして取り残されている

本 ADR の結論はすべて「実害が無いから触らない」に依拠している。

- 決定1（164行）: 「しかしこれが実際に問題を起こした**実機インシデントは無い**」
- 決定2（177行）: 「動機だった『双方向の衝突』は既に解消済み…**現在進行形の実害が無い**」
- 非スコープ（272-273行）: 「**実害の記録が無い限り**、本ADRの範囲では着手しない」

ところが `docs/adr/132-*.md` の「次のアクション」（979-990行）は、**まさにその実害の有無を
判定する手順**を未完了タスクとして持っている:

```
1. Phase 2（B1修正）を実機ソークし、次の実機報告で`[tsf-eager-warmup]`
   /`[warmup-gate]`/`force-ON (ImmBrokenForceOn)`のgrep突合せから
   92件相当の内訳（B1由来 vs #6由来）を確定する。
2. 内訳確定後、#6（`apply_force_on_for_imm_broken`）側の同型修正
   （`check_drift_correction`との排他、または別の設計）を要否判断する。
   B1由来がほぼゼロだった場合、Phase 2は「効果薄だが無害な予防線」
   として維持しつつ、#6側の修正を優先する。
```

そして ADR-132 の status 節（`docs/adr/132-*.md:8`）はこう書いている:

> **実機ソークは未実施のまま残る。** #6(`apply_force_on_for_imm_broken`)との競合は
> 未解決のまま残る、B1由来の内訳確定は次回実機報告待ち

つまり:

1. **ADR-172 の「実害が無い」は "no evidence of harm" であって "evidence of no harm" ではない。**
   ADR-132 が指定した測定（`origin=` タグの grep 突合せによる内訳確定）が一度も実行されて
   いないから記録が無いのであり、測って害が無かったのではない。ADR-172 はこの区別を
   どこにも書いていない。この ADR が数ヶ月後に読まれたとき、「ADR-172 で実害なしと確認済み」
   と誤読される（このリポジトリで ADR のステータス文言を鵜呑みにして誤答した前例がある）。
2. **ADR-172 決定2 は、ADR-132 次のアクション2（#6 = `apply_force_on_for_imm_broken` 側の
   同型修正の要否判断）そのものである。** ADR-172 は ADR-132 を `related_adr` に挙げ
   （18行）、決定1 の出典としてのみ参照している（162-163行、295-296行）が、**決定2 が
   ADR-132 の未完了タスクを引き取った／見送ったという関係に一言も触れていない**。
   このまま確定すると、ADR-132 は「#6 側の修正を要否判断する」というタスクを持ったまま、
   ADR-172 は「#6 側は直さないと決めた」と書いている、という**2つの ADR が矛盾した状態**で
   並存する。
3. **ADR-132 次のアクション1 は、ADR-172 が避けようとしている「消費者のいないインフラ投資」
   ではない。** 必要な計装（`WarmupOrigin` の `Gated`/`Actuated`/`Off` タグ、
   `[warmup-gate]` ログ）は ADR-132 Phase 2 の敵対的レビュー対応として**既に実装済み**
   （`docs/adr/132-*.md:841-856`、`output/mod.rs:1124-1131` の doc、
   `architecture_guard.rs:4192` のガード）。残っているのは「次の実機報告が来たときに
   ログを grep する」だけで、コストはほぼゼロである。ADR-172 205-210行が
   「消費者＝実際に変更したい人がいない状態でテスト基盤だけ先に作るのは…無駄」として
   評価手順の整備を見送った判断は、決定2 の journal コーパス検証基盤については妥当だが、
   **既に仕込み済みの ADR-132 の内訳確定には当てはまらない。**

**必要な修正（いずれも追記のみ、コード変更なし）:**

- 決定1・決定2 の「実害が無い」を「**実害の記録が無い。ただし ADR-132 次のアクション1
  （`origin=` タグによる B1由来 / #6由来の内訳確定）が未実施であり、これは『測って害が
  無かった』ではなく『まだ測っていない』という意味である**」と書き換える。
- 「次のアクション」に、ADR-132 次のアクション1 を引き継ぐ項目を追加する:
  「次の不具合報告を受け取ったときに `[tsf-eager-warmup] origin=` / `[warmup-gate]` /
  `force-ON (ImmBrokenForceOn)` を grep し、内訳を確定する。その結果 #6 由来が有意に
  出た場合は、決定2 の『実装しない』判断を再検討する」。
  これが入って初めて、本 ADR の「実害が出るまで触らない」に**実害を検知する経路**が付く。
  入っていない現状は、依頼者が懸念した「単なる先送りの言い訳」との区別が付かない。
- ADR-132 側の次のアクション2 のステータスをどう扱うか（ADR-172 が引き取って
  「当面見送り」とするのか、ADR-132 に残すのか）を1行書く。

### S2. ADR-157 からの導出という書き方が正確でない（結論そのものは妥当）

151-158行:

> **ADR-157が既に示した教訓**（「発火する仕組みの上に抑止する仕組みを重ねるより、発火源
> そのものの条件を直す方が優れている」…）を設計原則として採用する。round1・round2を経て、
> **この原則を最も素直に適用した結論は「実害の無いゲートを、机上の議論だけで直そうと
> しない」だった**

ADR-157 の教訓は「調停機構より発火源修正」であって「実害が無いなら触らない」ではない。
しかも ADR-157 が撤回に至ったのは **実機ソークまで完了させた後**である（ADR-172 自身が
153-154行でそう書いている）。つまり ADR-157 は「測ってから捨てた」事例であり、
ADR-172 は「測らずに捨てる」判断である。**同じ教訓の適用ではなく、別の原則**
（証拠の無い変更はしない／YAGNI）である。

この書き方のまま確定すると、将来「ADR-157 の教訓により、実害が無いので触らない」という
論法が、実際には ADR-157 が支持していない場面でも再利用されうる。

**推奨**: 「ADR-157 の教訓（発火源修正 > 調停機構の積み増し）は当初案の却下に効いた。
加えて本 ADR は、ADR-157 が実機ソークを経て撤回に至ったのに対し、本件は**測定前の
段階で実装不能と判明した**ため、測定手順を残して撤退するという別の判断を採る」と
2つを分けて書く。関連: B1（測定手順を残すこと自体が未達）。

### S3. 決定2 の「評価手順」で挙げるコーパスの実態が、その目的に対して薄い

196-203行は評価手順の材料として `bug-131-report-01m29kdnz.json` を挙げ、
「実際に1件…force-on関連の記録が既に存在する」と書く。実測（37レコード）の内訳:

| `caller` | 件数 |
|---|---|
| `ForceOnRomajiCorrection` | **2** |
| `ForceOnBootstrap` | **0** |
| `ReassertExplicitPhysicalKey` | 13 |
| その他 | 22 |

- force-on 関連は 37 件中 **2 件**。差分検証のコーパスとしては薄い。
- **`try_force_on_bootstrap`（`ForceOnBootstrap`）のレコードは 0 件。** round2 B1 が
  「除外を入れるとこの機構の発火条件とほぼ完全に潰れ合う」と指摘した、最もリスクが高い
  入口のデータが存在しない。
- 評価手順として残すなら、この実態（「現コーパスでは bootstrap 入口の検証ができない。
  変更を提案する人はまず bootstrap 経路を含む報告を集める必要がある」）も書くこと。
  書かないと、次の人が「コーパスがあるから検証できる」と思って着手し、
  肝心の入口のデータが無いことに後から気付く——本 ADR が round1/round2 で2回繰り返した

### S4. 決定1 の「実機インシデントは無い」は Actuated 経路全体については言い過ぎ

164行「しかし**これが**実際に問題を起こした実機インシデントは無い」の「これ」＝
Gated/Actuated ゲート非対称、という読みなら正しい。しかし同じ ADR のチェックリスト項目2
（246-248行）はこう書いている:

> BUG-113: 半角/全角キー単独タップで`VK_IME_ON`が重複SendInputされない
> （ADR-149/167適用後の実測で3回→2回、**残り1回はwarmup由来として既知**…）

この「残り1回」の供給元は `platform.rs:1605-1615` の随伴 warmup、つまり **Actuated 系の
まさにその呼び出し**である。Actuated 経路は BUG-113（「@」混入）の必要条件（1打鍵あたり
連続2回以上の SendInput）に実際に寄与した実機インシデントの当事者であり、
ADR-149 / ADR-167 はこの経路を直接触って送信回数を減らしている。

「ゲート非対称が原因のインシデントは無い」と「この経路に実害が無い」は別である。
164行を「**`off_drift_active` ゲートを通らないことが原因**と特定された実機インシデントは
無い（Actuated 経路そのものは BUG-113 で ADR-149/167 が既に一度触っている）」と
精密化すること。

## 依頼事項への直接回答

**(1) 方針転換自体は妥当か。ADR-157 の教訓の正しい適用か、それとも先送りの言い訳か。**

**転換自体は妥当。** 特に round2 B3（「観測ソースの信頼判定」を4箇所目に増やす）を
回避したのは正しい判断で、これを押し切っていたら ADR 自身の動機（BUG-110 型の分散判定を
直す）と正反対の結果になっていた。実装不能な設計を3回目も出すより止める、という判断に
異論はない。

ただし **ADR-157 からの導出という説明は不正確**（S2）。ADR-157 は実機ソーク完了後に
撤回した事例であり、「測らずに撤退する」本件とは別の判断である。

**「先送りの言い訳」との区別が付くかどうかは、B1 の修正にかかっている。** 先送りが
正当化されるのは (i) 実害を検知する経路が残っていること、(ii) 次に触る人が同じ罠を
踏まない情報が残っていること、の2条件が揃うときである。(ii) はチェックリスト項目6
（`BaseDecision` を使え、`most_recent_trusted()` では効かない）で満たされている——
これは round2 B2 の知見が正しく負債記録に変換された良い例である。
**(i) が現状欠けている**: 実害の有無を判定する手順（ADR-132 次のアクション1）は
別 ADR に未完了のまま放置され、本 ADR はそこへリンクしていない。B1 を修正すれば
2条件が揃い、「先送り」ではなく「証拠が出るまで保留」という説明可能な判断になる。

**(2) 「既知の技術的負債として記録する」がコードに矛盾なく反映されているか。doc 追記の
保留は妥当か。**

**反映されていない。保留は妥当でない**（S1）。ADR-172 の決定は ADR 本文にしか存在せず、
