# ADR-197 敵対的レビュー round1（Opus、2026-09-23）

対象: `docs/adr/197-msime-legacy-custom-keymap-runtime-warning.md`（草案、commit `8f761b17`）

結論: **このままでは実装に進めない。** 警告の前提（旧UIの`CE`割当てが、既定の挙動と比べて実際に
awaseとの状態のずれを生むこと）が実機で確かめられていない。さらに、直前にマージされたADR-192の警告
基盤と、打鍵予測（ADR-191）が互換モードで置かれている状況を踏まえていない。Blocker 2件、Must-fix 5件、
Should-fix 7件、Minor 2件。

---

## Blocker

### B1. 警告する症状が実機で確かめられていない。確認済みの唯一の事例（変換）は既定の挙動と区別できない

ADR本文の「実機確認済みなのは1列目（直接入力→ON方向）のみ」は、ADR-148の記録より強い主張になっている。

- ADR-148「Phase 2 実機確認」（`docs/adr/148-bug-report-ime-keymap-attachment.md` 未解決点リスト）は
  **「『無変換』側で同じ非対称性（ON方向のみ有効）が起きるかは未検証（実機テストは『変換』のみで実施）」**
  と明記している。無変換の`CE`が実際に効くかは、一度も実機で試していない。
- では、試した「変換」の結果（直接入力中に変換を押したらIME ONになった）は何を示すのか。ADR-197自身が、
  NATURALの`変換=87 ...`を「変換=IME ON（awaseが元々前提にしている標準MS-IME挙動そのもの）」と解釈している。
  学習済みの表`key_effect_table.rs::MSIME_NATIVE`にも`cell(false, None, Stage::None, TableKey::Henkan, true, ...)`
  （IME OFFで変換→ON）がある。つまり**既定の設定でも、直接入力中に変換を押せばIME ONになる**。
  ADR-148の実験は`CE`が効いた結果なのか、既定の挙動がそのまま出ただけなのかを区別できない
  （比較対照が無い）。
- したがって、
  - **変換**: `CE`でも既定でも「OFF中に押すとON」という同じ結果になる。awaseの予測器もONと予測する。
    **警告しても競合は存在しない**（誤警告）。決定1の文言「直接入力中にこのキーを単独で押すと OS 側だけ
    IME が ON になり、awase の管理外で状態がずれる」は、変換については既定の挙動の説明にすぎない。
  - **無変換**: 既定（`MSIME_NATIVE`: OFFで無変換→OFFのまま）と`CE`（→ON）で結果が変わりうる唯一のケース。
    ところが実機では**一度も確認していない**。

**必要な対応（実装前）**: dragonflyg4で`keystyle=Custom`と`keystyle=NATURAL`の両方について、IME OFFの
状態で**物理キー**の無変換と変換をそれぞれ単独タップする。IMMで状態を読めるアプリ（メモ帳等）を使い、
開閉状態の実測値を並べて比べる。この結果で表を作る。「Customで無変換を押すとONになり、NATURALではOFFのまま」
が確認できたキーだけを警告対象にする。
ユーザーのフィードバック「設計の前に症状の存在を実機で確認する」（ADR-193で5ラウンド回した末に症状が無いと
分かった件）とADR-148自身の「推測しない、実測した部分だけ使う」方針が、どちらもこの順序を求めている。

### B2. `NoTsf3Override2`を読まないと、互換モードOFFのユーザーに「解除しようのない警告」が起動のたびに出る

非目的節は`NoTsf3Override2`を判定に使わない理由として、「false negativeの方がfalse positiveより悪い」を
挙げている。しかし、この設計で起きるfalse positiveは「無害な警告が1回多く出る」程度では済まない。

具体的な失敗シナリオ:
1. Windows 11で新しいMS-IME（互換モードOFF、既定）を使っているユーザー。Windows 10時代か一時的な互換モード
   利用のときに旧UIの「ユーザー定義」を開いて保存したことがあり、`keystyle=Custom`と`CE`が残っている。
   ADR-148が明記するとおり、「ユーザー定義」タブを開いて保存しただけで`keystyle`は自動的に`Custom`に
   切り替わる。dragonflyg4自身にも、このADR-148の実験の残骸が今も残っている。
2. 互換モードOFFでは旧UIの設定が効かない場合（本ADRの「残された未検証事項」がまさにこの点）、実害は
   何も無いのに警告が出る。
3. ユーザーが「はい」を押すと`ms-settings:regionlanguage-jpnime`が開く。しかし互換モードOFFの設定画面からは
   旧UIの「詳細キーカスタマイズ」へたどり着けない。**解除するには、互換モードをONにして旧UIを開き、直して
   保存し、互換モードをOFFに戻す、という手順が要る。**
4. デデュープラッチ（`Runtime`フィールド）はプロセス内でしか保持されない。そのため**awaseを起動するたびに**
   同じモーダルが出る。

ここで起きるのは「無害な警告が1回多く出る」ことではなく、実害の無い設定について毎回モーダルが出ることで
ある。これはADR-192決定2bが`Composition`をダイアログ化しなかった理由（毎回モーダルが出る問題）と同じ種類の
退行である。

また、決定1の手順2は`None`（判定不能）を「警告しない」、つまりfalse negativeの側に倒している。一方で非目的節は
「false negativeの方が悪い」を理由に`NoTsf3Override2`を読まないとしている。同じADRの中で2つの判断の原則が
食い違っている。

**必要な対応**: 「残された未検証事項」の実機A/B（互換モードOFF＋`keystyle=Custom`で無変換/変換を単独タップ）は
「推奨」ではなく**実装の前提条件**にする。結果に応じて次のどちらかを選ぶ。
- (a) 互換モードOFFでは効かない場合: `NoTsf3Override2 == Some(1)`のときだけダイアログを出す。
  それ以外（0、または読めない）はログだけにする。
- (b) OFFでも効く場合: 旧UIへの到達方法（互換モードを一時的にONにする必要があること）を案内文に書く。

どちらの場合も、`NoTsf3Override2`の生の値はログと不具合報告に載せる（S6）。

## Must-fix

### M1. ADR-192（直前にマージ済み）の警告基盤と方針を無視して、3本目のダイアログ経路と3本目のラッチを足している

- frontmatterの`related_adr`はADR-148とADR-092だけで、**ADR-191とADR-192が入っていない**。
- ADR-192の決定2は「既存の`msime_key_assignment::check_and_warn`…**新しい独立ダイアログは追加しない**」とし、
  決定2bは「**判定を2箇所に重複させない**」としている（`docs/adr/192-*.md` 決定2・決定2b）。
- MS-IME向けの警告の状態は、現在すでに2系統ある。
  `Runtime::msime_key_assignment_warned`（`runtime/mod.rs:364-369`）と、
  `state_dependent_key_warning`/`state_dependent_key_warning_dialog`（`runtime/mod.rs:1238-1306`）である。
  ADR-197はこれに3本目のラッチ`msime_legacy_keymap_warned`と、3本目の別スレッドダイアログを足す。
  ADR-158（複雑性を減らす方針）の流れや、`.claude/rules/complexity-budget.md`（まだ効力は無いが方向は同じ）に
  逆行する。

**推奨設計**: 新しい関数を並べて呼ぶのではなく、**既存の`msime_key_assignment::check_and_warn`自体を拡張する**。
- `read_legacy_toggle_assignment()`も呼び、`conflict_warning()`の列挙に「無変換キー → IMEオン/オフ
  （以前のバージョンのIMEの詳細キーカスタマイズ）」を加える。
- ダイアログは1つにまとめる。
- ラッチは既存の`Option<u8>`をそのまま使い、bit2/bit3を旧UI用にする。

こうすれば、Q5の「2つのダイアログが同じtickで同時に出る」問題（下記S4）も、Q3のラッチ型の問題（M5）も、
構造的に起きなくなる。非目的節の「別ダイアログのまま両方出す方が実装コストが低い」は正しくない。
既存関数の列挙に1行足すほうが、新しいラッチとswap/resetメソッドを足すより小さい。

### M2. 呼び出し条件`detected && MicrosoftIme`では、ATOK・Japanist・未知のTIPのユーザーにも警告が出る

決定1は、既存の条件（`message_handlers.rs:939`）の中で呼ぶとしている。しかし`key_pipeline.rs`の
`kp_predict_key_effect`のコメント（レビュー round2 NB1）がはっきり書いているとおり、
**`active_ime_kind() == MicrosoftIme`は「GJI以外」という意味でしかなく、ATOK・Japanist・未知のTIP・
IMM32 HKLを含む**。`ime_kind_detected()`も「CLSID判定が一度でも走った」ことしか表さない。そのため予測器の
側では`obs.ms_ime_native_identified()`で絞っている。

失敗シナリオ: ATOKユーザーが、過去に使っていたMS-IMEの旧UIの残骸（`keystyle=Custom`）を持っている。
この場合、今使っていないMS-IMEの設定について起動のたびに警告が出る（B2と重なる）。

既存の新UI警告にも同じ穴があるが、それを真似して広げる理由にはならない。旧UIの判定は
`ms_ime_native_identified()`で絞ること。M1の方式を取るなら、既存の新UI側も同時に直すこと。

### M3. 「予測器への統合は危険なので非目的」という理由付けは逆向き。統合しない現状こそ、誤った予測を積極的に行っている

非目的節は「ON→OFF方向が未確認のまま予測に組み込むと、誤った前提で予測するリスクがある」としている。
しかし現状はこうなっている。

- ADR本文が自分で確認したとおり、互換モードでもTIPのCLSIDは同じなので、`ms_ime_native_identified()`は
  trueになる。そのため互換モードのユーザー（dragonflyg4の日常の環境そのもの）の打鍵は、
  `KeymapCache`→`read_key_effect_keymap_native()`→`KeymapPreset::MsImeNative`で予測される
  （`key_pipeline.rs` `kp_predict_key_effect`）。
- `for_msime_native`（`key_effect_predictor.rs:485-498`）は新UIのDWORDしか見ない。旧UIで無変換に`CE`が
  割り当てられていても、`MSIME_NATIVE`の`cell(false, None, Stage::None, TableKey::Muhenkan, false, ...)`
  （OFFで無変換→OFFのまま）をそのまま予測として`apply_key_effect_prediction`に流す。
- B1の実機確認で無変換の`CE`が効くと分かった場合、awaseは**実際はONになった状態を「OFFのまま」と能動的に
  予測してbeliefに書く**ことになる。TsfNativeアプリのように観測が届かない窓では、この誤りは直らない。

`for_msime_native`の`henkan_reassigned`/`muhenkan_reassigned`を、旧UIの検出が`Some(true)`のとき
（`None`も含めるかは要検討）にtrueにすれば、`predict`は該当キーで`None`を返す（予測しない）。
**これは確信度を上げる変更ではなく下げる変更**であり、`ime-belief-architecture.md`の方針にむしろ沿う。
あわせて次の点も確認した。
- `native_assignment_stamp()`に旧UIの状態（`keystyle`と`key`のバイト長またはハッシュ）を含めないと、
  キャッシュが無効化されない。
- `classify_state_dependent_mode_key`は、`MsImeNative`プリセットを`reassigned`を見る前に
  `CannotPredict(InsufficientData)`で返す（`key_effect_table.rs:525-529`）。そのため、この変更でADR-192の
  ダイアログが新たに出ることは無い。

さらに根本的な未検証事項として、**`MSIME_NATIVE`の表（CIのwindows-latestで学習したもの）が、互換モード
（旧エンジン）の挙動を表しているのか**が確かめられていない。これは本ADRの範囲を超えるが、
「互換モードでは新IME用の表を当てている」事実として、本ADRの背景か未検証事項に記録すべきである。
予測器への統合を非目的にするなら、「現状は誤った予測を積極的に行いうる」ことを明記したうえで判断すること。

### M4. 動機のシナリオ（Customに切り替えた瞬間）をこの設計では検出できない

背景節は「ユーザーが旧UIで`keystyle`を`Custom`に切り替えた瞬間…awaseは気づけない。これが本ADRの動機」と
している。しかし`sync_ime_kind_from_observation`が走るのは、起動時とIME種別の変化時（GJIとMS-IMEの切替）
だけである（`msime_key_assignment.rs:141-147`のdocもこの制約を認めている）。awaseの動作中に旧UIを変更しても、
次にawaseを起動するかIMEを切り替えるまで警告は出ない。

動機の説明を実際の検出範囲に合わせて直すか、M3の方式（`KeymapCache`の`RECHECK_MS=2000`で再確認する）を
採用して、動作中の変更も予測の抑止には反映されるようにすること。

### M5. デデュープラッチの仕様が決まっていない（`None`のときにリセットするか、型の選択）

- `LegacyKeyStyle`は`#[derive(Debug, Clone, Copy, PartialEq, Eq)]`（`msime_legacy_keymap.rs:156`）なので、
  `Option<(LegacyKeyStyle, bool, bool)>`を`Option::replace`で扱うことはできる。ただ、決定2の
  「（または同等にハッシュ化した値）」は2案を併記しただけで、決定になっていない。
- **`None`（判定不能）のときにラッチをリセットするかが書かれていない。** 新UI側の真似をして「競合なし→
  リセット」の分岐に`None`も入れると、次の順で同じポップアップがもう一度出る。
  1. 1回目の種別確定で`Some(true)`になり、警告を出す。
  2. 一時的な読み取りエラー（`read_raw_value`の`Err`経路、`msime_legacy_keymap.rs:296-298`・`322-324`）で
     `None`になり、リセットされる。
  3. 次の種別確定で`Some(true)`に戻り、**同じ内容でもう一度ポップアップが出る**。
  リセットは両キーとも`Some(false)`と確認できたときだけにし、`None`のときはラッチを変えない、と明記すること。
- M1の方式を取るなら、既存の`u8`に2ビット足すだけで済む。プリセット名は同一性の判定に不要である。
  ユーザーから見れば、どのプリセットに`CE`があるかは違いにならない。

### （M5補足・Q2への回答）`None`をダイアログに出さないこと自体は妥当。ただし理由の書き方が誤っている

`None`になる経路は3つある（`msime_legacy_keymap.rs:371-385`）。
1. `keystyle`の値が無い（`Ok(None)`、372行目）。旧UIを一度も開いていない環境では、これが**最も多い**可能性が
   高い。実質的には「未カスタマイズ」である。
2. レジストリの読み取りエラー（一時的なもの）。
3. `Other`（ADR-148で実測した6つの名前以外）。

「ユーザーが独自の名前でプリセットを保存すると`Other`になる」という懸念は、ADR-148の実測と合わない。
ADR-148は「ユーザー定義」タブで保存すると`keystyle`が`Custom`に自動で切り替わることを確認しており、
任意の名前で保存できるUIの存在は確認されていない。したがって`Other`は、将来の値やローカライズされた値
程度のまれなケースと見るのが妥当である。

1をダイアログにするとほぼ全ユーザーへの誤警告になるので、`None`でダイアログを出さない判断は正しい。
ただしADRは次の2点を満たすこと。
- 判断の理由を「経路1が支配的だから」と書き、非目的節の「false negativeの方が悪い」と矛盾しない形にする。
- `None`のときは理由（値なし／読み取りエラー／`Other`）を`info`ログに残す。

## Should-fix

### S1. 「はい」を押したときの遷移先が、旧UIの設定画面に届くか確認されていない

決定1の手順4は`spawn_yes_open_ime_settings_dialog`（`ms-settings:regionlanguage-jpnime`）を再利用し、
「旧UIは数クリック奥」と案内するとしている。しかし旧UIの詳細キーカスタマイズ（`IMJPUEX.EXE`）へ、この設定
ページから互換モードONの状態で何クリックでたどり着けるかは確認されていない。ユーザーが実際に取る行動の
入口がここなので、dragonflyg4で手順を実際に操作して確かめ、その手順を案内文にそのまま書くこと
（B2(b)とも関連）。

### S2. 修飾キー付きと`S1key`〜`SEkey`を除外する根拠が、書かれていない前提に依存している（Q6）

- 修飾キー付きを除外してよい理由は「素の単独タップだけが親指シフトと衝突するから」とされている。しかし
  awaseの既定のIME ON/OFFキーは**`Ctrl+変換`/`Ctrl+無変換`**（`src/config.rs:569-570`）である。ADR-148の
  実機記録には「`Ctrl+変換`の直前に新規挿入」とあり、旧UIの表には`Ctrl+変換`の行が既定で存在する。
  修飾キー付きの除外が安全なのは、「awaseは`Ctrl+変換`/`Ctrl+無変換`を常に消費し、OSへ素通ししない」ことが
  前提になっている場合に限られる。この前提をADRに書くこと。ユーザーがこれらのキーを素通しする構成にした
  場合の扱いも書くこと。
- 小指のShiftを押したまま親指を単独タップしたとき、`Shift+無変換`として素通しされる経路がある。その場合は
  旧UIの`Shift+無変換`の行が効き、本ADRの検出からは漏れる。
- `S1key`〜`SEkey`が本体`key`を上書きする場合、補助テーブルにだけ`CE`があるCustom設定は「割当てなし」
  （`Some(false)`）と**確認済みの誤った値**になる。つまり`None`ではなく`Some(false)`で漏れる。これは
  `Option<bool>`設計が防ごうとした「判定不能を安全と読み違える」誤りそのものである。少なくとも、
  補助テーブルに`CE`が1つでもあるかを、ログか不具合報告に載せること（判定には使わない）。

### S3. テスト計画が無い。判定を純関数にしてLinuxでテストすること

成功基準4は既存のテストが通ることしか求めていない。新UI側の`MsImeKeyAssignment::conflict_warning()`は純関数で、
単体テストがある（`msime_key_assignment.rs:382-411`）。旧UI側にも同じ形で純関数の判定を作り、少なくとも次の
組み合わせをテストすること。
- `Some(true)`と`Some(false)`と`None`の組み合わせ
- ラッチのリセット条件（M5）
- B1の結果、変換を対象から外すならその固定

成功基準5の理由付け（再発しやすい領域に該当するが、known-bugsは不要）も混乱している。本ADRは`feat`なので、
`fix-requires-evidence`の適用対象かどうかをはっきり書くこと。

### S4. 2つのダイアログが同じtickで出る場合の検討が無く、成功基準3がそれを望ましい状態として固定している（Q5）

`spawn_yes_dialog`（`msime_key_assignment.rs:305-335`）は、呼び出しのたびに`std::thread::spawn`で
`MessageBoxW(None, …, MB_TOPMOST | MB_SETFOREGROUND)`を出す。共有状態は無いので、クラッシュや競合は起きない。
しかし次の問題がある。
- 2つのモーダルが画面中央にぴったり重なり、ユーザーは1つを閉じても同じ見た目の2つ目が残るように見える。
- 2つ目は、1つ目がフォアグラウンドを取った後のフォアグラウンドロックで前面に出られない可能性がある
  （`MB_TOPMOST`なので表示はされるが、フォーカスは取らない）。
- 両方の「はい」が同じ`ms-settings`を2回開く。

成功基準3（両方の警告が独立に出ること）は、この使い勝手の悪さを成功条件にしてしまっている。M1の方式で
1つのダイアログにまとめること。

### S5. `warn_state_dependent_mode_keys`（ADR-192のユーザー向けopt-out）を尊重しない

ADR-192は警告をブロックせず、ユーザーが「警告しない」を選べる（既定on）としている。本ADRの新しいダイアログは
このopt-outの対象かどうかを定めていない。B2の「起動のたびに出る」問題と組み合わさると、止める方法が無い。

### S6. `NoTsf3Override2`をログと不具合報告に載せる対応が、決定に入っていない

非目的節は「ログに残す価値はある」と書きながら、決定に含めていない。B2の検証を実機で1回やっても、
ユーザーの環境では分からない。不具合報告のたびにこの値が付いていれば、互換モードとの相関を後から分析できる。
コストは`read_dword`1回で済む。

### S7. ADR-148とADR-197で「互換モードのチェックボックスが何を切り替えるか」の説明が食い違っている

- ADR-148（frontmatter summary）: 「新IME/旧IMEは別製品ではなく**同一エンジン(v15.0)の2つの設定UI**」。
  未決事項節: 「本ADRの設計はこのトグルの値そのものには依存しない」。
- ADR-197（背景）: チェックボックスは「MS-IME**内部**でどちらのキーカスタマイズ機構が有効か」を決める。

どちらも実機では確かめられていない。ADR-197の前提が正しい場合、**既存の新UI警告**（`check_and_warn`）と
`for_msime_native`は、互換モードでは効かないDWORDを見て警告や予測を行っていることになる。互換モードONの
dragonflyg4で新UIの`IsKeyAssignmentEnabled=1`が効くかも、B2と同じ実機A/Bで一緒に確かめ、結果をADR-148に
追記すること。

## Minor

### m1. NATURALのコード`97`/`87`を「IME OFF/IME ON」と解釈したのは推測である

`msime_legacy_keymap.rs`のモジュールdocは、「『IMEオン/オフ』以外の機能のコード値」を未解読の範囲として挙げている。
ADR-197がdragonflyg4の実測値の節で「無変換=IME OFF/変換=IME ON」と断定しているのは、ADR-148の
「推測しない」方針に反する。
ただしこの解釈が正しければ、B1の「変換は既定でもON」という判断を補強することになる。どちらの場合も
「推測」と明記するか、B1の実機確認で裏付けること。

### m2. `summary`で本ADRの範囲を「実機で確認できた範囲（直接入力→ON方向のみ）」と書いているが、B1のとおり無変換は確認されていない

summaryとstatus節の表現を、B1の実機確認の結果に合わせて直すこと。

## 依頼された観点への回答（まとめ）

| 観点 | 回答 |
| --- | --- |
| 1. 新UIと対称にする方針 | 非対称をそのまま持ち込むのは不適切。変換は既定の挙動と区別できず（B1）、互換モードOFFでは解除できない（B2）。新UIと対称にするのは表示の部分（既存ダイアログへの統合、M1）だけでよく、判定の条件は旧UI専用に絞る必要がある |
| 2. `None`で警告しない | 結論は妥当（最も多い経路は`keystyle`の値が無い＝未カスタマイズ）。ただし理由の書き方が非目的節の原則と食い違っている。`Other`の懸念は実測と合わない（M5補足） |
| 3. ラッチ設計 | 型としては成立する（`LegacyKeyStyle`は`Copy + Eq`）。ただし`None`のときのリセット規則が未定義で、同じポップアップが再び出る。既存の`u8`拡張で足りる（M5） |
| 4. `Tsf3Override`を読まない | 実装前に検証を必須とすべき。検証しないと、起動のたびに解除できない誤警告が出る（B2）。最低限、ログと不具合報告には載せる（S6） |
| 5. 同一tickの2つのダイアログ | クラッシュはしないが、重なる・前面に出ない・遷移が2回、という使い勝手の問題がある。成功基準3がそれを固定している（S4）。M1で解消できる |
| 6. 修飾キー付き・補助テーブルの除外 | `Ctrl+変換`の除外は「awaseが常に消費する」という書かれていない前提に依存。補助テーブルは`Some(false)`の誤判定で静かに漏れる（S2） |
