## Blocker

### B9. 「**両方のバイナリが起動時に必ず`ensure_user_data_present()`を呼ぶ**」という要件が決定文から消えている。`awase-settings.exe`を先に起動して一度保存するだけで、ユーザー設定が恒久的に失われる

v4の決定2には「`awase-settings`側も同様の構成にする」という明示があったが、
v5・v6では失われ、現在この要件は決定5の実装配置の説明文
（「呼び出し元（`awase-windows`/`awase-settings`）に残し」、248-250行）に
**間接的に読み取れるだけ**になっている。決定2は
「これら1〜4を単一の関数として…実装する」と書くのみで、**誰がいつ呼ぶか**を
規定していない（v4にあった「起動シーケンス（`bootstrap.rs`）の先頭で1回だけ
呼ぶ」という記述もv6には無い）。

`awase-settings.exe`はスタートメニューに独立したショートカットがあり
（`wix/main.wxs:207` `Name="awase Settings"`）、単独起動は通常運用である。
この呼び出しを`awase.exe`側だけに実装した場合:

```
1. MSI アンインストール → 再インストール
   → config.toml / layout\*.yab は工場出荷値
   → backup\ にはユーザー設定が入っている（唯一の原本）
2. ユーザーがスタートメニューから「awase Settings」を先に起動する
   → ensure_user_data_present() を呼ばない実装なので復元されない
   → 設定画面には工場出荷値が表示される（ユーザーは「設定が消えた」と思う）
3. ユーザーが何か1項目だけ直して保存する
   → 決定1の実行ゲート（フラグ未設定）によりバックアップ書き込みは抑制される
     ＝ここまでは v6 の設計が正しく守っている
   → しかしディスク上の config.toml は「工場出荷値＋1項目」になる
4. その後 awase.exe が起動する（ログオン時／トレイから）
   → フェーズ1の復元条件「内容が埋め込み既定値とバイト一致」が
     **もう満たされない**（1項目変わっているため）→ 復元されない
   → ロード成功 → フラグ設定 → 契機3が発火
   → backup\config.toml が「工場出荷値＋1項目」で**上書きされる**
5. ユーザーの元の設定は、本体からもバックアップからも消滅。復旧手段は無い。
```

決定1の実行ゲート（プロセスローカルフラグ）はステップ3のバックアップ汚染を
防ぐが、**ステップ4の「復元条件が成立しなくなること」は防げない**。
つまりフラグゲートはB4型（原本が2箇所同時に消える）を防ぐ仕組みであって、
この「片方のバイナリが復元を通らずに本体を書き換えてしまう」経路は守備範囲外である。

しかも失敗は静かで不可逆であり、ユーザーから見ると
「アンインストールして入れ直したら設定が消えた」——本ADRが解決しようとした
症状そのものが、より複雑な機構を足した末に残る形になる。

**要求**: 決定2に呼び出し要件を明示的な条項として復活させること。

> **呼び出し要件**: `awase.exe`・`awase-settings.exe`の**両方**が、起動
> シーケンスの中で、`AppConfig::load()`／`.yab`の読み込み／
> `AppConfig::save()`のいずれよりも**前に**`ensure_user_data_present()`を
> 1回だけ呼ぶ。`awase-settings`側の呼び出し位置は
> `SettingsApp::new`が`find_config_path()`→`AppConfig::load`を行う
> （`crates/awase-settings/src/main.rs:542-556`）よりも前とする。

加えて、防御の二重化として決定7に
「`ensure_user_data_present()`を呼ばずに`AppConfig::save()`相当を行った
場合、バックアップが更新されないこと（フラグゲートが効くこと）」の
自動テストを入れておくと、片側実装漏れの被害が「復元されない」だけに
限定され、バックアップの消滅までは進まないことを機械的に保証できる。

## Major

### M1. 同梱`.yab`を「存在しないだけ」で埋め込み既定値から再生成する一般規則は、ユーザーが意図的に削除した配列を**毎起動復活させる**（決定6の通知も毎起動出る）

決定2の「復元条件」は`config.toml`と`.yab`で共通の
「存在しない**または**（既定値一致＋バックアップ差分）」であり、
フェーズ3の一般規則は復元元を「バックアップが無ければ**埋め込み既定値**」と
している。この組み合わせにより、**バックアップが1つも無い同梱`.yab`でも、
ファイルが存在しなければ毎回書き戻される**。

`awase-settings`の配列一覧は`layouts_dir`内の`.yab`を列挙する構造なので、
「使わない同梱配列（`nicola_us.yab`・`nicola_f.yab`・`nicola_kb232.yab`等）を
削除して一覧を整理する」のは自然な運用である。v6以降、これらは

- 起動のたびに復活し、
- そのたびに決定6の通知（「設定ファイルを再作成しました…」）が出て、
- ユーザーには止める手段が無い（`backup\`を消しても関係ない。むしろ
  埋め込み既定値から再生成されるので、消す対象が存在しない）

という状態になる。**保護でも復旧でもない、単なる押し付け**であり、
ADRの「解決されること」にも対応する記述が無い（意図した仕様ではないはず）。

「ファイルが存在しないから既定値で作る」ことに保護上の意味があるのは
`config.toml`だけである（無いとアプリが起動できない）。`.yab`については、
1本も有効なものが無い場合の起動不能を救う機構が**決定5として別に用意
されている**ので、一般規則で個別に埋め戻す必要はない。

**要求**: 復元条件を`config.toml`と`.yab`で分けること。

- `config.toml`: 現行のまま（存在しない → 埋め込み既定値から生成、が必要）。
- `.yab`: 「**バックアップが存在し妥当である**場合に限り復元する」
  （＝「存在しない＋バックアップあり」または「既定値一致＋バックアップ差分」）。
  バックアップが無い`.yab`は、存在しなくても復元しない。
  有効な`.yab`が1本も無くなった場合だけ決定5の救済が発動する。

この変更で、「ユーザーが使っていた配列は守る／ユーザーが消した配列は
復活させない／起動不能だけは救う」という三者が矛盾なく両立する。
決定7にも「バックアップの無い同梱`.yab`を削除した状態で起動しても
復活しないこと」をテスト項目として追加すること。

### M2. フェーズ2の中断条件が`Dangerous`限定で、`NotFound`（フェーズ1の復元書き込みが失敗した場合）を取りこぼす

決定2フェーズ2（157-160行）:
> このロードが失敗した場合（`Dangerous`分類）、フェーズ3と決定1の契機3は
> 共にスキップする

しかし`classify_load_error`（`src/config.rs:848-858`）は
`io::ErrorKind::NotFound`を`NotFound`に、それ以外を`Dangerous`に分類する
**二分**であり、「ロード失敗＝`Dangerous`」ではない。フェーズ1の復元
書き込みが失敗した場合（決定2の「失敗時の挙動」191-193行が想定している
ディスク書き込み不可の環境、あるいは開発ビルド除外で復元しなかった場合）、
`config.toml`は存在しないままなので**ロードは`NotFound`で失敗する**。
この経路は上記条件に当てはまらず、決定文上はフェーズ3へ進むことになる。

フェーズ3は`validate()`後の`layouts_dir`を必要とするが、ロードが失敗して
いるのでその値は無い。実装者は`AppConfig::default()`を使う誘惑に駆られるが、
それは`layouts_dir = "config"`（`src/config.rs:477`）であり、決定3が
明示的に禁止している値そのもの——`<exe_dir>\config\`という存在しない
ディレクトリを`create_dir_all`で作り、そこへ`.yab`6本を書き出す、という
B6・B7と同種の「誤った場所への書き込み」が起きる。

**要求**: 中断条件を「ロードが失敗した場合（**分類を問わず**）」に修正する。
併せて「フェーズ3は`validate()`が成功した`layouts_dir`の値でのみ実行し、
`AppConfig::default()`の値で代用してはならない（決定3の禁止と同じ理由）」を
明記すること。

### M3. 決定2の`target`配下判定（B7除外）が`current_exe()`依存のままで、決定5のシグネチャ（`exe_dir`引数）と矛盾する。このままだと**決定7の自動テストが全て「復元スキップ」経路を通る**

決定2（129-133行）は
> `current_exe()`の祖先に`target`という名前のディレクトリが含まれる場合…
> には行わない

と書く一方、決定5（235-246行）はM4対応として
「判定に必要な**生の入力**を受け取る純粋関数」にし、`exe_dir: &Path`を
引数で渡す設計に確定させている。両者は両立しない。

`current_exe()`をコア関数の内部で呼ぶ実装にすると:

- `cargo test`実行時、`current_exe()`はテストバイナリ
  （`<root>/target/debug/deps/awase-XXXX`）を指すため、**祖先に必ず`target`が
  含まれる**。したがって決定7が挙げる復元系の自動テスト
  （B1・B8・B4・B6・M1…）は**すべて除外規則に引っかかり、実際の復元
  ロジックを一度も実行しない**。
- テストが「復元されること」をassertしていれば失敗するので気づけるが、
  そこで初めてシグネチャの設計変更（`current_exe()`を引数に切り出す）が
  必要と分かり、実装が一度巻き戻る。決定7が「純粋関数だからホスト
  ターゲットで自動テストできる」ことを設計の売りにしている以上、
  この矛盾は設計段階で潰しておくべき。

**要求**: 決定2の除外判定を「**引数で渡された`exe_dir`**の祖先に`target`と
いう名前のディレクトリが含まれる場合」に書き換える。`current_exe()`の呼び出しは
呼び出し元（`awase-windows`/`awase-settings`）に残す——これは決定5が
「OS依存部分のみ呼び出し元に残す」としている方針とも一致し、テストからは
任意の`exe_dir`を注入できるようになる（決定7の「B7の直接再現:
`exe_dir`が`target/debug`相当のパスである場合」という項目は、既にこの形を
前提にした書き方になっている）。

## Minor

### m1. 開発ビルドでは「復元は止まるがバックアップは動き続ける」非対称を明記すること

決定2のB7除外規則は「復元（および決定5の救済）」のみを対象としており、
決定1のバックアップ契機1〜3は開発ビルドでも動作する
（`ensure_user_data_present()`が早期復帰してもフラグは立つ、決定1の
実行ゲートの定義より）。その結果、`cargo run`で起動すると
`<root>/target/debug/backup/`にバックアップが作られる。`target`配下なので
実害は無いが、「開発ビルドでは自己修復機構を動かさない」と読んだ人が
混乱するので、意図的な非対称であることを1行書いておくこと
（バックアップ側も止めると、開発中に機構そのものを動作確認できなくなる
ため、動かしておくほうが妥当）。

### m2. 実機確認（決定7）の比較対象は「現在のワーキングツリー」ではなく「そのMSIをビルドしたコミット」の実ファイル

決定7の実機手順（317-322行）は「リポジトリの`config.toml`/`layout/*.yab`と
バイト一致することを確認する」とあるが、検証時点のワーキングツリーが
MSIビルド時点から進んでいると当然一致しない（このリポジトリは
`config.toml`・`layout/*.yab`を実際に更新してきている）。
「検証に使ったMSIをビルドしたコミットの`config.toml`/`layout/*.yab`」と
比較する旨を明記すること。ADR-177の実機検証でも「検証に使用したMSIは
配布物ではない」ことの記録が後から効いている（同ADR「検証の限界」7）。

### m3. インストール先パスに`target`という名前のディレクトリが含まれると自己修復が丸ごと無効になる

B7除外規則は`src/paths.rs`の既存ヒューリスティックを共用するが、
読み取り側でこの判定が誤爆しても「フォールバック候補が1つ増えるだけ」で
無害なのに対し、復元側では**機能そのものが無効化される**点で影響の
性質が異なる。ポータブルZIPを`D:\target\awase\`のような場所に展開した
ユーザーは、自己修復が一切効かないまま気づかない。発生確率は低いが、
「この判定は開発ビルド検出のヒューリスティックであり、誤爆した場合は
自己修復が無効になる（安全側に倒れるので許容する）」と1行残しておくと、
将来この挙動を調査する人の時間を節約できる。

### m4. 決定7の「B5の回帰確認」は新規テストではなく既存テストの維持でよい

`layouts_dir`が絶対パスの場合と`cargo run`相当のフォールバックは、
`src/paths.rs`の既存テスト（`absolute_path_is_returned_unchanged`、
`falls_back_to_workspace_root_when_run_from_cargo_target_dir`）が既に
固定している。決定2が「読み取りは変更しない」と決めた以上、新規に
書くのではなく「これらの既存テストが変更されないこと」を条件として
書くほうが正確で、レビュー時にも確認しやすい。

### m5. 未解決事項3（`ConfigLoadState::NotFound`の扱い）は実質決着している

決定5（230-233行）が「開発ビルドや復元失敗時には依然到達しうるため
削除しない方向」と理由付きで結論を書いているので、未解決事項から外して
決定文に一本化してよい。M2の指摘（`NotFound`でのロード失敗を中断条件に
含める）を反映すると、`NotFound`は分岐として明確に生き残る。

## 総評

v6でB7・B8は解消され、決定1〜7は「何を・どの順で・どこに書くか」に加えて
「テストで何を固定するか」まで含めて実装可能な状態にある。
6ラウンドを通じて検出されたBlocker11件のうち10件が解消済みで、残るB9は
**v4に存在した1文がv5・v6の圧縮で落ちた**ことによる欠落であり、
条項を1つ戻せば済む。

Majorのうち **M1（消した同梱配列が毎起動復活する）** は、これまでのラウンドで
一度も表面化していない「やりすぎ方向」の副作用である点に注意してほしい。
ここまでのレビューは一貫して「復元が発火しない」欠陥を潰してきたため、
v6では条件が十分に広くなり、今度は**発火しすぎる**側の穴が開いた。
`config.toml`と`.yab`で復元条件を分けるのが最小の修正になる。

**M3（`current_exe()`と`exe_dir`引数の矛盾）** は、放置すると決定7の自動テストが
書けない／全て空振りするため、実装開始前に必ず直しておくこと。

これらを反映すれば、round7は確認のみで収束できる見込みで、
以後は実装フェーズに進んでよい水準に達していると考える。
