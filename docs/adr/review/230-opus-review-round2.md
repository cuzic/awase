# ADR-230 Opus 敵対的レビュー round2(追加分のみ)

対象: round1 反映後の `docs/adr/230-scancode-map-bijective-swap-editor.md`(173行)。
round1 の B1/B2・S1〜S7 は方向として反映済みと確認した。以下は、反映によって新たに生じた矛盾と、反映が指摘の意図とずれた箇所。

---

## Blocker

### B3. 決定2「修飾キー ⇄ 英数 は許可外」が、決定1 の Swap 移行と既存の CapsAsExtraCtrl に正面から矛盾する

- 決定2(230:77-79)は「修飾キー ⇄ 半角/全角・かな・**英数** は実機で確かめるまで許可リストの組から外す」とする。
- しかし決定1(230:42-44)は、既存の `Swap` を `{(0x003A, 0x001D)}`、つまり**英数 ⇄ 左 Ctrl**の1ペアとして読むと決めている。
  これは決定2 で禁止した組そのもの。
- 失敗シナリオ: 既存の Swap 利用者が新 UI を開く。決定3 の分類表(230:98)では、Pair の条件は「許可リスト内」。組が許可外なので
  Caps⇄LCtrl は **Unclaimed(読み取り専用)** に落ち、awase 自身が書いた入れ替えを awase から解除できなくなる。
  仮に Pair として読んでも、`compute_swap_write` の再検証(230:137-138)で SwapError になり、他のペアを1つ足すだけの適用も失敗する。
- `CapsAsExtraCtrl`(英数位置を Ctrl にする)も同じ仮説の対象で、仮説が正しければ既存プリセット自体が成り立たない。
  英数(0x3A)の位置が Ctrl として押し続けられることは ADR-111/126 の出荷機能が前提にしている(実機検証は ADR-111「未解決の疑問」で
  未実施だが、利用者からの不具合報告は無い)。round1 の S4 で私が挙げた仮説に英数を含めたのは過剰だった。英数は仮説から外すこと。
- 修正: 押しっぱなしの仮説の対象を **半角/全角(0x29)とかな(0x70)だけ**にする。さらに「組の禁止」はキー単位の許可リストとは別の関係
  なので、`SwapError::UnverifiedCombination{a,b}` のような専用の種類と、分類表上の扱い(読み込んだ既存ペアが禁止の組だった場合は
  Pair として読み、編集・削除はできるが新規作成はできない)を決めること。

### B4. 他ツールのエントリが1件増えただけで、awase が書いた入れ替えを awase から解除できなくなる(現行からの後退)

- 分類表(230:102, 104)は `A→B, B→A, C→A` を全部 Unclaimed、同じ from が2件あれば**全体を** Unclaimed にする。
- 失敗シナリオ: awase で Caps⇄LCtrl を入れたあと、別ツールか手動 regedit で `0x7B→0x3A`(無変換 → 英数)が足される。
  分類は3件とも Unclaimed になり、UI では読み取り専用になる。ユーザーは awase から Caps⇄LCtrl を外せない。
  `0x3A` を含む新しいペアも、`0x7B→0x3A` の to と衝突して `CollidesWithForeignTarget` で作れない。
  現行の `compute_new_entries` は `current_preset` の包含判定で Swap を検出し、from=0x3A/0x1D の2件だけを消すので、**今は解除できる**。
- 「全体を Unclaimed」は特に影響が広い。他ツールの壊れた1件で、無関係なペアまで含めて全部が編集不能になる。
- 修正案:
  - 分類は「Pair と読めるが、他のエントリと交わっている」を **Pair(警告つき)** として別に持つ。新規作成では止めるが、
    **削除は常に許す**(読み込んだ時点で実在した2エントリを消すだけで、多対一を新しく作らない)。
  - from 重複は、重複したエントリだけを Unclaimed にして、他のエントリの分類には波及させない。
  - 決定3 の検査を「書き込み後の写像が、書き込み前より悪くならない(多対一・from 重複を**新たに**作らない)」と言い換えると、
    削除だけの操作が常に通ることが規則から導ける。

## Should-fix

### S8. 「再起動またはサインアウト」は ADR-111 決定5 の訂正を元に戻している

- 230:150「反映には再起動またはサインアウトが要る」。ADR-111 決定5(111:200-210)は「サインアウトでは不十分、再起動が必要」と
  訂正済みで、今の UI 文言(`main.rs:3139-3141`)も再起動を求めている。高速スタートアップでは `shutdown /s` でも反映されないことがある、
  という注記もこの ADR に引き継ぐこと。

### S9. CapsAsExtraCtrl との排他の書き方が2通りあり、矛盾している

- 230:45-46 は**キー単位**(CapsAsExtraCtrl が有効なら 0x3A/0x1D を含むペアだけを禁止)、230:47 は**モード単位**
  (3択で、CapsAsExtraCtrl とペア編集の全体を排他)。
- モード単位にすると、CapsAsExtraCtrl の利用者は `無変換⇄左 Alt` のような無関係な入れ替えも一切できなくなる。理由が無い制限なので
  キー単位に揃え、UI は「Caps を追加の Ctrl にする」をチェックボックスにして、オンのときは 0x3A/0x1D を候補から消す形にすること。
  `compute_swap_write` の引数 `preset` もキー単位の前提と合う。

### S10. 「他ツールのエントリ」の定義が無い。差分計算の対象が曖昧

- 決定3 の検査(230:86-89)は「他ツールのエントリ」と書くが、決定4.3(230:129)では他ツールが書いた完全な入れ替えは編集可能なペアになる。
  つまり「他ツールのエントリ」は書いた主体ではなく、**`detect_swap_pairs(existing)` が Unclaimed と分類したもの**と定義するしかない。
  明記すること。
- `compute_swap_write(existing, pairs, preset)` の `pairs` が「編集後のペア集合の全体」なのか「追加・削除の差分」なのかも未定義。
  決定4.2 の「差分で書く」と合わせるなら、`compute_swap_write` が内部で `detect_swap_pairs(existing)` を呼び、
  既存の Pair のうち `pairs` に無いものを削除対象にする、と書くこと。そうでないとプロパティテスト(230:107)の等式が何を比べるのかも決まらない。
- プロパティテストの等式は `pairs` だけでなく `caps_extra_ctrl` と `unclaimed`(保持されたものが入力の Unclaimed から Displaced を
  引いたものに一致)まで含めること。今の書き方は Unclaimed の保持を括弧書きで済ませており、保持の検査が抜けやすい。

### S11. 確認済みの Displaced が昇格側に渡っていない

- UI は「他ツールのエントリ `A→Y` を消します」と確認する(230:88-89)。しかし昇格側に渡すのは、ペア集合と UI が読んだエントリ列だけ
  (230:136-137)。昇格側は再計算で同じ Displaced を得るが、それをユーザーが承認したかどうかは知らない。
- 比較交換で入力が一致していれば Displaced も決定的に同じになるので実害は小さいが、「Displaced が空でないのに承認フラグが無ければ
  書かない」(`--allow-displace` 等)を入れておけば、UI の確認を飛ばした呼び出し(UI の不具合や手入力)で他ツールのエントリが消えるのを防げる。

### S12. 巻き戻し用に保存する「書く前の値」の形が決まっていない

- 230:143 の「書く前の値へ書き戻す」は、パース済みのエントリ列ではなく**生のバイト列**(と、値が無かったという事実)で持つこと。
  `parse_entries` は短すぎる値や壊れた値を空リストにする(`scancode_map.rs:96-101`)ので、エントリ列から作り直すと元の値を復元できない。
  元の値が無かった場合の巻き戻しは `delete()` になる。
- 同じ理由で、比較交換の比較もパース後のエントリ列で行うなら、**壊れた既存値**(parse が空を返す)を「空」と誤認して上書きする。
  これは現行コードにもある既存の穴なので、ここで「パースに失敗した既存値があるときは書かない」と決めておくとよい。

## Note

- **N9. SAS の主張は未確認のまま事実として書かれている**(230:75)。「SAS は変換後のスキャンコードで判定される」は round1 で私が
  書いたもので、一次資料で確かめていない。Scancode Map はキーボードクラスドライバで効くので、その上で動く win32k の
  Ctrl+Alt+Del 判定は変換後の値を見る、というのが妥当な推測だが、ADR には「推測、実機確認の項目」として書くこと。
  未確認の節(230:159-165)に1行足せばよい。
- **N10. 配列は利用者ごと、Scancode Map はマシン全体**。230:66 は JIS 専用キーを JIS 配列のときだけ候補に出すとするが、
  配列の判定方法(config の `keyboard_model`、`GetKeyboardType` など)が書かれていない。また、ある利用者が JIS で書いた
  `無変換⇄左 Alt` を、US 配列の別の利用者が開くと、その人には許可外のキーになる。決定3 の分類表に従えば Unclaimed で、
  解除できない。分類(Pair かどうか)は配列に依存させず、配列は**新規作成の候補の表示**だけに使うこと。
- **N11. 親指キー警告の対象**(230:71): 「無変換/変換」と固定せず、config の実際の親指キー(`left_thumb_vk`/`right_thumb_vk`)から
  決めること。親指キーを別のキーに設定している利用者には、固定の判定だと警告が外れる。
- **N12. ADR-127 追記が前提条件**(230:149, 170)なのはよい。ただし「別名のボタン」は ADR-127 の発端の苦情(ボタンが2つ)を
  名前で区別するだけで、数は2つのまま。ADR-127 側の追記で「このセクションの適用ボタンは画面共通の適用とは別の操作で、レジストリにだけ
  書く」と、原則の例外として明文化しておくこと(今の追記予定は表示と破棄確認だけ)。
