## Blocker

### B1. 決定1「適用済み(有効)」は、Q2 未解決のままでは誤表示になる。段階1 に入れると今より悪くなる

- 根拠: ADR-248:44-47(決定1)、:87(段階1 に決定1 を含む)、:99-100(Q2)。現状は `main.rs:514-515` の `scancode_restart_pending: bool`
  (プロセス内のフラグ)で、`main.rs:3202-3207` が立っている間だけ「再起動後に有効」を出す。今の画面は「有効」とは一度も言っていない。
- 失敗シナリオ: 適用 →「今すぐ再起動」を押さずに設定画面を閉じる → 後で設定画面を開き直す(まだ再起動していない)。フラグは消えているので、
  決定1 の状態行は「適用済み(有効)」を出す。実際には入れ替えは効いていない。利用者は「効いていない、壊れている」と判断するか、もう一度
  適用して同じ状態に戻る。Q2 の書きぶり「再起動を挟むと消える」は逆で、**問題は再起動の前に設定画面を閉じると消えること**。
- 高速スタートアップ: 利用者が「シャットダウン → 電源オン」を再起動のつもりで行うと、カーネルは休止状態から復帰するので
  Scancode Map は読み直されない(ADR-111 決定5・`main.rs:3147-3148` の注意と同じ)。プロセス内フラグも LastWriteTime 方式でない比較も、ここで
  「有効」と誤表示する。
- 推奨修正:
  - Q2 を段階1 の前提条件にする。候補は「`HKLM\SYSTEM\CurrentControlSet\Control\Keyboard Layout` キーの LastWriteTime
    (`RegQueryInfoKeyW`、非昇格の `KEY_QUERY_VALUE` で読める)と、カーネルの起動時刻の比較」。記録を増やさない(ADR-230 決定4 と整合)。
    高速スタートアップでの電源オンはカーネルの起動時刻を更新しない、というのが**推測**(タスクマネージャーの稼働時間がリセットされない、という
    よく知られた現象から)で、そうなら LastWriteTime > 起動時刻 →「再起動後に有効」が正しく出る。起動時刻の取り方(`GetTickCount64` がスリープ・
    休止中の時間を含むか、`NtQuerySystemInformation(SystemTimeOfDayInformation)` の BootTime を使うか)は**未確認**。実機で
    「適用 → シャットダウン → 電源オン」「適用 → 再起動」の2つを確かめること。
  - キーの LastWriteTime は同じキーの別の値の書き込みでも進むが、誤りは「再起動後に有効」側(安全側)に倒れるので許容できる、と書く。
  - Q2 が解けるまでは「有効」と断定する文言を使わない(例:「レジストリに設定があります。再起動していなければ、まだ効いていません」)。

### B2. 決定5 の図は「位置 → 機能」が全単射のときしか描けない。全単射でない現実の状態の描き方とドロップの可否の規則が無い

- 根拠: ADR-248:57-59「各位置は、いまその位置で出る機能のラベルを持つ」、:64「Caps を Ctrl としても使うは図の外のスイッチ」、:72-73。
  分類の実装は `scancode_pairs.rs:118-204`、他ツールの to との衝突は `compute_swap_write` の手順5(`scancode_pairs.rs:334-342`)。
- 図に載る10(実際は9、N1)位置の「いまの機能」が1つに決まらない、または編集できない場合がある:
  1. **Caps 追加 Ctrl**(`0x3A→0x1D` 単独): 英数位置と左 Ctrl 位置の両方が Ctrl を出す。図の外にスイッチを置いても、図の英数位置のラベルは
     「Ctrl」でなければ嘘になる。その「Ctrl」ラベルをドラッグできるのか。オンのとき英数・左 Ctrl の位置はドロップ先にも元にもなれない
     (`SwapError::CapsExtraConflict`、`scancode_editor.rs:163-170, 186-191`)が、図での見せ方が決まっていない。
  2. **from が許可リスト内の他ツールのエントリ**(例 `無変換→0x1E`〈A〉、`変換→0x0000`〈無効化〉): その位置の機能は「A」「(無効)」。
     そこへドロップすると `displaced` になり、他ツールのエントリを消す確認が要る。
  3. **to が許可リスト内の他ツールのエントリ**(例 `0x3B〈F1〉→無変換`): 機能「無変換」を別の位置へ動かすと、新しい `X→無変換` が
     `CollidesWithForeignTarget` になる(`scancode_pairs.rs:339-341`)。ドロップしてから適用時にエラーを見せるのか、ドラッグ中に置けない
     位置を示すのか。
  4. **from 重複**(`A→B` と `A→Z`): どちらが効くかは未確認(ADR-230 未確認節・Q7)。「いまその位置で出る機能」が分からない。
  5. **他ツールの3巡回のうち許可リスト外のキーを含むもの**、**片方向**(`無変換→左 Alt` だけ): 決定6 で「他ツールの項目」のまま。
     図にはどう出るのか(位置「無変換」のラベルは「左 Alt」、位置「左 Alt」のラベルも「左 Alt」→ 2つの位置に同じラベル)。
- 失敗シナリオ: 2. の状態で、利用者が図の「無変換」位置(ラベル「A」)へ「スペース」を落とす。ラベル「A」は落とした元の位置へ移るのか
  (=他ツールの写像を awase が移動=新規に `スペース位置→0x1E` を作る。0x1E は許可リスト外なので `NotAllowed`)、消えるのか。どちらにしても
  図の「中身を入れ替える」という1行の規則からは決まらず、実装者が場当たりに決めることになる。
- 推奨修正: 位置ごとの状態を純粋関数で決めて図はそれを描くだけにする(決定4 の無効理由と同じ考え方)。
  `PositionState = Editable{function} | Locked{label, reason}`。`Locked` は (1)Caps 追加 Ctrl の2位置、(2)(3)他ツールのエントリが
  from/to に現れる位置、(4)from 重複、(5)他ツールの片方向・混在循環の位置。ドラッグ中の置ける/置けないは、ドロップ後の状態に
  `compute_swap_write` 相当の検査を当てた結果で決め(同じ関数を使い判定と表示をずらさない)、置けない位置には理由を出す。
  `displaced` を伴うドロップを許すかは決定として書く(許すなら確認ダイアログに載る)。これらを決定3 の表のように「入力 → 図の表示」の表にして、
  必須テストにする。

### B3. 図に描かない位置(US 配列で隠す JIS 専用キー、許可リスト外のキー)が入れ替えに含まれると、awase から解除できなくなる(ADR-230 round2 B4・N10 の後退)

- 根拠: ADR-248:62「JIS 専用キーは US 配列では位置ごと図から隠す」、:68「許可リスト内の全単射を単位にする」、:71-72「許可リスト外のキーを含む循環
  …は従来どおり他ツールの項目」、:115「図は許可リストの10キーの位置だけ」。対して ADR-230 決定2(230:72-73)「分類は配列に依存させない
  (JIS で書かれた `無変換⇄左 Alt` を US の利用者が開いても Pair として読め、解除できる)」、決定3 の表(230:126)「許可リスト外でも Pair として読む」、
  実装 `scancode_pairs.rs:405-410`(`pair_outside_allowlist_is_still_a_pair`)と `scancode_editor.rs:202-233`(`candidates` は今入っている許可リスト外の
  キーを常に候補に含める)。
- 失敗シナリオ1(配列): 共用 PC で、JIS の利用者が `無変換⇄左 Alt` を書いた。US 配列(`keyboard_model = "us"`)の利用者が設定画面を開く。
  無変換の位置は図から隠れている。左 Alt の位置にはラベル「無変換」が出るが、そのラベルを元の位置(隠れている)へ戻す操作が無い。今の画面なら
  行の「削除」で解除できる(`main.rs:5049`)。決定5 で行の一覧を撤去すると、解除の手段が無くなる。Scancode Map はマシン全体の値なので、
  これは ADR-230 が明示的に塞いだケースそのもの。
- 失敗シナリオ2(許可リスト外): 決定6 の「他ツールの項目は従来どおり」の「従来」は誤り。今は長さ2の循環は許可リスト外でも Pair(編集・削除できる)。
  決定6 どおりに読み替えると、`0x0010⇄0x0011` のような既存のペアが Unclaimed に落ち、今日は消せるものが消せなくなる。許可リストは「データなので
  表に足せば広げられる」(ADR-230 決定2)ので、将来キーを外した場合も、そのキーを含む awase 自身の書き込みが解除できなくなる。
- 推奨修正:
  - 「図に描く位置」を「許可リスト ∩ 配列」ではなく「許可リスト ∩ 配列 ∪ いまの入れ替えに含まれる位置」にする(隠すのは、何も入れ替えていない
    JIS 専用キーだけ)。図に描けない位置(許可リスト外)を含む編集可能な循環は、図の下に一覧で出し「解除」ボタンを付ける。
  - 分類規則を明記する: 「完全な循環(from も to も重複しない閉じた鎖)は、許可リストに関係なく編集可能な置換として読む。新規に作る・変える
    ときだけ許可リストを当てる」(ADR-230 の Pair の規則をそのまま循環へ一般化)。決定6 の「許可リスト内で閉じた循環」は撤回する。
  - 「削除は常に許可」の性質テストを、隠れた位置・許可リスト外の位置を含む入力で回す。

### B4. 決定7 の復旧手順「再起動前なら『元に戻す』→適用」は、同じ決定7 の「元に戻す」の定義では何も戻らない

- 根拠: ADR-248:78「元に戻す(編集を適用済みの状態へ戻す)」と :80「再起動前なら「元に戻す」→適用」。現行 `EditorState::reset`
  (`scancode_editor.rs:261-274`)も「読み込み時の状態」へ戻すだけで、適用後はレジストリを読み直すので(`main.rs:3293-3295`)読み込み時の状態=
  適用した後の状態。
- 失敗シナリオ: 適用直後に「やっぱりやめたい」と思った利用者が、困ったときの手順どおり「元に戻す」を押す。編集が無いのでボタンは無効
  (`main.rs:5111` の `dirty || incomplete`)。押せても何も変わらず、適用ボタンも無効のまま。手順が成り立たない。
- 推奨修正: 復旧用には別の操作が要る。どちらかを決定にする。
  - 「すべて解除」(図を全部恒等に戻す。Caps 追加 Ctrl もオフ。他ツールのエントリは残す)。`compute_swap_write(existing, &[], false)` で
    書けるので核の変更は要らない(削除は常に通る)。
  - 「適用前の状態へ戻す」(適用直前の `expected` をプロセス内に保持し、それを目標に書く)。ただし設定画面を閉じると消える(B1 と同じ問題)。
  手順の本文は「すべて解除 → 適用 → 再起動」にする。

## Should-fix

### S1. 決定6 の理由「ペアだけだと『入れ替え済みの位置には落とせない』規則が要る」は成り立たない。所有者へ別案を示してから決めること

- 根拠: ADR-248:66-67。
- ペアだけでも禁止規則なしの自然な操作は作れる: 「機能 F(元の位置 h)を位置 P に落とす = P または h を含む既存のペアを解いてから、P⇄h を作る」。
  どこへ落としても結果は常にペアの集合で、落とせない位置は無い。結果が分かりやすい(図の色付きの位置は常に2つ1組)。
- 循環を許すことの費用(ADR に無い): Opus 3 ラウンド+コードレビュー2回で固めた核(`detect_swap_pairs` の貪欲な組み取り・値での削除・
  `revealed`)を書き直すことになり、コードレビュー round1 の B1(同値の複製の値削除がペアの片方を消す)と同じ型の穴が循環で再発しうる。
  ADR-230 段階5(実機確認)も未着手のまま、その上に新しい核を積む。
- 推奨修正: 「ペア+解いてから作る」案を ADR の却下案(または比較)に書き、所有者に「循環を許す」判断をこの比較の上で確認する。
  所有者が循環を選ぶならそれでよい(判断を覆す趣旨ではない)が、ADR の理由の文は直すこと。

### S2. 循環になると向き(from→to)が効いてくる。ペアでは向きの誤りが見えなかったので、今のテスト・注意書きは向きを検証していない

- 根拠: `Pair` は順序を持たない(`scancode_pairs.rs:48-81`)。`cautions`(`scancode_editor.rs:332-355`)は `(a,b),(b,a)` の両向きを見る対称な判定。
  バイト配置は `build_bytes`(`scancode_map.rs:52-67`、to が先)と片方向プリセットのテスト(同 :209〜)で固定されているので、レジストリ層は正しい。
  危ないのはその上の「位置 → 機能」と「機能の名前 → 位置」の変換。
- 失敗シナリオ: 3巡回「無変換の位置→英数、英数の位置→左 Alt、左 Alt の位置→無変換」。親指キー(無変換)の機能は左 Alt の位置へ移り、
  無変換の位置は英数を出す(Shift と押すと CapsLock)。注意書きが「親指キーの位置へ英数の二重人格が移る(`CapsWithThumbKey`)」なのか
  「親指の機能が左 Alt の位置へ移る(`ThumbKeyMoved`)」なのかは向きで決まる。実装が `(to, from)` で組み立てると、逆の置換(σ⁻¹)を書き、
  注意書きも逆の位置を言う。長さ2ではσ=σ⁻¹ なので、既存のテストはどれもこの取り違えを検出しない。
- ワンクリックの意味も向きで分かれる(ADR-248:65「2つの位置を入れ替える動作のショートカット」): 既に `英数⇄無変換` がある状態で
  「英数/Caps ⇄ 左 Ctrl」を押したとき、(a)英数の**位置**と左 Ctrl の**位置**の中身を入れ替える(σ∘(英数 左Ctrl))のか、(b)英数の**機能**と左 Ctrl の
  **機能**を入れ替える((英数 左Ctrl)∘σ)のかで結果が違う。今の `quick_available` は「どちらかが使用中なら無効」なので問題にならなかった。
- 「もう一度ドロップして元の位置へ戻せば、その入れ替えは消える」(:59)はペアでしか成り立たない。2回のドロップで作った3巡回は、1つのラベルを
  元へ戻すと長さ2の循環が残る。
- 推奨修正: 用語を「位置 P は機能 σ(P) を出す。エントリは `(P, σ(P))`」と ADR に1行で定義する。必須テストに非対称な3巡回の固定ケース
  (バイト列まで)と、`cautions` の向きのケースを足す。注意書きは「位置 → 機能」で書き直す(`ThumbKeyRestored` も同様)。ワンクリックの意味
  ((a)/(b)、使用中のとき無効のままにするか)と、位置ごとの「この位置を元に戻す」操作を決定に書く。

### S3. 決定6 の核の一般化に、分類の優先順位と「残す・消す」の単位が書かれていない

- 根拠: ADR-248:68-73。現行は「入力順に最初のペアを採る」貪欲(`scancode_pairs.rs:123-146`)、残す/消すはペアの値の一致
  (`scancode_pairs.rs:265-313`)。
- 決まっていないこと(どれもテストの境界になる):
  - 循環の候補が重なるとき: `A→B, B→A, B→C, C→A` は `A⇄B` か `A→B→C→A` か(from 重複を含む)。`Caps→左Ctrl, 左Ctrl→X, X→Caps` は
    3巡回か、Caps 追加 Ctrl + 他ツール2件か(`caps_pos` の判定 `scancode_pairs.rs:151-162` との順序)。
  - 「残す」の単位: 既存の3巡回 `(A B C)` を利用者が `(A B)` に変えたとき、`A→B` のエントリは「残す」のか、循環ごと消して新しい循環として
    作るのか。新規作成だけに当てる許可リスト・Caps 追加 Ctrl の検査(`scancode_pairs.rs:273-292`)がどちらを対象にするかで結果が変わる。
  - 同値の複製(コードレビュー round1 B1 の型)と循環の組合せ。
- 推奨修正: 「循環単位で、全エントリが値として一致すれば残す、1つでも変われば循環ごと消して新規に作る」のように単位を決め、ADR-230 決定3 の表に
  循環の行(上の3つと、警告つき循環・from 重複つき循環)を足して必須テストにする。小さい宇宙の全列挙(Q6)は「悪くならない・削除は常に通る・
  往復」の3性質に加え、「書いた置換が読み戻しで同じ置換として読める」(向き込み)を含めること。

### S4. 昇格側で「置換であること」を検査すると書かれていない(`perm=` に片方向が入りうる)

- 根拠: ADR-248:74-75「`pairs=` は置換の表現(例 `perm=003A>001D,001D>003A`)へ置き換える(書式は実装時に決め…)」。現行は `Pair` で受けるので、
  昇格側が書けるのは構造上「両向きのエントリ」と固定の `Caps→左 Ctrl` だけ(`scancode_apply.rs:188-193`、コードレビュー round1 N7)。
- 失敗シナリオ: UI の不具合で `perm=0039>001D` だけが渡る。from/to の集合が一致するかを見なければ、昇格側は「スペースの位置→左 Ctrl」の片方向を
  書き、スペースを出すキーが無くなる。`perm=003A>001D` 単独は Caps 追加 Ctrl と同じ値で、`caps=0` との矛盾も検出されない。
- 推奨修正: `compute_*` の入口で「from が重複しない・to が重複しない・from の集合 = to の集合・固定点を含まない」を検査し、新しい
  `SwapError::NotPermutation` を返す。昇格側は再検証でこれを必ず通す、と決定に書く。`decide` は `compute_swap_write(&existing, &request.pairs, …)`
  (`scancode_apply.rs:257`)で `ApplyRequest.pairs: Vec<Pair>`(:76-85)と `to_spec`/`from_spec`(:129-177)も変わるので、「scancode_apply.rs は変えない」
  (:74)は「比較交換・読み戻し・巻き戻しは変えない」に正す。

### S5. 確認ダイアログを「必ず出す」(決定6)は、ADR-230 段階4 が避けた「毎回の警告で読まずに押す」を作る

- 根拠: ADR-248:76。現行は注意が要るとき・`displaced`/`revealed` があるときだけ出す(`scancode_editor.rs:388-398`)。理由は
  `scancode_editor.rs:281`「適用済みのペアに毎回出すと、警告を読まずに押すようになる」。
- 推奨修正: 変わる位置の一覧(位置 → 機能)は、適用ボタンの直上に常時の差分表示として出す(図の色付きと同じ情報を文字でも)。確認ダイアログは
  今の条件のまま。長い循環で確認を足したいなら「長さ3以上の循環を含むとき」に限る。

### S6. 状態行は1軸ではない。4つの文言では表せない状態がある

- 根拠: ADR-248:44-45。
- 表せない状態:
  - 適用済み・未再起動で、さらに未適用の編集がある(「再起動後に有効」と「未適用の変更」が同時に真)。
  - 入れ替えをすべて外して適用した直後(レジストリは空で効いているのは前の入れ替え。「入れ替えなし」と出すと誤り)。
  - 他ツールのエントリだけがある(「入れ替えなし」は誤解を招く)。
  - 壊れた値・読み取りエラー(`main.rs:3166-3181`)。
- 推奨修正: 「レジストリと起動時の値の関係(一致/再起動待ち/不明)」と「編集(なし/未適用あり)」の2軸を、それぞれ1語で並べる。文言を決める
  純粋関数は決定4 と同じく `scancode_editor.rs` に置き、全組合せのテストを持つ。

### S7. 決定2 は「一本化」になっていない。画面上の適用ボタンは2つのまま

- 根拠: ADR-248 title・:48-49。画面共通の「適用」(ADR-127)とセクションの「入れ替えを適用」は、枠で囲んでも2つ。ADR-127 追記(127:1280〜)の
  例外はそのまま残る。現状の差は、ボタン名が既に別(`main.rs:5104`)なので、枠と説明文1文の削除だけ。
- 推奨修正: タイトルと決定2 を「入れ替えの適用を枠で区切る」と正しく言う。本当に一本化したいなら、「キーの入れ替え」を画面共通の
  「適用/キャンセル」が出ない独立したタブ(またはウィンドウ)へ移す案を比較に書く(ADR-127 の例外がいらなくなる)。

### S8. 決定7 のセーフモード手順は、キーボードの問題の対策にならない可能性が高い。マウスだけで戻せる手順を先に書く

- 根拠: ADR-248:79-81、Q3(:101)。
- 未確認だが重要な点: Scancode Map はキーボードクラスドライバ(kbdclass)が `CurrentControlSet` から読む。セーフモードでも kbdclass は
  読み込まれるので、**入れ替えはセーフモードでも効く可能性が高い**(推測。実機で確かめること)。そうならセーフモードの利点は「他のソフトが
  動かない」だけで、キーボードは同じ状態。セーフモードへ入る手順(設定 → システム → 回復 → PC の起動をカスタマイズする → トラブルシューティング →
  詳細オプション → スタートアップ設定 → 再起動 → 4 または F4)は最後にキー入力が要る。
- 回復環境(WinRE)の regedit でオフラインの SYSTEM ハイブを読み込む場合、パスは `CurrentControlSet` ではなく
  `<読み込んだ名前>\ControlSet001\Control\Keyboard Layout`(ハイブの読み込み時は CurrentControlSet が無い)。ADR のパスのままでは見つからない。
- 許可リストの中だけの全単射なので、文字キー・Enter・Shift・Tab は影響を受けず、サインインはできる。本当に困るのは「機能が、その機種に物理的に
  無い位置へ移った」場合(S9)。その場合の第一手順は、マウスで設定画面を開いて「すべて解除」(B4)→ 適用 → 再起動。キーが要る場面
  (UAC の資格情報など)は、画面キーボード(`osk.exe`、サインイン画面の「アクセシビリティ」からも開ける)で打てる。画面キーボードは
  SendInput で注入するので kbdclass の Scancode Map を通らない、というのは推測(要実機確認)。
- 推奨修正: 「困ったとき」の順序を (1)マウス+設定画面の「すべて解除」 (2)画面キーボード (3)システムの復元 (4)WinRE のオフライン編集
  (ControlSet001 のパス)にし、セーフモードは実機で効くと確かめられた場合だけ載せる。Q3 に「セーフモードで Scancode Map が効くか」を足す。

### S9. 図によって「物理キーの無い位置へ機能を移す」事故が起きやすくなる。ADR-230 の「打てないキーは生じない」はこの場合に成り立たない

- 根拠: ADR-230 決定2(230:84-85「全単射なので打てないキーは生じず」)、同 :92-93「この機種には英数キーが無く…許可リストの英数/Caps は機種により
  物理キーが無い(候補は物理キーの有無に関わらず出す)」。ADR-248:57-58 は図に全位置を描く。
- 失敗シナリオ: 右 Alt やかなキーが無いノート PC(機種の実在は推測)で、利用者が図の上で「スペース」を右 Alt の位置へ落とす。全単射でも、
  スペースを出す物理キーが無くなる。ドロップダウンより図のほうが「位置がある」ように見えるので起きやすい。
- 推奨修正: スペース・左 Ctrl・左 Alt の機能を、機種により無いことがある位置(右 Alt・かな・英数)へ移すときは確認つき注意(`Caution` を1つ足す)。
  図の該当位置に「機種によっては無いキー」と注記する。復旧手順(S8)にこの状況を明記する。

### S10. 段階の順序: 所有者がどこで迷ったか(Q5)を聞く前に、核の一般化(段階2)へ進む

- 根拠: ADR-248:85-94、Q5(:104)。決定6 は決定5(図)のためだけに要る。

  作って所有者に触ってもらい、循環が本当に要るかを確かめる。段階2 に進むなら、ADR-230 段階5 の実機確認(未着手)を先か同時に済ませる
  (積み上げる土台が未確認のまま)。

### S11. egui 0.31.1 の DnD は API としては存在するが、この ADR の要件に足りない部分がある

- 確認した事実: `Ui::dnd_drag_source`(`egui-0.31.1/src/ui.rs:2772`)、`Ui::dnd_drop_zone`(同 :2824)、`Response::dnd_set_drag_payload`/
  `dnd_hover_payload`/`dnd_release_payload`(`response.rs:423, 440, 456`)がある。Esc でドラッグを中止(`drag_and_drop.rs:33-43`)、
  ボタンを離せば必ず中止(同 :51-58)。eframe 0.31.1 は既定で accesskit が有効。
- 足りない点:
  - `dnd_drop_zone` は「その型のペイロードなら受け付ける」見た目しか出さない(`ui.rs:2836-2849`)。位置ごとの置ける/置けない(B2)は
    `dnd_hover_payload` を使って自前で描く必要がある。
  - `dnd_drag_source` は `Sense::drag()` で当たり判定を作る(`ui.rs:2810-2812`)。同じキーをクリック2回の操作にも使うなら、中のボタンの
    クリックとドラッグの両方が同じ矩形で効くかは**未確認**(試作で確かめる)。
  - 確認ダイアログ中は `add_enabled_ui(!modal_open, …)`(`main.rs:3184`)で編集を止めているが、`dnd_drag_source` は `ctx.is_being_dragged(id)`
    を見るだけなので、無効な Ui の中でドラッグが始まらないかは**未確認**。モーダル中はドラッグ元を描かない、と明示的に分岐する方が確実。
- アクセシビリティ: ドラッグはキーボードで操作できない。クリック2回の操作を、Tab で移れる・Space/Enter で押せる・選択中が文字でも分かる・Esc で
  取り消せるボタンにすることを決定に書く(「ドラッグしにくい環境の逃げ道」ではなく、同等の主経路として)。色だけで変更済みを示さない
  (決定5 :59「色を変え」に、文字の印〈例「→ 左 Alt」〉を併記)。キーボードのリマップ画面なので、操作にキーボードを使う利用者が多いはず。

## Nit

- **N1. 許可リストは9キー**(`scancode_pairs.rs:33-43`、英数と Caps は1項目)。ADR-248:57「10キー」、:105「10! 通り」、:115「10キー」は誤り。
  9! = 362,880、US 配列(JIS 専用4つを除く)では 5! = 120。確認ダイアログの行は高々9行なので、Q6 の「文面が破綻しないか」は数の問題ではなく、
  S3 の分類の曖昧さの問題。Q6 をそう書き直す。
- **N2. 「現状のずれ」#7 の例が誤り**: `0x003A` は許可リスト内で `key_label` は「英数 / Caps」を返す(`scancode_editor.rs:19`)。16進で出るのは
  許可リスト外(例 `0x003B`)。決定8 の「不明なキー(0x003A)」も同じ。また、許可リスト外の名前は配列で変わる(`0x0029`・`0x003A`・`0x007D` 等)ので、

- **N3. 決定3 の見出し「キーを入れ替える(A ⇄ B)」**は、決定5 の「A ⇄ B は紛らわしい」・決定6 の循環と食い違う。ワンクリックの名前

- **N4. 決定5「ADR-110 は再導入せず」**: 押下の検出(押して指定)は読むだけで、ADR-110 の hook リマップとは別物。押して指定をやめる理由は
  「入れ替え後は入れ替え先のスキャンコードが見える(SharpKeys FAQ の誤判定と同型)」「IME に奪われる(Q1)」で足り、ADR-110 を持ち出す必要はない。
- **N5. 決定7「読み直す」は外部で変わった疑いがあるときだけ出す**: 疑いの検出方法が無い(毎フレーム読まない方針、`main.rs:507-508`)。
  `RegNotifyChangeKeyValue` か、タブを開いたとき・ウィンドウがフォーカスを得たときに読む、のどちらかを書く。比較交換(`Changed`)があるので
  実害は小さい。
- **N6. 「Scancode Map は連鎖しない」を1行書く**: `A→B, B→C` で A を押すと B が出る(C にはならない)ことが循環の前提。ペアでも同じ前提だが、
  循環を許す ADR では明記したほうが読み手が迷わない(一次資料の確認はしていない。広く知られた挙動という推測)。
- **N7. frontmatter の related_adr**: 本文が参照する ADR-110・ADR-111・ADR-126・ADR-217 が無い。
- **N8. ADR-231 との接点**: ADR-230 非目標(230:200-201)は「Caps を無変換にして、無変換に IME トグルを割り当てる」を同じ画面で2段階に案内すると

  入れるなら「案内は ADR-231 側」と書く。
- **N9. 決定9**: 重複は `main.rs:3279` の成功メッセージと `main.rs:3203` の固定文。決定1 の状態行に寄せるなら、`RollbackFailed` のときの
  再起動案内(`main.rs:3272-3276`)も状態行で表せるかを確かめる(「書き込みの結果が不明」は S6 の「不明」に当たる)。

## 先行事例の表(ADR-248:29-38)の主張の裏付け

本レビューでは出典を開いていない(ネットワークを使っていない)。以下は記憶との突き合わせで、**どれも未確認**。表の右列は、出典の該当箇所を
引用(1文)で添える形にすることを勧める。

- #1「SharpKeys・KeyTweak は書き込み前後で状態を明示する」: SharpKeys は書き込み後にメッセージボックスで再ログオン/再起動を促すだけで、次に
  開いたときに「再起動待ち」を示す画面は無い、という記憶がある。「書き込み後に案内する」に弱めるのが安全。また、その案内が「ログオフまたは再起動」
  だった記憶があり、ADR-111 決定5(サインアウトでは不十分)と食い違う。引用するなら注記が要る。
- #3「持っていない・使えないキーは外すか注意を出す(PowerToys FAQ)」: PowerToys の doc にあるのは「割り当てられないキーの一覧」(Fn、Win+L、
  Ctrl+Alt+Del 等)で、UI が無効理由を隣に出すという主張の裏付けにはならない可能性がある。該当文を確認すること。
- #4「GNOME は swapcaps と nocaps を別の名前付き選択肢にしている」: xkb のオプション名としては正しいが、GNOME Tweaks では両方とも同じ
  「Ctrl の位置」グループ内の選択肢として並ぶ(記憶)。そうなら「別の見出しに分ける」(決定3)の根拠ではなく、「同じ見出しの中で名前で区別する」
  の根拠になる。
- #6「SharpKeys の復旧(セーフモードで削除)は作者が自己責任としている」: SharpKeys FAQ にセーフモードの記述があるかは記憶に無い。引用が要る。
  S8 のとおり、セーフモードで Scancode Map が効かなくなるかも未確認。
- #5「押下検出は割り当て済みキーや Fn で誤判定する(SharpKeys FAQ)」: Fn がスキャンコードを出さないことは一般的な事実。割り当て済みキーの
  誤判定は Scancode Map の仕組みから導けるので、出典が無くても主張は成り立つ。
- #6「macOS の Restore Defaults」: 修飾キーの設定に「デフォルトに戻す」ボタンがあることは記憶と合う。
