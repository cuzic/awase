対象: round1 反映後の `docs/adr/231-gji-custom-keymap-tsv-generator.md`(184行)。読み取りのみ。
round1 の Blocker 3 件はいずれも意図どおりに反映されている(土台=現在の実効の表、CUSTOM 切替の副作用の明記、BSD-3)。

## 指摘の意図とずれた直し方

### M1. 決定1 の「`config1.db` が読めない → MS-IME を土台」は、B1(既存の割り当てを消す)を例外経路で再発させる(L69)

B1 の意図は「ユーザーの現在の割り当てを、知らないまま上書きしない」こと。決定1 末尾は「読めない(不在・パース不能)場合は
MS-IME プリセットを土台の候補にする」と、**不在とパース不能を同じ扱い**にしている。

- 不在: Mozc は既定設定(Windows では MSIME)として扱う(ADR-199 決定6-3、`key_effect_predictor.rs::from_config1_db_read`)ので MS-IME で正しい。
- パース不能・読み取りエラー(権限、ロック中、GJI の版で protobuf が変わった等): 実際には CUSTOM 表を持っている可能性がある。
  ここで MS-IME から生成して import させると、B1 と同じく割り当てが全部消える。awase 側の既存規約も両者を分けている
  (`from_config1_db_read` は不在=既定、読めない/パース不能=`None`〈不明〉。`BundledPresetLookup::ConfigUnreadable` も別値)。

直し方: 不在 → MS-IME。読めない/パース不能 → 同梱表を既定にせず、**GJI のエクスポート経路(決定2)を必須にする**(または生成を止める)。

### M2. 決定6 の「同梱表を通す互換性テスト」は実装できない(L144-145)。S2 の意図は「import 後の差分で拾う」

S2 の意図は「GJI は知らない行を黙って捨てるので、それを検出できるようにする」こと。決定6 の箇条4は
「同梱表の各行を、その版の GJI が知るコマンド名・状態名か確認できる範囲で検査する」とあるが、awase には
**ユーザーの GJI の版が知っているコマンド名の一覧を得る手段が無い**(GJI は版を公開 API で返さず、コマンド一覧は GJI のバイナリの中)。
Linux のテストで検査できるのは「同梱した Mozc の版で有効か」だけで、版ずれは原理的に拾えない。

実際に拾えるのは import 後の比較(決定6 箇条2)だけである。そこで:
- 箇条4を削り、箇条2の比較で「生成したのに `custom_keymap_table` に無い行」を**GJI に捨てられた行として一覧表示**する
  (`ReportBug` は既知として除外)。Backspace 等の基本キーが含まれていれば「GJI の版が古い可能性。GJI からエクスポートした表を
  土台にして作り直してください」と案内する(決定2 の代替入力へつなぐ)。
- 比較が不一致のときの文言を「失敗」一般にせず、「捨てられた行」「余分な行」を分けて出す。

### M3. 決定4 の表は awase 側の結果を無条件に書いているが、実際は条件付き(L112-119)。S5 の意図は「何が起きるかを正しく見せる」

S5 は「生成したトグルで awase の挙動が変わることを書け」だったが、表は `key_role` が `ImeToggle` を返せば能動、と言い切っている。
実際に `shadow_action` が付くかは `key_role` の後に次の条件が掛かる(`state/key_effect_runtime.rs::key_shadow_action` L585-601):

- **明示 config と重なると付かない**(`explicit_overlap`、ADR-199 決定8)。ユーザーが `keys.ime_on`/`ime_off`/`ime_toggle` に
  同じキーを書いていれば受動。
- 学習表との矛盾で狭める(`hz_omit_verdict`、半角/全角)。
- `overlay_keymaps` があれば変換/無変換は受動(決定3 に書いたとおり)。
- 土台に `ON`/`OFF` 行が全開状態で揃っていないと `key_role` 自体が受動(`custom_table_has_toggle`)。決定1 で**ユーザーの CUSTOM 表**を
  土台にするようになったので、`ON`/`OFF` 行の無い古い表(手書き・他所から入手した TSV を import した表)では、トグルをコピーしても受動になる。
  round1 時点(素のプリセット土台)では常に揃っていたが、B1 の修正でこの前提が崩れた。
- 変換/無変換は ADR-206 の `role_open_action` が効くのは単独タップが Passthrough のときだけ(ADR-199 L431 付近)。
- 表の「Suppress して `VK_IME_ON/OFF` を送る」は ADR-199 でも「Suppress されうる」(`transport.rs::plan` の条件次第)で、言い切れない。

直し方: 表は「`key_role` の結果」の列に限定し、awase の実際の扱いは「次の条件で変わる」と条件を列挙する。UI の
「awase が IME を開閉します」表示は `key_role` だけでなく、少なくとも `explicit_overlap`(現在の config.toml)と土台の `ON`/`OFF` 行の有無を見て出す。
テストも `key_role` に加えて「土台に ON/OFF 行が無い CUSTOM 表ではトグルをコピーしても受動」を固定する。

### M4. 非目標「`keys.ime_on` などとの連動は独立(二重管理にならない)」は、M3 の `explicit_overlap` と矛盾する(L165-166)

`keys.ime_on` 等は「強制復帰キー」として独立に使えるが、**同じキーに書かれていると GJI 表由来の役割を打ち消す**
(ADR-199 決定8、`key_shadow_action` の `explicit_overlap`)。連動(自動で書き換える)を非目標にするのはよいが、「独立」とは書けない。
「連動はしない。ただし新しいキーが `keys.*` に既に書かれていれば、GJI 表の役割は awase では使われない(決定8)ので UI で警告する」に直す。

## 新たな Should-fix

### S8. KOTOERI / MOBILE プリセットのユーザーの土台が未定義(決定1 表 L65 と決定2 L73 の食い違い)

決定1 は「プリセット → そのプリセットの表(決定2)」、決定2 は同梱を `ms-ime.tsv`・`atok.tsv` の2つに絞った。
Windows 版 GJI のプロパティにはことえりが出る(`config_dialog.cc` L153-156 に "Kotoeri")ので、`session_keymap == KOTOERI` のユーザーは
あり得る。MOBILE(4)は GUI に出ないが値としては `role.rs` も扱っている。このとき土台が無い。
直し方: KOTOERI → GJI のエクスポート経路を必須(同梱しない理由と整合)。MOBILE → `role.rs` テストのとおり `ms-ime.tsv` と同一なので MS-IME 表
(取得時に diff で同一と確認済み、`role.rs` L388)、と表に書く。

### S9. コメント行の位置を規定していない。先頭に置くとヘッダが「非表示行」として `config1.db` に残る(決定7 L151-152)

決定7 は「`#` コメント行に入れてよい」とだけ書く。GJI の `LoadFromStream` は**1行目を中身を見ずに捨てる**(`keymap_editor.cc` L330-332)ので、
コメントを1行目に置くと、2行目のヘッダ `status\tkey\tcommand` がデータ行として読まれる。キー `key` は `KeyParser` で解釈できず
`IsVisibleKey` が偽 → 非表示行として `invisible_keymap_table_` に入り、保存時に**表の末尾へ付け直されて `config1.db` に残る**(L367-372、L455)。
Mozc 本体の読み込みや awase の `parse_custom_keymap_table`(内容でヘッダを判定)では実害はほぼ無いが、決定6 の比較で「余分な行」になる。
直し方: 「1行目は必ずヘッダ。コメントは2行目以降」と書く。正規化関数も「1行目を無条件に捨てる」を再現する(ヘッダの内容判定ではなく)。

### S10. 新しいキーと振る舞い元が同じキー(別名を含む)のとき、(a)→(b) の順で表からそのキーが消える(決定3 L89-90)

(a) 振る舞い元の行を新しいキーで複製して追加 → (b) 新しいキーの既存行を全状態で正規化照合で除去、の順だと、
新しいキー = 振る舞い元(例: `Hankaku/Zenkaku` に「IME ON/OFF トグル = `Hankaku/Zenkaku` の行群」をコピー、あるいは別名 `zenkaku`)のとき、
追加した行も元の行もまとめて消える。順序を「(b) を先に行うが、振る舞い元の行群は除去前に取り出しておく」にし、
新しいキーと振る舞い元が正規化後に同じなら UI で選べないようにする。「移動」でも同様に、振る舞い元の除去が新しいキーの行を消さないことをテストで固定する。

### S11. 決定6 の正規化関数の仕様が GJI の実挙動と細部でずれる

決定6 の箇条1を実装すると、次の点で GJI と食い違う(いずれも `keymap_editor.cc` L345-461):
- 列分割は `absl::StrSplit(line, '\t', absl::SkipEmpty())` で、**連続タブは1区切り**になる。`tsv.rs::parse_custom_keymap_table` は
  `split('\t')` なので空列を数える。生成側はタブを1つずつしか出さないので問題は起きにくいが、ユーザーの CUSTOM 表(決定1)や
  エクスポートファイル(決定2)を土台にするときは、正規化関数を GJI 側の規則に合わせる。
- 非表示になる条件は「キー」だけでなく**コマンド**(`InsertCharacter`/`EditInsert`/`ReportBug`〈デバッグ版〉)と、
  **キーが解釈できない行**(`IsVisibleKey` が偽)も含む。決定6 箇条2 の「非表示キーは表示キーと別なので、並べ替えは後勝ちに影響しない」は、
  コマンド由来の非表示行(表示キーに `InsertCharacter` を割り当てた行など)では成り立たない。プリセット表では起きないが、
  ユーザーの CUSTOM 表を土台にした以上、言い切らずに「同じ (状態, キー) で非表示行と表示行が両方ある表は、生成前に警告する」とする。

## Note

### N9. 決定5(a)の案内文「学習をやり直すと予測が戻ります」の範囲

学習は `awase-settings` の学習ウィザード(`keymap_learn_launcher.rs`)で手動起動。学習・予測の対象は `TableKey` の13キーで、
F13〜F24 は含まれない(`role.rs` テスト `TABLE_KEY_MOZC_NAMES`)。F13 にトグルを付けた場合、予測が「戻る」のは既存の IME キーの分だけで、
F13 の予測は元から無い。文言を「既存の IME キーの予測は学習をやり直すと戻ります」に。
