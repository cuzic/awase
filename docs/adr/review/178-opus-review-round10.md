## Blocker（v10で表面化）

### B14. 戻り値が**生の`AppConfig`**のみで、`ConfigLoadState`（ロードの成否・分類）を返さない。このままだとADR-099決定4の「`Dangerous`を静かに既定値へフォールバックさせない」保証が壊れ、決定5自身が要求する「`Dangerous`時にバックアップ復元を提案する」UIも実装できない

決定5のシグネチャ（270-275行）は

```
pub fn ensure_user_data_present(exe_dir: &Path, backup_dir: &Path)
    -> (AppConfig, RestoreOutcome, UserDataGuard)
```

で、`AppConfig`は`Option`でも`Result`でもない。一方、決定2ステップ2は
「このロードが失敗した場合（分類を問わず）」という分岐を持ち、決定5は
「`classify_load_error`が`Dangerous`に分類した場合は自動復元しない。…
`awase-settings`のUIで『バックアップから復元しますか？』と提案する」と
書いている。**ロードが失敗したときに何を`AppConfig`として返すのかが
未定義**であり、呼び出し元は「成功したのか失敗したのか」を判別できない。

これが壊すもの:

1. **ADR-099 決定4（F4 / round2 MF-2）の中核保証**。
   `classify_load_error`（`src/config.rs:840-858`）のdocは
   > `NotFound` 以外の I/O エラー（`PermissionDenied` 等）を誤って
   > `NotFound` 扱いにすると、**危険な失敗が静かにデフォルト値へフォール
   > バックしてしまう**（ADR-099 F4、round2 指摘 MF-2）

   と明記している。`ensure_user_data_present()`が失敗時に黙って
   既定値相当の`AppConfig`を返せば、**呼び出し元から見て「正常にロード
   できた」と区別がつかず**、この保証がそのまま失われる。しかも
   チェックリスト#3が「呼び出し元は初期ロードを自分でやり直さない」と
   定めているため、呼び出し元には分類を取り戻す手段が無い。
2. **`awase-settings`の既存挙動**。`SettingsApp::new`は
   `(config, config_load_state)`のペアを保持し（`crates/awase-settings/src/main.rs:543-556`）、
   `config_load_state`が`Dangerous`のときだけ
   - 危険な設定である旨のUI表示（`main.rs:1124`付近）
   - 保存前の`config.toml.bak`退避（`main.rs:786`の`is_dangerous`）

   を行う。`ConfigLoadState`が戻り値に無いと、この分岐が再現できない。
3. **決定5自身の「バックアップから復元しますか？」提案**が実装できない
   （`Dangerous`であることを知らなければ提案を出せない）。

参考までに、`awase-settings`が現在ロード失敗時に使う`default_config()`は
`toml::from_str("[general]")`（`main.rs:5473-5475`）＝`GeneralConfig::default()`
であり、**`layouts_dir = "config"`**（`src/config.rs:477`）になる。
これは決定3が「使うな」と名指しした値そのもので、`ensure_user_data_present()`が
失敗時にこれと同じものを黙って返すと、決定3の禁止事項を戻り値経由で
迂回することにもなる。

**要求**: 戻り値にロード結果の分類を含めること。例:

```
pub struct EnsureOutcome {
    pub config: Option<AppConfig>,      // またはResult<AppConfig, ..>
    pub load_state: ConfigLoadState,    // Loaded / NotFound / Dangerous(reason)
    pub restore: RestoreOutcome,
    pub guard: UserDataGuard,
}
```

併せて決定文に次を明記すること。

- `Dangerous`の場合、`config`は`None`（または`Err`）とし、**既定値を
  黙って返さない**。呼び出し元（`awase-settings`）が従来どおり
  `default_config()`を使うか、`Dangerous`用のUIを出すかを判断する。
- 決定2「失敗時の挙動」のインメモリ・フォールバック（復元書き込みが
  失敗した場合に埋め込み既定値で起動継続）は、**`load_state`で
  区別できる形**にする（「埋め込み既定値で継続している」ことが
  呼び出し元・決定6の通知から見えるようにする）。
- チェックリストにも1項目として追加する（「戻り値は`ConfigLoadState`を
  含み、`Dangerous`時に既定値を黙って返さない（ADR-099決定4）」）。

## Major

### M1. バックアップ契機（決定1の契機2・3）と復元可能範囲が非対称で、`layouts_dir`が絶対パスのユーザーには**永久に使われないバックアップ**が作られる

- 決定2の復元は「`validate()`後の`layouts_dir`が**相対パス**である場合に限り」
  行う（177-179行、B6対応）。絶対パス（例: `layouts_dir = "D:\\my\\yabs"`）の
  ユーザーには`.yab`復元が一切行われない（「解決されないこと」にも明記済み）。
- ところが決定1の契機2は「保存先が**現在の`layouts_dir`配下**であり、かつ
  ファイル名が同梱6ファイルのいずれか」でバックアップする（120-122行）。
  この`layouts_dir`が絶対パスでも条件を満たす。契機3も同様。

結果、絶対`layouts_dir`のユーザーは`backup\`に`.yab`を溜め続けるが、
**それが復元に使われることは決してない**。これはround8 M2で
「ユーザー自作`.yab`をバックアップして復元しないのは『使われない
バックアップ』になる」として対称化した論点と同型の非対称が、別の軸
（`layouts_dir`が絶対か相対か）で残っているもの。

実害:
- ユーザーのカスタム配列がバックアップという見えない場所に複製され続ける
  （プライバシー/ディスクの問題ではないが、意図しない複製）。
- 決定4の「完全削除」や決定6の「`backup\<ファイル名>`を削除してください」
  という案内が、実際には何の役にも立たないファイルについて出る。
- 「バックアップにあるのに復元されない」という問い合わせを生む。

**要求**: 契機2・契機3のバックアップ対象条件に「`validate()`後の
`layouts_dir`が相対パスである場合のみ」を追加し、**バックアップする範囲と
復元しうる範囲を一致させる**こと（チェックリスト#5にも追記）。
`config.toml`側は常にexe隣固定なのでこの問題は無い。

### M2. `Dangerous`時に「バックアップから復元しますか？」を出すための情報経路が未定義。UI側が独自に`backup\`を覗く実装になると、判定ロジックがコアと`awase-settings`に二重化する

決定5は`awase-settings`のUIで復元を提案するとしているが、提案を出すには
少なくとも

- `backup_dir`がどこか（`exe_dir.join("backup")`の導出）
- そこに`config.toml`のバックアップが存在するか
- それが妥当か（`toml::from_str`が通るか）

を知る必要がある。ところが`Dangerous`ケースでは決定2の復元が発火しない
ため、`RestoreOutcome`にはこの情報が載らない（載せる、とも書かれていない）。
放置すると`awase-settings`側が独自に`backup\config.toml`を読んで妥当性を
判定する実装になり、**round7 M4で「判定ロジックをコアの1箇所に集約する」
と決めた方針**（決定5の実装配置の根拠そのもの）が崩れる。

**要求**: どちらかを決定文に書くこと。

- (a) `RestoreOutcome`（またはB14で導入する`EnsureOutcome`）に
  「バックアップが利用可能か（存在し妥当か）」をファイル単位で含める。
  `Dangerous`で復元しなかった場合もこの情報は埋める。
- (b) コアに`pub fn backup_available(backup_dir: &Path, name: &str) -> bool`
  相当を1つ置き、UIはそれを呼ぶ（妥当性判定のロジックはコアに残る）。

(a)のほうが呼び出し回数もI/Oも少なく、B14の戻り値拡張と同時に片付く。

### M3. 契機1のゲート「保存先パスが書き込み（復元）先と一致する場合のみ」の**パス比較方法**が未定義。不一致になるとバックアップが静かに作られず、フェイルサイレントで復元不能になる

決定1の契機1（118-119行）は「保存先パスが書き込み（復元）先
（チェックリスト#11、`exe_dir.join("config.toml")`）と一致する場合のみ」
バックアップするとしている。しかし実際に保存に使われるのは
`awase-settings`の`self.config_path`＝`find_config_path()`の結果
（`main.rs:542`）、`awase.exe`側は`crate::app::find_config_path()`の結果
（`tray.rs:1042-1046`）であり、いずれも`resolve_relative_to_exe()`が返す
**読み取り解決の結果**である。

通常は`exe_dir.join("config.toml")`と同一文字列になるが、比較方法を
決めていないと以下で不一致になりうる:

- `current_exe()`が返すパスの表記ゆれ（大文字小文字、`\\?\`プレフィクス）。
- `%LOCALAPPDATA%`がジャンクション/シンボリックリンク経由の環境
  （`fs_atomic::write_atomic`のdocが「`path`がシンボリックリンクなら
  実体側へ書き込み」と述べており、リンク運用は想定内）。
- 片方が正規化済み、片方が未正規化。

不一致になった場合の症状は**何も起きない**（警告も出ない）——
バックアップが作られないまま運用され、MSI再インストール時に初めて
「復元されない」として顕在化する。B1修正の実効性がパス比較の実装詳細に
ぶら下がる形で、テストでも気づきにくい（テストは同じ関数から導出した
パスを渡すため常に一致する）。

**要求**: 比較をなくす方向で解決すること。すなわち

> 契機1は「保存先パスを比較して判定する」のではなく、**バックアップ対象の
> 保存経路そのものを、`ensure_user_data_present()`が返した復元先パスを
> 使って行う**（呼び出し元は保存先として戻り値由来のパスを使い、
> それ以外のパスへの保存はバックアップを呼ばない）。

比較が必要な設計を残す場合は、少なくとも「比較前に両者を
`std::fs::canonicalize`で正規化する（失敗時はバックアップしない＋警告ログ）」
と明記すること。現状の「一致する場合のみ」だけでは実装者ごとに結論が変わる。

## Minor

### m1. 「全`KeyboardModel`バリアントで試す」は現状`Jis`単独と等価。理由を書いておかないと「無駄な2回パース」として最適化されうる

`KeyboardModel::Jis`の行サイズは13/12/12/11、`Us`は12/12/11/10
（`src/scanmap.rs:28-41`のdocコメント）で、**`Jis`は`Us`の上位互換**。
したがって「`Jis`で成功 or `Us`で成功」は現状「`Jis`で成功」と同値である。
将来3つ目のモデルが増えたときに自動的に正しくなる点で全バリアント試行は
妥当な判断だが、その意図を1行書いておかないと、後日「どうせ`Jis`だけで
同じだから」と単純化され、モデル追加時に静かに壊れる。

### m2. 決定7から「テストの配置分担」（round7 m3で追加した記述）が落ちている

round7 m3で「`wix/main.wxs`を含む照合は`crates/awase-windows/tests/`側、
埋め込み既定値の内部整合はコア`awase`の`#[cfg(test)]`側」と分担を決め、
v8まで記載されていたが、v10の決定7（303-304行「3箇所同期テスト」）からは
消えている。決定7冒頭が「原則としてホストターゲット…コア`awase`クレートの
純粋関数」と書いているため、`wix/main.wxs`を読む照合までコア側に置く
読み方ができてしまう（コアからリポジトリルートを辿るテストは
`wix_installer_guard.rs`の前例と非対称になる）。

**これは「圧縮で記述が落ちる」事故のもう1件**であり、チェックリストが
カバーしていない領域（決定7の実装詳細）で起きている。チェックリストに
テスト配置まで入れるか、決定7に分担を書き戻すこと。

### m3. `backup_dir`引数は`exe_dir`から導出できるため、両呼び出し元に同じ導出が重複する

`backup_dir` = `exe_dir.join("backup")`（決定1）であり、
`ensure_user_data_present(exe_dir, backup_dir)`の2引数だと、
`awase-windows`と`awase-settings`の両方が同じ導出を書くことになる
（チェックリスト#10が既に警告している「2クレート同型実装」の増加）。
関数内部で`exe_dir`から導出し、テスト用に上書きしたい場合だけ
`Option<&Path>`を受けるほうが重複が減る。

### m4. `validate()`が関数内部と呼び出し元で2回走る。警告（`Vec<String>`）の扱いを決めておくこと

`ensure_user_data_present()`は内部で`validate()`して`layouts_dir`を得るが、
戻り値は生の`AppConfig`なので、呼び出し元（`awase.exe`は
`init_engine_validated`へ渡す前、`awase-settings`は警告表示のため）は
再度`validate()`を呼ぶ。`validate()`は純粋なのでコスト以外の副作用は
無いが、**警告のログ出力が二重になる**可能性がある（現在は
`bootstrap.rs`/`awase-settings`が1回ずつ出す前提）。
「関数内部の`validate()`は`layouts_dir`取得専用で警告は出力しない」と
1行書いておくこと。

### m5. 未解決事項#7は今回対応済みなので次版で落とすこと

「レビュー記録へのfrontmatter付与と`docs/adr/index.md`補助資料節への登録」は
今回のv10と同時に実施したとのことなので、未解決事項から外す。
残す場合は「round10以降の記録も同様に追加する」という継続タスクとして
書き換えること。

## 総評

v10でB13は解消され、その前提（`KeyboardModel`が2値であること、
列数超過が警告ではなく`Err`であること）もソース上で裏が取れた。
round9のMajor 3件も的確に反映されており、チェックリストは15項目に育って
「圧縮による要件欠落」への対策として機能している。

残るB14は、v9→v10で戻り値の型が具体化したことで初めて可視化されたもので、
**`AppConfig`だけを返す形はADR-099決定4（`Dangerous`を静かに既定値へ
落とさない）と両立しない**。`ConfigLoadState`を戻り値に含める修正は
小さく、M2（`Dangerous`時の復元提案に必要な情報）も同時に解決できる。

Majorはいずれも「対称性」に関するもので、
- M1: バックアップする範囲と復元しうる範囲のズレ（絶対`layouts_dir`）、
- M2: 判定ロジックをコアに集約する方針と、UI側が必要とする情報のズレ、
- M3: 「保存先」と「復元先」を**比較**で結びつけている箇所のズレ、

といずれも数行で閉じる。特にM3は、これまでB2・B5・B6・B12として4回
形を変えて現れた「読み取り先と書き込み先」問題の5回目の現れであり、
比較をやめて「戻り値由来のパスを使う」構造にすれば恒久的に閉じる。

B14とMajor 3件を反映すれば、**次ラウンドは確認のみで収束し、実装フェーズへ
進んでよい**水準にある。
