## Blocker

### B1. 決定4 案A(cache.toml に所有を記録)は ADR-126 が却下した案の再提案で、却下理由に答えていない

- ADR-230:66-68 は「ADR-111 が別 ADR 相当として先送りしていたマーカーを、ここで導入する」と書く。先送りではなく、
  **ADR-126「却下した代替案」(126:611-617)で検討済み・却下**されている。却下理由は「Scancode Map は OS レベルで awase の設定とは
  独立して存在し続けるので、マーカーとの同期が別途壊れる(アンインストール後に Scancode Map だけ残る、マーカーだけ消える等)」。
  ADR-230 はこの理由に一言も答えていない。出典も ADR-111 と誤っている。
- 置き場所として cache.toml は特に悪い:
  - cache.toml は **exe と同じディレクトリ**にある(`focus/classifier.rs:49` `CACHE_FILENAME`、`ImmCapabilityCache::new(base_dir)`)。
    一方 Scancode Map は **HKLM・マシン全体・全ユーザー**の値(ADR-111 決定6)。インストール先(ユーザーごとの Scoop ディレクトリ、
    ポータブル展開など)が違えば、同じ PC で別ユーザーの awase-settings は記録を持たない。結果として、その人には awase が書いたペアが
    「他ツールの値」に見え、上書き前の差分確認が誤って出るか、記録が無いので全部 Unclaimed 扱いになる。
  - cache.toml は「捨ててよい学習キャッシュ」として運用されている(`message_handlers.rs:1288-1299` の学習キャッシュ削除、
    BUG-108 の「cache.toml を確認してください」案内、v2 では較正値の移動先)。ユーザーが cache.toml を消すと所有の記録だけが消え、
    レジストリには awase のペアが残る。これは ADR-126 が予言した失敗そのもの。
  - **書き込み主体がずれる**。レジストリは昇格側プロセス(`run_elevated_worker`)が書く。UAC の over-the-shoulder 昇格
    (標準ユーザー + 別管理者アカウントの資格情報)では、昇格側は別アカウントで動く。cache.toml をどちらが書くのかが決まっていない。
    昇格側が書くと exe ディレクトリへの書き込み権限・ファイル所有者が変わり、非昇格側が書くと「レジストリ書き込み成功、記録失敗」の
    半端な状態が生じる。2つの書き込みは原子的ではない。
  - 別 PC への設定移行、OS 再インストール後の awase 再導入、他ツール(PowerToys・Ctrl2Cap・手動 regedit)による書き換えのどれでも、
    記録とレジストリは食い違う。その場合案Aは「差分を表示して確認」になるが、ユーザーに見せる内容は結局「今のレジストリの中身」であり、
    記録は何の判断材料も増やしていない。
- **代案(推奨)**: 所有の記録を持たない「レジストリが唯一の真実」型にする。
  1. 読み込み時に `detect_swap_pairs` で、許可リスト内の完全な相互エントリ(`A→B` と `B→A` が両方あり、A/B がほかのエントリの
     from にも to にも現れない)を**編集可能なペア**として、それ以外を**読み取り専用の一覧**として全件表示する。
  2. 書き込みは「読んだときのエントリ列」と「編集後のペア集合」の差分で計算する。削除したペアは、読んだ時点で実在した2エントリを
     そのまま消す。ADR-230:69-70 が案Bの欠点として挙げた「残骸が残るか無関係なエントリを消す」は、記憶した集合ではなく
     **読んだ状態との差分**で計算すれば起きない。
  3. 第三者がたまたま許可リスト内の完全な入れ替えを書いていた場合は、awase の UI に編集可能なペアとして見える。
     これは画面に出ているので、ユーザーが自分の PC の設定として扱えばよく、黙って消える事故(ADR-126 の B1 の型)にはならない。
     「原理的限界」の実害は「見えない所で消える」ことであり、全件表示すれば解消する。
  - この方式なら、新しい永続状態・同期の失敗モード・アンインストール時の後始末がどれも増えない。
- どうしてもマーカーが要るなら、置き場所は cache.toml ではなく **同じ昇格プロセスが同じタイミングで書く HKLM 配下の値**
  (例: `HKLM\SOFTWARE\awase\ScancodeMapOwned` に awase が書いたエントリ列のバイト写し)にする。HKLM・全ユーザー・昇格側という
  性質は Scancode Map と一致する。それでもアンインストール時の残留問題は残るため、上の代案より劣る。

### B2. 全単射の保証が awase のエントリに閉じており、保持する第三者エントリとの合成が保証されていない

- ADR-230:36-37「欠落・重複・チェーンが構造上作れない」は、`compute_swap_entries(pairs)` が**ペア集合だけを入力に取る**
  (ADR-230:53)から成り立つ話で、実際に書くのは「保持する第三者エントリ + ペアのエントリ」の合成。
- 既存のマージ規則は **from 側でしか衝突を見ない**(`scancode_map.rs:200-204` `filter(|&(from, _)| !clear.contains(&from))`)。
  これを一般化すると、次の失敗が起きる。
  - 失敗シナリオ1(多対一): 第三者が `X→A` を書いている(例: PowerToys 由来で `0x3A→0x1D` 以外の何か → Left Ctrl)。ユーザーが
    awase で `A⇄B` を追加する。from=X は掃除対象外なので残り、結果は `X→A`, `A→B`, `B→A`。**物理キー X と B の両方が A を出し、
    X のスキャンコードはどのキーからも出ない**。全単射ではない。SwapError にこの衝突の種類が無いので検出されない。
  - 失敗シナリオ2(from の重複): 第三者 `A→Y` と awase のペア `A⇄B`。今の規則では from=A は掃除されるので第三者エントリが黙って消える。
    ADR-111 決定3 の「無関係なエントリは保持」を、ペアの数だけ破る範囲が広がる。少なくとも UI で「このペアを作ると、他ツールの
    エントリ `A→Y` を消します」と事前に出す必要がある。
  - Scancode Map で同じ from が2件あるときにどちらが効くかは文書化されていない(`ntinput.c::MapScancode` の線形探索なら先勝ちだが
    未確認)。この状態を作らないことを不変条件として明記すること。
- 必要な修正:
  - API に**マージ関数**を明示する。例:
    `compute_swap_write(existing: &[(u16,u16)], pairs: &PairSet, keep_preset: Option<CapsAsExtraCtrl>) -> Result<(Vec<(u16,u16)>, Vec<Displaced>), SwapError>`。
  - 検査対象は「書き込む全エントリ列」にする: from が重複しない、ペアのキーが第三者エントリの to に現れない(現れたら
    `SwapError::CollidesWithForeignTarget{entry}` で止める)、from が衝突する第三者エントリは `Displaced` として返し UI で確認する。
  - 「保証するのは awase が書くペア部分の全単射であり、OS 全体の写像が全単射になるのは第三者エントリと交わらない場合だけ」
    と言葉を正す。

## Should-fix

### S1. 決定5「読み戻し検証に失敗したら書く前の値に戻す」は ADR-111 と同じではなく、新しい挙動

- ADR-230:74-78 は「ADR-111 と同じ」と言うが、現行の `run_elevated_worker_windows`(`scancode_map_admin.rs:58-69`)は
  読み戻し不一致で **終了コード1を返すだけで、元に戻さない**。ADR-111 決定3-2 も「失敗を表示して config に触れない」までで、
  巻き戻しは無い。
- 巻き戻しを足すなら、「書き込みは成功、読み戻しは一致しない、巻き戻しの書き込みも失敗」の3段の失敗を設計すること。
  ユーザーに見せる状態は「今のレジストリの中身」を読み直して出すのが安全。
- 読み戻し比較は `Vec` の順序込みの一致比較(`verified == new_entries`)で、ADR-126 M13(126:311-320)が「内部で順序を変えたら
  比較側も多重集合比較にせよ」と警告している。ペアの集合を `BTreeSet` などで持つ実装は自然に順序を変えるので、決定3 に
  「出力順は既存保持分を既存順、ペア分を末尾・入力順」か「読み戻しは多重集合比較」のどちらかを明記すること。

### S2. 昇格側への受け渡しと TOCTOU が書かれていない

- 現在の CLI は列挙子1つ(`as_cli_arg` → `"swap"` 等、`scancode_map.rs:73-92`、`main.rs:361`)。ペア集合を渡すには、
  シリアライズ形式(例: `--scancode-pairs 3A-1D,7B-38`)・**昇格側での再検証**(許可リスト・自己ペア・重複は昇格側でも
  `compute_*` を通す。非昇格側の検査結果を信用しない)・パース失敗時の終了コードを決める必要がある。
- 非昇格の UI がレジストリを読んでからユーザーが UAC を承認するまでの間に、他ツールや別ユーザーの awase-settings が値を変えうる。
  昇格側はもう一度読み直して計算するので、**ユーザーが見て確認した差分と実際に書く差分が違う**ことが起きうる。
  「UI が読んだエントリ列(またはそのハッシュ)を引数で渡し、昇格側で読んだ値と食い違ったら書かずに専用の終了コードで戻る」
  という比較交換を入れること。B1 の代案(差分で書く)とも整合する。

### S3. ADR-127(画面の適用はただ1つ)との整合が崩れる

- ADR-127 D4 がこのセクションを例外にした理由は「ラジオを押した瞬間に UAC → 即時書き込み・再読込」で、編集途中の状態が無いこと
  (`main.rs:3208-3222` の `if selection != derived { self.apply_scancode_map_change(selection) }`)。
- ペアの追加・削除は複数操作をまとめてから書くので、このセクション専用の**編集途中の状態と「適用」ボタン**が要る。それは画面下部の
  共通「適用」とは別の、2つ目の適用ボタンになり、ADR-127 の発端になった苦情(「適用が2つあってどれが反映か分からない」)を再生産する。
  ADR-230:76 の「ADR-127 がすでに認めた領域」は、例外の前提(即時適用)が変わるので流用できない。ADR-127 への追記
  (このセクションの適用ボタンの文言・未適用の編集があるときの表示・タブ移動や終了時の破棄確認)を決定に含めること。

### S4. 許可リストの中身と危険な組み合わせが未検討

ADR-230:43 は候補の列挙だけで、各キーのスキャンコード・配列依存・危険な組を決めていない。少なくとも次を決定に含めること。

- **スキャンコードの表を ADR に書く**(Set 1、E0 は u16 の上位バイト): Caps/英数 `0x003A`、LCtrl `0x001D`、RCtrl `0xE01D`、
  LAlt `0x0038`、RAlt `0xE038`、LShift `0x002A`、RShift `0x0036`、無変換 `0x007B`、変換 `0x0079`、かな `0x0070`、
  半角/全角 `0x0029`、LWin `0xE05B`、RWin `0xE05C`、App `0xE05D`。
  Scancode Map のエントリは u16 で E0 を上位バイトに持つので、LAlt/RAlt は値として最初から別物。BUG-132(ADR-230:46-47 の引用)は
  **フックの KBDLLHOOKSTRUCT で scan と拡張フラグが別フィールドになる層**の話で、この層には当てはまらない。引用するなら
  「許可リストを `u8 + bool` で持つと BUG-132 と同型の取り違えが起きるので、u16(E0 込み)の1つの値で持つ」と書くこと。
- **配列依存**: `0x0029` は US 配列では半角/全角ではなく `` ` `` の文字キー。`0x0070/0x0079/0x007B` は US 物理キーボードには無い。
  ADR-230:42 の「任意の scancode は選ばせない」の目的(文字キーを選ばせない)は、配列により `0x0029` で崩れる。
  JIS レイアウトのときだけ出すか、表示名を配列に応じて変えるかを決めること。
- **押しっぱなしにできないキーとの入れ替え(実機確認項目に追加)**: JIS キーボードの 半角/全角・カタカナひらがな・英数は、機種や
  レイアウトドライバによって「押した瞬間に Down と Up が続けて出る」ものがあるという報告がある(本レビューでは未確認の仮説)。
  そうなら Ctrl/Alt/Shift をその物理位置に移すと**押しっぱなしにできない修飾キー**になる。Scancode Map はドライバの上の層なので、
  ハードウェア側で Up が出ているなら入れ替えでは直らない。「修飾キー ⇄ 半角/全角 / かな」を許すかは実機で確かめてから決めること。
- **英数(0x3A)の二重人格は移動する**: `0x3A` を X と入れ替えると、X の物理位置が `0x3A` を出す。レイアウトドライバの
  「英数単独 = `VK_DBE_ALPHANUMERIC`、Shift+英数 = `VK_CAPITAL`」(ADR-111 決定1)と、Shift/Ctrl/Alt+CapsLock の IME ショートカット
  (PowerToys #3397 の原因)は X の物理位置に付いていく。ADR-230:48-49 は「UI の説明に残す」とだけ書くが、X が 無変換/変換
  (= NICOLA の親指キー)の場合、親指キーを Shift と一緒に押すと CapsLock が点灯するという awase 固有の実害になる。
  「`0x3A` と親指キー候補(無変換/変換)のペアは警告する」程度の具体策を決めること。
- **NICOLA 親指キーとの相互作用が書かれていない**。awase の親指キー設定は VK(`left_thumb_vk` 等)で持つので、無変換/変換を
  入れ替えると**親指シフトの物理位置が動く**。この機能の主な利用者は親指シフトのユーザーなので、意図した結果か注意点かを
  UI の説明と ADR に書くこと。ADR-196 の学習表(キー効果)は VK 単位なので影響しない、とあわせて明記すると誤解が減る。
- **ログオン画面への影響**: HKLM の値なのでログオン画面でも効く(ADR-111 決定3)。Caps を入れ替えたまま CapsLock が点いた状態に
  なると、パスワード入力の大文字小文字が分からなくなる。全単射なのでどのキーも打てなくなることはなく、Ctrl+Alt+Del も
  入れ替え後の位置で打てる(SAS は変換後のスキャンコードで判定される)ので、締め出しの危険は低い。この点を「検討済み」と
  一行書いておくと、次のレビューで同じ懸念を繰り返さずに済む。
- 置き場所: ADR-230:44 は「`awase-vkmap` か同等の場所」とするが、`awase-vkmap` は VK → `PhysicalPos` の表(`lib.rs:19 vk_to_pos`、
  97行)でスキャンコードを持たない。`SCANCODE_CAPS_EISU` などが既にある `scancode_map.rs` に置くのが自然。

### S5. ADR-126(CapsAsExtraCtrl)との関係が「排他にするか」で止まっている

- ADR-230:38-39 は排他にするかを決定3に委ね、決定3(:54)は `SwapError` に「ADR-126 片方向との衝突」を入れている。つまり排他にする、
  ということなので、そう言い切ること。
- 決めるべき細部:
  - CapsAsExtraCtrl が有効なとき、`0x3A` と `0x1D` の両方を許可リストから外すのか、`0x3A` だけか。
    ADR-126 決定3 の非対称(0x3A は awase が所有、0x1D は所有しない)をそのまま引き継ぐなら、外すのは `0x3A` だけで、
    `LCtrl⇄X` のペアは作れる。その場合 `Caps→LCtrl`, `LCtrl→X`, `X→LCtrl` となり、Caps と X の両方が LCtrl を出す
    (B2 と同じ多対一)。これを許すのか禁止するのか。
  - UI の形: 「無効 / CapsAsExtraCtrl / ペア編集」の3択にするのか、ペア編集とチェックボックスの併置にするのか。

### S6. 既存2プリセットからの移行が書かれていない

- 現在の状態は `detect_status`/`current_preset`(`scancode_map.rs:145-161, 211-217`)と、`ScancodeMapStatus::Active{preset}`
  (`scancode_map_admin.rs:84-94`)・`main.rs:3151-3206` の3か所の match で読まれている。ADR-230 はどれをどう置き換えるかを書いていない。
- 自然な移行は「`ScancodeMapPreset::Swap` を廃止し、`{(0x3A,0x1D)}` の1ペアとして読む。`CapsAsExtraCtrl` だけプリセットに残す」。
  これで既存の Swap 利用者は、新 UI を開いた瞬間に `Caps ⇄ LCtrl` のペアが1つある状態として見える。決定として明記すること。
  同じ exe 内の CLI なので、`"swap"` 引数の互換は不要(ADR-217 の方針どおり、互換の名目で残さない)。
- 既存の「曖昧な状態」(CapsAsExtraCtrl + 第三者の `0x1D→0x3A`)は、新しい `detect_swap_pairs` でも `Caps⇄LCtrl` のペアに読まれる
  (今の Swap 優先判定と同じ結果)。B1 の代案どおり全件表示すれば、ユーザーにはペアとして見えるので、黙って消える問題は
  表示で解消する。テスト `ambiguous_third_party_entry_colliding_with_swap_reverse_value_is_not_preserved`(`scancode_map.rs:503-524`)を
  どう引き継ぐか(期待値を変えるのか、そのまま固定するのか)を書くこと。

### S7. `detect_swap_pairs` の分類規則が未定義で、テストの境界が決まらない

ADR-230:55-56 の `(Vec<Pair>, Vec<Unclaimed>)` では次の入力の扱いが決まらない。決定として表にすること(そのままテストケースになる)。

| 入力 | 想定 |
| --- | --- |
| `A→B`, `B→A`(A,B 許可リスト内、他と交わらない) | Pair |
| `A→B`, `B→A` で A か B が許可リスト外 | Unclaimed(読み取り専用) |
| `A→B` だけ | `Caps→LCtrl` なら CapsAsExtraCtrl プリセット、それ以外は Unclaimed。戻り値にプリセット検出の欄が要る |
| `A→B`, `B→A`, `C→A` | A が2つの to に出る。Pair にすると B2 の多対一を「awase のペア」として抱え込むので Unclaimed にすべき |
| `A→B`, `B→C`, `C→A`(3巡回) | 全単射だがペアではない。Unclaimed |
| 同じ from が2件 | 全体を Unclaimed にし、UI で警告 |
| `A→0x0000`(キー無効化) | Unclaimed |
| `A→A`(恒等) | Unclaimed(または無視)。`SwapError::SelfPair` との対称性を書く |

- 戻り値は `(Vec<Pair>, Option<CapsAsExtraCtrl>, Vec<Unclaimed>)` 相当が必要。Unclaimed は「なぜペアと読めなかったか」の理由を
  持つと UI 表示とテストの両方が楽になる。
- 往復性質 `detect_swap_pairs(compute_swap_write(existing, pairs)) == (pairs, …)` は、プロパティテスト1本で全単射と保持の両方を
  押さえられる。決定3 にテスト方針として書くこと。

## Note

- **N1. 過剰設計かどうか**: 「プリセットを数個足す」案は安くない。今の2プリセットですら `current_preset` に「Swap は CapsAsExtraCtrl を
  包含するので先に判定」という順序依存があり(`scancode_map.rs:143-161`)、`owned_from_codes` の非対称(ADR-126 決定3)と
  「原理的限界」を生んでいる。プリセットを足すたびに包含関係・判定順・所有の組が組み合わせで増える。
  ペア集合に一般化し、Swap をただのペアにするほうが条件分岐は減る。**過剰なのは一般化ではなく決定4 案A(永続の記録)**で、
  B1 の代案にすれば新しい永続状態はゼロ。複雑性予算(`.claude/rules/complexity-budget.md`)は未発効で、対象も actuation 合流点と
  tuning 定数なので本 ADR には及ばない。
- **N2. 要望の出典が無い**。「IME キーや Ctrl/Alt を入れ替えたい」は誰の、どの報告か(issue 番号・不具合報告 ID・所有者の発言)を
