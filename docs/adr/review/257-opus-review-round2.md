## Must

### M1. 対照シナリオの PASS 条件が定義されていない。決定4 で対照は期待値の出どころになったので、対照の判定を実測値自身と比べると循環する

決定6-5 は「対照が FAIL なら run 全体を検証不能」とするが、対照の期待値が書かれていない。決定4 で、写像シナリオの期待 `vk` は「対照で測った値」になった。
対照を「対照で測った値」と比べれば常に PASS になり、番兵の役目を果たさない。

求める修正(決定4 または決定6 に書く): 対照の PASS は、写像を使わない独立の条件で決める。
1. 各打鍵の Raw Input の `MakeCode`+E0 が、シナリオ表に書いた scancode と一致する。
2. LL フックの `scanCode`+`LLKHF_EXTENDED` が、Raw Input の `MakeCode`+E0 と一致する(写像が無いので、両者は同じはず)。
3. 英字キーだけは、手書きの小さな表(A=0x41 など。配列に依存しない)の `vkCode` と一致する。

同じ箇所で、決定4 の「期待の `vk`」がどのフィールドかを明記する。決定2 に合わせて LL フックの `vkCode` とし、Raw Input の `VKey` は参考として記録だけする。
今の書き方だと、Caps→左 Ctrl の期待が Raw Input 由来の `VK_CONTROL` になりうる。そうなると、決定2 で LL フックを足した理由(左右の区別)が期待側で失われる。

### M2. from 重複のシナリオには事前の期待値が無い。PASS/FAIL ではなく「観測」の種類として定義する

決定5 は「from 重複の先勝ち/後勝ち」を表に入れるが、決定4 は「期待を手書きする」とし、決定6 は前提がそろえば PASS か FAIL のどちらかを出すとしている。
先勝ちか後勝ちかは未知なので、手書きの期待を置けない。どちらかを仮に期待として置くと、外れた初回の run が FAIL になる。

求める修正: シナリオの種類に「観測」(`kind: observe`)を設ける。初回の run では結果を記録するだけで、FAIL にしない。結果を ADR(と `scancode_pairs.rs:963` のコメント)に書いた時点で
「検証」(`kind: verify`、期待値あり)へ昇格させる。昇格するまでは、決定7 の再試行の対象にもしない。

### M3. Q5 の答えによっては、ADR-230 の親指キーの注意が根拠を失う。その帰結を Q5 に書き、段階1の結果を ADR-230 段階5 の判断条件にする

awase は物理キーを LL フックの `scanCode`+拡張ビットで同定している(`vk::thumb_latch_identity`・`should_release_thumb_latch`、fix-requires-evidence.md の「物理キー押下ラッチ」行)。
ADR-230 :87-88 は「入れ替えた位置のキーは、入れ替え先の scancode のキーとして OS に見える」と書き、この前提の上に段階4 の「親指キーの移動」の注意と、
ADR-248 の親指キーの注意が乗っている。

Q5 の結果は2通りありうる:
- (a) LL フックの `scanCode` が写像後。ADR-230 の前提は正しく、Raw Input の `MakeCode` だけが例外になる。
- (b) LL フックの `scanCode` も写像前で、`vkCode` だけが変わる。この場合、awase は入れ替えた位置のキーを、元の scancode のキーとして同定する。
  例えば無変換と変換を入れ替えると、親指キーの左右の同定(`vkCode` 由来)とラッチの解除(`scanCode` 由来)が食い違う。
  BUG-131/132 と同じ型の固着が新しく起きうる。

現在の Q5 は「ADR-230/248 の推測を訂正する要否を決める」とだけ書き、(b) のときに awase 本体のコードを見直す必要があることに触れていない。
求める修正: Q5 に (a)/(b) の帰結を書き、(b) なら hook 側の同定を見直す BUG/ADR を起票すると決める。段階3 の反映先に、hook の同定規則も加える。

### M4. 決定8 のハンドシェイクは、全回失敗した画面の検出に依存したままで、代わりの手段が無い

決定8 は「probe が窓の色を変え、ホストが色の変化を確かめる」としている。これは事実7 で 0/4 だったサムネイルの検出と同じ仕組みである。
原因の調べは「1回確かめる」としか書かれていない。検出が直らなければ、段階1 は再び固定待ちに戻り、事実7 の偽 FAIL の発生源がそのまま残る。

求める修正: 段階1 の完了条件を「画面の検出が N 回連続で成功する」と明記する。あわせて、画面に依存しない代わりの手段を1つ決めておく。
案: ホストは起動直後から「番兵キー → テストの打鍵列 → 番兵キー」の塊を、数秒おきに繰り返し送る。probe は READY のあとの記録だけを残す。
判定には、READY のあとで最初に完全な形でそろった塊を使う。この方法は、決定6 の条件3(打鍵数の一致)を「塊の中で」に読み替えれば両立する。

## Should

### S1. 検証不能を failure にするなら、このジョブを required check にしないことを決定7 に書く

インフラ起因の検証不能が failure になる。required check にすると、`scancode_*` を触った PR が、入れ子仮想化の不調だけでマージできなくなる。
決定7 に「required にしない。failure は PR の担当者が理由の番号を見て判断する」と1行足す。

### S2. 決定11 の上限45分は、決定7 の再試行と決定6-5(対照の FAIL で run 全体が検証不能)を組み合わせると破れる

対照が検証不能になると run 全体を再試行し、所要時間が2倍になる。決定11 の45分の上限と、ワークフローの `timeout-minutes` の関係を書く。
案: 再試行は「検証不能になったシナリオ(起動)だけ」に限る。対照が検証不能のときは、対照だけを先に再試行し、ほかのシナリオは対照の確定後に始める。
そのために、対照は run の先頭で単独に回す。

### S3. 対応表の「ADR-248 Q3: `ControlSet00N` の N の確認は VM で可」は誤り(round1 S7 の私の誤り)

VM で `reg load` しているのは WinPE の `boot.wim` の SYSTEM ハイブである。WinRE からオフラインで削除する対象は、インストール済みの Windows の SYSTEM ハイブで、
その `Select\Current` の値は WinPE からは分からない。VM にインストール済みの Windows は無い。
この行は「不可(インストール済み OS が要る)。実機」に直す。

### S4. 決定10 の golden の JSON に、項目ごとの出どころと、期待値の手書き部分の扱いを書く

JSON には性格の違う3種類の値が入る。
1. `decide` の生成物(16進。golden で再生成)。
2. 手書きのバイト列(from 重複のシナリオ。`decide` を通らない)。
3. 手書きの期待(決定4)。

golden の更新手順(`UPDATE_GOLDEN=1` のような再生成)で 3 まで上書きすると、決定4 のトートロジー防止が崩れる。
求める修正: 3 は別のファイル(または別のキー)に置き、golden の再生成の対象から外すと決定10 に書く。

### S5. 決定3 で `decide` を通すときの入力の制約を書く

`decide` は `existing != request.expected` のとき `Stop(Changed)` を返し、`plan.entries == existing` のとき `Stop(Ok)` を返す(どちらも書き込まない)
(`scancode_apply.rs:272-300`)。生成器は `expected` に既存値をそのまま入れること、`Decision::Stop` になったシナリオは golden の時点でエラーにすることを決定3/10 に書く。
「既存の他ツールのエントリを保持」のシナリオは `allow_displace` も関わるので、表の列に入れる。

## Nit

- N1. 決定9 の「`scancode_diagram.rs` も含めたいなら明示」は、判断が残ったままになっている。描画だけのモジュールで `ApplyRequest` を組まないなら「含めない(理由)」と書き切る。
- N2. 決定6-4 の「写像前の値」は、Raw Input の `MakeCode`+E0 と明記する。Q5 の結果で、LL フックの `scanCode` も写像前と分かる可能性があるので、どちらのフィールドかを固定しておく。
- N3. 決定9 の定期実行が失敗したときの通知先は、cron 行を最後に変えた人になる(GitHub の仕様)。誰が見るかを1行書く。
