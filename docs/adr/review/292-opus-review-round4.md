# ADR-292 Opus 敵対的レビュー round4(P の節のみ)

対象: `8d369faf7`(ブランチ `docs/adr292-key-effect-prediction-vs-observation`)の「P の詳細」節
round3 の T1〜T4 の反映は確認した。解放の判定の起点(T1)、保留中のモードキー(T2)、窓の変更と上限(T3)、始める条件・定数・遅延の測定(T4)は、いずれも指摘の意図どおり。

## 判定: 条件付き収束

設計の方向に新しい問題は無い。ただし、**文章どおりに実装すると P が働かない、または保留が繰り返される箇所が 2 つある**(U1・U2)。どちらも 1〜2 文の修正で閉じられ、設計の変更は要らない。U1・U2 を直せば、**これ以上のレビューは不要(収束)**と判断する。直したことの確認は team-lead が差分で行えば足りる。U3〜U5 は実装 PR で扱ってよい。

---

### U1(重大、文言): 「`ImeNotActive` で即座に解放」が、P が待っている「閉」の読みそのものを含んでいる

- T4 の箇条は「保留中にブロックが読めなくなったら(`Unreadable`/`ImeNotActive`)、即座に解放し現状の挙動に戻す」と書いている。ところが `ComposeSkip::ImeNotActive` は `!b.active || !b.effective_open` のときに出る(`mozc_shm.rs:739-740` の `judge_compose`)。つまり**「IME が閉じている」という読みも含む**。
- この文のとおりに `judge_compose` の分類を流用すると、BUG-233 の状況(Mozc が閉)で最初の読みが `ImeNotActive` になり、P は即座に解放する。予測の開のまま流すことになり、BUG-233 がそのまま再現する。
- **要求**: 即座に解放する条件を「読めない(`Unreadable`・`Rejected`・`Failed`)または TIP が無効(`active == 0`)」に限ると書き換えること。`effective_open == false` は解放ではなく「閉の候補」として 3 値の判定(settle の後に閉と確定 → R6、それまでは保留を続ける)に入れる。`ImeNotActive` という名前は使わない。`judge_compose` の判定は流用せず、P 専用の純粋関数で判定すること。

### U2(重大、文言): 始める条件 (c)「予測の開が未照合」と D1 の柵が噛み合わず、保留が繰り返される

- P が開と読んで解放するのは、モードキーから 170ms より前でありうる(Mozc が warm なら数十 ms で開く。T1 の起点でそれを認めたのが今回の改善)。一方、予測を「照合済み」にする `reconcile_key_effect_open` は、`pred.at_ms` から `KEY_EFFECT_SETTLE_MS` が過ぎるまで予測を消さない(`ime_model.rs:815`、D1 の柵)。さらに、P の読みを通す `report_mozc_shm` の `decide_use` は、一致する読みにローリング baseline を使い続ける。解放して流した打鍵がそれを押し出すので、`Use` 自体が遅れうる。
- その結果、解放した後も条件 (c)「未照合」が真のまま残る。次の打鍵でまた P が始まり、また読んで、また解放する。モードキーから 170ms 以上経って照合されるまで、**毎打鍵が 16〜30ms ずつ保留される**。
- **要求**: P は**予測ごとに 1 回**と定義すること。条件 (c) は「予測の開が未照合 かつ その予測(`pred.at_ms` で識別)について P がまだ『開』で解放していない」とする。開で解放した予測には、照合が済むまで P を掛け直さない。モードキーを押し直して新しい予測ができたら、また P の対象になる。これを単体テストの表に入れること。
- あわせて、一般化の文(「P が保留している間、`decide_use` に渡すどちらの baseline にも保留中の打鍵を含めない」)の範囲を、「その予測が照合されるまで」に広げるかを決める。広げれば、`report_mozc_shm` 側の照合も同じ起点で早く済み、上の問題は二重に閉じる。広げない場合は、上の「予測ごとに 1 回」だけで足りる。

### U3(中、実装 PR で可): 再生したモードキーを、本当に「再生の時点」で予測するか

- 保留したモードキーは、フックで抑止済みだ。再生は `INPUT_DEFER.replay_later` からパイプラインを通り、OS へは awase の注入として出る。T2 の規則(予測と S1 の打刻を再生の時点で行う)が成り立つかは、再生の経路が `enrich_key_role` → `apply_key_effect_prediction` を通るか、また注入したモードキーが自己注入として予測から除外されないかにかかっている。`focus_switch_hold` は既にモードキーを保持の対象にしている(`focus_switch_hold.rs:19`・`:56`)ので、その経路で予測がいつ dispatch されているかを確かめて、ADR に 1 行書くこと。推測で「同じ規則にする」と書かない。

### U4(中、実装 PR で可): R6 の (i) で開き直しに成功した後、保留中のモードキーを再生する問題

- (i) で awase が開き直しに成功した後、保留中にあった 2 回目の変換キーを流すと、Mozc はもう開いている(Precomposition)。MS-IME 互換の keymap では、この状態の変換キーは**再変換**になりうる。利用者の「開きたい」は既に満たされているので、流すと意図しない動作になる。
- 「(i) が成功したら、保留中の『開』を予測するモードキーは流さずに消費する(ログに残す)」という規則を、P と R6 の (i) の接点として書くこと。黙って消費するわけではない。意図は既に果たされているので、BUG-074 型の消失には当たらない。

### U5(小): 始める条件 (b) の述語

- `mozc_shm.polling` は `wants_timer` が真のとき真で、`Rejected`(`active=0`)や読みの失敗のときも真になる(`mozc_shm.rs:495-497` の doc)。条件 (b) の「読めるブロックがある」は、直前の読みが `Outcome::Accepted` で、そのブロックが `active` だったことで判定すること。`polling` で判定すると、TIP が無効な窓で P が始まり、即座に解放される無駄が出る(U1 を直せば害は無い)。
