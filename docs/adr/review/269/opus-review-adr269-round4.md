# ADR-269 レビュー(round 4): 新しいスレッドでの TIP の問い合わせ(D1a)と再現実験

対象: `fix/bug-207-mozc-server-io-monitor` の HEAD `4d66891d`。差分は `git diff 809930e1..4d66891d`。

## 自分で確かめたこと(run 39182258683 の成果物を取得して数え直した)

### 切り替えの構成 `ts-tsf-mozc-switch-*`

| 構成 | ハーネスの `[switch]` | awase の `detaching` | 間隔 |
| --- | --- | --- | --- |
| 8000ms-1 | 00:50:13.539 | 00:50:15.026 | 1.49 秒 |
| 8000ms-2 | 00:50:14.297 | 00:50:16.071 | 1.77 秒 |
| 20000ms-1 | 00:51:46.905 | 00:51:48.726 | 1.82 秒 |
| 20000ms-2 | 00:52:07.565 | 00:52:09.129 | 1.56 秒 |

- ADR の「約 1.4〜1.8 秒」は正しい。上限は 1.82 秒なので「約 1.5〜1.8 秒」が正確。4 本とも PASS。
- **8000ms の 2 本は、ready の最初の打鍵が 00:50:22 以降**。切り替え(13〜14 秒)から detach(15〜16 秒)の窓には、打鍵が 1 つも無い。8000ms は「起動後に切り替えた後」の確認にはなるが、窓の確認にはならない。
- 20000ms の 2 本は、試行が切り替えをまたいでいる。20000ms-1 では試行の境が 47.688、その次の試行が detach の 48.726 をまたぐ。窓の中の打鍵で誤判定は出ていない(n=2、連続打鍵の warm の状態)。
- 20000ms の「疑い 1」は 20000ms-1 が 00:51:42.253、20000ms-2 が 00:52:02.907。どちらも切り替え(46.9・07.6)の **前**。ADR の「切り替え前の GJI の打鍵〈未確認〉」の「切り替え前」は確認できた。本物の GJI のリテラルか誤判定かは未確認のまま。

### 再現実験 `ts-{,raw-}{tsf,chromepage}-mozc-{cold,idle}-20ms`

- 32 本とも `verdict=PASS loss=0 literal=0`。awase ありの 16 本は `raw TSF literal suspected` も 0。
- 試行数は cold が 1 本あたり 2、idle が 6。cold の開始は 16 回(awase なし 8・あり 8)、5 秒 idle の後の試行は 96(48・48)。

## 結論

D1a は BUG-207 の「起動後に GJI → Mozc へ切り替える」経路を直しており、方向は正しい。直してからマージしたほうがよい点が 3 つある。

1. 接続したときの問い合わせが古いマネージャーのまま(1-1)。
2. 新しいスレッドで取れなかったときに古い値へ戻る(1-2)。
3. 問い合わせに時間の上限が無い(1-3)。

どれも数行で直る。再現実験の結論は「この条件では観測されなかった」に弱め、陽性対照を足すこと(4)。

## (1) `query_active_kind_on_fresh_thread` のバグ・副作用

### 1-1. 接続したときの問い合わせが古い `mgr` のまま。デバウンスを通さずに種別を書き戻す(中、要修正)

- `gji_monitor.rs:473`: GJI に接続した直後に `query_active_kind(mgr)`(**起動時のスレッドの mgr**)を呼ぶ。`TSF_OBS.set_tsf_active_kind(kind)` と `set_ms_ime_native_identified` を、デバウンス無しで直接書く。
- D1a の前提は「この mgr は起動後の切り替えに追随しない」。なので、この呼び出しは **起動時の古い種別を、新しいスレッドで確定した値の上に書き戻す**。
- 失敗の例 1(MS-IME の利用者が GJI のリテラル判定を受ける):
  1. 起動時は GJI。古い mgr はずっと GJI を返す。
  2. 利用者が MS-IME に切り替える。新しいスレッドの問い合わせとデバウンスで、kind は MicrosoftIme になる。
  3. その後、GJI の変換サーバーが再起動するなどで `GJI process exited` → 再接続する。
  4. 接続時の古い問い合わせが GJI を返し、kind を GoogleJapaneseInput に書き戻す(`WM_IME_KIND_CHANGED` も出す)。
  5. `gji_is_active_ime()` が真になり、静止した GJI を証拠に、MS-IME の利用者の打鍵へ literal 判定が走る。BUG-207 と同じ型の誤判定(消す)になる。
  6. 次の新しい問い合わせで MicrosoftIme に戻るが、kind のデバウンスは 2 連続を要求するので、最大約 4 秒続く。
- 失敗の例 2: 起動時は MS-IME。GJI に切り替えた後、GJI の変換サーバーが遅れて起動して接続する。古い問い合わせが MicrosoftIme を書き戻し、warmup の戦略が MsImeStrategy に作り直される。BUG-017 が記録した「確立済みの warm の状態を捨てる」型で、最大約 4 秒。
- 直し方: 接続したときの問い合わせも `query_active_kind_on_fresh_thread()` にする。あるいは、接続したときの書き込みをやめて次の定期の問い合わせに任せる。後者のほうが「種別はデバウンスを通ってだけ変わる」という規律に揃う。
- 起動時の `:351` は、起動時点の値なので古い mgr でも問題ない。

### 1-2. 新しいスレッドで取れなかったときに古い値へ戻る(中)

- `.or_else(|| query_active_kind(mgr))`(`gji_monitor.rs:391-392`)。新しいスレッドの問い合わせがときどき失敗すると、新しい値と古い(起動時の)値が交互に入る。
- 切り替えの後なら「新しい値 → 古い値 → 新しい値」の往復になる。失敗が 2 回続けば、kind・identity・target のデバウンスがどれも古い値で確定する。
- 外す向き(`NoEvidence`)は 1 回で確定する。なので古い値が「Mozc」(起動時が Mozc で、その後 GJI に切り替えた場合)だと、失敗 1 回で GJI の監視を外す。GJI の安全網が、次の 2 連続の観測まで(約 4 秒)外れる。
- 直し方: 新しいスレッドで取れなかった tick は「観測なし」にして何も更新しない。古い mgr は、新しいスレッドを作れない環境のための最初の値だけに使う。失敗した回数は debug ログに出す。

### 1-3. `join()` に時間の上限が無く、詰まると I/O の標本化も止まる(中)

- `query_active_kind_on_fresh_thread` は spawn してから `join()` で待つ。`monitor_loop` は I/O の標本化(10ms ごと)と同じスレッドなので、問い合わせが返らない間は `gji_write_bytes`・`gji_last_io_ms` が凍る。
- GJI の利用者では、凍っている間の per-VK の判定が「書き込み無し」で SuspectedLiteral になる。**GJI の利用者に BUG-207 と同じ型の誤判定が出る**。
- 以前も同じスレッドで `GetActiveProfile` を呼んでいたので、詰まる危険そのものは新しくない。今回はそれに加えて、2 秒ごとに次の処理が増えた。
  - スレッドの生成
  - DLL の THREAD_ATTACH
  - `CoInitializeEx`
  - `CoCreateInstance(CLSID_TF_InputProcessorProfiles)`
- CLAUDE.md の並行性の規約は「止まりうる Win32/COM は `run_with_timeout` で隔離」(`crates/win32-async/src/thread_timeout.rs`、300ms)。この呼び出しもそれで包むか、上限付きの `recv_timeout` で待ち、時間切れは「観測なし」にする。
- 「スレッドの生成と COM の初期化は ms 単位」(`tip_detector.rs:259` の doc、ADR の D1a)は測っていない。所要時間を debug ログに出し、CI の awase.log で分布を見てから書く。per-VK の判定窓は約 300ms なので、所要が数十 ms を越えるなら、標本化の遅れも判定に影響しうる。

### 1-4. COM の初期化と解放(低)

- `CoInitializeEx` の戻り値を捨て、`CoUninitialize` は無条件に呼ぶ(`tip_detector.rs:266-274`)。新しいスレッドで失敗することはほぼ無い。
- それでも、失敗したとき(`E_OUTOFMEMORY` など)は対にならない。`S_OK`/`S_FALSE` のときだけ解放するよう、成功したときだけ解放する。
- `mgr`・`_profiles` はクロージャの引数として受け取り、クロージャの終わりで解放される。`CoUninitialize` より前なので順序は正しい。HKL の分岐の `enabled_ja_tips(&mgr)` も同じスレッドの中で完結している。

### 1-5. static の安全性(問題なし)

- `GJI_CLSID`・`GJI_FAMILY_CLSIDS` は `OnceLock` の読みだけ。`PROFILE_DESCRIPTIONS`(`RwLock`)は `cached_profile_description` の読みだけ。`TSF_OBS.set_ime_product_name` は `RwLock` の書き込み。どれもスレッドをまたいで安全。
- `set_ime_product_name` は新しいスレッドから 2 秒ごとに書くようになる。デバウンスを通らないので、往復(1-2)すると BugReport の製品名が揺れる(診断のみ、低)。

### 1-6. BUG-09・BUG-195 との整合(中、記述の要修正)

- BUG-009:36 の「per-thread `GetActiveProfile` 固着」仮説の棄却は、「起動時の検出は正しかった」ことを根拠にしていた。「起動後に追随しない」ことは否定していない。今回の観測(起動時は正しく、起動後に追随しない)と矛盾はしない。ADR の D1a にそう 1 行書くと、後で「一度棄却された仮説の再導入」と誤読されない。
- **BUG-195 の CI 観測(run 37895475336 など)は、今回の原因にもっと近い**:
  - 「窓を持たない監視スレッドは、前面窓の切り替えでなく既定の入力方式の上書きを見ている可能性が高い」
  - 「起動済みの awase は約 25 秒間 Microsoft IME のまま」
- D1a の CI は `ActivateProfile(... TF_IPPMF_FORSESSION)` で切り替えている。新しいスレッドがセッションの値を読めることは示したが、次の 3 つは示していない。
  - 実際の Win+Space(BUG-195 では CI で効かなかった)
  - `FORSESSION` なしの窓のスレッドでの切り替え
  - 「アプリごとに入力方式を切り替える」が ON の場合
- ADR の D1a と `tip_detector.rs:255` の「(`TF_IPPMF_FORSESSION`、Win+Space と同じ効果)」は確かめていない。「Win+Space と同じかは未確認(BUG-195)」に直す。
- D1a は BUG-195 の挙動も変えうる(起動後の上書きの変更に追随するようになる)。BUG-195.md に関連として 1 行書く。

### 1-7. kind_debounce・identity_debounce・TargetSwitch への影響(低〜中、要測定)

- 3 つとも、入ってくる値が「起動時の固定値」から「2 秒ごとの新しい値」に変わる。
- BUG-017 は、Chrome の cold reinit(実 `VK_IME_OFF→VK_IME_ON`)の直後に別スレッドの問い合わせが一時的に別の種別を返す、と推定していた。新しいスレッドでこの単発のずれが増えるのか減るのかは分からない。
- 増えると次のようになる。
  - kind は 2 連続で確定するので、単発なら吸収する。
  - `TargetSwitch` の外す向きは 1 回で確定する。GJI と Mozc の両方がある環境で単発の「Mozc」を読むと、GJI の安全網が約 4 秒外れる。
- 測り方: 既存の GJI の e2e(Chrome の cold reinit を通す `tsx-chrome*`・`sc-*`)を修正後の HEAD で回し、awase.log の `IME kind candidate`・`TIP identity candidate`・`converter target →` の件数を develop と比べる。

## (2) 新しいスレッドの値が前面アプリの TIP とずれるときの最悪の場合

前提: BUG-195 の観測から、窓を持たないスレッドが読むのは「セッション/既定の上書き」で、前面の窓のスレッドの TIP ではない可能性が高い。

| 実際(前面) | 新しいスレッドが読む値 | 結果 | develop との比較 |
| --- | --- | --- | --- |
| Mozc | GJI(Google 版) | target=Gji、静止した GJI に接続 → BUG-207 の症状(消す) | develop と同じ(悪化しない) |
| GJI(Google 版) | Mozc | target=NoEvidence → GJI の安全網が外れる → GJI の本物の cold リテラル(BUG-002 の型:「toいう」「bあ」)が回収されず残る | **悪化**。GJI と Mozc の両方を入れ、「アプリごと」ON か、上書きと実際の利用がずれている利用者に限る |
| MS-IME・ATOK | GJI | `gji_active` 真 → 静止した GJI を証拠に誤判定(消す)。warmup も GjiFsm | BUG-195 の逆向きと同じで、develop にもある。D1a で「起動時の値」から「現在の上書き」に変わるだけ |
| GJI | MS-IME | `gji_active` 偽 → GJI の安全網が外れ、MsImeStrategy | BUG-195 そのもの。develop と同じ |

- **新しく悪化するのは 2 行目だけ**。「消す」ではなく「消さない(リテラルが残る)」の向きで、D1 の根拠(誤判定の害>未検出の害)の範囲には収まる。それでも GJI の利用者にとっては退行なので、ADR の既知の限界に、この行を条件付きで書く。
- 1-1・1-2 を直さないと、表に無い「古い値と新しい値が混ざる」場合も加わる。とくに 1-1 の「MS-IME の利用者が GJI の判定を受けて消される」は、上の表のどの行よりも悪い。

## (3) ADR-269 の D1a・「段階 2 の前提」の記述

1. **D1a の「メッセージループを持たない。そこで…古い値を返し続けた」**: メッセージループが原因というのは推測で、確かめていない。確かめるなら、監視スレッドで `PeekMessageW` を回すだけの対照を CI で 1 回走らせる。「メッセージループを持たないスレッドでは…(原因は未確定。ループの有無が効くかは未検証)」にする。新しいスレッドにもメッセージループは無いのに追随した。なので「ループが無いから」より「インスタンスか、スレッドの TSF の状態が起動時の値を保持する」可能性のほうが高く、本文の因果は逆にも読める。
2. **D1a の「Win+Space と同じ効果」**: 未確認(1-6)。
3. **D1a の実測「8000ms は修正前・一度目の修正 INVALID ×4 → PASS ×2」**: 正しい。ただし 8000ms は窓に打鍵が無い。「切り替えの後の打鍵」の確認であって、窓の確認ではない、と書く。窓の中の打鍵があるのは 20000ms の 2 本だけ(n=2、warm)。
4. **D1a の「監視を外す経路・`gji_*` を 0 に戻す処理・即時の切り替えが CI で動いた」**: `detaching` の行と、その後の `gji_io=` のログで確かめたか。0 に戻ったことの直接の証拠(detach 後の `FocusProbe gji_io=` や `[h1-send] gji_idle=` が develop の Mozc 単独と同じ大きな値になる)を 1 行添える。私は `detaching` の行だけを確かめた。
5. **既知の限界の 1 つ目「最大約 2 秒」**: 実測 1.49〜1.82 秒と合う。ただし新しいスレッドの所要時間を足すと 2 秒を越えうる(1-3)。「ポーリングの周期と問い合わせの所要時間」とする。
6. **「段階 2 の前提」の見出しと結論「Mozc で本物のリテラルは、この範囲では再現しなかった」**: 「この範囲では」は付いているので断定ではない。ただし見出しが「再現するか」なので、結論が「再現しない」と読まれやすい。(4) のとおり、陽性対照が無いので「検出できたはずのものが無かった」とは言えない。「観測されなかった(陽性対照なし、検出力は未確認)」にする。
7. **再現実験の数**: 「32/32」は構成と回数の数。実際の機会は「cold の開始 16 回、5 秒 idle 後の試行 96」。こちらを書かないと、32 回の機会があったように読める。
8. **ADR の実 GJI の構成 `mozc-gji-real`(結果の節)**: 「PASS ×3、残り 1 本は chocolatey のインストールが 3 回失敗」は、自分では確かめていない。修正と無関係という判断は妥当。
9. 「本番の安全網なしの awase あり」(`ts-{tsf,chromepage}-mozc-*`): Mozc 単独では判定が走らないので、awase ありの literal=0 は「awase がリテラルを出さなかった」の意味で正しい。ただし awase は per-VK でなく一括で送る(Mozc 単独の develop と同じ)。GJI の cold の段取り(F2 の先行バッチ)も Mozc に対して動いている。この段取りが Mozc のリテラルを防いでいる可能性は分けられていない。awase なしの対照も PASS なので、その可能性は低い。

## (4) 再現実験の結論の言い方と陽性対照

- 言い方: 「Mozc Readable で、cold の開始 16 回と 5 秒 idle 後の 96 試行(tsf・CI の Chrome のページ、awase あり/なし)では、リテラルは観測されなかった。同じハーネスで GJI のリテラルを観測できるかは確かめていない」。D1 の根拠には「起きないことを示した」ではなく「起きた観測が無い」として使う。
- **陽性対照は要る**(安く作れる)。同じ構成の `ime=gji`、awase なしを足す。
  - `ts-raw-{tsf,chromepage}-gji-{cold,idle,longidle}-20ms`
  - GJI の Chrome での cold リテラルは、実機で 8.7 秒〜28 秒の idle の後に観測されている(tuning-constants.md の `79134f5`・`9a7e699`)。CI でも raw の GJI で literal>0 が出れば、ハーネスと Chrome の経路にリテラルを検出する力があると言える。そのうえで Mozc の 0 件に意味が出る。
  - GJI でも 0 件なら、この CI の環境(専用デスクトップの Chrome、ADR が書いている限界)ではリテラル自体が起きない。Mozc の結果は何も言っていないことになる。
- longidle(30 秒)は、この陽性対照と組にして初めて解釈できる。単独で 0 件でも結論は変わらない。
- 試行数の目安: cold は 1 本あたり 2 試行と少ない。GJI の陽性対照で literal の率が分かれば、Mozc で「率が GJI の 1/10 以下」と言うのに要る試行数を見積もれる。率が分からないうちに試行を増やしても、解釈は変わらない。
