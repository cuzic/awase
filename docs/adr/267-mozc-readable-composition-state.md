# ADR-267: mozc-readable の共有メモリに組成の状態を足す(version 3)

## 背景

ADR-265 の共有メモリ(`TipSharedState` version 2、48 バイト)が外に出す値は、IME の開閉・入力モード・`active` だけである。「いま未確定文字列(preedit)があるか」「候補ウィンドウが出ているか」「未確定文字列が何文字か」は分からない。

次の 2 つの需要がある(ユーザー指摘 2026-10-18)。

1. **awase**: リテラル混入の取り消しなど、**BackSpace を何回送るかをヒューリスティックで決めている箇所**がある(`tsf/output.rs::flush_raw_tsf_literal_backspaces`、`output/vk_send.rs` / `output/probe_io.rs` の `ze_bs_count`)。IME 側が数えた未確定文字列の長さが読めれば、推定を実測で裏取り・置換できる。
2. **QMK など自作キーボード**: 「変換中だけ別レイヤーにする」「候補が出ている間だけ Enter/矢印の意味を変える」「OLED に組成中を出す」。

IME 側の根拠: TIP の `UpdatePrivateContext`(`tip_edit_session_impl.cc`)は、Mozc セッションの `Output` を打鍵ごとに受け取る。`Output` は `preedit`(セグメント・カーソル位置)と `candidate_window` を持つ。現行の `Publish()` もこの処理の近くから呼ばれており、同じ場所で値を渡せる。

## 決定

### D1. 構造体を version 3 にし、末尾に 16 バイト追記する(64 バイト)

既存の取り決め(追記のみ。互換を壊すときだけ `version` を上げる)に従い、オフセット 0〜47 は変えない。

| オフセット | 型 | 名前 | 意味 |
| --- | --- | --- | --- |
| 48 | u32 | `composing` | 1 のとき、Mozc セッションに未確定文字列がある(`output.has_preedit()` かつ 空でない) |
| 52 | u32 | `candidates_visible` | 1 のとき、候補ウィンドウが表示対象(`output.has_candidate_window()` かつ候補が 1 つ以上) |
| 56 | u32 | `preedit_chars` | 未確定文字列の長さ。**Unicode コードポイント数**(全セグメント合計。`composing=0` なら 0) |
| 60 | u32 | `preedit_cursor` | 未確定文字列内のカーソル位置(コードポイント数。先頭=0) |

- `version` は `3`。version 2 の読み手は 48 バイトまでしか読まず、`version >= 2` の判定のままで動く(追記のみのため)。version 3 の項目を使う読み手は、`version >= 3` を確かめる。
- マッピングのサイズは 64 バイトにする。version 2 の読み手が 48 バイトで `MapViewOfFile` しても読める。
- 値を載せる条件は version 2 と同じ(書き出しは `active` を含む全項目のどれかが変わったときだけ、seqlock、変化時に pulse)。

### D2. 長さは「コードポイント数」で出し、UTF-16 の長さは出さない

- BackSpace は、アプリが 1 文字として扱う単位で消す。かな・漢字(BMP)ではコードポイント数と UTF-16 の長さが一致する。サロゲートペアの文字(一部の漢字・絵文字)だけ食い違うが、アプリごとに 1 回で消えるか 2 回かが違うため、**IME 側の数値だけでは決まらない**(下記 D5)。
- UTF-16 の長さが要る読み手は、仕様に書く「コードポイント数 ≥ UTF-16 長 / 2」の範囲で扱う。必要になったら項目を足す(追記のみ)。

### D3. 未確定文字列の「中身」は出さない

長さ・カーソル位置・有無だけを出す。文字列そのものは出さない。

- 他のプロセスから、パスワード欄などの入力内容が読めるようになるのを避ける(共有メモリの DACL は現在のユーザー全体に読み取りを許す)。
- `preedit_chars` も入力量の手がかりにはなる。ただしキーボードの打鍵数と同程度の情報で、キーロガーの類いが既に取れる範囲を超えない。仕様書に「パスワード欄などの入力スコープでは `composing` / `preedit_*` を 0 に落とす」を書くかは **未決(Q1)**。

### D4. `candidate_count` は足さない

候補の数・選択位置は、Mozc 側の表示順・ページ送りと絡み、読み手の用途(有無の判定)に対して過剰になる。必要になったら追記する。

### D5. 値は「Mozc セッションから見た状態」であり、アプリが実際に持つ文字数とは限らない

- 値が更新されるのは TIP が `Output` を受け取った時点で、アプリ側の編集セッションが適用された時点とずれうる。**awase が打鍵を高速に送るときは、直前の打鍵が反映される前の値を読むことがある**。
- したがって awase の BackSpace 数は、この値を**唯一の根拠にせず**、次のように使う。
  - 既存の推定(awase が自分で送った文字数)と食い違ったときの**検算**として、journal に両方を残す(ADR-265 D3 と同じく、最初は観測のみ)。
  - 一致率を実測してから、推定の置換を決める(実測なしに置換しない。ADR-158 の複雑性予算にも反する)。
- 読み手は、`seq` が前回の読み取りから進んでいるか、`update_tick_ms` が直近の打鍵より新しいかを確かめて、**古い値を使わない**。

### D6. 書き出しの負荷を実測してから確定する

- version 2 は「変化が無ければ書かない」ことで、無駄起床を 97 回→5 回に減らした(ADR-265 の実測)。
- version 3 は打鍵ごとに `preedit_chars` が変わるため、**書き込みと pulse が打鍵ごとに起きる**。`composing` / `candidates_visible` の 0↔1 だけを使う読み手にとっては無駄な起床になる。
- 対策の候補は 2 つ。実測してから選ぶ(**未決 Q2**)。
  - (a) pulse は `composing` / `candidates_visible` / 開閉 / モードの変化のときだけにし、`preedit_chars` だけの変化は共有メモリへ書くが pulse はしない(読み手が、必要なとき読みに行く)。
  - (b) 項目を 2 つのイベントに分ける(状態用・長さ用)。
- 測るもの: 連続打鍵(例: 1 秒に 10 打鍵)でのキー→反映の遅さ、ホストアプリの入力遅延の増加、読み手の起床回数。

## 実装の段階

1. **mozc-readable**: `readable/docs/shared-memory.md` に version 3 を書く(仕様が正)。`tip_state_publisher.{h,cc}` と `UpdatePrivateContext` 周りの配線。CI で、別プロセスから「入力前=0、`k`→`composing=1,preedit_chars=1`、`ka`→かな 1 文字、Space→`candidates_visible=1`、Enter→0」を確かめる。
2. **awase**: ADR-265 段階 1 の Observe(読み取り)が入った後で、journal に `composing` / `preedit_chars` を記録する(観測のみ、挙動は変えない)。
3. 一致率の実測(D5)。結果次第で BackSpace 数の検算・置換を別の ADR にする。
4. **QMK 向け**: `examples/read_ime_state.py` を version 3 に対応させ、`composing` / `candidates_visible` を Raw HID の 3 バイト目以降へ載せる例を足す(スケッチのまま。実機未検証と明記する)。

## 未決

- **Q1**: パスワード欄などの入力スコープで、`composing` / `preedit_*` を 0 に落とすか。
- **Q2**: D6 の対策 (a) / (b)。
- **Q3**: 組成中でも、変換前(ローマ字入力の途中)と変換中(Space 後)を区別する項目を足すか。Mozc の `Output` からは取れる見込みだが、読み手の需要を確かめてから決める。

## 確認していないこと

- `Output.preedit` のコードポイント数が、Chrome・Notepad・UWP の実際の表示文字数と一致するか(D5 の実測で扱う)。
- `candidate_window` の表示対象と、実際にウィンドウが画面に出ているかの一致(候補ウィンドウの描画は別プロセス)。
- AppContainer 内の窓での読み取り(version 2 と同じ。64 バイトでも名前空間の扱いは変わらない見込みだが、CI で確かめる)。
