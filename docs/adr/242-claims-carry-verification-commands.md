# ADR-242: docs・PR 本文の主張に、再確認のコマンドを添える

## 位置づけ

規約の本体は ADR-243 の `.claude/rules/agent-handoff.md` の規約の 3(243 の D1 の 3「報告と主張の独立な再確認」、番号付き 7 項目の 3 番目)に置く。自動で読み込まれる rules を 1 ページ増やすと、ADR-158 RC4(加算だけが義務化される)の型の加算になる。この ADR は次の 2 つを残す。

1. その 3 行の根拠になった実測(下の表)。
2. 「コマンドを添える」規約の効き目が小さいという結論。主張の誤りを捕まえていたのはレビューの観点のほうだった。

### 表から分かること

- **書いた時点でコマンド 1 本で結論が出て、添えていれば防げた**のは #5 だけ。#1 は結論は出るが、主張が誤りだったかは争える。#2・#3 は否定や数値の主張ではない(設計判断・計画)。#4・#8 は書いた時点では正しく、後のコミットに追随しなかった。#6 はコマンドが 2 本要る。#7 は答えを知らないと grep を打てない。
- **捕まえたのはレビューと本人の訂正**: #5・#7 は Opus レビュー、#1・#6・#9 は本人が同じ PR の中で直した。develop に誤りが残ったのは #2(#523 本文の前提)と、#1・#4 の件名の 3 件だけ。
- **件名が残る**: develop の件名に、`cb581901`(#524 のブランチのコミット、merge commit で入った)と `ae59ee2c`(#530 の squash)が誤ったまま残っている。`git log --grep` で引くと誤った主張が出てくる。
- 補足: #526 の本文は 19 行目で「ゲートが見ていたのは `d75c1d8b` より前の旧文言」と書き、32 行目では「正規表現は取得できなかった」と書いている。`5645908a` はローカルで読めるので、32 行目の主張も訂正が要る。

**未確認**: brief が挙げた「#518 の『26 行 PASS』」は、今の #518 本文が「24 PASS・`#[ignore]` 1」になっていて、直す前の文言を確かめられなかった。件数には入れていない。

## 決定

### D1. 規約は ADR-243 の `agent-handoff.md` に 3 行で畳む(独立したページは作らない)

ADR-243 の規約の 3(D1 の 3)に、次の 3 行を足す(文案。243 の付録は 343447f6 でこの文言どおりにそろえてある)。

```markdown
他人が次の作業の前提にする事実の主張(ある・無い・何件)には、確かめたコマンドを 1 行添える。git grep は打ったコミット、gh は PR の head SHA か日時を添える。
コマンド 1 本で確かめられない主張(CI の run・実機が要るもの)は「未確認」と書き、確かめる手段(run ID・ジョブ名)を添える。
PR に後からコミットを足したら、タイトルと本文の数値がまだ合っているかを見直す(#530・#531)。
```

対象を「否定・全称・数値」という型で列挙しない。上の表では、型で切ると対象外になる誤り(#2・#6・#9)とコマンドで防げない誤り(#4・#8)が多く、型の境界も曖昧だったため(「〜だけ」「以前から」)。3 行目のタイトルの確認は、マージの手順(ADR-237)に置くほうが自然なら、そちらへ移してよい。移す場合は 242 と 243 の規約の 3 を同時に直す。適用はエージェントに限り、人のセッションへ広げるかは 243 の質問 3 で決める。

### D2. レビューの観点は今の依頼文を続ける(グローバルの skill は変えない)

主張の誤りを実際に捕まえたのは、team-lead の Opus レビュー依頼文にある「主張を独立に再確認する」という観点だった(#5・#7)。新しく足すものは無い。`opus-adversarial-consult` は `~/.claude/skills/` にある全プロジェクト共通の skill なので、awase 固有の文は入れない。入れる場合も、プロジェクトに依存しない 1 行(「本文の存在・非存在・件数の主張のうち 3 つを、添えられたものとは別の方法で確かめ直す」)にとどめる。「別の方法で」とするのは、#1・#5 のように、読み手がコードの外(`docs/`・`tools/`)にいる誤りがあったため。同じ範囲の grep を打ち直しても、こうした読み手は見つからない。

### D3. CI での機械検査はしない

否定表現を拾う lint、主張とコマンドの宣言表、コマンドを CI で再実行する仕組みは作らない。ADR-218〜220(PR #429)が見送った理由は「実害の記録に対して削減量が小さい」だった。上の表では、規約で防げた実害は 1〜2 件で、どちらもマージ前に捕まっている。同じ基準を当てると、機械検査はもちろん、規約 1 ページも見送りになる。D1 を 3 行にとどめた理由もここにある。

## 却下した案と理由

| 案 | 理由 |
|---|---|
| `.claude/rules/claims-carry-verification.md` を独立に置く(初版の案) | ADR-243 の `agent-handoff.md` と趣旨が重なる(どちらも「報告の前に確かめる」)。同じタスク表の行(V2 の 2)を 2 本の PR が別々の文に書き換えてしまう。自動で読み込まれる rules が 1 ページ増える加算に見合う実害の記録も無い(上の表) |
| 主張を検出する lint・宣言表・CI での再実行 | D3 |
| 全ての文に出典を付ける | 負担が大きく、形骸化する |

効果の比較(訂正が減ったか)はしない。基準が 1 日分しかなく、数え方次第で 1〜9 件に揺れるため(上の表)。ADR-232 への遡及適用もしない。232 は develop に入っており、232 の実装 PR と同じファイルを触ると衝突する。

## リスクと限界

- コマンドを添えても、範囲が狭ければ同じ誤りは起きる(#1・#5 は読み手がコードの外にいた)。D1 の効き目は、レビュアーが添えられたコマンドを見て範囲の狭さに気づけるようにするところまで。
- CI の run・実機が要る主張(#3)には、「未確認」と書かせる以上の効き目は無い。
- 人(所有者)の docs の誤りは、上の 9 件に入っていない。9 件はすべてエージェントの PR・docs・コメントのもの。
- **未確認**: 今日より前の期間の件数。#518 の直す前の文言。
