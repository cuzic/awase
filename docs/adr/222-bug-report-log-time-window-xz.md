# ADR-222: 不具合報告のログを「直近10分」で決め、xz圧縮して送る

## 背景(実測、report `01M42BME26GDQ3CJ4F5DMGT0MP`)

- journal の種類別の残存時間: GjiFsmTransition 966 秒、ConvClassifyCall 786 秒、**KeyInput 165 秒(73 件)**。
  `DumpTruncated`: 全 2560 件中 891 件のみ、`dropped_key_input=439`、ring 追い出し 17,464 件。
- LINE へ最初にフォーカスしたのはクリックの約 6 分前で、その時間帯の打鍵は残らなかった。
- 打鍵レーン: ring 512 件(`journal_policy.rs::LaneKind::capacity`)。ダンプ時のバイト配分 15%(`RESERVED_PERCENT`)。1 件平均 460 バイト。
- 打鍵頻度(`awase.log.old` 00:54Z〜02:29Z の実測): 5 分間の最大 1,167 件、1 分間の最大 475 件。
- 圧縮率(同 journal 204,753 バイト): gzip 15,886 / xz 10,876。awase.log 204,800 バイト: gzip 19,867 / xz 14,288。
  キー名省略+時刻差分の JSON でも xz 8,244 で、**専用バイナリ形式の上乗せ効果は xz に対し約 1/2 止まり**。
- awase.log は 199KB が約 32 秒分(DEBUG 行中心、平均 3.7KB/秒、ピーク 6KB/秒)。journal 本体の複製(`awase::journal:`)は 8% にすぎない。
- 512KiB(`MAX_BODY_BYTES`)は ADR-095 実装時に決めた暫定値で、Cloudflare 側の制約や費用の実測に基づかない。

## 決定

- **D1 残す範囲は時間で決める**: 打鍵(KeyInput)は直近 10 分を残す。他のレーンも同じ時間幅にそろえる(レーンごとのバイト配分は廃止)。
  メモリ上限として件数の安全弁(打鍵 8,192 件など)は残すが、通常の打鍵頻度(最大約 4,750 件/10 分)では当たらない値にする。
- **D2 xz で圧縮して送る**: journal と awase.log を xz 圧縮し base64 にして新フィールドで送る。送信前プレビューは非圧縮の本文を表示し続ける。
  旧フィールド(`log_excerpt`/`app_log_excerpt`)は旧クライアント互換のため受理を続ける。
- **D3 awase.log は報告用に間引く**: 高頻度で調査価値の低い行(`[actuation-record]`、`Timer set/killed`、`[ime-io]` プローブ、UIA/MSAA の分類途中経過、
  journal 複製行)を、**添付時にだけ**除外する。ファイル自体は変えない。除外対象は実データの頻度順に決め、除外した件数をヘッダに残す。
- **D4 KeyInput は報告用に省略表現にする**: vk・押下/解放・判定・時刻差分など判断に必要な項目に絞る(目標 約 120 バイト/件)。journal 本体の型は変えない。
- **D5 ボディ上限を引き上げる**: 10 分分 + 他フィールドが収まる値(2MiB を第一案)にする。Worker とクライアントで同じ値を持つ。
- **D6 専用バイナリ形式は採らない**: 上の実測で xz に対する効果が約 1/2 に留まる一方、スキル・調査スクリプト・プレビューの全てにデコーダが要り、`grep`/`jq` で直接読めなくなる。

## 未決・要確認

- 10 分の打鍵 + journal 全体 + awase.log の圧縮後の合計サイズ(別環境のログでも確認する)。
- xz の Rust 実装(純 Rust の `lzma-rust2` を第一候補、Windows クロス `cargo check` で扱いやすい)と、Worker/調査スクリプト側の解凍手段(Worker は解凍せず保存のみ)。
- 旧クライアントとの互換期間と、Worker のデプロイ手順(所有者の承認が必要)。
