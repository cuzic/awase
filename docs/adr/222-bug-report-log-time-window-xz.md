# ADR-222: 不具合報告のログは ring の中身を圧縮して送る(打鍵は最低 10 分)

## 背景(実測、report `01M42BME26GDQ3CJ4F5DMGT0MP`。Opus round1 で照合済みの値)

- 打鍵(KeyInput)は 165 秒・73 件しか残らなかった。他レーンは 13〜16 分残っていた(GjiFsmTransition 966 秒、ConvClassifyCall 786 秒)。
- **主因はダンプ時のバイト配分**: `journal_policy.rs` の `RESERVED_PERCENT` で打鍵は 15%、さらに余り予算の配分優先度(`lane_priority`)も最下位。
  (204,800−2)×0.15 = 30,719B ÷ 打鍵 1 件約 418B ≒ 73 件。ring(512 件)には 512 件あり、うち 439 件を予算が落とした。
  ring の大きさが主因だったかは、この報告からは判定できない。
- 訂正: 「追い出し 17,464 件」は打鍵レーンだけの件数(全レーン合計は 28,966 件)。打鍵 1 件は平均 418B(旧記述の 460B は誤り)。
  journal 複製行は awase.log の 9.8%(旧記述 8% は誤り)。
- 切り詰めは 2 段ある: `journal.rs::to_json_capped`(レーン配分あり)と、`bug_report.rs::truncate_journal_json_tail`(レーンを区別しない末尾切り)。
- 打鍵頻度(`awase.log.old`、1 分最大 475 件。`journal: key input` 行の件数)。5 分間の最大 1,167 件は未再確認。
- 圧縮率(journal 204,753B): gzip -9 15,886 / xz -9e 10,876(preset 6 は 12,112)。awase.log 204,800B: gzip 19,867 / xz -9e 14,288。差は約 1.4 倍。
- LINE への最初のフォーカスは、クリックの約 8.8 分前(T−529s)にもあった(旧記述の「約 6 分前」は別の回)。10 分では余裕が約 71 秒しかない。
- awase.log が DEBUG 行で埋まるのは `RUST_LOG` を設定した環境だけ(既定は `info`、`bootstrap.rs:152`)。この報告は開発者本人の環境。
- 512KiB は ADR-095 実装時の暫定値で、Cloudflare 側の制約や費用の実測に基づかない。

## 決定

- **D1 予算で絞らず、ring の中身を全部ダンプする**: `RESERVED_PERCENT` / `select_tail_within_budget` / `to_json_capped` の予算ループ / `truncate_journal_json_tail` を削除する。
  圧縮すれば journal 全体で数 KB〜十数 KB で、絞る理由が無い。サイズ超過時は「時間窓を短くして圧縮し直す」に一本化し、
  ヘッダに**レーンごとの実際に残った最古の時刻**と追い出し件数を記録する。
- **D2 打鍵 ring を最低 10 分に広げる**: 最大頻度(約 4,750 件/10 分)でも溢れない 8,192 件前後。時間の端の判定は、畳み込まれた自動リピート(ADR-169)の
  `elapsed_ms`(最初の押下)ではなく `last_elapsed_ms` で行う。ring の事前確保メモリ(約 2.3〜2.9MB)と、ダンプ時間(メインスレッドで数 MB を serde)を実測して ADR に追記する。
  外部注入の打鍵(畳み込まない)で溢れた場合は、ヘッダの最古時刻で分かるようにする。
- **D3 圧縮して送る**: 方式は未決(下記)。圧縮は awase-settings のログ読み込み時に 1 回だけ、別スレッドで行って結果を保持する(説明欄の入力ごとの再圧縮は禁止)。
- **D4 schema_version を 4 に上げる**: 古い Worker は新フィールドを黙って捨てて 201 を返す(`index.ts:608-638` は許可項目だけで組み直す)ため、
  上げないと「ログだけ消えた報告」が気付かれずに溜まる。新 Worker は 3 と 4 の両方を受理し、**Worker を先にデプロイ**してからクライアントを出す。
  ボディ上限 2MiB の引き上げも同じ順序(クライアントが先だと 413)。
- **D5 ボディ上限を 2MiB に引き上げる**(所有者決定): 試算(Opus): 打鍵 4,750 件 ≒ 125KB(xz)、journal 他 ≒ 11KB、awase.log(DEBUG)10 分 ≒ 270KB で、
  base64 込み約 545KB。一般ユーザー(`info`)ならさらに小さい。2MiB には 2.6〜4 倍の余裕がある。
- **D6 専用バイナリ形式は採らない**: xz に対する効果が約 1/2 に留まり、`jq`/`grep` で直接読めなくなる(標準の `base64 -d | xz -d` で読める範囲に留める)。
- **D7 Worker は旧フィールドの報告も無期限に受理する**: v1 保守ライン(`v1-main`/`v1-develop`)の旧クライアントは今後も旧フィールドで送り続ける。
  新フィールドの検証: base64 の文字種・`length % 4 == 0`・長さ上限・圧縮形式のマジック(xz なら `/Td6WFoA`、gzip なら `H4sI`)・`attach_log=false` のとき null。
  旧フィールドと新フィールドが両方あれば拒否する。
- **D8 R2 には JSON 1 オブジェクトのまま保存する**: 巨大フィールドは base64 のまま保存し、調査スクリプトが解凍する(書き込みを分けると一部だけ失敗する状態が生じる)。
  調査スクリプト側は、解凍後のサイズに上限を設ける(解凍爆弾対策、例 64MiB)。
- **D9 旧 D3(awase.log の間引き)・旧 D4(KeyInput の省略表現)は今回見送る**: 間引き対象([ime-io]、Timer set/killed、MSAA 分類)は
  BUG-027/031/054/111/113/126 などで決定的な証拠だった。間引いても xz で約 35% しか減らず、2MiB に対して不要。
  代わりに、(a) `[actuation-record]` の長い固定文言を出力元で短くする、(b) `awase::journal` の複製行だけは除く、にとどめる。
  KeyInput の省略は、プレビューのサイズが問題になった場合に、情報を落とさない形式(往復変換テストつき、平均約 67B/件)としてだけ採る。
- **D10 awase.log の時間窓**: 時間(行頭の RFC3339)で切り、`awase.log` と `awase.log.old` の両方を読む(ローテーション直後は新ファイルがほぼ空)。
  時刻の無い継続行は直前の行に付ける。

## 未決(所有者の判断が要る)

1. **圧縮方式**: Opus は gzip(`flate2` は既存依存、Worker が `DecompressionStream` で解凍して中身を検証できる)を第一候補に推奨。
   xz は約 1.4 倍小さいが、新クレート(`lzma-rust2`、動作確認済み)と、Worker が解凍できないことによる検証の弱さが代償。数 MB の実データで両方を測ってから決める。
2. **プレビューの作り直し**: 現状は「プレビューの文字列そのものを送る」(`awase-settings/src/bug_report.rs:397`)で、ユーザーが行を消せる。
   圧縮して送ると、消した行が圧縮データの中に残る。ログは読み取り専用の表示(必要な行だけ描画)にして、送信時に表示中の内容から圧縮する案を第一とする。
3. **10 分ぶんの全打鍵を送ること**(この間に打ったパスワードも文章として復元できる)は、ADR-095 決定4(生の打鍵はマスクしない代わりにプレビューで確認できる)の前提が変わるため、所有者の再確認が要る。
