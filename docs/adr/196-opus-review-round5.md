## Should-fix

### S-1. advise sinkが生きているかは、COMのAPIの戻り値では確かめられない。フックと同じ「自分の操作に通知が返ってくるか」で確かめる

**該当**: 106行目（「advise sink登録済みのCOMオブジェクトが生きているか〈advise/unadvise呼び出し結果やCOMエラーコード〉を
セッション中に確認し」）。

`ITfSource::AdviseSink`の戻り値が分かるのは登録したときだけである。登録後にsinkへ通知が来なくなっても、
こちら側のCOM呼び出しがエラーを返す場面は無い。考えられる原因は、TSFの内部でsinkが解除される、
スレッドのドキュメントマネージャーが切り替わる、窓のサブクラス化が外れて`WM_IME_NOTIFY`が届かなくなる、
などである。つまり書かれている方法では、round4で問題にした「検出器が黙って止まる」を捕まえられない。

**対応案**: 項目4のフックの確認と同じ形にする。学習プロセスが自分で注入したキーによって、`read_status`で観測できる
開閉・変換モードの変化が起きたなら、対応するcompartment変更通知（または`WM_IME_NOTIFY`）が届いているはずである。
「状態は変わったのに通知が来なかった」ことが1回でもあれば、通知の経路が止まったとみなしてセッションを失敗にする。
既に行っている観測を突き合わせるだけなので、追加のコストはかからない。106行目の括弧内をこの方法に置き換えればよい。

### S-2. 89行目が、1eで訂正済みの「段階4の読込時に判定する」をまだ述べている

89行目: 「段階4の読込時、正答率が暫定95%未満…なら、その表を不採用とし…」。

129行目（1e）は「1aの『段階4の読込時に判定』という記述はこの1eに合わせて訂正する」と書いているが、89行目の本文は
直されていない。1eの方が後から優先されると読めば実害は無い。ただ、実装者が1aだけを読むと、読込時に判定を
やり直す実装になりうる（196行目の成功基準「段階4の読込は判定をやり直さない」と矛盾する）。
89行目の主語を「学習セッションの末尾（1e）で」に書き換える。

## Nice-to-have

### N-1. `RtlGetVersion`は未文書化のAPIではない

186行目は`RtlGetVersion`を「未文書化APIへの依存を避けるため候補から外す」としている。実際には`RtlGetVersion`は
Microsoftが文書化しているAPIである（カーネルモード向けのヘッダで公開され、ユーザーモードからもntdll経由で使われる）。
レジストリの`CurrentBuildNumber`に統一するという結論は妥当なので変えなくてよい。理由の説明だけを
「互換性のためのシムの影響を受けず、追加の依存も要らない単純な読み取りで済むため」などに直すとよい。

## 依頼事項への回答

1. **番号の修正**: 91行目の2か所は「1b-8」、142行目は「1b-9」、171行目は「1〜6」に直っており、現在の項目1〜9の並び
   （100〜117行目）と一致する。171行目の範囲に、項目5「セッション中の監視」は名指しで含まれている。
   ほかの相互参照（111・115・119・196行目）も数え直したが、ずれは無かった。
2. **S-f**: 対になる確認を足したという意図は満たしている。ただし、書かれている確認方法（COMのAPIの戻り値）では、
   sinkが途中で外れたことを検出できない。フックの確認と同じく「自分の注入で状態が変わったのに通知が来ない」ことを
   検出条件にするよう求めた（S-1）。Should-fixであり、実装を始めることは妨げない。
3. **S-g**: 満たしている。152行目と153行目は別の行・別の文言になっており、MS-IME本体の側は
   「実機での精度検証待ちのため既定では使用しません」で、不一致率の数字を出していない。
4. **5ラウンドを通しての収束判定**: **Blocker 0件、Must-fix 0件。実装着手可。**
   各ラウンドの流れは次のとおりである。
   - round1: 内蔵表で学習結果を棄却する検査が、ADR-195のBlocker B-1への回答の一部だったことを指摘した。
   - round2: round1で私が提案したA'自己診断に、原理的な欠陥があったことを指摘した。
   - round3: 検出対象の目印が1種類に限られていたことと、フックが黙って外れる問題を指摘した。
   - round4: 項目の挿入で内部参照の番号がずれたことを指摘した。

   ラウンドごとに指摘の重さは単調に下がった。round4以降は文言の整合だけが残っている。骨格の3点は
   round3以来変わっておらず、繰り返しの検証に耐えている。
   - 学習結果を正とし、内蔵表は初期値と再測定の引き金にとどめる
   - 失効ではなく要再検証にする
   - 学習窓への外部からの書き込みを直接観測する
