# ADR-145: Scancode Map によるかな系キー入れ替え代替案（検討・比較用）

## ステータス

**検討・比較用（2026-09-06起票、実装しない前提の記録）。**

[ADR-144](144-gji-keymap-kana-alternative.md)と対になる代替設計案。
既存の Scancode Map 機構（ADR-111/126、`crates/awase-windows/src/
scancode_map.rs`、Caps(英数)⇔Ctrl入れ替えプリセットで実装・実機運用済み）
を、かな系キー（変換・無変換・スペース・かなスロット）の入れ替えに
拡張できないかを調査した上で起票する。**本ADRも不採用と判断し、却下した
代替案として記録する**（結論は末尾の比較参照）。

## 背景

ADR-111は「Caps(英数)⇔Ctrl入れ替え」を、当初検討していたhookベースの
汎用リマップ機構（ADR-110の`key_remap`）ではなく、レジストリベースの
Scancode Map方式**のみ**で実装するという決定を下している。その決定の
根拠（ADR-111背景3・4）は次の通りだった:

- `docs/experiments.md`エントリ07/08/09で、`VK_DBE_ALPHANUMERIC`を
  `SendInput`で注入する手法はこのリポジトリで既に3回失敗・撤去済み。
- **PowerToys（Microsoft製）が全く同じ「CapsLock→Ctrl + 日本語IME」の
  組み合わせで2020年から問題を抱え続けている**（Issue #3397、
  Issue #32344）。根本原因は「Shift+CapsLock/Alt+CapsLock/
  Ctrl+CapsLockは日本語IMEの入力方式切替のグローバルショートカットで
  あり、IME側がフックより前の層でキー状態を読むため、フック側で
  CapsLockを抑制・リマップしても検出されてしまう」という構造的な問題。

この結論は、**「IMEが特別な意味を持つキー位置」をhookで安全に扱うのは
構造的に困難であり、レジストリレベル（フックより手前）で物理的に
すり替える方が安全**という一般原則を導いている。ADR-141/143が、まさに
「IMEが特別な意味を持つキー位置」であるかな系キーをhookベースで扱うと
決めたことは、この既存の教訓と表面上矛盾する（詳細は決定4参照）。

ユーザーの「GJI前提の補助ツールで80%満たせたのでは」という疑問と対に
なる形で、「そもそもレジストリレベルのScancode Mapで十分だったのでは」
という問いにも答える必要があるため、本ADRを起票した。

## 調査結果（`scancode-map-extension-research`エージェント、2026-09-06）

1. **実装コストは小さい**: 既存の`ScancodeMapPreset`列挙体・
   `entries()`/`build_bytes`/`current_preset`/`detect_status`のパターンに
   従い、かな⇔変換のプリセットを追加するのは技術的に容易（既存の
   Caps⇔Ctrlプリセットとほぼ同型、数行〜数十行程度）。
2. **反映には完全な再起動が必要**（ADR-111決定5と同じ制約、ログオフでは
   不十分）。
3. **システム全体・全ユーザーに適用される**（`HKLM`配下、ADR-111決定6と
   同じ制約）。
4. **動的な切替が原理的に不可能**: レジストリの静的な値であり、awaseの
   `engine_enabled`（エンジンON/OFF）と連動させる手段が存在しない。
   ADR-143 decision3の「かなスロットが関与するサイクル全体をエンジン
   OFF時に無効化する」という、ユーザー自身が明示的に要求した仕様
   （安全な3キー入れ替えは継続、かな系のみエンジン連動）は、Scancode
   Map方式では**原理的に実現不可能**。
5. **新規の条件付き機能が実現不可能**: ADR-143 decision7の「Shift+代入先
   キー→カタカナ」のような、新しい条件分岐を伴う機能は、純粋な静的
   スキャンコード置換の枠組みには存在の余地がない。
6. **好意的な副次効果（未検証の推測）**: 物理かなキーの実際のVK出力は
   既にIME状態依存で動的に変わる
   （[[project_adr133_bug113_wt_vk_kana_investigation_2026_09_05]]、
   `VK_DBE_HIRAGANA`/`SBCSCHAR`/`DBCSCHAR`として届く）。変換キーの
   スキャンコードをかなキーのスキャンコード（`0x70`）にScancode Mapで
   すり替えれば、Windows/IMEはそれを**本物の物理かなキー押下**として
   扱うため、「1回目ひらがな・2回目カタカナ」というIME内部の状態機械が
   **自動的に動作する可能性が高い**——ADR-143 decision2/decision7が
   `ime_open_before`スナップショットや`send_ime_mode_key_with_shift_
   release_prefix`の1行修正まで含めて作り込んだ複雑な機構が、丸ごと
   不要になる可能性がある。ただし実機未検証・推測の域を出ない。
7. **ADR-111自身の先例との緊張関係（重要）**: ADR-111背景3・4が明記した
   「IME関連キーのグローバルショートカットはIMEがフックより前で読むため
   hook側の抑制・リマップは効かない」というPowerToys由来の教訓は、
   ADR-141/143がまさに同じ性質のキー（かな系、IME入力方式切替に直結）を
   hookベースで扱う設計を選んだこととの整合性が問われる。両者の違いを
   説明できなければ、ADR-141/143の設計判断そのものの妥当性に疑義が
   生じる（決定4で検討）。

## 想定する設計（仮に採用する場合の骨子）

- `scancode_map.rs`の`ScancodeMapPreset`に、変換⇔かな（および必要なら
  無変換⇔かな、スペース⇔かな）のプリセットを追加する。
- ADR-111の決定3〜4（既存値との共存・検出・マージ、自己昇格フロー）・
  決定5〜6（再起動要件・適用範囲の明示）をそのまま踏襲する。
- ADR-141/142/143のhookベース機構（sentinel VK、hold-state、
  `engine_enabled`連動、Shift+代入先キー機能）は**一切実装しない**。

## 決定1: 対象は「静的・恒常的な入れ替え」のみに限定される

ADR-143の全単射モデル4要素（変換・無変換・スペース・かなスロット）の
うち、Scancode Mapで表現できるのは「常時有効な1対1の物理的すり替え」
のみ。ユーザーが後から設定画面でON/OFFを切り替える、あるいはengine
ON/OFFに連動して挙動を変える、といった**動的な要素は一切持てない**。

## 決定2: Shift+代入先キー→カタカナ機能はスコープ外にせざるを得ない

決定的観測6の通り、変換キーの物理位置そのものがOS/IMEレベルで
「本物のかなキー」にすり替わるため、Shift+変換キーがそのままGJI/MS-IMEの
既存のShift+かな挙動（1回目ひらがな・2回目カタカナ、実機観測済み）を
**そのまま**引き継ぐ可能性が高い。これはADR-143 decision7が実現した
機能と同じ結果を、実装ゼロで得られる可能性を示す一方、「IMEの実際の
設定・状態を無視して特定の動作を強制してはいけない」というユーザーの
設計原則にむしろ最も忠実な実現方法でもある（awase側は何も判断せず、
IME自身の挙動にそのまま委ねるため）。ただし未検証であり、確証が
取れない限り本ADRの決定事項としては採用できない。

## 決定3: エンジンOFF時の挙動はADR-143の意図と両立しない

ユーザーは明示的に「安全な3キー同士の入れ替えは継続してほしい（engine
非依存）、かな系のみengine連動で無効化してほしい」という製品要求を
出しており、ADR-143 decision3はこれに応えるために6段階の試行錯誤を
経て「サイクル単位の無効化」という設計に到達した。Scancode Map方式は
この要求を満たす手段を持たない（決定1参照）。ユーザーが真にこの要求を
維持したいなら、Scancode Map方式は不採用にせざるを得ない。

## 決定4: ADR-111の先例との整合性 — 「常時ショートカットの横取り」と「特定物理キーの入れ替え」は別の危険性を持つ

ADR-111が警告したのは、「CapsLockキーという1つの物理キーは維持したまま、
それに付随する複数のIMEショートカット（Shift+CapsLock/Alt+CapsLock/
Ctrl+CapsLock等）をhookで**選択的に**書き換えようとする」ケースであり、
IME側がキーの押下状態を独自に（フックとは別経路で）監視しているために
hookの介入が効かない、という構造的な問題だった。

一方ADR-141/143が行っているのは、**vkそのものを別の正規のvkに書き換える**
（例: 変換キーが押されたら`VK_DBE_HIRAGANA`相当のsentinel経由でIME
actuationを起動する）ことであり、これは「ショートカットの選択的無効化」
ではなく「別の物理キーが押されたのと（IMEから見て）区別できない状態を
作る」試みである点で、ADR-111が問題視したケースとは異なる。ただし、
この違いが実際に安全性を担保するかどうかは、ADR-143が25ラウンド超の
敵対的レビューを要した事実（sentinel VK設計・`kana_cycle_active`・
Shift+代入先キー機能のいずれも、当初案は複数のBlockerを含んでいた）
自体が示す通り、**自明ではなく、大量の検証コストを払って初めて確認
できた**。Scancode Map方式（決定的観測6）が示唆する「OSレベルで本物の
かなキーにすり替える」アプローチは、この検証コストの多くを構造的に
回避できる可能性がある——これはADR-111の教訓（「IME関連キーはフックより
手前で扱う方が安全」）とも整合する。

## 却下理由（本ADRを不採用とする理由）

1. エンジンON/OFF連動というユーザー自身の明示的な製品要求
   （決定3、[[project_key_role_kana_followup_priority_2026_09_06]]の
   前提を踏まえた要求）を原理的に満たせない。
2. Shift+代入先キー→カタカナ機能を含む「新規の条件付き挙動」を
   一切追加できない。
3. かなスロット以外の3キー同士の入れ替え（ADR-141の主機能）と
   統合された単一の設定UIにできない——ADR-142が設計した設定画面・
   全単射バリデーションの枠組みに乗らない。
4. 再起動必須・システム全体適用という制約はADR-111で既に許容されて
   いるが、それは「1プリセットのみ」だったからこそ許容できた面がある。
   かな系まで含めると、ユーザーが持ちうる組み合わせが増え、
   Scancode Map方式の「事前に決め打ちしたプリセットの組」という設計
   （ADR-111決定2〜3のマージ・共存ロジック）が煩雑になる。

## 採用を再検討する条件

- 決定的観測6（変換キー→かなキー位置のスキャンコード置換で1回目
  ひらがな/2回目カタカナが自動的に再現されるか）を実機検証できた場合、
  ADR-143 decision7（Shift+代入先キー機能）の実装コストを丸ごと
  回避できる可能性があるため、**ADR-143 decision7のみをScancode Map
  併用に置き換える**というハイブリッド案は再検討の価値がある。
- ユーザーがエンジンON/OFF連動の要求を撤回する（かな系入れ替えも
  常時有効でよいと判断する）場合。

## 未解決の疑問

1. 変換キーのスキャンコードをかなキーのスキャンコード（`0x70`）に
   Scancode Mapで置換した場合、実機でIMEの「1回目ひらがな・2回目
   カタカナ」挙動が本当に自動的に再現されるか（決定的観測6）。
2. ADR-111が警告した「IME関連キーのフック介入は効かない」という
   構造的問題が、ADR-141/143のsentinel VK方式（ショートカットの選択的
   無効化ではなくvk自体の全面置換）には本当に当てはまらないと
   言い切れるか（決定4）——実機ソーク未実施のADR-141/143自体にも
   共通する未検証事項。

### 結論

- **ADR-141（3キー汎用入れ替え）の価値はADR-144/145のどちらでも代替
  できない**。ユーザー自身が指摘した通り、この部分の設計・実装は
  かな系拡張の是非とは独立に価値を持つ。
- **ADR-143（かな系拡張）に限れば、GJI専用でよいという前提を置くなら
  ADR-144の実装コストはADR-143よりはるかに小さい**。Mozc `key_parser.cc`
  の直接確認により、キーマップの表現力自体（`henkan`等をトリガーに
  IMEOn/InputModeHiragana/InputModeFullKatakana等を割り当てられるか）は
  もはや不確実要素ではなくなった。特にdecision7相当（Shift+代入先キー→
  カタカナ）はIME ON状態でのコマンド発火であり配送経路の懸念自体がなく、
  **`keymap.txt`に1行追加するだけで実現できる可能性が高い**——ADR-143が
  この1機能のために費やした`ime_open_before`スナップショット・
  `send_ime_mode_key_with_shift_release_prefix`の左右Shift修正まで含む
  大掛かりな設計・実装コストと比べると、対費用効果の差は大きい。
  残る唯一の未検証点は「DirectInput（IME OFF）状態で変換キーの
  KeyDownがMozcへ配送されるか」という1点（ADR-144決定3）に絞られており、
  これは実機で数分あれば検証できる規模の疑問である。
- 総じて、ユーザーの「GJI前提の補助ツールで80%満たせたのでは」という
  疑問は、**技術的にはほぼ肯定される**——「変換キーでIME ONにする」
  「Shift+変換キーでカタカナにする」という2つの主要機能は、GJIユーザーに
  限定してよいならADR-144の`keymap.txt`生成ツールだけで、ADR-143の
  複雑さの大部分を負わずに実現できた可能性が高い。ADR-143の複雑さが
  真に必要だったのは、**MS-IMEユーザーも含めてIME非依存に対応する**
  という、awaseがADR-141以来掲げてきた設計方針を維持する場合のみである。
  この場合分けが製品判断として妥当かどうか（GJI専用機能として先に
  安く出荷し、MS-IME対応は需要を見て後日検討する、という段階的
  リリースも選択肢になりうる）は技術調査だけでは決められず、次の
  アクション（ADR-144のkeymap.txt生成ツールを先行実装する / 決定3の
  実機検証を先に済ませる / ADR-143をそのまま実装する / スコープを
  MS-IME対応込みで維持するかを再確認する）はユーザー自身の判断に
  委ねる。
