## Blocker（v7で新規）

### B10. 決定5のシグネチャ（`layouts_dir_setting: &str`を呼び出し元から受け取る）が、決定2の「呼び出し要件」および2フェーズ構成と**実装不能な矛盾**を起こしている。誤った解き方をするとB9の損失経路が再発する

3つの条項が互いに矛盾している。

1. 決定2「呼び出し要件」（102-107行）:
   > `AppConfig::load()`／`.yab`の読み込み／`AppConfig::save()`のいずれよりも
   > **前に**`ensure_user_data_present()`を1回だけ呼ぶ

2. 決定2「2フェーズ構成」（139-160行）: 関数**自身**が
   フェーズ1（config復元）→ `AppConfig::load()` → `validate()` →
   フェーズ3（yab復元）を順に行う。

3. 決定5「実装配置」（234-240行）:
   ```
   pub fn ensure_user_data_present(
       exe_dir: &Path,
       layouts_dir_setting: &str,  // validate() 後の生の設定値
       backup_dir: &Path,
   ) -> RestoreOutcome
   ```

**呼び出し元は`layouts_dir_setting`（＝`validate()`後の値）を、
`AppConfig::load()`を呼ぶ前に知ることができない。** 1と3は両立しない。
また2の通り関数が内部でload+validateするなら、その値を引数で受け取る必要も無い。

実装者がこの矛盾に直面したとき、素直に取りうる解き方は
「**呼び出し元が先に`AppConfig::load()`→`validate()`して`layouts_dir`を得てから
`ensure_user_data_present()`を呼ぶ**」である。これはB9の損失経路をそのまま
復活させる:

```
1. MSI 再インストール直後（本体＝工場出荷値、backup＝ユーザー設定）
2. awase-settings.exe 起動
   → 呼び出し元が先に AppConfig::load() → 工場出荷値をメモリに読む
   → その後 ensure_user_data_present() が config.toml をバックアップから復元
   → しかし画面に表示されているのは「先に読んだ工場出荷値」
3. ユーザーが「設定が消えた」と思い、1項目直して保存
   → 復元済みの config.toml が、工場出荷値＋1項目で上書きされる
   → 以後フェーズ1の復元条件（既定値とバイト一致）は成立しない
   → 契機3 が backup を「工場出荷値＋1項目」で上書き
4. ユーザーの元の設定が本体・バックアップ双方から消滅
```

決定1のフラグゲートはこの経路を止められない（`ensure_user_data_present()`は
呼ばれているのでフラグは立つ）。B9対策として入れた「呼び出し要件」も、
シグネチャに従う限り物理的に守れないため機能しない。

**要求**: 決定5のシグネチャを、決定2のフェーズ構成に合わせて書き直すこと。

```
pub fn ensure_user_data_present(
    exe_dir: &Path,       // OS依存の解決結果（current_exe().parent()）のみ呼び出し元から
    config_path: &Path,   // 復元・ロード対象。exe隣の絶対パス
    backup_dir: &Path,
) -> RestoreOutcome       // ← 検証済み設定を含めて返す（下記）
```

`layouts_dir`は関数内部のフェーズ2（`AppConfig::load()`→`validate()`）で得る。
`AppConfig::load`も`validate()`もコア`awase`クレート（`src/config.rs`）に
あるため、コアのOS非依存原則（ADR-019）には抵触しない。相対/絶対の判定も
従来どおりコア側に閉じる（決定5がM4対応で狙ったとおり）。

**併せて（Major相当だがB10と不可分なのでここに書く）**: 戻り値に
**ロード・検証済みの`ValidatedConfig`（または`AppConfig`）を含め、呼び出し元は
それを使う**こと。そうしないと、

- 呼び出し元が改めて`AppConfig::load()`を呼ぶ＝**同じファイルを2回読む**ことになり、
  その2回の間に他プロセス（もう一方のバイナリの復元）が書き込むと、関数が
  検証した内容と呼び出し元が使う内容がずれる。`awase.exe`が
  `warn_layout_fallback`経由で`awase-settings`を起動する経路があるため、
  2プロセスの起動が重なるのは実際にありうる（決定2が`write_atomic`を要求している
  のと同じ理由の裏返し——原子性は「破れた内容を読まない」ことしか保証せず、
  「2回読んだら同じ」は保証しない）。
- 上記の誤った解き方（呼び出し元が先にload）へ戻る誘惑も消える。

決定7の「B9の直接再現」テストも、この形なら「呼び出し元がloadしてから呼ぶ実装に
なっていない」ことを型で担保できる（呼び出し元に`AppConfig`を読む手段を
渡さない＝戻り値経由でしか得られない設計にする）。

## Major

### M1. バックアップの実行ゲートが「プロセスローカルな`OnceLock<bool>`」では、決定7のテスト（特にB9再現テスト）が**テスト順序に依存して壊れる**

決定1「実行のゲート」（87-91行）は
> `ensure_user_data_present()`から復帰した時点で…立てるプロセスローカルな
> フラグ（`OnceLock<bool>`等）が立っている場合に限り実行する

としているが、`cargo test`は**1プロセス内で複数テストをスレッド並列実行**する。
したがって:

- 決定7の「B9の直接再現」（`ensure_user_data_present()`を呼ばずに保存 →
  バックアップが更新されないこと）は、**同じプロセス内の他のテストが先に
  `ensure_user_data_present()`を呼んでいるとフラグが既に立っており、
  バックアップが更新されてしまって失敗する**。逆に実行順によっては通る。
  典型的なフレーキーテストになる。
- 同様に「手編集した`config.toml`がバックアップへ捕捉されること」
  「M1の直接再現（既定値と一致する内容はバックアップされないこと）」も、
  フラグの有無に依存するためテスト間で状態が漏れる。
- `--test-threads=1`や`serial_test`で回避する手もあるが、決定7が掲げる
  「純粋関数だからホストターゲットで自動テストできる」という設計上の売りを
  自ら損なう。

**要求**: グローバルな暗黙フラグではなく、**明示的な能力トークン**にすること。例:

```
pub struct UserDataGuard { /* 非公開 */ }          // 構築手段は下記のみ
pub fn ensure_user_data_present(..) -> (RestoreOutcome, UserDataGuard)
pub fn backup_config(guard: &UserDataGuard, ..)    // トークンなしでは呼べない
pub fn backup_layout(guard: &UserDataGuard, ..)
```

これなら「復元ステップを通らないプロセスはバックアップを汚さない」という
B4・B9対策の保証が**コンパイル時に**効き（グローバル状態の実行時チェックより
強い）、テストはトークンを作る／作らないだけで両ケースを並列に検証できる。
`awase.exe`側は`AppState`に、`awase-settings`側は`SettingsApp`にトークンを
持たせればよい。

### M2. バックアップ対象の範囲が、契機2（同梱6ファイルのみ）と契機3（`layouts_dir`内の全`.yab`）で食い違っており、**復元されることのないバックアップ**が生まれる

- 契機2（決定1-2、64-66行）: 「ファイル名が同梱6ファイルのいずれかと一致する
  場合のみ」バックアップ。
- 契機3（決定1-3、67-71行）: 「`.yab`読み込みが成功した時点」でバックアップを
  更新。読み込みの実体は`LayoutEntry::scan_all`で、これは`layouts_dir`内の
  **全ての`.yab`**（ユーザーが自作した`my.yab`等を含む）をパースする。
- 復元側（決定2フェーズ3、152-155行）: 「**同梱6ファイル**のそれぞれについて」。

素直に実装すると、ユーザー自作の`my.yab`は契機3でバックアップされるが、
復元対象には一切入らない——**永久に使われないバックアップ**がディスクに
溜まり続ける。決定4の「完全削除」案内やサポート時の挙動説明も、
「backupに何が入るのか」が説明できなくなる。

どちらに寄せるかは設計判断で、両方に根拠がある:

- **6ファイルに揃える（推奨・小さい）**: 契機3も同梱6ファイル名に限定する。
  ユーザー自作`.yab`はMSIが削除しない（`File`テーブルに無い）ので、本ADRが
  守ろうとしている「MSIに消される」リスクが元々無い。スコープが
  「MSIが配置・削除するファイル」で一貫する。
- **自作`.yab`も守る**: 契機3の範囲を維持し、復元側も「backupに存在する
  `.yab`はすべて復元対象」に広げる。ユーザーの誤削除からも守れるが、
  本ADRの目的（MSI由来の喪失）を超える範囲拡大になり、
  「`layouts_dir`外に保存したファイル」との線引き（B3で一度整理した論点）が
  再び曖昧になる。

**要求**: どちらかを決定文に明記すること。決めずに実装に入ると、契機3の
実装者が`scan_all`の結果をそのまま回して前者と後者の中間（バックアップは
広い・復元は狭い）になり、上記の「使われないバックアップ」が既定路線になる。

### M3. 決定1の「開発ビルドでの非対称」の説明（93-98行）が事実と食い違っており、記載された根拠が成立していない

決定1の括弧書きは
> `cargo run`で起動すると`<root>/target/debug/backup/`にバックアップが
> 作られるが、`target`配下なので実害は無く、**開発中に機構を動作確認
> できるようにするための意図した非対称である**

としているが、v7の他の条項と突き合わせると、開発ビルドでは実際にはほぼ
何もバックアップされない。

- 契機1のゲートは「保存先パスが`resolve_next_to_exe("config.toml")`と一致する
  場合のみ」（決定1-1）。`cargo run`では`resolve_next_to_exe`＝
  `<root>/target/debug/config.toml`である一方、実際に読み書きされるのは
  `<root>/config.toml`（`resolve_relative_to_exe`のワークスペースルート
  フォールバック）なので、**ゲートは常に不一致＝バックアップしない**。
- 契機3は「内容が埋め込み既定値と一致するならバックアップしない」（決定1）。
  開発時に読まれる`<root>/config.toml`は`include_str!`が読んでいる
  **まさにそのファイル**なので、内容は定義上一致する＝バックアップしない。

つまり「開発中に機構を動作確認できる」という根拠は成立しておらず、
非対称を残す理由が実質的に無い（残しても害も無い）。記述を実態に合わせるか、
「開発ビルドではバックアップ機構も事実上動作しない」と正直に書くこと。
このままだと、実装者が「dev で backup ができるはずなのにできない」と
デバッグに時間を使う。

## Minor

### m1. `.yab`の初期化（意図的な削除）の逃げ道が、決定6の案内では粗すぎる

M1対応（round6）で`.yab`は「バックアップがある場合のみ復元」になったため、
「かつてカスタマイズしたが今は不要になった同梱配列」を削除しても、
バックアップがある限り毎起動復活する。逃げ道は
`backup\<その配列名>.yab`を消すことだが、決定6の通知文は
「`backup\`フォルダも削除してください」とフォルダ単位の案内しかない
（それを実行すると`config.toml`のバックアップまで失う）。
通知に**どのファイルを復元したか**を含めるか、案内を
「該当ファイルを`backup\`から削除してください」に改めること。

### m2. `config.toml`の復元元（バックアップ／埋め込み既定値）の記述がフェーズ3側にしかない

「復元元は、バックアップが存在しかつ妥当ならバックアップ、無ければ埋め込み
既定値」（152-155行）はフェーズ3（`.yab`）の節に書かれており、フェーズ1
（`config.toml`）については「復元条件」の括弧書き
（「ファイルが無ければ、実質的に埋め込み既定値へ落ちる」）から読み取るしかない。
`config.toml`にも同じ1文を明記すること。

### m3. 決定7の「B6の直接再現」は、M1対応後は**決定5の救済経路**を通る

`layout\`ごと存在しない状態でバックアップが無ければ、`.yab`の復元条件
（バックアップ必須）は満たされず、有効な`.yab`が0本になるので決定5の救済が
発動して6本が書き戻される——という経路になる。テストの意図（ディレクトリが
作成されること・`.yab`が復元されること）は達成されるが、**どちらの機構を
検証しているのか**が曖昧なままだと、将来どちらかを変更したときにテストが
何を守っていたのか分からなくなる。「バックアップ有り（一般規則経路）」と
「バックアップ無し（救済経路）」の2ケースに分けること。

### m4. `create_dir_all`が決定5の救済経路にも適用されることを明記すること

`create_dir_all`は決定2の「書き込み（復元先の決定）」節（136-137行）に
書かれているが、決定5の救済もディレクトリが無い状態で発動しうる
（m3の経路がまさにそれ）。同じ書き込み手順を共有することを1行書いておくこと。

### m5. `RestoreOutcome`が決定6の通知に必要な情報を持つことを明記すること

決定6は「バックアップから復元／既定値で生成」を区別して表示するとしているので、
`RestoreOutcome`はファイルごとに「何もしなかった／バックアップから復元した／
既定値から生成した／失敗した」を返す必要がある。未解決事項2
（シグネチャ・戻り値設計）に含まれてはいるが、決定6が要求する粒度
（ファイル単位・理由つき）を1行書いておくと設計がぶれない。

### m6. 「経緯の要約」の圧縮で条項が落ちる事故が繰り返されている。要件は経緯と分離して保持すること

B9は「v4にあった1文がv5・v6の圧縮で落ちた」ことによるBlockerだった。
v7でも経緯の要約（29-37行）は各ラウンド1行まで圧縮される一方、
決定文側は逐次追記で膨らんでいる。今後の改訂で同じ事故を防ぐため、
**決定文の中の「守るべき要件」を箇条書きの短いリスト（例:「実装チェック
リスト」節）として独立させ、経緯・根拠の散文とは別に保持する**構成を
勧める。実装時にもそのリストがそのままレビュー観点になる。

## 総評

v7でB9は解消され、round6のMajor 3件（特にM1の「発火しすぎる」方向の穴）も
的確に反映されている。`config.toml`と`.yab`で復元条件を分けた判断は正しく、
決定5の救済との役割分担も実際に破綻していないことを確認した。

残るB10は、**新しい欠陥というより「B9対応で追加した条項」と「v6から据え置きの
シグネチャ例」の突き合わせ漏れ**であり、決定5のシグネチャを決定2のフェーズ
構成に合わせて書き直す（`layouts_dir_setting`を削り、`config_path`を受け取り、
検証済み設定を返す）ことで解消する。ただし誤った解き方をするとB9がそのまま
復活するため、Blockerとして扱った。

Majorの M1（`OnceLock`ではテストできない）は、決定7が掲げる「純粋関数だから
自動テストできる」という設計方針を守るために、実装開始前に能力トークン方式へ
変えておくことを勧める。M2（バックアップ範囲の食い違い）は、どちらに寄せるかを
1行決めるだけで済む。

B10とM1・M2を反映すれば、**次ラウンドは確認のみで収束し、実装フェーズへ
進んでよい**と考える。7ラウンドを通じて検出されたBlocker12件はすべて
「実装前に文面で潰せたもの」であり、この規模の自己修復機構としては
妥当な収束の仕方をしている。
