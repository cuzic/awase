# ADR-222: 入力言語の切替をキー入力の時点で検知する

## 背景(事実、すべて CI 実測)

BUG-183(report `01M4047347…`、issue #445): MS-IME で入力言語のホットキー(左Alt+Shift+3)でロシア語に切り替えると、awase のアイコンが
オレンジのまま(Engine が活性のまま)になる。Alt+Shift や Win+Space では実機で即座に灰色になる。`lang_switch_probe`(`ci/bug183-lang-switch`)で測った。

1. **言語が切り替わっても、awase は自力では非活性にならない**(run 37171454298)。Alt+Shift・Win+Space・ホットキー・`WM_INPUTLANGCHANGEREQUEST`
   のどれでも、言語は 2〜114ms で切り替わったが、14 秒待って `Engine deactivated` は 16/16 で出なかった。切替の 1.5 秒後にフォーカスを移すと、移動の約 80ms 後に
   非活性になった(8/8)。原因の見立て: IME の定期読み取りは明示意図(`explicit_intent`)があると予約を止める(ADR-187、`runtime/mod.rs`)。言語変更は意図を捨てる契機ではない。
2. **シェルフック `HSHELL_LANGUAGE`(wparam=8)は一度も届かない**(run 37172398639、前面プロセス 24/24 で 0 件。背景リスナーも 0 件。他のシェルイベントは届く)。
3. **TSF の言語プロファイル通知は前面プロセスにしか届かない**(run 37172398639・37172857037)。`ITfActiveLanguageProfileNotifySink`・`ITfLanguageProfileNotifySink` は、
   前面のプローブでは 24/24 で言語切替の 3〜150ms 後に届いたが、前面にならない別プロセス(awase と同じ条件)では、同じ切替で **0 件**だった(AdviseSink 自体は成功)。
4. **言語切替ホットキーは、レジストリから読める**(run 37173478484、`reg-hotkeys.txt`、ja-JP と ru-RU を追加した windows-latest)。
   - 言語ごとの直接切替キー: `HKCU\Control Panel\Input Method\Hot Keys\00000104` に `Key Modifiers`(DWORD。下位バイト: 1=Alt, 2=Ctrl, 4=Shift、上位 `c0` は左右どちらでも可)、
     `Virtual Key`(DWORD)、`Target IME`(DWORD。HKL。例 `11,04,01,e0` = 0xE0010411 = 日本語 IME)。この実例は Ctrl+Shift+0 → 日本語。報告者の Alt+Shift+3 → ロシア語も同じ形式で並ぶはず(未確認)。
   - 全体の切替キー(Alt+Shift / Ctrl+Shift / なし): `HKCU\Keyboard Layout\Toggle`。既定ではキーは空で、値が無い=OS 既定(Left Alt+Shift)。
   - `Hot Keys\00000010〜12`・`70〜72`・`200〜203` は IME 固有のキー(Ctrl+Space 等)で、言語切替ではない。Win+Space は固定でレジストリに無い。
5. 実機で Alt+Shift・Win+Space が即座に灰色になる理由は未確認(CI ではこの 2 つも非活性にならなかった)。言語表示でフォーカスが動くため、という仮説(未検証)。

実害: 非日本語の言語に切り替えた後も Engine が活性なので、NICOLA がその言語の打鍵を日本語の同時打鍵として処理してしまう(アイコンの色は結果)。

## 検討した案

| 案 | 評価 |
|---|---|
| A. 通知の購読(HSHELL_LANGUAGE、TSF のシンク) | **不可**(上記 2・3)。購読できるのは前面プロセスだけ |
| B. 定期ポーリング(常時、またはホットキー後 5 秒間 100ms) | 常時はやりたくない(ユーザー判断)。「ホットキーの後」は、任意に割り当てられる言語ホットキー・Win+Space・言語バーやトレイのマウス操作を、キー列で特定できず取りこぼす |
| **C. 物理キーの KeyDown の時点で前面スレッドの HKL を読む(推奨)** | ポーリング不要。問題が起きる打鍵(日本語配列として処理される前)に確実に検知できる。コストは非ブロッキングの 3 回の呼び出し。切替直後〜次の打鍵までアイコンが古いままになるのは許容(操作が起きない間は害が無い) |
| E. レジストリのホットキー設定で切替キーを検出し、その直後に 1〜2 回だけ HKL を読む(事実 4 を使う) | 切替の完了は 2〜115ms(実測)なので、ポーリングは不要(押下の約 150ms 後と 400ms 後に 1 回ずつで足りる)。キー入力を待たずにアイコンを更新できる。**マウス操作(言語バー・トレイ)の切替は検出できない**。`Hot Keys` の値の解釈(左右ビット、修飾キー単独の Alt+Shift/Ctrl+Shift の押下完了の判定、`Target IME`)を自前で持つ必要があり、保守が増える |
| D. C + ホットキー後の短い追跡 | アイコンの即時性が欲しい場合のみ。いまは足さない(複雑性を増やさない) |

## 決定案

### D1: KeyDown ごとに前面スレッドの言語を観測する(段階 1)
物理(非注入)の KeyDown で `GetForegroundWindow` → `GetWindowThreadProcessId` → `GetKeyboardLayout` を読み、`LANGID` が日本語かを得る。
belief の `is_japanese_ime` と食い違うときだけ、Observe → pure `classify_*` → `reduce()`(`ime-belief-architecture.md`)の経路で更新する。
**`set_is_japanese_ime` を直接呼ぶ近道は作らない**(ADR-093 のアップグレードは直接 setter だが、ダウングレードは誤検知の害が大きいので、規則どおりのイベント経路に乗せる)。
ポーリング・タイマー・購読は足さない。

### D2: 段階 0 は記録のみ(誤検知の定量)
ADR-093 は「`is_japanese_ime` は probe ベースの確率的信念で、スリープ復帰・フォーカス変更直後に false を誤答しうる」と記録している。前面スレッドの HKL が
UWP の入力面・TSF ネイティブ(Chrome、Windows Terminal)で正しいかは未測定。段階 0 では、KeyDown の度に食い違いをログ(`[lang-check] ...`)に出すだけにして、
既存の CI e2e(実 Chrome・各 IME・フォーカス往復)で**日本語のまま食い違いが 0 件**であることを確認してから、段階 1 で更新を有効にする。

### D2b: アイコンの即時更新は案 E で足す(段階 2、任意)
C だけでは、切替から次の打鍵までアイコンが古い。必要なら、事実 4 のレジストリから「言語切替キー」の一覧(修飾+VK、または修飾のみ)を起動時と設定変更時に読み、一致した押下の約 150ms 後と 400ms 後に、D1 と同じ観測を 1 回ずつ行う。
C を土台にして、E は表示を早めるだけの追加にする(E 単独にはしない: マウス操作の切替を取りこぼし、レジストリの解釈が間違っていても C が補う)。

### D3: 範囲
変更は観測点 1 か所と、pure 関数・イベント 1 つの追加。IME への書き込み(actuation)は増やさない。日本語に戻ったときの活性化は、同じ経路の逆向き(false→true)で、
既存の ADR-093 のアップグレードと整合させる。

## 未確定(レビューで詰める)
- 前面スレッドと入力フォーカスのスレッドが違う場合(UWP の InputSite、Chrome の子ウィンドウ)の HKL。`GetGUIThreadInfo` のフォーカススレッドを使うべきか(既存の `read_ime_state_full` はこちら)。
- 食い違いの判定の履歴(連続 N 回で確定するか、1 回で即時か)。ホットキーの途中の打鍵(Alt+Shift+3 の `3` 自体)で切替が間に合っているか。
- 日本語以外の言語でも日本語 IME(MS-IME)の同じ HKL を持つケース(同一 LANGID の別レイアウト)は問題にならないか。
- レジストリの `Target IME` と `Key Modifiers` の左右ビットの正確な意味、Win11 の設定画面で変えたときの書き込み先(`Hot Keys` が増える/書き換わる)。実機(dragonflyg4)で、設定画面から割り当てを変えて `reg export` を取る必要がある。
- 切替で非活性にしたとき、`explicit_intent` と IME の定期読み取りの停止(ADR-187)が残る件を、この ADR で扱うか別にするか。
