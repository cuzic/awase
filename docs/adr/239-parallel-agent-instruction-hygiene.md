# ADR-239: 並列エージェント開発での指示の取り違えを減らす(一時停止・取り消し・順序)

## この ADR の位置づけ

これはコードの変更ではなく、AI エージェントとの運用の約束である。ADR にする価値は小さく、本体は `.claude/rules/` の規約 1 ページで足りる。それでも ADR の形で残すのは、(i) 置き場所と pre-push フックの扱いが所有者の判断であること、(ii) 「受信箱の仕組みを作る」「フックを書き換える」などの却下した案と理由を残さないと、次の事故のたびに同じ案が出ること、の 2 点のためである。規約が定着したら、この ADR は「規約の由来」として読むだけのものになる。

隣の ADR との分担(同時に起草中): マージの直列化とマージ直前の `mergeStateStatus` の扱いは ADR-237。ADR-238(主張に再確認のコマンドを添える)は、独立した規約ファイルを作らず、この ADR の規約の 1 項目(D1 の 3「報告と主張の独立な再確認」)に畳む。規約の行数の上限は、238 の分を含めた 1 枚の合計で数える。

## 背景(実測した事実)

### 共通の約束が散らばっていた

この日の約束は 3 か所にあった。

1. scratchpad の指示書(`impl-brief.md` 40 行、`adr-brief.md`・`inv-brief.md`・`w0-brief.md`)。セッションが終われば消える。同じ指示書の中で 21 行目(`--no-verify`)と 31 行目(`git push -u`)が食い違っている。
2. `docs/tasks/fcis-layering-tasks-2026-10-06.md` の「§0 全タスク共通のルール」8 項目と「完了前チェック(V2)」4 項目。FCIS のタスク表の中にあり、自動では読み込まれず、FCIS 以外のタスクの指示書からは参照されない。V2 は `82de11aa`(04:58Z)で足され、d(04:30Z)より後にできた。
3. メモリ(`feedback_verify_commit_landed_not_backgrounded_2026_10_06`・`feedback_worktree_per_session`・`feedback_forks_may_ignore_investigation_only_instructions`・`feedback_no_local_builds_use_github_actions_2026_10_04`)。team-lead の会話には読み込まれるが、起動された実装エージェントが読むとは限らない。

一方で、`.claude/rules/*.md` は全セッションで自動的に読み込まれる(CLAUDE.md の「Repo-specific workflow rules」節)。並列のエージェントに同じ文が届く唯一の置き場所である。その代わり、人のセッションや FCIS 以外の作業にも毎回読み込まれるので、FCIS 固有・期間限定の約束は置かない。

### 取り消しが届かない理由

a・b は、team-lead が一時停止・取り消しを送った時点で、エージェントが一続きの作業(編集 → push → `gh pr create`)の途中にいた。SendMessage ツールの説明には「メッセージは受け手の次のツール呼び出しの区切りで届く」とある(実際の到着時刻を実測したわけではない)。この説明どおりなら、`git push && gh pr create` を 1 つのコマンドにつないだ場合は、その途中では読まれない。どちらにしても、取り消しが PR 作成に間に合わないことはあり得る、という前提で約束を書く。b の実際の後始末(PR をコメント付きで閉じる)は、コストが小さく正しかった。

### `--no-verify` で失うもの

- xwin check: CI の `windows-cross-check`(`.github/workflows/ci.yml:111` の `cargo xwin build --tests --target x86_64-pc-windows-msvc -p awase-windows`)が上位互換。
- fix-requires-evidence の警告: `.githooks/pre-push:23` が新しいブランチ(`rsha` が全 0)では最初から飛ばしている。エージェントの最初の push は常に新しいブランチなので、失うのは**レビュー指摘を直した 2 回目以降の push での警告だけ**。
- pre-push の正規表現と表の整合(xtask、ADR-158 TB2)は CI ジョブなので影響を受けない。
- ADR-236 の「pre-push に足さない」とは方向が一致する(pre-push の効きが薄いという前提を強めるだけで、236 の決定を弱めない)。

## 決定

### D1. 規約 1 ページを `.claude/rules/agent-handoff.md` に置く(25 行以内、ADR-238 の分を含む)

中身は下の「付録: 規約の文案」。FCIS に依存しない次の 7 つだけを書く。

1. **PR 本文の取り違え防止**(d): 本文は自分のタスク名の付いたファイルから書く。共有の `/tmp/*.md` や `b.md`・`body.md` のような名前は使わない。更新後に `gh pr view <N> --json body` で自分の本文か確かめる。
2. **DIRTY の確認**(f): PR を作った後と「CI を待っている」と報告する前に、`gh pr view <N> --json mergeable,mergeStateStatus` が CONFLICTING・DIRTY でないか見る(DIRTY だと `pull_request` の CI が起動しない)。DIRTY なら最新の `origin/develop` に rebase して push し直す。
3. **報告と主張の独立な再確認**(e・ADR-238): PR の状態・CI・マージの有無・コミットの有無・件数などは、報告や docs に書く直前に実行したコマンドの出力で書き、コマンド 1 行と打ったコミットを添える。コマンド 1 本で確かめられないものは「未確認」と書く。ADR-238 の書き方(否定・全称・数値の主張の扱い)の詳細はこの項目の中に 3〜5 行で置き、238 は独立したファイルを作らない。
4. **レビュー指摘への返信の形**(c): 指摘 ID(Must-1・S2 など)ごとに「反映した(コミット)/反映しない(理由)」を列挙する。まとめて「反映した」と書かない。
5. **取り消し・一時停止**(a・b): 出す側は 1 行目に「作業を止める。PR は作らない」(または「PR #N を閉じる」)、2 行目に対象のブランチ名と PR 番号。受ける側は、PR がもうあれば理由をコメントして閉じる(#536 の形)。ブランチは消さない。push と `gh pr create` は別々のツール呼び出しにする(間で届いたメッセージを読めるように)。
6. **push**(g): team-lead が起動したエージェントの作業に限り `git push --no-verify origin <ブランチ>`(宛先を明示)。2 回目以降の push の前に、再発ファミリーのファイルを変えたなら PR 本文に fix-requires-evidence の (a)/(b) を書いたか確かめる(失われる警告の代わり)。人のセッションには適用しない。
7. **指示書の仕様は最新版を引用**(i、team-lead 向け): 承認済みの文書の該当行を、最新の origin/develop のものとしてそのまま引用し、ファイル名・節・コミットを添える。要約し直さない。

FCIS 固有の完了前チェック(新しい純粋モジュールを `CORE_MODULES` と `examine_globs` に載せる、再発ファミリーなら pre-push の正規表現と表にも)は、タスク表の V2 の 1 に残す。

### D2. 重複の整理(D1 と同じ時期、ただし文言が一致する部分だけ)

規約文案と**文言が一致する部分だけ**を参照に置き換える。行番号でなく文で特定する。

- `docs/tasks/fcis-layering-tasks-2026-10-06.md` の V2 の 2 のうち「本文が自分の PR のものか」の部分を「`.claude/rules/agent-handoff.md` の 1」への参照にする。「数値を CI のログから写したか、`#[ignore]` の数を含む」は D1 の 3 に対応するので同様に参照にする。V2 の 1・3・4 と §0 の 1(ローカルでビルドしない)・6(CI ログの見方)は規約に対応する文が無いので残す。**この ADR の PR ではタスク表を書き換えない**(並行 PR との衝突を避けるため。タスク表の改訂は ADR-238 と合わせて 1 つの PR だけが行う)。
- scratchpad の指示書 `impl-brief.md`(リポジトリ外): 21 行目のうち push の文(「push は `git push --no-verify` を使う…」)を規約の 6 への参照にする(ローカルでビルドしない、の文は残す)。37 行目(コミットの確認)は規約の 3 に含まれるので参照にする。35 行目(`gh api -X PATCH` の手順)は規約に無いので残す。31 行目の `git push -u origin <ブランチ>` は、21 行目と食い違っているので `--no-verify` を付ける(1 行の修正。規約を足すより効く)。

行数の見込み: リポジトリは規約 +25 行、タスク表 −1〜−2 行(V2 の 2 を参照 1 行に)で、正味 +23 行前後。増える分の撤去先は、ADR-238 が作る予定だった独立の規約ファイル(30 行程度)を作らないこと。指示書(リポジトリ外)は 2 文が参照に変わる。

## 却下した案と理由

- **受信箱を確認する仕組み・ロックファイル・「PR 作成の前に team-lead の許可を待つ」手順を作る**: a・b の実害は PR 1 本の作成と閉じる手間で小さい。許可待ちを全 PR に入れると、46 本すべてに往復 1 回の待ちが乗る。取り消しは「PR を閉じる」で十分に後始末できる。
- **pre-push フックをこの ADR で書き換える**(docs のみのときスキップ、環境変数でスキップ): フックは人のセッションの安全網でもあり、変えるかは所有者の判断。選択肢を並べるだけにする。
- **ガードの再確認ラウンド(j)をこの規約で減らす**: 原因はガードの走査の穴で、V3(`strip_comments` の共通化)の対象。
- **規約を docs/tasks/ に置く**: 自動で読み込まれず、FCIS のタスク表なので FCIS 以外のタスクの指示書からは参照されない。
- **FCIS 固有のチェック(CORE_MODULES・mutants)も規約に入れる**: 全セッションで読み込まれ、FCIS が終われば古くなる。V1 の CI が一部を担い、残りは V2 の 1 にある。
- **ADR-238 と別々の規約ファイルにする**: 同じ日に 2 枚(合計 55 行程度)を自動読み込みの場所に足し、同じタスク表の同じ節を別 PR で書き換えることになる。報告前の状態確認(239)は主張の再確認(238)の特例なので 1 枚にする。
- **チェックを CI のジョブにする**: PR 本文の取り違え(d)・古い報告(e)・DIRTY の放置(f)は、エージェントの報告と PR の外で起きるので CI では捕まらない。DSL 化・宣言テーブル化・汎用ツールキットは ADR-218〜220・229 で却下済みで、ここでも作らない。

## 段階

| 段階 | 内容 | 撤去対象 | 検証方法 | 取りやめ条件 |
|---|---|---|---|---|
| 1 | `.claude/rules/agent-handoff.md` を足す(docs のみの PR、develop へ)。ADR-238 の規約の中身をその 3 に入れる。CLAUDE.md の rules 一覧に 1 行足す | ADR-238 の独立の規約ファイル(作らない) | `wc -l .claude/rules/agent-handoff.md` が 25 以下。`ls .claude/rules/claims-carry-verification.md` が無い | 所有者が置き場所に別案を選ぶ |

| 3 | 段階 1 の後の 2 週間(または次の 46 本の PR の早い方)で、機械的に数えられる型だけを数える | — | (i) d 型: 期間中の各 PR の `userContentEdits` に、別の PR の本文(他 PR のタイトルの一部)を含む版がある件数。(ii) 取り消しの放置: 取り消しを受けた PR のうち、閉じられずに 1 日以上残った件数(閉じたものは規約どおりなので数えない)。(iii) f 型: マージ担当(ADR-237)がマージ直前に記録した DIRTY の件数(マージ後は UNKNOWN になるので事後には数えられない) | 今日の同じ型の件数(d 型 1/46、取り消しの放置 0、マージ直前の DIRTY は未記録)と比べ、(i) か (ii) が 1 件でもあれば、守られなかった項目の文を書き直す(項目を足さない)。0 件なら段階 3 を終える |

全体の取りやめ条件: 規約が 40 行を超えたら削る(足し続けると、自動で読み込まれるコストが全セッションにかかる)。並列のエージェント開発をしなくなったら、規約を消してこの ADR を「廃止」にする。

## リスクと限界

- 規約は守られるとは限らない。メモリ `feedback_forks_may_ignore_investigation_only_instructions` のとおり、明記した指示でも無視されることがある。段階 3 で数えるのはそのため。
- 自動で読み込まれる規約は、並列開発をしていない人のセッションにも読み込まれる。25 行の上限と、FCIS 固有の項目を置かないのはこのコストを抑えるため。push の項は「team-lead が起動したエージェントのみ」と項目自体に書く。
- メッセージがツール呼び出しの区切りで届くというのは SendMessage ツールの説明による。実際に a・b で取り消しがどの時点で届いたかは**未確認**。push と `gh pr create` を分けるのは、この説明が正しいときにだけ効く。
- 段階 3 の標本は小さく、0 件でも規約の効果とは言い切れない(今日の d 型も 46 本で 1 件)。段階 3 は「規約が守られなかった項目を見つける」ためのもので、効果の証明ではない。
- h(マージ時の `mergeStateStatus`)、c・e・f の報告、g の実際の発生は**未確認**。

## 付録: 規約の文案(`.claude/rules/agent-handoff.md`、段階 1 で置く)

```markdown
# 並列エージェント開発の約束(ADR-238・ADR-239)

適用: team-lead が実装・レビューのエージェントを並列に起動して PR を作るとき。3 は人のセッションにも適用する。

1. PR 本文は自分のタスク名の付いたファイルから書く(共有の /tmp/*.md、b.md・body.md のような名前は使わない)。更新後に gh pr view <N> --json body で自分の本文か確かめる。
2. PR 作成後と「CI を待っている」と報告する前に gh pr view <N> --json mergeable,mergeStateStatus を見る。CONFLICTING・DIRTY なら CI は起動しないので、最新の origin/develop に rebase して push し直す。
3. 報告と主張は、直前に実行したコマンドの出力で書き、コマンド 1 行と打ったコミットを添える(PR の状態・CI・マージ・コミットの有無・件数)。
   - 否定・全称(「〜は無い」「〜だけ」「すべて」)と数値は特にそうする。develop が動くとコマンドの結果が変わるので、コミットも書く。
   - コマンド 1 本で確かめられないもの(CI の run・実機)は「未確認」と書き、run ID かジョブ名を添える。
   - squash マージの前に、PR のタイトルが本文の訂正に追随しているか見る。
4. レビュー指摘への返信は、指摘 ID ごとに「反映した(コミット)/反映しない(理由)」を列挙する。
5. 取り消し・一時停止: 出す側は 1 行目に「作業を止める。PR は作らない」(または「PR #N を閉じる」)、2 行目にブランチ名と PR 番号。受ける側は、PR がもうあれば理由をコメントして閉じる(ブランチは消さない)。push と gh pr create は別々のツール呼び出しにする。
6. push(team-lead が起動したエージェントのみ): git push --no-verify origin <ブランチ>。2 回目以降の push の前に、再発ファミリーのファイルを変えたなら PR 本文に fix-requires-evidence の (a)/(b) を書いたか確かめる。
7. 指示書に仕様を書くとき(team-lead): 最新の origin/develop の該当行をそのまま引用し、ファイル名・節・コミットを添える。要約し直さない。
```
