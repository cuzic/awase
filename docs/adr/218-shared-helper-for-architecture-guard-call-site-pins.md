# ADR-218: 呼び出し元固定ガードの重複を、共通ヘルパー 1 本で除く

## 背景

`crates/awase-windows/tests/architecture_guard.rs` は 5,916 行・`#[test]` 115 本(2026-10-02、`origin/develop`)。
その中の「ファイル → 出現数/呼び出し元の固定」型は、Opus round1 の全数確認で 16 本(同じテスト内の 2 表は 1 本と数える)。
当初案はこれを `GuardRule` 宣言テーブルにまとめるものだったが、次の理由で取り下げた。

- 数え方は「どこを数えるか(Region: ファイル全体 / `production_code_only` / `strip_any_test_module`)」×「何を数えるか(Unit: `count_real_calls` の行数 / `matches` の出現数)」の 2 軸で、
  パイロット 5 本だけで 4 通りある。532 の `platform_state.rs` の件数 2 は片方がテストモジュール内で、本番だけ数えると 1 になる。つまり件数を変えずに表へ移せない。
- 16 本中 10 本(1024・1209・1265・1896・1945・2321・3570・3633・3790・5700)は既に `src/` 全体を走査し、表に無いファイルを 0 件と期待している。「移行 PR は `Scope::Listed`」にすると、
  1209 などの検出力が黙って落ちる。「合否が変わらない」基準ではこれを検出できない。
- `tests/guard_rules.rs` を足すと、別の integration test バイナリになり、`ci.yml:47`/`:337` の `--test` 指定に載らない。`xtask-adr-evidence`(`extract_guard_expectations`)は
  architecture_guard.rs の `(".foo(", N)` を文字列走査で拾うので、表を移すと CI が赤になる。
- 試算では、コメントを残す限りパイロット 5 本で差し引き約 +12 行、16 本全体でも純減は約 200 行(ファイルの約 3.5%)。
- 例外が既に 4 種ある(ファイルごとに needle が違う 962、特定ファイル除外 2366/2613/5719、複数 needle の合計 1700、`src/` 外の走査 4554)。

一方で、重複の実体は小さく具体的である: 「`files_with_calls` を集めて sort → `expected` を作って sort → `assert_eq!`」の約 20 行が 1222〜1243 / 1268〜1289 / 1903〜1925 / 1955〜1977 の 4 か所にほぼそのまま複製されている。

## 決定

### D1: ヘルパー関数 1 本。数え方の組み合わせはヘルパー内で固定する

round2 で、4 本(1209・1265・1896・1945)のブロックは `list_src_files()` から `assert_eq!` の第 2 引数まで一字一句同じで、違うのは needle 定数・`known_sites`・メッセージの 3 つだけと確認された。
全て `production_code_only` + `count_real_calls`(行単位)の組み合わせである。そこで Region/Unit を関数ポインタで受けず、名前で固定する。

```rust
fn assert_production_call_sites(needle: &str, known: &[(&str, usize)], why: &str)
```

- 別の組み合わせ(`non_comment_lines` は `String` を返すので `fn(&str) -> &str` に型が合わない、`strip_any_test_module`、出現数)を使う呼び出し元が実際に現れたら、そのときに引数を足すか別のヘルパーを作る(目標を先に決めない)。
- `list_src_files()` で全ファイルを走査し、`known` に無いファイルは 0 件を期待する。**`known` に件数 0 のエントリがあれば panic する**(0 は書かずに省略する規約。0 を許すと、実際側が「件数 > 0 のファイルだけ」を集める比較と食い違い、正しいのに落ちる。逆に 0 を除外して比べると、ファイル名を変えても 0 で通り続ける)。
- 失敗メッセージには needle、想定の一覧、実際の一覧、元のテストの `why`(ADR 参照と確認事項)を含める。1896 の「想定(空)」の文言は `known` が空のときに保つ。
- 各 `#[test]` は残す。名前、doc コメント(経緯の記録)、`cargo test <name>` での個別実行、nextest の個別表示は変えない。移るのは重複していた突き合わせブロックだけ。
- 既存テストの Scope をそのまま写す。`Listed`(列挙のみ)のテストを全体走査へ強化する変更は別 PR・別議論(211・532・637・4158・4355・4411 の 6 本)。

### D2: 検証は手動のミューテーション 2 種

同値テストは Region・Unit・Scope のどれかが変わる移行に限る(本 ADR の範囲では変えないので不要。ブロックが同一であることは差分で分かる)。各テストについて次を手で確かめる。

1. 呼び出しを 1 行足すと落ちる。足す場所は **`known` にあるファイルと、`known` に無いファイルの両方**で試す(後者は全体走査が効いていることの確認)。
2. `known` の件数を 1 変えると落ちる。

落ちたときの出力に needle・想定・実際・`why` が含まれることも、このときに確認する。1265 のように後ろに構造検査が続くテストでは、ヘルパーの後の構造検査が引き続き実行されること(ヘルパー側で早期 return しない)を確認する。

### D3: 対象と対象外

- **対象**: 1209・1265・1896・1945 の 4 本に加えて、2526 `raw_mechanism_write_sites_are_confined_to_chain_writers` の第 1 部(同じ組み合わせ・同じ集合比較。期待値を `vec![..]` で書いているだけ)。1265 と 2526 は「件数ガードの部分だけヘルパーを使い、構造検査の部分は残す」。その後の対象拡大は、同じ組み合わせで書けるものだけ。
- **対象外(b) 例外つき**: 962(ファイルごとに needle が違う)、2321(第 2 部に `src/ime.rs` の除外、第 1 部は否定ガードの混在)、2366/2613/5719(特定ファイル除外。5719 は needle と組)、1700(複数 needle の合計)、4554(`src/` 外の走査)。
- **対象外(a) 構造検査**: `extract_fn_body`/`extract_all_balanced_blocks` を使う部分(4375 の `per_fn_expectations` など)。
- **対象外(c) dylint と実際に重なっているもの**: 1436 の `ENTRY_POINTS`(`.set_ime_open(`/`.apply_ime_open_with_view(` は `RESTRICTED_CALLS` と xtask で照合済み)。注意: **2321・2526 は dylint の対象でも置き換え予定でもない**(`apply_mechanism(`・`set_ime_open_then_conv_for_target(`・`set_ime_open_cross_process_async(` はどれも `RESTRICTED_CALLS` に無く、ADR-161 D1 M2 の TB2 は `.apply_ime_open_with_view(` の 1 件で完了済み。移すタスクは起票されていない)。
- **削除候補(別途検討)**: `lints/ime_event_guard` の `ALLOWED_FNS`/`RESTRICTED_VARIANTS` と、**構築元の関数の限定が重なる**テキストガード 4 本。491 `panic_reset_event_is_limited…`、511 `hwnd_cache_restored…`、3686 の `ModeKeyPassedThrough`、5420 の `KeyEffectPredicted`。ただし dylint が見るのは構築式(`ExprKind::Struct`)だけで、許可も関数名で判定する。**許可された関数の中での件数(491・511・5420)と、パターン・定義の固定(3686)は dylint では守られない**ので、削除できるのは重なる部分(構築元の限定)だけで、5420 のように前半の件数部分のみが対象になるものもある。重ならない部分は残す。削除前に確認すること: テキストのガードは Linux の CI(`ci.yml:47`)で毎回走るが dylint は別ジョブ(`ci.yml:125`、約 17 分)なので、dylint ジョブが required check か、lint 水準が `Warn` 宣言でも `DYLINT_RUSTFLAGS="-D warnings"` で失敗扱いになるかを確かめる。
- 当初案の「コメントを除いて数え直す」は行わない。件数が変わる修正は本 ADR の範囲外。参考: `InputRelay` をコメント除外で数えると `ime_controller.rs` 1→0、`open_chain.rs` 4→0、`class_names.rs` 12→9、`physical_disposition.rs` 2→1。0 になる 2 エントリは否定ガードにしかならず、InputRelay ゲートの存在は 4355 の `decide_gate(` 固定が担うので、別 PR で「数え直す」でなく「削除する」ことを検討する。

### D4: 中止基準

行数ではなく、検出力と失敗メッセージの保存で判定する(純減は 5 本で約 −60 行と見込むが、これは移行の目的でなく結果)。

- (a) D2 のミューテーション 2 種が全対象で落ちる。
- (b) 落ちたときの失敗メッセージに、needle・想定・実際・元の `why` が含まれる。
- 満たせない対象があれば、そのテストは移行せず元のまま残す。全対象で満たせなければ、ヘルパーを撤去する。

## 検討した代替案

- **何もしない**: 純減は約 45〜60 行でファイルの 1% 未満。重複が実際に問題を起こした記録(4 か所のうち 1 か所だけ直して他を直し忘れた等)も確認できていない。
  → ヘルパー案を選ぶ理由は「同じ型のガードを次に足すとき、26 行をコピーせず 7 行の呼び出しで済ませられる」ことだけで、弱い。これを認めたうえで、4 か所の複製が既にあり、メッセージ・組み合わせの手書きの食い違い(Region の取り違え)が黙って入りうるため、小さく抽出する。**D4 の基準を満たせなければ、または次に同じ型を足す予定が無いなら、何もしないが結論**(ヘルパーは次に同じ型のガードを足すときに作る、という縮小も可)。
- **宣言テーブル + 汎用チェッカー(当初案)**: 上の理由で取り下げ。全ルールを一覧できる以外の利点がヘルパーより小さい。
- **Region/Unit を関数ポインタで受けるヘルパー**: 対象が全て同じ組み合わせで引数が使われない。`non_comment_lines` 系は型が合わない。D1 で固定にした。
- **ルールごとに `#[test]` を生成する `macro_rules!`**: テスト名は残るが、エラー位置が悪くなる。ヘルパーで足りる。
- **dylint へ一本化**: ADR-161 D1 M2 が対象ごとに採用済みだが、移すタスクがあるのは `.apply_ime_open_with_view(` の 1 件のみ。本 ADR は dylint が見ていない件数ガードだけを扱う。

## 影響

テスト専用。ホスト(Linux)で実行できる。CI の `--test architecture_guard` 指定、`xtask-adr-evidence`、`fix-requires-evidence.md` の対象ファイル表には触れない(新ファイルを作らないため)。
