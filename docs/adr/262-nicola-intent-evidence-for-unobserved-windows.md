# ADR-262: 観測の無い窓で、親指シフトの最初の同時打鍵を契機に IME ON を明示する

## ステータス

起草(2026-10-16)。round 1 のレビューを受けて 2026-10-17 に書き直した。実装・測定なし。

## 背景

- issue #623(一太郎・GJI)の app log: 別アプリで IME OFF → 一太郎へ移る → `HwndCache: restore ime_on=true` → `FocusProbe: ime_on=true(shadow)`。
  **belief は ON、実 IME は OFF** のずれである(ADR-261 背景)。一太郎は `ImmCapability::Unavailable` と学習され、窓内の IMM が読めない。
- [ADR-260](260-eisu-toggle-no-mode-prediction-when-observable.md) は読みが効く窓にしか効かない。[ADR-261](261-taskbar-indicator-glyph-observation-for-unreadable-windows.md) は字形で読む案だが、
  一太郎でインジケーターが実状態を映すかが未測定で、go/no-go が立っていない。
- 根本原因(belief が違うのか、書き込みが届かないのか)は分かっていない。所有者は一太郎を持っていない。

## 着想

状態が読めないなら、打つ人の意図を契機にする。親指シフトで打つ人は、最初の同時打鍵で「NICOLA で打つつもりだ」と確実に言える。
7 打鍵や 2.5 秒の統計を待つ案は、v3 構想(打鍵列を保持して最尤で決める)の調査を 2026-10-16 に断念した(Phase 2 は全決定の 0.07%)ことと、所有者が撤回したことにより採らない。

## 所有者判断(2026-10-17)

1. 新しい order 起案の入口が増えることは許容する(D3 は入口を増やす前提で書く)。
2. 一太郎で明示の IME ON が効くことは前提とする(Q2 は前提に昇格。段階 1 の実機で検証し、効かなければ本 ADR は撤回する)。

## 決定

### D1: 向きは「belief が ON(Engine 活性)」だけにする

belief が OFF のとき Engine は Phase 2 で `pass_through` し、NicolaFsm に届かない(`src/engine/engine.rs:558-568`)。
このため、belief OFF の向きには「同時打鍵の成立」を判定する主体が無く、扱わない(殻に二つ目の検出器を置くと、同時打鍵のタイミング判定を二重に持つことになり、ADR-019 に反する)。
#623 のずれは belief ON の向きなので、本 ADR の対象はそれに一致する。belief OFF・実 ON の向きは対象外と明記する。

### D2: 契機と、動く条件

契機は、Engine が NICOLA の同時打鍵(親指キーを含む)を**確定**した時点。以下を全部満たすときだけ動く。

1. 観測の無い窓。述語は `ImmCapability::Unavailable` と学習された窓(`AppImeProfile::Imm32Unavailable` ではない。Chrome・tsf フォームは後者で、読めるので対象外。ADR-260 の区別に従う)。
2. 窓切替から、または無操作の終わりから、最初の確定であること(エピソードごとにラッチ 1 回)。無操作の閾値は既存の idle 系の判定を再利用し、新しい定数を足さない。足す場合は `#[measured]` と実測を添える。
3. そのエピソード内で、利用者が明示の IME キーを押していないこと(前の窓での押下は数えない。#623 の再現手順がまさに「前の窓で OFF にして移る」ため)。
4. 修飾キーなし、かつ awase 自身の注入でないこと。ADR-255(IME OFF のとき親指キーを Space にする)は belief OFF の向きの機能なので、D1 により衝突しない。

### D3: 動作 — 入口を 1 つ足す

- 純粋な判断(Plan)を `state/` に置く: 引数は Facts(窓の種別・エピソード・ラッチ・直前の明示キーの有無)、戻りは「何もしない/ON を送る」と理由。理由つきで journal に境界で記録する(ADR-250 の方式。手書きログを増やさない)。
- 実行は新しい order 起案の入口 1 つ。ADR-208 L1 の 3 点に従う:
  - `claim_press_write` は**押下に由来しない**ので使わず、`press=None` とする(drift correction と同じ分類)。
  - `applied` を、送る**前に未知にする**(S-1: `press=None` のままだと stale な `applied=Some(true)` で already-matched になり何も送られない。`state/sync_actuation.rs:315-316`、`ime_actuation_decision.rs:187`)。
    押下の `explicit_press_applied_pair` と同じ未知化を、press に依らず行う。
  - 送ったあとも `applied` は**未知のまま**にし、`Confirmed(true)` を書かない(効いていない ON を確認済みにすると、以後の補正が省かれる。M1)。ADR-214(Sent と Confirmed の分離)は保留中なので、「未知のまま」で足りるかをレビューで確かめる。
- belief(`desired_open`・`last_intent`)・IntentStore は**動かさない**。D1 の向きでは belief は既に ON なので、動かす必要が無い。これで `UserImeSetIntent` の偽装(意図の偽装)を避ける。
  Engine に `SetOpen` を出させる案も、`dispatch_set_open` を殻から直接呼ぶ案も採らない(前者は IntentStore に明示の意図を書き、後者は belief と実状態を割る)。
- `RESTRICTED_CALLS`(`lints/actuation_call_guard/src/lib.rs`)の許可呼び出し元と `tests/architecture_guard.rs` の入口ガードに、この入口を登録する。
  `press_id_is_claimed_and_carried_at_every_order_issuing_entry` は「`press=None` を許す入口」の分類に追加する。
- 授権(warrant): どの `WarrantBasis` で通るかは、実装前にコードで確認して本 ADR に追記する(未決 Q5)。`Unwarranted` で止まるなら、新しい basis を足さず、この入口の設計を見直す。

### D4: 出力との順序

確定した同時打鍵の出力は、ON の送信が返るまで同じ処理の中で保留する(新しい defer キューは作らない)。保留の上限は短い期限とし、超えたら ON を諦めて出力する。
期限は段階 0 で実測してから決める。GJI の OFF→ON 直後の最初のローマ字がリテラル化しうる(BUG-002 系)ので、既存の warmup の判断(`state/warm_send_plan.rs`)に乗せる。
乗せられない場合は本 ADR の段階 1 に進まない。

### D5: 下限の主張は弱めて書く

「効かなければ今と同じ」ではない。効かなかった ON は IME の状態を変えないが、(a) cold-start のリテラル化、(b) ADR-256 の書き込み遅延の抑止期間(外部変更の検出が鈍る)、(c) 保留による最初の 1 打の遅れ、を起こしうる。
段階 1 は設定で有効化し、既定は無効にする。

## 先行する撤去との関係(要確認)

ADR-178 領域 A(reassert + force-on)の撤去と、ADR-212(予防的・補正的 actuation の段階撤去)は、「状態が合っていそうなのに、念のため ON を書く」系を撤去する方向だった。
本 ADR の ON の送信は、形としてはこれらの reassert に近い。違いは、(1) 観測の無い窓だけ、(2) エピソードごとに 1 回だけ、(3) 意図の証拠(親指シフトの確定)を契機にする、(4) 読める窓には出ない、の 4 点。
読める窓では補正が観測で効く一方、読めない窓には補正の経路が無い、というのが再導入の根拠である。この区別が撤去の理由と衝突しないかは、`docs/experiments.md` の該当エントリと ADR-212 の撤去理由を読んで、レビューで確かめる(未決 Q6)。

## 段階

- **段階 0(挙動を変えない)**: 観測の無い窓で D2 を満たすエピソードが生じたとき、次を境界で journal に記録する。
  - 窓切替/無操作からの経過 ms、プロセス名・クラス名、そのときの belief(open/mode と観測元)、`ImmCapability` の学習状態(降格が何回目のフォーカスで起きたか)。
  - **利用者の訂正の代理指標**: 確定の直後 N 秒以内の BackSpace の連打、明示の IME キー、Esc。N と連打の閾値は今は決めず、生の時刻を残す。
  - ADR-261 の字形が使えるなら、その読み。GJI プロセス I/O の有無(`GjiIoInference`)。
  - 合格基準: 報告者の journal で、「確定の直後に訂正が現れたエピソード」が 0 でないこと。0 件なら、直す対象が見つからなかったことになり、本 ADR は撤回する。
- **段階 1(設定で有効化、既定は無効)**: D3・D4 を実装する。報告者の実機で、段階 0 で見えた訂正の頻度が減るかを比べる。一太郎で ON が効くことの検証もここで行う。

## 範囲外

- belief OFF・実 ON の向き(D1)。
- 問題 2(英数を押してもモードずれが解消しない、ひらがな/半角英数のずれ)。開閉軸だけを扱い、変換モードは扱わない。GjiDirect の ON は GJI の前回のモードを復元するだけなので、#623 を閉じる ADR ではない。
- 常時の判定、英数側の統計判定。

## ADR-261 との関係

ADR-261 は「読む」、本 ADR は「書く」。ADR-261 が go で字形が読めるなら、字形の読みを優先し、本 ADR の段階 1 は動かさない(読める証拠があれば推論は不要)。
ADR-261 が no-go(H1: インジケーターが別コンテキスト)なら、書き込みも別コンテキストに効く恐れがあるが、所有者判断により前提としたうえで、段階 1 の実機で検証する。
両 ADR の go/no-go は同じ実機確認(一太郎でインジケーター・実入力・SendInput の ON の一致)に依存するので、報告者への依頼は一回にまとめる。
